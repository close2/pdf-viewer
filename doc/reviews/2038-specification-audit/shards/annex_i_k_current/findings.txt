# Annex I compatibility and Annex K XFA boundaries

This pass covers effective ISO 32000-2:2020 (EC3) Annex I I.1-I.3 and Annex K K.1-K.2, with the current feature ledger, implementation, public consumer paths, assertions, and directly relevant ADRs. Primary-source locators are PDF physical pp. 951-952 (printed pp. 936-937) for Annex I and physical pp. 959-961 (printed pp. 944-946) for Annex K. Physical p. 953 / printed p. 938 begins Annex J and is outside this review. Rendered primary pages are saved here; the scoped pages' visible text has no correction overlay. `doc/errata-read.md` has no direct Annex I or K entry. EC3 Issue #399 is relevant to I.2's version history through §7.7.2, not an Annex I erratum.

Annex I makes a feature-by-feature choice whether to ignore an object not understood or inform the user. Existing public tests choose both paths on a single page: an unsupported image filter is reported while the neighboring understood fill draws; an unknown page-dictionary entry is ignored with the full page drawn and no note. Separate feature tests show an unknown annotation subtype can still draw its normal appearance and an unknown shading type is reported. These are concrete assertions, not proof of every feature's compatibility behavior. The source itself is discretionary for I.1 and describes three classes in I.3 (printed p. 937): dictionary additions an older reader ignores, features that cannot be ignored without error, and features whose omission can silently degrade output.

I.2 has one processor `shall`—attempt to read files newer than the processor—and multiple `should` recommendations. `Document::version` takes the maximum numeric version from the header and the cumulative catalog revisions; EC3 #399's §7.7.2 change is accounted for by the revision walk. A strict-xref PDF 2.1 test asserts parsing without recovery, opening, supported-page pixels, and a version warning when the host requests the report. The reader does not gate opening on version. Current version and unmet-requirement messages include both clauses of the warning: reading may be unsuccessful and modifying/saving may be unavailable. Insertion of pages now raises the catalog version to the newer effective input version; the paired test covers both input orders. Incremental output preserves original header bytes. Archive conversion of a source above 2.0 is a named PDF/A-4 history-preserving case, not an unrecorded general rewrite.

The first-error suppression recommendation is explicitly declined: the reader reports every unrecognized feature rather than stopping after the first. This is the owner's choice in `doc/questions/A834` item 4 and ADR 2815 §2, and the test asserts that two unsupported objects both reach the report. It is a recommendation-level departure, not a normative failure. The two-part newer-version/unmet-requirement messages are correct in code, though the ledger's I.2 note still says the version warning is given before any page is drawn; the actual `Command::Report` path follows the first frame. Annex I does not specify timing, so update the wording if that ledger sentence is reused as evidence.

Annex K states it is deprecated in PDF 2.0 but still contains its normative rules. K.1 requires an interactive processor that supports XFA to identify the interaction as XFA; a PDF processor may choose not to implement schema-driven page generation, and whether generated pages are materialized is implementation-dependent. This program supports the static hybrid form path and tells the host what it reads and writes. The checked-in `annotation-text-widget.pdf` public integration fixture opens without xref recovery and the viewer's `Command::Report` returns a clear XFA identity, including that the shown/filled form is the AcroForm and what XFA behavior is or is not carried out. Dynamic template page generation is accepted and scheduled after the ISO ledger work by ADR 2876, but is not yet built; the interim K.1 permission to decline it is currently exercised. The notice path also distinguishes `/NeedsRendering` without an XFA resource.

K.2 describes an XFA resource as a whole XML stream or packet array and sets writer-side consistency requirements for hybrid PDF/XFA forms. `Resource::read` handles both resource representations; current checked-in corpus tests edit and reopen real hybrids and assert saved field/dataset values. Current authored tests cover calculations and validation paths as well. K.2's producer rules do not imply a reader must reject a malformed hybrid, nor a mandate to implement every XFA 3.3 feature. Unsupported fields and behaviors are named; dynamic layout is accepted and scheduled after ledger work, but is not yet built; interim K.1 permission to decline it is currently exercised. Existing ledger marks K.2 implemented under the accepted static-XFA scope. Residual: this review samples the mapped resource, save, and interaction assertions; it does not independently certify all XML/XDP/XFA 3.3 grammar or all hybrid writer cases.

No new test draft is proposed: the existing strict future-version read, version-upgrade input-order pair, two contrasting I.1 feature tests, two-object first-error policy test, and real hybrid public report provide discriminating controls for the selected requirements. No Cargo commands were run.
