Bounded audit: ISO 32000-2:2020 with EC3, §7.11 and §14.13. This is not a whole-clause or whole-ledger certification.

Corrected locator handed off from FDF audit: general Table 43 is printed p.134 / PDF physical p.149. FDF Tables 251–253 are printed p.565 / physical p.580. The earlier Table 43 citation at printed p.451/physical466 was an unrelated prefix match and is corrected in fdf_current/features.json.

Most consequential possible discrepancy is in FileSpec's API: Table 43 explicitly says the PDF reader shall use /UF when present instead of /F. display_name() does so, and tests prove that display result. However from_dictionary() retains /F in bytes, and components(), is_absolute(), and resolve_against() interpret those bytes. If these are intended to expose the reader's effective path, they contradict precedence; if they deliberately expose raw legacy /F bytes without consumers, current user-visible impact is unproven. No production caller of these helpers surfaced in scoped rg search. FDF's separate Reference::read dictionary case does choose UF first; parent draft should be treated as missing direct assertion, not a confirmed failure.

Associated-file scope is broad and generally has both model and consumer work. EC3 #374 changes the marked-content key to MCAF, tested alongside the direct named-array property-resource shape. Yet model parsing any dictionary does not itself establish all dispatch sites listed by §14.13.1/§14.13.5: metadata stream /AF, Type 3 glyph descriptions, patterns, and annotation appearances require their own carrier paths or explicit scope explanation. Preserve this residual instead of blanket-certifying the shared helper.

Producer requirements were not converted into mandatory reader-rejection assertions: Table 43 required/indirect constraints, §7.11.4 MIME/subtype/Params details, and §14.13.2 preferred embedded form. The standard's reader-facing duties identified here are UF name selection and representing associated relationship information. External associated files are correctly reportable by name/relationship without opening them; embedded extraction remains a host/user action.

FDF overlap: Table 253 /F permits a file specification. The prior draft has exact xref and no-recovery assertions and contrasts /UF against /F in the actual ViewState::import callback path. The current code seems to pass that assertion. It should be promoted as coverage, not a claimed fix.

Follow-up call-path trace

External file references opened from GoToR/GoToE: pdf_model::action::target_root parses the file spec; non-URL paths use display_name(), which selects /UF then /F. viewer-core queues the returned name; viewer-host::policy::remote/resolve_import and read_remote resolve it under the document directory and read it. FDF Table253 is a separate named_page::Reference::read path, and its dictionary form explicitly searches UF then F; ImportData likewise parses FileSpec and uses display_name. The host does not call FileSpec path helpers. Thus local path-opening paths honor UF-first; no observed end-to-end violation. Embedded-file extraction uses the tree key for EmbeddedFiles rows, and associated file names use display_name; the user action passes decoded bytes to host, which owns writing.

Path helper contract: file_spec.rs itself defines components as byte-preserving path components and its unit test explicitly asserts /F components survive even when /UF differs. This makes them a deliberate low-level /F API today, and no production callsite was found. That avoids a confirmed user-facing defect, but the public methods are attached to a FileSpec abstraction and Table43 says a reader shall use /UF. The scratch discriminator `drafts/file_spec_path_precedence_candidate.rs` contrasts /F and /UF for absolute path parsing plus URL accessor, labeling URL conflict as an unresolved clause-scope question. Parent can decide whether to rename/document raw-F methods or add effective-path methods; do not force a production fix in this audit.

Associated carrier callgraph: page and catalog AF are in viewer-core attachment query; annotation AF is collected by pointer interaction and panel. Structure-element/DPart paths have explicit consumers/tests. AF-tagged marked content is processed in `content/run/marked_ops.rs` and returned in `Interpretation::associated_files`; the interpreter recursively runs forms, Type3 CharProcs, and tiling cells on the same interpreter, so those carriers reach the public model report. Existing tests verify page content, not nested Type3/pattern carriers. Annotation appearance interpretation does not route through this content interpreter and no MCAF report hook was found. Metadata-stream AF is absent from the public attachment enumeration: catalog metadata is parsed for XMP properties, while attachments() walks EmbeddedFiles/catalog AF/DParts and viewer-core adds page AF. Since §14.13 does not say a processor shall list associations in an attachment panel, these are unsupported/unverified carrier-report paths rather than mandatory reader failures.


Nested marked-content test drafts added

`drafts/nested_marked_content_associated_files.rs` contains three self-contained candidate tests using exact-xref/no-recovery PDFs. Each asserts a target attachment's literal name, /Desc, /AFRelationship, and stream, plus the associated text range; each also puts a decoy MCAF array in an ordinary `/Span` property list and checks ordinary page text as a positive control. The Form, Type 3 glyph, and tiling-pattern targets are separate objects. Embedded streams include valid MIME top-level/subtype and `/Params << /ModDate ... >>`, honoring the §14.13.2 producer recommendation/requirement relevant to this fixture. These are scratch drafts and were not run.

Relevant ADR disposition: ADR 0918 expressly limits the then-new external-file note to catalog and says other carriers reach no caller; ADR 2799 later defines `Query::ExternalFiles` population as catalog plus current page, explicitly because §14.13.1 gives no processing instructions and the panel's population is a product boundary. ADR 1186 brings page dictionary AF into the current-page attachment query. ADR 1040 brings DPart AF through the document-part tree. ADR 1461 fixes EXAMPLE 2's direct array-valued named resource. The current implementation has since grown beyond the old no-caller assertions in ADR 0918/2799 for page, structure, DPart, annotation, and marked content; the callgraph/test evidence above is current code, not grounds to rewrite history. The residual is now narrowed: Metadata stream /AF and MCAF inside annotation appearance do not reach a public association report, while Type3/Form/tiling MCAF do through the page Interpretation route.
