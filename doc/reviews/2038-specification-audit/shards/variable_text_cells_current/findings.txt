The clearest Table 228 problem is `/DS` lookup across the whole field-parent chain. EC3 Table 228 (printed p. 533, physical p. 548) labels `/DA` and `/Q` “inheritable”; it does not do so for `/DS` or `/RV`. §12.7.4.1 (printed p. 530, physical p. 545) says inherited attributes are designated in their tables. A separate Widget may read its owning terminal field’s DS/RV because the Widget is a child of that field, but that is not permission to inherit from the terminal’s nonterminal ancestor.

`rich_text::for_field` calls `nearest(document, chain, "DS")` and, for a stored rich value, the corresponding lookup for RV. `Inherited::chain()` is only the Widget plus a flattened resolved-ancestor dictionary; the inheritance leak originates earlier: `inheritance.rs::READ_UP_THE_CHAIN` includes RV and DS, and `Resolved::stated_over` merges those entries from nonterminal ancestors despite the adjacent prose correctly saying they are not designated inheritable. The existing `variable_text.rs::a_rich_text_fields_flag_and_rv_are_found_up_the_parent_chain` puts Ff/RV on the field immediately owning the Widget; it proves valid separate-widget lookup, not reading from a nonterminal ancestor. `a_rich_text_fields_default_style_string_is_drawn` uses a merged widget/field, so it does not distinguish ancestor lookup either.

The integrated test derived from `drafts/rich_text_default_style_noninheritance.rs` tests the rendered public path. It compares (1) no DS, (2) DS on the terminal variable-text field as a positive style control, and (3) DS only on a nonterminal ancestor. The exact-reference field tree has a `/Kids`/`/Parent` relation, a separate Widget with `/P` and page `/Annots`, DA/DR Helvetica, a terminal RichText value with a matching RV, and `/NeedAppearances true` because the PDF 1.7 Widget has no stored AP. It expects ancestor-only DS to render like the no-DS control, while the local DS control is taller. Parent reports the ancestor-only case failed; the local style and local-over-ancestor controls passed.

Other Table 228 routes look directly connected to the consumers: DA is retained as operator bytes (EC3 #318) and its AcroForm fallback/resource route is exercised by the public edit-save-reopen test; Q’s direct 0/1/2 ink positions are independently measured. Parent integrated `drafts/quadding_field_tree_precedence.rs` as an additional public-render probe with exact edge coordinates and a separate Widget; it checks terminal-over-parent, parent-over-form, AcroForm Q, and absent-value default controls. Parent has not sent this shard a run result. Table 227 conditions are likewise split at their actual use: ReadOnly blocks a person’s edit but does not block reset/import, Required is checked at form export, and NoExport outranks an action’s field list. The test suite has independent assertions for those three meanings. ReadOnly’s SHOULD behavior for mouse interaction/hover appearance is a separate host assertion and is not established by the value-edit test.

At shard start the current manifest had no Table 227/228 finding. Parent reports wave87 AA/NeedAppearances results and the wave89 DS failure with positive controls; the Q test was integrated and augmented at wave89b, with result pending to this shard. These are parent-reported, not executed by this shard. Remaining limits: this is a bounded table-cell audit, not a complete XFA certificate. An RV-only noninheritance differential would omit a terminal RV while non-null V and RichText are present, contrary to Table 231; RV therefore remains a code/source residual without a valid test here. The Required assertion is a composition-report test, not proof of host blocking at send time; that boundary is under separate review.
