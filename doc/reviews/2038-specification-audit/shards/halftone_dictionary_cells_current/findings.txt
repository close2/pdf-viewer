# Halftone dictionary cells: Type 1, Type 6, Type 10

This is a bounded cell/assertion review at baseline `b901326c`. I read the primary EC3 PDF and the actual annotation objects for physical pages 389–396, then traced the table cells to `pdf-model`'s live graphics-state consumer and current transfer assertions. No Cargo was run, and no tracked file was edited.

The table locators are: Table 128 on physical 389 (printed 374), Table 129 across physical 390–391 (printed 375–376), and Table 130 on physical 393 (printed 378). This check exposes a locator mistake in the older `halftones_separations_current/features.json`: it assigns physical-391 Issue #310 to Table 130. Table 130 is actually two printed pages later. The physical-391 Issue #310 overlays Table 129's Type 6 `TransferFunction` note; the second #310 at physical 395 overlays Table 132. Issue #12 is also on physical 395, and #311 on physical 396 strikes the whole Type 5 contrast/fallback paragraph. These are different table targets and should not be collapsed into a generic “#310 affects Type 10” claim.

Table 128 carries the Type 1 screen's required Frequency, Angle, and SpotFunction; the PDF 2.0 SpotFunction cell allows an array of names and specifies first-recognized/default behavior. AccurateScreens is optional and defaults false; true selects the precise algorithm, while false or absent selects ordinary screening. HalftoneName is optional; Type and HalftoneType have their stated producer constraints. None of these screen cells is read by the current raster consumer. The remaining Table 128 TransferFunction cell is read and applied, separately from screen generation.

Table 129 is the Type 6 stream dictionary: Width and Height define the device-pixel array, whose stream bytes are Width×Height one-byte thresholds ordered from (0,0), horizontal fastest. Its TransferFunction cell is read from the stream dictionary. The effective EC3 annotation at physical 391 gives the conditional Type 5/nonprimary component presence note and Identity option. That conditional is a producer/table condition; this code review does not establish a reader rejection duty when a field is absent.

Table 130 is the Type 10 stream dictionary. Xsquare and Ysquare replace Width and Height and define two squared threshold blocks: X first, then Y; each has the same device/image-sample ordering. Table 130's TransferFunction wording says it shall override the current component transfer. It enters the same `ext_gstate.rs::halftone_transfer` stream-dictionary path as Type 6. The screen squares and geometric mapping are not consumed.

The actual reader split matches the stated output-device scope. `halftone_transfer` reads an `/HT` dictionary or stream dictionary; it only branches on `HalftoneType == 5` to select per-component entries. Other dictionary/stream types read `TransferFunction` generically. It does not inspect Type 1 frequency, angle, spot function, or AccurateScreens, nor Type 6/10 dimensions or decoded threshold bytes. No screen is applied to the continuous-tone RGB raster. §10.1 makes halftoning conditional on the raster device; §10.6.1 says continuous-tone output need not be halftoned; §10.6.5.1 permits ignoring some or all document halftones. Thus the unconsumed screen cells are an intentional capability boundary, not a demonstrated reader-conformance defect. The boundary does not waive transfer functions, and the code/test path continues to apply them.

Assertion quality is adequate for the feature this reader actually implements. The preexisting Type 1 test differentiates a halftone override from /TR, but uses its helper result rather than the public raster interface. The newer `halftone_transfer_public_spec_audit.rs` includes a Type 5 public raster test and a Type 6 stream public raster test with same-route controls and literal values derived from constant type-2 functions. The parent review for `rendering_intent_transfer_current` records all four tests in that file passing on CPU (`fonts-transfer-wave23c.log`). No Type 10-specific TransferFunction fixture exists, but the Type 6 stream test exercises the same generic stream-dictionary function and no Type 10 code branch is missing. I therefore record this as a narrow test-coverage gap, not a runtime failure. No new draft was justified: another Type 10 test would repeat the exact generic route, while screen-generation assertions would test an optional downstream feature this reader does not provide.

The ledger marks §10.6.5.2–.4 implemented because the TransferFunction carrier is implemented. Its notes explicitly scope that status to one table entry and say the screen cells are ignored. The status must not be read as evidence that Type 1/6/10 screen rendering, threshold decoding, or AccurateScreens is implemented. Relevant ADR 1535 remains justified by the current continuous-tone output boundary; ADRs 0204/0505 preserve the screen-versus-transfer distinction and do not license broader CMYK/press conclusions. ADRs 1965/2034 address archive transformation and do not add a reader screen requirement.

Remaining limits: no screen-generation, spot-function fallback, AccurateScreens, Type 6/10 payload-order, nonzero-angle Type 10, Type 16, Type 5 screen, CMYK-native, or press-output certification. No malformed screen-dictionary rejection conclusion is drawn from producer constraints.
