# Partial and writer-side disposition audit

Scope was enumerated from the current `doc/conformance/ledger.toml`: eight `partial` rows and two `writer-side` rows, no assumed historical list. All ten dispositions remain defensible, with qualifications below. This was a status audit, not a full feature certification.

Five of the eight partial rows are aggregates: §7.6, §7.6.5, §12.8, §12.8.3, and §12.8.3.4. The three nonaggregate rows are §7.6.5.3, §12.2, and §12.8.3.4.4. ADR 1599's leaf-derived convention is still coherent for the aggregate rows. The ledger's aggregate test lists are evidence pointers, not coverage proofs. In particular, §12.8.3.4 remains partial because its profile leaf is partial; this must not imply every child marked `implemented` has been revalidated.

The genuine incomplete public-key leaf is §7.6.5.3. Its ledger evidence discloses unsupported 1-Pass ECMQV and brainpoolP512r1 while current agreement code refuses them by name/curve. RFC 5753 §3.2 identifies 1-Pass ECMQV as optional, so avoid phrasing this as an unqualified mandatory-reader failure. The status remains partial as a truthful feature-coverage declaration. The public-key shard already has broad algorithm vectors/witnesses; its Table 24 permission mapping test draft is helper-level and unrun. I did not duplicate it.

§7.6.7 is correctly `writer-side`. The source's custom-security-handler wrapper `shall` instructions address a producer; no current writer emits such a wrapper. Reader prose about an unencrypted wrapper displaying normally is met, and the payload metadata reader exists. Neither producer constraints nor the desired automatic payload presentation establish a reader rejection requirement here.

§12.2's partial status is grounded in Table 147 `/Enforce`, whose source says a user-interface choice shall not override the enforced preference. The core and Qt path can hold the restriction; GTK and the C FFI report it before presenting print controls that the user can still change. This is an actual host integration limitation, although the specific native-dialog override is established by code inspection rather than a discriminating dialog test. `/HideMenubar` is a separate departed preference, not the basis for `partial`.

§12.8.3.4.4 is still credibly partial, but its note should be read with successor work: policy parsing/binding/fetching has advanced (ADRs 2560, 2580, 2604, 2624, 2644, 2710). The current residuals concern policy semantics not evaluated, human-readable constraints, policy-defined `other` revocation, signed assertions and signer-attribute value constraints, and trusted-list inputs that are not supplied. Older absence claims superseded by these ADRs should not be counted as open.

Two potential child-status overclaims within the signature aggregate should remain visible to parent reconciliation, not be hidden by the aggregate's honest partial status. §12.8.3.4.5 is marked implemented, but current `viewer-core/src/notes.rs` performs verification through report/about processing, while `Command::Open` does not validate PAdES at open; the existing `pades_report_spec_audit.rs` tests report behavior, not the source's open/request trigger. §12.8.3.4.8 is also marked implemented; parent finding B47 reports an OCSP response whose producedAt is before the trusted historical instant failing while the later-issued control passes. These are references to already collected evidence, not new tests or fresh execution in this shard.

§E.2 is correctly `writer-side`: its rules govern extension authors' naming choices, and no current writer emits a developer-specific extension key/value. The archive's resource name is a content-stream resource, not an extension key. ADR 1461 remains applicable. §7.6.7 and E.2 have no need for reader-side conformance tests absent writers that create the respective structures.

Aggregate headings were checked as heading/child structure; no separate requirements inferred from them.
