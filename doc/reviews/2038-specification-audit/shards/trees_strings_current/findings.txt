Bounded audit: ISO 32000-2 §7.9.1, §7.9.2 (excluding language escapes/dates), §7.9.6, §7.9.7. Effective source is the primary PDF plus Errata Collection 3. Processed Markdown gives useful line references but is stale where annotation text was dropped. Relevant printed page references were checked against the source inventory: §7.9.6 begins printed p.119 (physical PDF p.134), §7.9.7 printed pp.122–123 (physical pp.137–138). Do not use printed page numbers as physical page indices.

The key behavior is present in code: `TreeKey::Name` compares raw string bytes, `TreeKey::Number` compares integers, lookup descends through Kids, and `name_pairs`/`number_pairs` enumerate leaf pairs. Public consumers include named destinations (`Destination::named`) and page labels (`PageLabels::read`). I found no behavior defect in sampled valid inputs. I did find that extant deep-tree tests are not valid producer fixtures: the syntax unit trees put direct dictionaries in Kids, while Table 36/37 requires indirect references. The byte-order integration fixture stores `/Names` in correct byte order (A, a, a-NUL, decomposed e-acute, composed é) and its query loop is in a different order; it is valid flat-tree exact-byte coverage, but not a deep-tree public-consumer control. The two standalone drafts provide exact-xref, no-recovery, valid indirect-child controls through public consumers.

Do not overstate this as mandatory reader validation. Table 36/37 producer constraints include exactly one root form, indirect Kids, sorted pairs, no overlapping ranges, exact Limits, and #307's no-null-key rule. These do not by themselves require a reader to reject malformed trees. Missing Limits are tolerated by the implementation. Conversely, a present but false Limits excludes a branch; that is a local recovery choice and is not settled by this audit. Values: any PDF object is allowed; stream values shall be indirect, whereas several other indirectness conventions are SHOULD statements. No claim was made that every value category is validated.

String interpretation is contextual. `Object::String` retains bytes; text decoding belongs to property consumers, and tree keys must remain bytewise. The prior claim that `FormsData::Status` used the wrong decoder is obsolete at baseline b901326c: the current reader calls the PDFDocEncoded-specific function. This shard excludes language-escape syntax and dates and does not certify every text-string consumer.

EC3 matters materially here: #214 strikes lexical phrasing but leaves explicit byte-sequence prefix/equality rules; therefore byte lexicographic comparison remains the supported operational rule. #307 adds the null-key writer constraint to both Names and Nums. The processed markdown still displays struck language and cannot be used alone as the effective wording. ADRs 0439, 0660, 1211, 0053, and 0054 were reviewed only on these claims; no whole-ADR certification.
