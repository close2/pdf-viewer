# Annex E writer and private-name routes

This bounded pass checked EC3 issues #229, #239, #340, and #732 against the primary PDF annotations, the writer code paths, and existing assertions. It does not re-audit the reader's treatment of unknown extensions.

The annotation groups were read from the primary EC3 PDF itself. On physical page 893 / printed 878, #229's Caret inserts “where otherwise stated in this specification.” into the second-class-name exception. The adjacent #340 StrikeOut/Caret pair replaces the old “not necessary to register” statement. The Caret replacement says `XX` is reserved for private data keys and third-class names cannot be registered in the PDF Names list. On physical page 158 / printed 143, #239 replaces “shall” with “should” in the ExtensionLevel increase-over-time sentence. On physical page 157 / printed 142, #732's paired annotation changes the Table 49 URL label from Optional to Required, while a separate Caret recommends a unique URL per extension.

One relevant writer exception appears in §14.7.3 physical page 742 / printed 727: PDF writers “may use any names for their structure types.” The archive's `roles::entries`/`extended` path can write a supplied custom structure type such as `/Chapter` into `/RoleMap`, paired with a standard target such as `/Sect`. That is a custom structure-type route expressly permitted by §14.7.3, not a PDF private-data name whose prefix must be selected under Annex E. Existing archive assertions `a_producers_own_types_are_mapped_where_the_operators_table_names_them` and `the_producers_own_role_map_entries_are_kept_and_only_the_unmapped_type_gains_one` check that output, including preserving an existing mapping. This qualifies rather than contradicts ADR 1461's narrower claim that the program does not emit a *developer extension*.

The writer inventory found no current production route that synthesizes a PDF Catalog `/Extensions` entry, a Table 49 dictionary, or private `XX` data. `pdf-syntax::write_name` and `serialize` are generic encoders of caller-supplied `Name` and `Assembly` values; they do not select a private/second-class name or enforce Annex E registration. `update` preserves supplied source data and its second-class trailer test proves §7.5.6 restatement, not a name-class decision. `split` and `merge` build Catalogs from explicit whitelists that omit `/Extensions`, while their object-closure copying may retain extension-specific entries on kept objects. Annex E recommends that developers add an extension declaration, but this pass found no explicit rule requiring these transforms to preserve that declaration. Treat the consequence as a product-policy/traceability question, not a confirmed failure.

The archive writer does add `pdfaExtension:schemas` in XMP for described custom metadata properties. Those are XML qualified names and schema descriptions under ISO 19005/XMP, not PDF Name objects or Catalog `/Extensions`/Table 49 records; their assertions do not cover #229, #340, or #732.

There is also an unresolved source tension around #732: Table 49's effective row says URL is Required, but §7.12.6 still describes the “optional URL entry.” This pass records both pieces of effective source and does not decide whether the changed table row supersedes the surviving subclause phrasing. `requirements::Extensions::read` retains an absent URL as `None`; that is reader tolerance, not evidence for writer output. No writer emits a Table 49 dictionary, and no writer-side URL test is warranted for current generated output.

The `extensions_are_read_under_their_registered_prefixes` test covers parsing of Catalog `/Extensions` and PDF 2.0 array form, including an entry without URL. It does not validate a prefix against the PDF Names list, enforce #340 for output, or prove #732 URL generation. The XMP schema tests likewise are not Annex E PDF-name tests. No new draft was justified: the only output route with custom PDF structure names already has focused §14.7.3 assertions, and no route currently creates the Annex E objects targeted by these issues. Split/merge retention is left as an explicit policy residual. No Cargo command was run.
