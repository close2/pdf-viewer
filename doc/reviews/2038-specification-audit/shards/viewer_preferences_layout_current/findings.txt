Audit scope: ISO 32000-2 §7.7.2 Table 29 (catalog open behavior, PageLayout and PageMode), §12.2 Tables 147–148 (viewer preferences), and §12.6.3 Tables 197–200 (page and document trigger events), against EC3 and current ledger/code/assertions. This is a bounded review, not a certification of every Table 29 entry or all printing behavior.

Source check: Table 29 is printed pp. 99–100 (physical pp. 114–115). Its `/OpenAction` permits a destination to be displayed or an action to be performed when the document opens. `/PageLayout` and `/PageMode` each say they shall be used when opening; defaults are `SinglePage` and `UseNone`. The current Table 29 includes `UseAttachments` (PDF 1.6). Table 147 is printed pp. 437–440 (physical pp. 452–455). EC3 Issue #275 adds `UseAttachments` to `/NonFullScreenPageMode`; the effective list and current model both include it. Table 198 is printed p. 509 (physical p. 524): page `/O` is independent of OpenAction and “shall be executed after such an action.” Table 197, printed p. 508 (physical p. 523), says annotation `/PO` follows both page `/O` and catalog OpenAction. These are direct order statements, not a UI preference.

The clearest test gap is observable and specific. `viewer-core/src/viewer/opening.rs:283–290` processes the newly opened document and calls `page_events` during `Command::Open`; that raises non-script page `/O` and annotation `/PO` actions immediately. `viewer-core/src/viewer.rs:668–679` performs the catalog action in `Command::Presented`, after the host's first presentation. `interact::open_action` and ADR 2814 explain the latter timing. Thus when `/OpenAction` is an action, current operation order is page O, annotation PO, catalog action, whereas Table 198/197 require catalog action, page O, annotation PO. The comment in `opening.rs:284–289` says action execution does not affect the ordering, but that is only true for a catalog OpenAction destination already consumed by `Open::around`, not for an action dictionary performed at first Presented.

The existing public test `viewer-core/tests/headless.rs::a_page_turn_raises_the_events_the_clause_orders` (line 7070) proves the page-turn close/open sequence and initial page O/PO order, but its catalog has no OpenAction. `script_view.rs::the_open_sequence_runs_at_the_first_present_and_once` covers script open-sequence timing, not a non-script catalog action interleaved with page O/PO. A direct public `Viewer` test using three URI actions can make the normative order observable without relying on a script engine or another renderer. A no-OpenAction control proves that the page triggers still occur. Draft: `drafts/open_action_precedes_initial_page_events.rs`. It uses exact xref offsets generated from object starts and asserts both `Open` and first `Presented` results, plus no `Event::Reported` recovery diagnostics; parent must compile/run it.

Other §12.6.3 evidence is stronger: the headless turn test names each URI trigger and asserts page sequence, and model tests cover annotation event extraction and `/A` precedence. The ledger says page `/O`,`/C`, annotation `/PO`,`/PC`,`/PV`,`/PI` are read and `Viewer::visibility` differentiates visible pages. Table 200 has five ECMAScript triggers `/WC`, `/WS`, `/DS`, `/WP`, `/DP`; it has no automatic catalog-open trigger. Current `CLAUDE.md` plus Q286/A286 moved confined in-document JavaScript into scope, while network/external effects remain excluded. `/WC` is invoked by viewer close; save and print trigger rows are outside this shard's detailed assertion review.

Preferences and defaults: `pdf-model/src/viewer_preferences.rs::table_147s_entries_are_read` reads the full preference shape, and tests cover defaults, invalid range handling, page-layout/mode decoding, and conditional `/NonFullScreenPageMode`. `viewer-host::Tab::of_page_mode`, `viewer-core::layout`, `viewer-host::presentation`, and native window consumers carry values into actual presentation. Page geometry/layout assertions exist in viewer-core headless tests, but this shard does not recertify their geometry. Table 147 `/Direction` expressly has “no direct effect” on document content or numbering and only says it “may” influence side-by-side/n-up positioning; leaving it unapplied to the explicit left/right choice of `/PageLayout` is a defensible optional choice, not an unimplemented shall. `/ViewArea` and `/ViewClip` are deprecated for producers but still describe screen-reader behavior and have consumers/tests; deprecation is not a reader exemption. `/DisplayDocTitle` uses “should”; current shared title consumer reads XMP and fallback. Print-only entries are identified in features.json but not reopened in depth.

Current host/product limits that should remain distinct from source requirements: `/HideMenubar` is deliberately not obeyed in GTK/Qt because that menu contains reader restriction controls (ADR 1145, corrected by ADR 1429); `/CenterWindow` cannot be performed by GTK4 (ADR 1429). `/Enforce` is an active reader restriction for Table 148 PrintScaling under A834/ADR 2840, default `warn`, and is not merely reported; the ledger still calls §12.2 partial because GTK and a C caller cannot lock their scaling dialogs. The Windows CI gate and native Xvfb results described in the ledger are prior owner evidence; I did not run tests here.

Remaining work/limits: Parent should run the drafted integration test and record actual result. This audit did not rerun native Xvfb or Windows CI, did not independently test every host's UI presentation, and did not re-audit print behavior or all §12.6.4 action semantics. The proposed order defect applies narrowly to initial page `/O` and annotation `/PO` when catalog `/OpenAction` is an action; destination OpenAction behavior and normal page-turn order are separate and remain supported by existing evidence.
