# §8.7.2, §8.7.3 and §8.10 bounded audit (baseline b901326c)

The strongest finding is a likely source/code mismatch in the degenerate Type 1 pattern BBox path. ISO 32000-2 physical p. 236 / printed p. 221, Table 74, says the BBox boundaries shall clip the pattern cell, then NOTE 1 says a zero-height or zero-width BBox still paints one pixel. Physical p. 399 / printed p. 384, §10.7.4, explains that result: a fill's scan conversion includes pixels crossed by a boundary even if its interior is empty; clipping uses the pixel set that would be included by a fill; and its example says a zero-height rectangle paints a one-pixel line. EC3 preserves the Table 74 rule; no Table74 erratum was found in `doc/errata-read.md`.

The implementation at `crates/pdf-model/src/content/pattern/tiling.rs:149-159` only stores the box if both extents are nonzero. A zero-height or zero-width box becomes `None`; `content/pattern/cell.rs:107-114` then has no BBox clip to apply. The in-code note and [ADR 0056](/home/cl/projects/pdf-viewer/.claude/worktrees/r2038-audit/doc/adr/0056-the-boundaries-shall-be-used-to-clip-the-pattern-cell.md) interpret NOTE 1 as a reason to leave the entire cell unclipped. That interpretation appears inconsistent with the main clipping requirement and §10.7.4's explicit clipping/scanning rules. Existing `tiling.rs::a_cell_is_clipped_to_its_bounding_box` covers a positive-area box and does not catch this branch. I drafted `drafts/degenerate_tiling_bbox_clip.rs`: it uses the same cell with a normal BBox as a positive control, requires some painted pixel near the degenerate boundary without prescribing exact ownership, and checks that a cell mark far from the boundary is clipped. The draft has exact computed xref offsets and `!was_recovered()`, but has not been compiled or run. Keep this specific issue separate from cases where the nondegenerate BBox has an empty intersection with another clip.

The pattern-space rules were checked at primary-source physical p. 235 / printed p. 220 (§8.7.2) and pp. 236-237 / printed pp. 221-222 (§8.7.3.1). The page CTM independence behavior is exercised by `tiling_patterns_audit.rs::page_ctm_changes_do_not_reanchor_a_pattern_selected_before_or_after_them`, which compares full raster bytes for CTM changes before/after `scn` and uses a translation not divisible by the tile step. Form anchoring is tested by `tiling.rs::a_pattern_inside_a_form_is_anchored_to_the_forms_space` with pixels that disagree under page anchoring. Parent-space nesting in a cell is implemented by temporarily swapping `Interpreter.base` in `pattern/cell.rs:148-162`; its existing regression uses a nested shading pattern, not a nested Type 1 tiling pattern. A focused nested-tiling test remains a coverage opportunity, but I found no present failure.

The rest of Table 74 reviewed has discriminating assertions. `tiling.rs` tests distinguish colored and uncolored paint types, including an underlying Separation color-space oracle (red tint versus the DeviceGray arity fallback), a cell color operator ignored in an uncolored pattern, and colored-cell stream-initial color versus fill-time color. `tiling.rs`'s lattice tests distinguish TilingType 1 from 2 by device-pixel period, test type 3 as a constant-spacing implementation, sweep the type-1 one-device-pixel step bound, and assert type 2's exact stated step. `pdf-render/src/lattice.rs::snap_lattice` separately measures worst transformed corner movement before accepting distortion. The clauses permit exact, unsnapped spacing for Type 2 and permit the extra Type 3 distortion without requiring it. Negative steps produce the same infinite lattice point set by sign reversal, though no test in this pass independently proves that equivalence.

Form invocation semantics in §8.10.1 (primary source physical p. 286 / printed p. 271) have direct controls: `form_xobjects_audit.rs` tests graphics-state restoration, a translated form Matrix and prior-location blank, a caller-scaled CTM to distinguish concatenation order, two differently colored invocations, and repeat placement. `transparency_groups.rs::a_forms_bounding_box_clips_what_it_draws` asserts a form is clipped at its BBox. The newly named form audit fixture computes exact offsets but its shared render helper does not assert `!was_recovered()`; other form/reference fixtures do. I found no uncovered core Form behavior in this bounded pass; affine rotation/shear are not specifically sampled.

Table 93 was checked at physical pp. 287-288 / printed pp. 272-273. EC3 issue #292 is completed and changes the Resources row: resources become sometimes required and independence is required from PDF 2.0; `doc/errata-read.md:102` records this. Matrix/BBox meaning is unchanged. Resource fallback policy is owned by existing ADR 1059 and was deliberately not re-audited. Optional content, group/transparency, associated-file, structure, metadata, OPI and reference semantics are outside this bounded Form dictionary review. The broad Form family is therefore not certified.

Current-basin diff (`4015a9ae..b901326c`) showed no functional change in the reviewed Form or pattern transform/clip paths. `pattern/tiling.rs` has a comment-only wording change about damaged streams. `content.rs` changes in this range concern Type4 function watching/fault reports and font glyph reachability/Type3 suppression; they do not alter the audited pattern/form behavior. Thus the BBox finding is a baseline behavior concern rather than a newly introduced regression.

ADR 1320's initial parent-stream graphics state is consistent with §8.7.3.1 step b and Table 74, with a direct color-state assertion; its transparency consequences are not reviewed. ADR 1080's TilingType snap policy is consistent with the inspected source/tests, with the normal bounds and transform limits noted in `features.json`. ADR 2820's missing `/Resources` policy was not independently reconsidered.
