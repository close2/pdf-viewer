## Scope and effective source

This bounded follow-up checked ISO 32000-2:2020 §12.3.3, focusing on outline `/Count` semantics and whether the implemented color/style fields are asserted through an actual panel consumer. Primary-source locators are directly verified in the sibling audit: §12.3.3 and Table 150 begin at physical p.459 (printed footer p.444), Table 151 spans physical pp.460–461 (printed pp.445–446), and Table 152 is on physical p.461 (printed p.446). The linked ledger row `doc/conformance/ledger.toml` marks §12.3.3 implemented. The prior effective-source review found no relevant EC3 overlay modifying these rules.

The clause's opening prose says an outline may be displayed, describes opening/closing entries and hiding descendants, and says clicking visible item text activates its destination or action. Table 151's item `/Count` uses its sign for open/closed state; a positive count is calculated as the visible descendants, not all descendants. Table 151 `/C` is the RGB color of outline text with default black. `/F` and Table 152 make bit 1 italic and bit 2 bold; the other bits shall be zero. These are presentation semantics for an implementation that displays an outline; a mandatory panel cannot be inferred from the clause's permission to display it.

## Count and panel behavior

The new `crates/viewer-ui/tests/outline_count_audit.rs::pdf_outline_count_controls_initial_panel_visibility_and_user_toggle` is substantially more discriminating than checking a decoded count or row total. Its exact classic-xref PDF has an open top-level branch, a nested positive-count branch, a negative-count closed child with a grandchild, and a following sibling. It asserts no xref recovery; model visible count 5; initial depth-first panel rows and item identities; then opening and reclosing the negative-count child while checking the revealed child and sibling's row position. The model unit test `crates/pdf-model/src/outline.rs::the_visible_count_skips_a_closed_items_descendants` independently checks the recursive count algorithm. Corpus test `a_stated_count_agrees_with_the_count_the_clause_defines` is producer/witness evidence and does not turn a stale producer count into a mandated reader error.

Current code paths agree: `pdf-model::read_item` derives `open` from `Count > 0`; `Outline::visible_count` skips descendants for closed items; `viewer-ui::Sidebar::flatten` begins with that state and `Sidebar::toggled` stores user changes as deltas from the initial state. `viewer-host::outline_rows` projects the same state to native tree rows. The outline panel behavior is therefore directly exercised at the public Sidebar consumer; named-destination behavior is outside this follow-up.

## Style/color assertion residual

Parser evidence exists: `pdf-model/src/outline.rs::the_linked_lists_read_as_a_tree` asserts `/F 2` is bold and `/C [1 0 0]` stays `[1.0,0.0,0.0]`. The script-facing Bookmark test checks style/color values, and `Sidebar::flatten` transfers `Item.bold`, `Item.italic`, and each RGB component into the rendered row. However, the panel test `the_panel_puts_ink_on_the_rows_it_lists` uses a shared outline item with default style and black color. I found no current public panel pixel assertion distinguishing a specified color from the default, nor a visual assertion for the two outline style bits. Thus, ADR 0144's code-level claim that the item style and color are implemented appears accurate, while a claim that their visual behavior is already verified by the existing panel tests would be too broad.

I drafted `drafts/outline_colour_reaches_panel_pixels.rs`: exact xref, `/C [1 0 0]` item beside a same-title no-`/C` default-black control, direct parse assertions, no-recovery assertion, and public Sidebar raster comparison using red-dominant pixels versus zero red-dominant pixels. It avoids a golden glyph image and makes no claim about font outlines. It is uncompiled and unrun here; parent should validate the `Raster` type/API and row bands before promotion. I did not draft a bold/italic pixel test because a defensible face/geometry oracle would need separate fixture work; existing parser and script projections show the field values but not their public visual application.

## ADR review and remaining limits

ADR 0144's visible-item activation decision remains sound. Its section closing §12.3.3 groups linked order, disclosure, `/C`, style flags, and activation as complete. Code tracing confirms a panel renderer consumes the fields, while the current UI output tests do not independently pin non-default color/style. Treat that as a focused assertion gap, not a discovered failure. ADR 0246's explanation that `/Count` controls expanded outline rows remains consistent; the new synthetic public test provides stronger semantic controls than the older census of expanded rows in a real tree.

Unreviewed: visual application of italic/bold in every native host; color parsing for malformed component types/ranges; outline title elision; all native Qt/GTK toolkit expansion callbacks; destination/action variants; malformed linked-list recovery. No producer-side mandatory validation rule is inferred from this bounded reader/UI audit. The new color draft is test-design evidence only until parent execution.
