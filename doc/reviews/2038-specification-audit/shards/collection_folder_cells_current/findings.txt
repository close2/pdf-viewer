# Collection folder links and public rows

I first checked the existing collection audit and table-cell review index. Neither Table 159 nor Table 160 is an explicit entry in `table-cell-review-index.json`; the earlier collection shard already gives a broad folder summary and separately covers navigator/layout choices. This shard narrows to whether Table 159's folder graph is evidenced through the actual host row consumer on a source-valid input.

The primary captions and locators are direct: Table 159 is “Entries in a folder dictionary,” physical pp. 468–469 / printed pp. 453–454; its hierarchy and file-key association prose continues on physical pp. 470–471 / printed pp. 455–456. Table 160 is “Entries in a navigator dictionary,” physical p. 472 / printed p. 457. It is not another folder dictionary table. EC3 #477 is a Caret/Replace annotation on physical p. 471 / printed p. 456 changing the navigator section heading to §12.3.5.3 (from published §12.3.6); it does not change Table 159. Inspection of annotations on physical pp. 468–470 found only cross-reference links, not corrections to Table 159.

Table 159’s key graph is precise. A folder ID is a required, unique, nonnegative integer. The root has no Parent. Every non-root folder’s Parent is required and an indirect reference to its parent. Child points to the first child where descendants exist; Next points to the next sibling except on the last sibling. The source describes those three keys as the tree relationships. Siblings SHOULD be ordered by the collection Sort key, or by folder name absent a Sort key. That is a producer recommendation; it does not create a reader requirement to reorder. Free is only read for ID allocation if the processor adds a folder, and no folder-add API appears in the viewer. Optional CI, description, dates, thumbnail and Free do not create an unhandled mandatory viewer feature here.

The model enters the graph from `/Folders`, then follows Child and Next, tracking visited indirect objects and applying its traversal limits. It reads IDs to associate `<id>filename` EmbeddedFiles keys with a folder. The host’s `collection_rows` recursively renders those parsed Folder objects and groups each attachment by its key’s folder ID; it keeps the complete tagged name-tree key as the extraction action while showing the decoded file name. It does not read Parent. Since Parent is a required producer backlink but the traversal is defined by the forward Child/Next links from the root, I found no source basis for requiring the reader to reject or repair a tree based on Parent inconsistency.

Current coverage has a useful mismatch in depth and validity. `host_mappings.rs::a_collection_becomes_a_folder_tree_with_the_schemas_columns` tests the real shared host row consumer with one root folder, no child/backlink. The model test `collection.rs::a_navigator_names_layouts_in_the_order_the_file_prefers_them` checks two siblings plus a grandchild, but its non-root Folder dictionaries omit the Table 159-required Parent links. That remains useful as a traversal witness, but not as evidence from a conforming producer-shaped hierarchy. A separate malformed-cycle model test intentionally checks recovery behavior and is not a valid-input control.

The scratch draft `drafts/valid_folder_backlinks_reach_public_rows.rs` fills that gap without asserting a new reader obligation: an exact-xref PDF 2.0 has a valid trailer ID pair, valid EmbeddedFiles keys, unique IDs, root with no Parent, correct indirect Parent backlinks for each descendant, Child/Next chains, and sibling names in the recommended order. It drives `Query::Collection` and `Query::Attachments` into `viewer_host::collection_rows`, then checks literal folder labels and extraction keys at root, sibling, and nested levels. It includes no Parent-mismatch rejection claim and is not executed. This is an assertion-depth improvement, not a known behavior failure.

The selected decisions are narrow. ADR 0083’s direction to parse Tables 153–160 and represent folder hierarchies stands; its evidence for this path currently relies on a malformed nested fixture plus a shallow public control. ADR 0711’s one-folder host test already verifies a tagged file under its matching ID and retention of an untagged root file. ADR 1050/1086 retain the accepted invalid-name support and normalization policy; the proposed fixture uses distinct valid names. ADR 1252 concerns the optional split and remains covered by the prior collection-presentation shard. No complete clause or ADR is certified here, and no tests were run.
