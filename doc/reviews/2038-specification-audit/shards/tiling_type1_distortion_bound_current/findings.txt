ADR 1080's wide-BBox fallback may be too permissive

I re-read the effective primary Table 74 instead of relying on ADR 1080's paraphrase. Type 1 says cells SHALL be spaced consistently by a multiple of a device pixel; the PDF processor MAY need to distort the cell by small adjustments to XStep, YStep, and the transformation matrix; distortion SHALL NOT exceed one device pixel. The table calls XStep and YStep the desired spacings. EC3 #428 concerns tile paint order, and #294 clarifies the stream-dictionary caption; neither edits Type 1's spacing obligations.

ADR 1080's implementation rounds the transformed step vectors by changing the pattern matrix, then measures the movement of the full BBox corners. If that movement exceeds one pixel, `snap_lattice` returns `None`; `Interpreter::lattice` then retains the original matrix and steps. The existing public Type 1 test uses a BBox equal to the 10.4-unit step, so it takes the snap and exhibits integer spacing. The separate unit test `a_cell_many_steps_across_is_left_alone_rather_than_distorted_past_the_bound` explicitly preserves the original lattice after a wide-box snap refusal. That behavior is current code, but the cap does not appear in the source as an exception to Type 1's SHALL.

A concrete source-supported alternative is XStep-only adjustment. At identity transform, magnification 1, XStep 10.4, and a 100-unit BBox width, setting XStep to 10.0 yields constant 10-pixel intervals, changes each desired interval by only 0.4 pixel, and leaves the cell transform/marks undistorted. Table 74 expressly lists XStep as an adjustment. The current matrix-only method instead would scale the cell and its 100-unit far corner by about 3.846 pixels, so it declines to snap. This suggests the algorithm's corner metric is not the only in-bound choice.

The bounded ambiguity is how the one-pixel “distortion” applies over many repeated sites: an XStep-only change moves each successive interval by 0.4 pixel from the requested lattice, so total displacement grows across a large filled area. Table 74 does not define a global error metric or say that displacement is bounded relative to the original ideal lattice at every site. The wording permits changing the desired step and limits distortion to one device pixel; it does not state the ADR's “does not ask” exception. I therefore record a likely policy gap for review, with that ambiguity explicit, rather than an adjudicated failure.

The scratch draft `drafts/type1_large_bbox_constant_spacing.rs` uses the existing exact-xref fixture helpers. It first verifies a Type 2 control preserves 10.4 spacing, then expects Type 1 intervals to be whole device pixels and within one pixel of 10.4. On the current path, the wide BBox should make the matrix snap fail its bound and expose the 10.4 interval. This draft has not been run and is not yet evidence of public output. It should be promoted only after the parent confirms the intended finite-page interpretation and fixture validity.

ADR 1031's old decision to count/report instead of implementing spacing was superseded by ADR 1080. ADR 1765 later confirmed that Type 1 is read and snapped, but did not examine this refusal boundary. No later ADR located in the current tree resolves the wide-BBox case. The review is limited to that fallback and does not revisit Type 2's one-pixel spacing latitude, Type 3's optional extra distortion, unsized caller behavior, or all raster backends.
