Selected audit of Table 168, Table 169, and the common border precedence

The primary EC3 PDF places §12.5.4 on physical pp.487–489 / printed pp.472–474, Table 168 on physical p.488 / printed p.473, and Table 169 on physical p.489 / printed p.474. I checked the actual table headings and page footer rather than a cross-reference. Physical pages 488–489 have hyperlink annotations to other clauses/tables but no EC3 Caret/StrikeOut amendment to the Table 168 or Table 169 cells. The operative related amendment is Issue #287’s actual Table 166 caret/strike pair (objects 4946 and 4952) at physical p.483 / printed p.468 strengthens “is ignored” to “shall be ignored.” The corresponding Table 166 note is physical p.483 / printed p.468. It confirms complete BS-over-Border precedence; it does not create a reader refusal rule.

Table 168’s default, style, width-zero, unknown-style, and dashed-pattern branches have actual assertions. In `annotation_border_audit.rs`, omitted D equals explicit [3], a changed pattern differs, and the output matches an independent line stroke with phase zero but not phase one. The empty BS dictionary equals explicit W=1/S=S and differs from changed width/style. Unknown S is tested against solid and a dashed control. Square B versus Link B documents the current subtype-dependent result: Square uses its own shape and Link receives the chosen relief. Table 180 explicitly limits BS to width/dash; Table 176 likewise calls out width/dash for Link, so the link relief is reported as the general Table 168 interpretation chosen by ADR 1061, not as an unambiguous Table 176 cell requirement. Widget I and link/free-text border tests document current implementation behavior; the Link/FreeText/Widget subtype rows describe BS as width/dash and the broader styles remain qualified by the Table 168/ADR 1061 reading. Width-zero and zero-width legacy border controls establish suppression.

For Table 166 precedence, current `bs_presence_ignores_conflicting_border_geometry_as_a_whole` holds the rest fixed while /Border conflicts on width, radii, and dash. Both solid and dashed BS outputs match their BS-only control, and each differs from Border-only. Parent review records all five tests in annotation_border_audit passing. This supersedes the older radius-only regression as the strongest current assertion; no current precedence defect is indicated.

Table 169 separates a required effect from chosen artwork. §12.5.4 says a BE dictionary specifies an effect that shall be applied; Table 169 says cloud borders should be a series of convex curved segments and explicitly requires BS width/dash to be honored. It sets S default to S/no effect, C to cloud, and I valid only with C in range 0–2 (default 0). Tests compare an empty BE with absent BE and explicit S; C is a distinct active control. Square, circle, and polygon cloud paths are rendered; PolyLine’s BE is tested as meaningful only for Polygon. Existing FreeText cloud coverage uses a field-shaped helper, while the separate standalone FreeText fixture disables its border with /W 0. Polygon width/dash controls assert that the stroke carries BS through a cloudy path. The exact cloud geometry is intentionally not a source-derived pixel oracle; radius, cusp count, color and spacing are policy choices under ADR 1057. Clamping an invalid intensity is also reader tolerance, not a source-mandated invalid-input rule.

The subtype rows for Link, FreeText, and Widget describe BS as specifying width/dash for their border; Line, Square/Circle, Ink, and Polygon/PolyLine rows also specify width/dash for their own line/shape. Table 168 defines S/B/I/U generally, but those subtype rows do not expressly repeat that those styles apply to each of Link/FreeText/Widget. The current application of B/I/U to such border consumers is the broader reading chosen in ADR 1061, not an explicit type-row requirement. Square-versus-Link tests document current behavior and the contrast with shape-path handling; I do not classify the narrower source wording as a confirmed behavior defect. BE is used for Square/Circle and Polygon, meaningful only for Polygon within the Polygon/PolyLine table, and is also permitted for FreeText from PDF 1.6. Stored AP takes the appearance route and bypasses construction characteristics. The FreeText cloud route formerly lacked an independent BS width/dash assertion on a clean standalone fixture; parent integrated `freetext_cloud_border_spec_audit::a_freetext_cloud_uses_its_bs_dash_and_width` and reports PASS in freetext-border-wave102.log. Its empty Contents and zero-width control make changed pixels attributable to the border. One scratch public raster draft remains: a no-entry Link with explicit color compared to [0 0 1] and explicit BS controls. It asserts no behavior beyond the Table 168/§12.5.4 default.

ADR 0293 is current for inside-border behavior and now-expanded whole-entry precedence; ADR 0294’s old subtype refusal was superseded by the later construction decisions. ADR 1057 properly distinguishes the required effect from unspecified geometry. ADR 1061 makes a visible but unspecified relief choice for B/I. No new normative behavior defect is established by this bounded review.
