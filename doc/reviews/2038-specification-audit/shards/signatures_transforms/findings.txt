# LTV, document timestamps, permissions, and legal attestations at b901326c

## Finding XFORM-1 — DocMDP comparison does not recognize DTS registration as part of the exception

**Verdict: a bounded implementation gap in the Table 257 /DSS-or-DTS-only update carveout.** The exception is per incremental update. A valid document-level timestamp is discovered by walking signature fields (§12.8.5.2), so adding a DTS commonly adds its signature dictionary, a new /FT /Sig field (or widget), and a catalog /AcroForm field-list revision. Those registration objects are necessary to add the timestamp, not unrelated document changes. At current baseline the comparison recognizes `/Type /DocTimeStamp` and the catalog gaining a `/DSS` key as validation material, but does not classify a new signature field or catalog/AcroForm registration as validation material. The update then appears mixed and the signature change is Unrankable instead of disregarded.

The source is explicit. Effective ISO 32000-2:2020 EC3 PDF, printed page 573 (DocMDP lead-in) and printed page 574 (Table 257), says P=1 permits subsequent DSS and/or document-timestamp incremental updates, and P=2/3 permit their workflow changes plus subsequent DSS/DTS updates. The lead-in says only data necessary to add DSS and/or timestamps does not count as a change. §12.8.5.2, printed page 590, says DTS existence is determined by examining signature fields. §12.8.5.3, printed pages 590–591, adds that evaluation of DocMDP restrictions shall ignore the presence of a timestamp and/or DSS. These requirements apply to processor validation/report behavior, not only timestamp authors. EC3 #55 records a producer order constraint at `doc/errata-read.md:1273`; it does not cure the classification gap.

Direct code path: `crates/pdf-signature/src/revision.rs::classify_one` marks an object as validation material if it is in the DSS arrays or is itself `/Type /DocTimeStamp`; catalog redefinition is specially recognized only when its changed key is `/DSS`. `dispositions` marks an update as Disregarded only when it contains validation material and nothing else. `viewer-core/src/notes.rs::modifications` invokes this comparison for the `/DocMDP` signature, so it can report an allowed timestamp update as unrankable. Existing `an_update_adding_only_a_security_store_is_not_a_change_to_the_document` and its page-change control test the DSS case. The timestamp stack tests verify RFC 3161 time/range/material coverage but do not call DocMDP comparison.

`drafts/docmdp_dts_carveout.rs` is a standalone public-API integration-test pair backed by actual fixtures under `fixture/`: a valid CAdES certification signature carries a DocMDP `/P 1`; revision 2 adds a zero-size signature widget on the page, its field registration, a `/DocTimeStamp`, and `/DSS` with signer/TSA certificate streams. The DTS ByteRange covers the complete updated file except Contents. The companion modifies page geometry by the same-length digit replacement `[0 0 200 200]` → `[0 0 201 200]` in that same update and has its own valid RFC 3161 token over those bytes. Both variants have exact classic xref tables and are accepted by qpdf. The test uses public `signatures`, `permissions`, and `Comparison` APIs; it verifies both signatures' digest and cryptographic authenticity, checks `/P 1`, checks the document was not recovered, then compares the certification signature's revisions. Its positive expectation is `WithinWhatIsPermitted` with zero changed objects, without pinning the count or classes of ignored collateral. The mixed control excludes `NoChangeToRank`, so an unrelated page edit cannot be mistaken for a DTS-only update. Parent independently extracted and OpenSSL-verified the base CMS and each DTS token; hashes are recorded in the review thread.

Parent's execution of the promoted integration tests confirms both signatures' integrity and authenticity for both PDFs, and the mixed page-change control passes. The DTS-only comparison fails with `NotClassified { level: None, objects: 7 }`. That observed result supports the narrow finding: necessary signature-field/page/catalog registration is not being recognized by the current update-scoped DTS exception classifier. It is a concrete false refusal in comparison/reporting, not evidence that the timestamp is invalid or that the page-change control is misranked.

This finding reopens a narrow part of ADR 0907. That ADR says the §12.8.5.3 requirement is met by construction because `restriction::asserted` does not consult `/DSS` or `/DocTimeStamp`. That accurately describes operation permission gating but not the independent DocMDP revision-comparison path, which does inspect and currently misclassifies the timestamp update. No general challenge is made to per-operation host restriction policy or its defaults.

## DSS and VRI evidence

Effective ISO 32000-2:2020 EC3 §12.8.4.2–.3 and Table 261, printed pages 585–586 describe preserved validation collateral and the catalog `/DSS` arrays. Code decodes indirect stream contents in `crates/pdf-signature/src/signature/security_store.rs`; `security_store_entries` separately retains object locations for timestamp-chain coverage, and `SecurityStore::material` passes decoded CRLs/OCSP responses to RFC validation. `viewer-core::notes::a_document_carrying_a_security_store_says_what_is_in_it_and_claims_nothing_from_it` uses empty-stream controls and asserts the reader does not call those invalid streams usable evidence. Positive crypto/path witnesses live separately in revocation and trust tests. No DSS writing is performed or required from this reader.

§12.8.4.4 and Tables 261–262, printed pages 587–588 make VRI optional and define the uppercase SHA-1 key over the full hexadecimal Contents string including zero padding. They say VRI describes one successfully validated signature and selected material; empty arrays should be omitted and CRL/OCSP references must point into DSS. The parser stores a raw VRI key and streams, but does not recompute/check its key against any signature and does not constrain which signature consumes its selection. The synthetic `ABCDEF` VRI in the tests is therefore a parsing/count fixture, not proof of a conforming VRI binding. The Report sentence “validation information recorded for N signature(s)” counts VRI entries without proving those entries correspond to N present signatures or prove successful prior validation; that wording can be misread as stronger evidence than the code has. The report does not call a signature valid on that basis.

§12.8.4.5, printed page 589 says the preferred lookup order **should** be VRI, DSS, embedded signature. The reader applies the entire DSS candidate set instead of narrowing to the VRI subset. I classify this as a departure from a recommendation, not a SHALL defect. Candidate certs/CRLs/OCSP are still individually checked against the validated path. Whether using all candidates can affect which valid cross-signed path is selected is beyond this bounded review; I make no claim the whole-store strategy is universally equivalent.

## DTS, subsequent timestamps, and effective corrections

§12.8.5.1–.2, printed page 590 states whole-file timestamp coverage except Contents and signature-field discovery. `timestamp.rs` parses the token/range and builds the time chain. Existing `timestamp/tests.rs` has actual TSTInfo member assertions, token authority positive/negative cases, range-coverage cases, and a later-token-over-earlier-and-material case; `viewer-core::notes` has a separate report witness. The new exact-xref fixture also independently verifies both DTS tokens with `openssl ts -verify`; both prove the timestamp bytes cover the respective entire revision. Those tests substantiate token validity/time and coverage, while only the new DocMDP pair can substantiate the Table 257 carveout (above).

§12.8.5.3, printed pages 590–591 addresses repeated LTV, materials for the previous timestamp's authority path before the later timestamp, and the DocMDP ignore rule. The repeated-timestamp material timing has an explicit test where the DSS is placed after the later timestamp and no longer covered. EC3 correction #55 is recorded at `doc/errata-read.md:1273` and requires a document timestamp follow a certification signature. No inspected viewer assertion reports that ordering specifically; creation order is producer scope and the clause does not turn absence of such a warning into failed token cryptography. This bounded shard does not certify every repeated-LTV edge or revocation reason/status.

## Permissions and UR3

§12.8.6 and Table 263, printed page 592 require permission-handler composition and state the `/DocMDP` enforcement/validation requirement. `pdf-model::restriction::asserted` returns all applicable permission reasons and includes `/DocMDP`; the viewer applies its explicit per-operation policy. The separate public Report path calls `revision::Comparison` for signature transform state. Relevant tests assert operation-level refusal and independent comparison classifications. Default restriction policy is off under the owner's explicit ADR 0803; this is product policy, not a claim that ISO transforms were never validated. The DTS gap prevents a complete transform-validation claim.

The same table makes UR3 conditional: only if the signature is valid and recognized shall additional processor rights be enabled. This program does not have a feature that it withholds by default and then enables through UR3; that positive grant path is not a reader debt. §12.8.2.3's separate SHOULD to remove UR signature association when saving beyond its grant is implemented by `ViewState::save` and covered by an inside/outside rights test. The otherwise non-field UR3 signature is added to the signature list through the `/Perms` association (`notes.rs::every_signature`) and undergoes the normal report-time signature assessment; the raw Table 258 parse alone is not represented as a signature-valid verdict. ADR 0159 is consistent with this boundary.

## Legal attestations

§12.8.7/Table 264, printed pages 593–594, says writers **should** create a Legal dictionary with certification signatures, while present entries shall be catalog `/Legal` and state all content that might cause unexpected rendering. `/Attestation` is optional and author-authored; the text asks reviewers to establish their own trust and says content may be reviewed in this context. It does not prescribe a reader-side exhaustive counting algorithm. The public library API returns author statements and compares ten count categories it can census against a whole-xref walk. The one direct test is calibrated: the URI declaration agrees with a present action, while two stated launches disagree with none found. Other Table 264 categories are not counted, so the library function can only compare a subset; that is not an unfulfilled reader SHALL under the reviewed text. I found no `viewer-core` consumer of `legal()` or `Legal::disagreements`, so this is public library support rather than a viewer report. No Legal writer is implemented or required for this reader. EC3 #218 (`doc/errata-read.md:2728`) modifies Table 264's UR3 /Reference shape, unrelated to this counter.

## Selected decisions

- ADR 0907: reopen narrowly because its “met by construction” argument covers the operation restriction path but misses the reporting/comparison path.
- ADR 0159: retain; usage rights parsing, signature trust, supported-operation ranking, and save withdrawal are separated.
- ADR 0803: retain product-policy default; it does not discharge transform validation.
- ADRs 1067 and 1071: retain distinctions among raw DSS counts, validated CRL/OCSP evidence, established timestamp time, and host anchors. Their positive tests do not cover the DTS DocMDP carveout.
