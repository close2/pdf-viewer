# Active halftone transfer function lost by the archive screen rewrite

This is a narrow output-preservation and authorization finding, not a PDF/A-4 conformance violation. ISO 19005-4:2020 erratum #314 removes the PDF/A-4 requirement that bans a halftone TransferFunction, so the absence of a PDF/A-4 transfer-row decision is correct. The source mapping remains active under ISO 32000-2 §10.5: a halftone dictionary's TransferFunction overrides the corresponding current transfer, while §10.6.1's continuous-tone permission only removes the halftone-screen step. Type 6 Table 129 provides the stream-dictionary carrier (physical 390–391 / printed 375–376). The held primary transfer review locates §10.5 at physical 379–380 / printed 364–365 and §10.6.1 at physical 381 / printed 366.

The public archive test `threshold_screen_authorisation_preserves_active_transfer_in_pdf_a_four` uses a valid PDF 2.0 fixture that is intentionally not PDF/A-4-conforming because it uses Type 6 halftoning, with an exact-xref page with a Type 6 stream carrying a Type 2 inversion (`C0=1`, `C1=0`, `N=1`). The source's interior RGB pixel is `[191,191,191,255]`. The otherwise-identical no-transfer-function control is `[64,64,64,255]` both before and after authorizing `Loss::Halftone`, calibrating the conversion's output-intent step and isolating the threshold-screen rewrite. For the transfer-bearing source, the same halftone-only authorization produces `[64,64,64,255]`; the test fails against the source-derived expected `[191,191,191,255]`. Its report authorizes only `graphics/halftone-type-is-one-or-five` as `Loss::Halftone`, says no screen appearance moves, and the project's local validator reports the output conforms to its implemented PDF/A-4 checks. That is not an independent/full external PDF/A-4 certification. The live TransferFunction mapping is silently disconnected when `/HT` becomes `/Default`.

This is an archive contract issue because the conversion presented a screen-only loss and offered no separate transfer loss under PDF/A-4. The mitigation text at `doc/pdf-a-mitigations.md` 4.3 explicitly separates transfer functions from halftones: §10.5 transfer functions decide the color a screen shows, while §10.6 halftones define the device screen; transfer removal can change the image even when screen removal does not. ADR 1964/2007 already give transfer loss a separate authorization/history route. The source output plus paired pixel control makes this a confirmed current behavior, rather than a prediction from the rewrite implementation.

The PDF/A-2 control `threshold_transfer_under_pdf_a_two_requires_separate_loss_authorisation` passes after its fixture was corrected to `Conforming::part_two()` so it emits the required PDF 1.7 header. With only `Loss::Halftone`, the still-applicable transfer row is Unauthorized and no output is written. With both losses authorized, it writes output and removes the transfer effect. This confirms the two losses can be kept separate where the validator still has the row; it does not cure PDF/A-4, where ISO 19005-4 erratum #314 removes that row.

Implementation trace: `halftone_and_intent_entries` writes `/HT /Default` to the graphics-state dictionary, disconnecting the Type 6 stream. Under PDF/A-2, `halftone-transfer-function-only-where-required` can prompt `TransferFunctionRemoved` separately. Under PDF/A-4, the erratum correctly removes that validator requirement; no independent screen-rewrite guard checks that the still-active stream transfer is being abandoned. `Object::as_dict()` accepts streams as dictionaries, so the earlier suspicion that transfer removal could not reach a stream was wrong. The corrected PDF/A-2 result is the source of truth on that point.

Safe product options include preserving the transfer mapping while replacing the screen, or refusing the combined loss unless separately authorized. This review does not prescribe which fix is preferred. It only establishes that the current PDF/A-4 screen-only route loses observable color mapping while reporting a screen-only change. No production/Cargo/git changes were made by this shard.
