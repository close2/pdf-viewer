Page dictionary Table 31 audit (current evidence, effective EC3)

Table 31 is §7.7.3.3 at physical pages 119–122 / printed 104–107. The source pages and footers were verified from the local EC3 extraction: page 119 begins Table 31; page 120 continues through Contents/Rotate/Group; page 121 holds B through SeparationInfo; page 122 holds Tabs through DPart and the table continuation. §7.7.3.4 starts on physical 122 / printed 107. The 33-entry matrix in features.json accounts for every cell and identifies the active owner, current tests and a qualified assessment. It does not certify every linked clause.

The inheritance contract is narrow and explicit: Resources, MediaBox, CropBox and Rotate only. Values are taken from the nearest ancestor as-is, without dictionary/array merging; a required inheritable value must be supplied in the page tree, while an absent optional value uses the row default. Existing tests cover nearest/empty Resources override, inherited MediaBox/Rotate and non-inheritable UserUnit; the current page-boundaries shard adds a public pixel assertion for inherited CropBox and leaf override. That closes the older page_resources_current residual; it must not be carried forward as an open gap. Annex F's explicit-field rule for linearized producers is separate from ordinary reader inheritance.

Resources and Contents have strong current evidence. Inherited Resources tests distinguish whole-dictionary shadowing from merge and use actual content execution; Content streams are consumed as one ordered stream with at least one whitespace at boundaries. Current content-window and contents-entry tests distinguish absent/null, multiple streams, operator operands across parts, empty valid streams, unreachable/nonstream parts and budget handling. The numeric budget is project policy, not an ISO number. EC3 #9 removes redundant page-array wording from the resource association prose but leaves Table31 and §7.8.2's concatenation rule intact. EC3 #81 clarifies that Resources remains required directly or by inheritance even if Contents is absent; this is a producer-validity clarification, not a mandatory reader-refusal rule.

The page action trigger route is also exercised. `pdf-model/src/action.rs::for_page` reads the page dictionary's `/AA` through `Document::get_key`, and its comment correctly states `/AA` is not inheritable. Current public tests `initial_open_order_spec_audit`, `script_triggers`, and `page_visibility_triggers_audit` use direct page `/AA` and direct `/O` or `/C` action forms. No indirect page `/AA` and indirect `/O` action pair was found. The draft `drafts/page_aa_indirect_reference_spec_audit.rs` builds both direct and indirect valid one-page PDFs with exact xref offsets and checks the same literal URI event via Viewer; it remains uncompiled/unrun and is a coverage improvement, not an implementation finding. I did not propose a `/Pages`-node `/AA` fixture because that is not a valid inheritable page attribute.

Other selected paths have independent evidence: page geometry and rotation have literal dimensions/pixels; Group is exercised by B39 and targeted transparency formulas; VP reaches measurement queries; AF uses payload-level associated-file tests; DPart has reciprocal page-range and file consequences. Page annotations, Tabs, named-page template markers, presentation actions and thumbnails each have dedicated current suites. Article `/B` order was aligned by EC3 #320; the published Table31 Optional/recommended descriptor still differs from §12.4.3's shall-contain sentence, so no new reader rejection rule is inferred. Table31 #106/#619 change `/ID` from indirect-reference preference to PDF2 deprecation; it is not a page-rendering behavior.

Selected limitations: LastModified/PieceInfo, page Metadata, StructParents, Tabs, PresSteps and all transition or viewport types are mapped to current owners but not re-certified here. Group/OutputIntents are only sampled through their dedicated transparency/colour shards. The draft is unrun.
