# Current-UTC CRL bound versus historical revocation check

**The primary source distinguishes the two modes.** ISO 32000-2:2020 + EC3 §12.8.3.4.7 (printed p.583, physical p.598) says a CRL used when verifying at current UTC is appropriate only when current UTC falls within the interval delimited by `thisUpdate` and `nextUpdate`. §12.8.3.4.8 (printed p.584, physical p.599) separately defines historical checking: the CRL must have been captured before the signer's certificate expires and its `nextUpdate` must follow the past validation time. The latter does not require `thisUpdate` to precede the past validation time. Thus the source requires context-specific applicability; a global lower-bound check would incorrectly reject valid later-collected evidence for a past signer time.

EC3's actual annotation inventory shows only cross-reference links on these physical pages, including links to §12.8.3.4.6 and §12.8.5. There is no erratum annotation changing either condition. The primary PDF text, not the annotation inventory or ledger prose, supports the distinction.

**The implementation accepts a future-issued CRL in every context.** `crates/pdf-signature/src/revocation.rs::from_list` verifies issuer match and CRL signature, returns a listed revocation before freshness handling (preserving ADR 1067's deliberate stale-revocation asymmetry), then applies `Issuance::admits` to `thisUpdate`. With no policy `fresh_after`, it requires `nextUpdate` and rejects only when `at > nextUpdate`; it has no `at < thisUpdate` check. Its lines 1620–1629 explicitly call a list issued after the requested instant acceptable and invoke EN 319 102-1 clause 5.2.5. That behavior is useful for historical evidence but not for the distinct ISO current-UTC requirement.

**The application calls need to carry the distinction.** `viewer-core/src/notes.rs::signatures` starts each signature at `BestSignatureTime::now(host_now)` and substitutes an established timestamp only when one is available. `about_one` calls `Signature::trust` with that selected time; `signature.rs` passes it to `trust::validate_constrained`; `trust::Search::walk` invokes `revocation::status_within` for each path certificate. This is the current-time .7 call when no authenticated earlier time is selected, and the historical .8 signer-path call when a timestamp proves a past time. Independently, `signature_timestamps_instant` invokes `signature_timestamp_established` with `AskedAt::TheCallersInstant(now)`, so the timestamp authority's own path is checked at current UTC even if its genTime later becomes the signer path's historical time. `status_within` has only the instant and `Issuance`, not a current-versus-historical context. Other policy-specific issuance bounds (e.g. `Issuance::fresh_after` for REQ-4.2-03) are separate and should remain separate.

**The ledger row overstates the current-time result.** `doc/conformance/ledger.toml` §12.8.3.4.7 is `implemented` and its note says a CRL answers Good only when the instant is between `thisUpdate` and `nextUpdate`; code does not implement that lower bound. §12.8.3.4.8 is also `implemented`, where later-issued evidence before certificate expiry and with later `nextUpdate` is consistent with its narrower historical condition. A generic one-ended rule cannot substantiate both rows.

**Test evidence is meaningful but conflates contexts.** `revocation/tests.rs::a_crl_that_does_not_list_a_serial_says_the_certificate_is_not_revoked` is a current-in-window signed-CRL positive at `AT = 2026-10-01`. `a_list_issued_after_the_instant_asked_about_is_evidence_about_it` uses the same OpenSSL-issued CA/leaf/CRL fixture and establishes the later-CRL behavior, but its 2025-10-01 query predates the fixture certificates' 2026-01-01 `notBefore`. It proves the low-level revocation function's one-ended behavior; it is not a valid historical certificate-path case. A better historical validation instant for this low-level control is 2026-03-01: after fixture CA/leaf `notBefore`, before CRL `thisUpdate = 2026-06-01`, and before `nextUpdate = 2036-06-01`. This does not test the separate §.8 condition that the CRL actually be captured before signer-certificate expiry; a DSS revision/capture witness would be needed for that.

The fixture is genuine and signed: `revocation/tests.rs::fixtures::CRL` is parsed, its issuer is checked against fixture `CA`, a direct status check must validate the signature under the issuer key, and the Good/Revoked controls exercise both absent and present serials. Literal CRL dates are asserted in `a_certificate_list_states_its_issuer_its_window_and_its_entries`. A March 2026 low-level query would be useful to document that the current generic routine permits later-issued evidence, but it would not distinguish a current check from a historical check or exercise the public PAdES caller.

**ADR decisions need a narrow qualification.** ADR 1067's Unknown/Good and stale-revocation asymmetry remain sound; this finding does not revise them. ADR 1112 correctly fixed historical validation so a later-issued CRL can answer a proven past time, and that control must remain. But its shared `from_list` change and blanket one-end comment collapse the separate §12.8.3.4.7 current-UTC interval into .8's historical rule; reopen that narrow applicability choice, not the whole timestamp or verdict design. ADR 2775's policy freshness bounds are configured issuance requirements that may replace a material window in that policy context; they do not erase ISO's distinct PAdES current-UTC rule. No scope ratification was found that excludes PAdES current-time validation.

**Recommended resolution:** make the PAdES caller's mode explicit (current UTC versus authenticated past validation time) before changing applicability. For the current mode, the source requires `thisUpdate <= now <= nextUpdate`; for the historical mode, retain the .8 rule allowing later-issued CRLs with `nextUpdate > past`, when the separate capture-before-expiry condition is established. Keep policy issuance semantics separate, preserve the rule that an explicit revocation entry remains Revoked even if its CRL's Good-answer freshness window does not apply, and do not treat `thisUpdate` as the actual capture time for the separate pre-expiry condition.

No Cargo tests were run or drafted in this shard. The test boundary is an explicit residual: a useful current-time regression needs a valid signed PDF/DSS route through `viewer-core::notes::signatures` or `Signature::trust`, with host-now context and a CRL future-dated relative to that instant; a separate authenticated historical test should retain a later-issued CRL. The existing low-level CRL fixture establishes cryptographic controls but cannot by itself distinguish those caller modes. A future-dated current CRL is possible through issuer clock skew or a future-dated entry in the document store, while a later-issued CRL answering a past timestamp is a normal LTV case and must remain supported.
