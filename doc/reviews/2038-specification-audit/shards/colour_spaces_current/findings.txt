Scope and evidence

This is a bounded audit of ISO 32000-2:2020(E) §§8.6.2–8.6.5.5 in the effective PDF+EC3 source. The source is `/home/cl/projects/pdf-viewer/scratchpad/r1983/spec-audit/source/spec-layout.txt`; each cited page has the `ISO 32000-2:2020(E)` footer. The primary source extraction labels physical pages, so printed page = physical page − 15. Feature mappings and exclusions are in `features.json`.

No current numeric defect was established in the reviewed device, CalGray, CalRGB, Lab, and supported ICC profile paths. The assertions are not merely all-green proxies: CalGray compares luminance output against independently calculated expected values; CalRGB uses asymmetric primaries/gamma and matrix columns; Lab checks white/black/chromatic anchors and its stated white point; ICC tests include real/constructed profiles, explicit profile ranges and matching output for a profile used by both fill and image. ICC parsing branches on the profile header's major version, consistent with EC3 #181's effective ICC 2.x/4.x rule.

The §8.6.3 ledger row names only `an_icc_space_prefers_its_stated_alternate`, so that row alone is weak evidence for the broad family classification claim; individual leaf rows supply focused tests. DeviceRGB initial value is asserted on the `ColourSpace` helper, but I did not find a public rendering regression that selects DeviceRGB after a nonzero prior colour and verifies reset to black. A public rendering draft is in `drafts/device_rgb_reset.rs`; parent has promoted it for execution. This is an assertion-strength gap, not observed incorrect behavior.

Candidate Table 65 Range issue, not yet a normative verdict

Table 65 (printed p. 191, physical p. 206) says an `/Alternate` must be used when the profile data is unsupported, and specifically directs that values be constrained first to ICCBased `/Range`, then to the alternate's range, with no tint-transform conversion. `parse_icc_based` returns the parsed alternate directly when `Profile::parse` fails. That drops the ICC stream dictionary's `/Range`; the returned colour space exposes only the alternate's range via `component_range`, and `to_rgb` clamps only to that range. Thus a narrower ICC `/Range` appears not to constrain operands on this fallback branch.

The current `an_icc_space_prefers_its_stated_alternate` test differentiates Lab from RGB but uses an empty unsupported stream, no ICC `/Range`, and an operand already within Lab range. It does not test the preceding source-value clamp. A later-version profile candidate has been generated: ICC.2:2023 §8.4 display profiles may use `mpet` A2B/B2A transforms, and §§9.2.1/9.2.38 explicitly permit `multiProcessElementsType` for A2B0/B2A0. This parser recognizes A2B0 but `parse_lut` does not support `mpet`, so this profile type is unsupported by the implementation and should reach `/Alternate`. The 528-byte profile has a Lab data signature and required display tags; a separate checker verifies version/class/PCS, required tags, tag bounds, MPE element offset/size, and the 3×3 matrix encoding against ICC.2:2023 §§8.2/8.4, Table 63 (§10.2.17), and Table 120 (§11.2.10). ICC's official iccDEV Python API `validate_profile_file` independently accepted it (`iccdev==2.3.2.5`, `ValidationStatus.OK`, empty report). The official ICC page describes iccDEV as supporting v5, and its open-source tools page describes its profile conformance utility. LittleCMS 2.20 `transicc` refuses the v5 header before inspecting tags, so it could not serve as the validator. The public exact-xref test draft is `drafts/icc_alternate_range.rs`: it sets Table 65 `/Range` to Lab Table 68 bounds, uses a wider alternate Lab range, and asserts that fallback `a*=150` matches direct alternate `a*=127`, with a direct 150 negative control. This establishes a validator-confirmed later-version profile candidate and an unasserted Table 65 requirement; the PDF-level regression remains unexecuted pending parent integration/run. No Cargo/test was run by this audit.

Other qualifications

Table 65's `/Alternate` test verifies the fallback choice but not all fallback rules. Its empty stream is not a valid ICC profile; it exercises recovery. The absent-Alternate N-based fallback is in code (`N=1` Gray, `N=4` CMYK, otherwise RGB), but no test was found for a valid unsupported-profile data stream; malformed or unknown N recovery is not promoted as a normative defect. CIE `WhitePoint` Y=1 and BlackPoint nonnegative requirements are producer constraints; accepting a nonconforming parameter is not, by itself, proof the reader violates a requirement. DeviceCMYK conversion to RGB, CIE conversion policy, defaults, intents, special spaces, patterns, and shadings are outside this audit.
