# Overprint and transparency interactions (bounded review)

I found no confirmed valid-input defect in the sampled pattern/transparency, group-space, spot-plane, overprint, or per-point transfer behavior. I also found no additional independent regression that would improve on the already-present tests without duplicating neighboring shards. This is not clause-wide conformance certification; the precise unreviewed combinations are listed in `features.json`.

The primary PDF was checked by physical page and ISO footer, rather than inferred from a markdown line or heading. The audited source spans physical 439–450 (printed 424–435); pages 439–449 contain the specific assigned text. The primary pages contain no EC3 annotations in the assigned range. Effective text was cross-read in `doc/md/ISO_32000-2_sponsored_EC3.md`. There were no applicable issue overlays to add to `doc/errata-read.md` for these particular pages. Referenced requirements in §8.6.7 and §10.5 have their own errata ownership and were not re-audited in full.

For §11.6.7, pattern evaluation and painting are separate phases: the content-defined pattern gets the prescribed implicit group, default transparency constants, and stream-start state; later use supplies the painting state. Current `PatternInitial`, cell wrapping and shading-pattern paths line up with that split. `tiling.rs` compares alpha on the completed pattern against per-cell behavior, exercises blending on the named non-isolated group and verifies the backdrop taken by a cell; shading tests cover inherited stream state and carrying the painting mark's constant. The prior `pattern_forms_current` and `shading_current` audits own geometry, matrix, and shading data; I do not recertify them. The recommendation that a rasterizer treat all tiles as one group is advisory; the observable seam behavior is the reason for it. The uncolored-cell prohibition on specifying color is a producer constraint, so its absence as a reader rejection is not a defect.

For §11.7.2, the implementation converts into the group's blending space before group composition and resolves outward after; the test suite includes direct DeviceCMYK/ICCBased CMYK redefinition, nearest CIE group-space behavior, and nested press/group conversions. The cited tests compare expected colors in group space or hand-controlled profile routes, rather than just checking that a display-list group exists. The resource budget can refuse an otherwise distinct press and reports that refusal, but this shard does not infer an unbounded profile requirement from §11.7.2.

For §11.7.3, both allowed spot strategies are observable: spot-plane tests show independent tints surviving a knockout group and crossing a differently colored group; RGB routes use the alternate representation. Soft-mask spot substitution has dedicated end-to-end fixtures for ordinary and RGB soft-mask groups, comparing against alternate-space controls. This confirms the mandatory soft-mask clause without conflating it with the permissible choice to preserve spots in a print/simulation route. Physical ink appearance and all host output devices remain output-dependent.

For §11.7.4, the general subsection explains opaque-model parameters and the distinction between appearance-space transparency and output-time device overprinting; it is not an independent special-mode requirement. The special mode in §11.7.4.3 is expressly optional. This implementation elects to implement it for supported four-component contexts, so the mode's conditionals apply. `overprint.rs` compares a zero process tint under OPM 1 with the independently named resulting CMYK color and with the erasing OPM 0/OP false route; it also checks no-zero tint, source space reversion, per-paint-part state, and implicit grouping for non-Normal mode. Separate three-component tests assert that opaque overprint has no effect where the output has no CMYK colourants. Those facts must remain separate: an RGB native-device no-op is not proof about the four-component transparency group, and the latter tests do exist.

Table 146's closing note says the group-object row uses Normal because a group carries no per-component source mask; `Do` group commands do not inherit the elementary object's compatible-overprint blend. The tests cited here sample supported reachable process rows and source-space transitions. This shard does not rederive every cell, nor every Separation/DeviceN/spot component by every output backend. Spot planes and soft-mask tests in the previous paragraph cover select cases, while the feature map records these narrower limits.

For §11.7.4.4, the existing paths and tests cover both the special first construction and the otherwise knockout-group construction. The text-mode `/TK` independence assertion matters because §11.7.4.4 expressly separates combined fill-and-stroke text from text knockout semantics. The fresh stroke/fill audit independently has a direct single-object raster test. I did not duplicate its proposed geometry cases here. Remaining checks include all four combined path operators, mode 6, unequal stroke/fill alpha, and further mode/soft-mask combinations.

For §11.7.5.2, the implementation's transfer channel selects by topmost elementary shape after composite, with separate opacity ancestry and per-component overprint handling. Tests cover translucent/group/mask/pattern/shading conditions and have a strong OPM1-vs-OPM0 control: when the component comes from the backdrop, that component is not opaque and takes the page default transfer; when source replaces it, the object's transfer applies. The adjacent `rendering_intent_transfer_current` shard already identifies a narrower assertion gap: Type 5 dictionary and Type 6 stream transfer overrides were manually applied from display-list transfer maps rather than directly rasterized. I leave that gap with the owning shard instead of drafting a duplicate. Screen behavior is not a mandatory output for this continuous-tone CPU rasterizer; that permission does not excuse transfer-function processing.

The source-to-ledger map and ADR reread are in `features.json` and `decisions.json`. All current ledger rows are marked implemented, while the current round clause inventory still says pending; this report is evidence for selected features, not a final inventory disposition. No tests were run or files outside this shard changed.
