# Clause 12 interactive framing (bounded)

I read the effective EC3-consolidated text for the requested Clause 12 rows, checked relevant primary-PDF overlays against `doc/errata-read.md`, and mapped the overview statements to existing specialized review shards and assertion bodies. Printed-page locators in `features.json` are paired with physical PDF locations; I used the source footer convention and existing source-verified shard locators. This is not a certification of every interactive annotation, form field, action, or geospatial method.

The main distinction is between truly introductory clauses and rows that happen to contain “General” in the title. §12.1 is a feature map; it contains no independent processor requirement. §§12.3.1 and 12.4.1 describe navigation families; their child rows own the operative destination/label/article/presentation behavior. §12.10.1 introduces the geospatial vocabulary. By contrast, §12.5.1 includes a supported keyboard navigation algorithm, §12.9.1 states reverse viewport/first-point selection rules, and §12.11.1 requires pre-script requirement evaluation and defines requirement entries. Those cannot be treated as empty introductions.

Document-level navigation is split across outline, thumbnails, destinations and collections. Existing tests observe click-to-page navigation, thumbnail pixels and outline structure. The destination follow-up separately shows why page-index success does not prove that GoToR/GoToE table-149 view parameters reach the target window; that trace and unrun discriminating draft remain live. Effective EC3 #477 moves the full published §12.3.6 navigator material to §12.3.5.3. The collections sibling found a concrete public host gap: Schema fields `S`, `D` and `CompressedSize` are read but not emitted in host cells, while the cited host test checks only F/Desc/Size. I preserve this as a carried-forward finding rather than claiming the aggregate `implemented` status certifies the whole collection UI.

§12.4's framing names labels, articles and presentations. Existing `thumbnails_transitions_current` evidence is based on rendered transition frames and notes that presentation mode is optional. `navigation_actions_current` covers §12.4.4.2 and EC3 #304; it notes one fixture does not assert no recovery. These remain local evidence limits. The aggregate heading cannot turn slideshow details or optional transition presentation into universal requirements.

Annotation and action headings contain useful boundaries. §12.5.1 says an interactive processor may permit keyboard navigation, then gives row/column/structure/array/widget order when used. The current implementation calculates all five modes and supplies focus/accessibility. The source's optional support matters: I found no universal duty to add a tab feature to every PDF reader. Test strength is narrower than implementation: `untagged_widgets.rs` has a geometric `/Tabs /R` control, while the generic headless forward/back walk does not distinguish all five modes. This is an assertion boundary, not an observed wrong-order result. §12.5.6.1 indexes the standard types and generic unknown-type handling; the actual public unknown subtype with an appearance test supplies a behavior witness, while each subtype remains assigned to its own child shard. The aggregate annotation status must retain accepted departures for writer appearances, stored AP transparency policy, and redaction composition rather than implying every producer/reader sentence is implemented.

The action type tables are indexes, not independent commands to execute every known action regardless of the project’s processor scope. The current action row records per-action performing, reporting, refusal, departure, and multimedia exclusions. Its children own actual trigger behavior; `/Next` ordering is a separate action-chain row. The selected GoToDp, Thread, and Transition review supplies public consumer drafts or residuals independently. No new action-order defect was found in this framing pass.

Forms framing distinguishes a field hierarchy from a Form XObject and summarizes button/text/choice/signature behavior. The specialized forms shards have real `Viewer`/host assertions for representative controls, state changes, imports, and exports. Their producer constraints (no incremental update, generation-zero unique object IDs, direct stream Length) are not, on their own, mandatory reader refusal instructions.
