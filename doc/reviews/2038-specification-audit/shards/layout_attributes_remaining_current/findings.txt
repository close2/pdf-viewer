§14.8.5.4.3/.4 layout-attribute feature audit

I inspected the effective EC3 PDF, the Markdown extraction, the ledger rows, current code, and selected ADR/test assertion bodies. Primary locations are physical pages 795–798 / printed 780–783 for Table 379, 799–800 / printed 784–785 for Table 380, physical 802 / printed 787 for Issue #152, and EC3 replacement Table 377 at appended physical pages 1013–1014. I verified the footer locators from `ec3-parent-layout.txt`; the appended errata pages have no ISO printed page.

Table 379 has thirteen entries. `/BBox` is an observable result (visible-content bounds) consumed by `Tree::bounds` and the accessibility component path; ADR 0301 and the tests it cites establish that route. `/SpaceBefore` and `/SpaceAfter` are consumed by allocation-rectangle construction and have source-derived rectangle tests; the separate §14.8.5.4.5 review owns their geometric test matrix. The other ten—indent/alignment, extent constraints, cell content alignment, border style and padding—configure a reflow/layout process. This viewer displays the geometry already recorded in PDF drawing commands and has no alternate-format reflow destination. Their writer-side defaults/applicability and implementation-dependent negative-indent language do not create a mandatory reader rejection or render path. The producer `should` for BBox is not a reader-side rejection rule.

The effective Table 377 applicability matrix matters: it allows several Table 379 fields on ILSEs whose Placement is not Inline, and EC3 explicitly allows Table 380 BaselineShift on BLSEs containing ILSEs or content. This changes where producers may state values; it does not itself require a display reader to perform reflow. Code reads spacing values whenever allocation is requested and does not strictly reject inapplicable values on malformed elements. I found no reader obligation to reject such producer-invalid combinations.

Table 380 has nine entries. Four reach the adopted accessibility export: `/TextDecorationType`, `/TextDecorationColor`, `/BaselineShift`, and `/TextPosition`. `Tree::inline_statements` ranks/parses those fields, the viewer-core walk applies inheritance by structure category, AccessKit receives text attributes on the element’s own runs, and the C ABI has a separate style query. The actual assertions cover allowed/unknown defaults, nested decoration stop at BLSEs, color inheritance, baseline sums and sign, nearest TextPosition choice, own-text headless delivery, AccessKit run attributes, and C ABI values. The AccessKit bridge must invent opaque black when decoration color is absent because its API requires a color; the core/C ABI keeps absence, and the source default (“current fill colour at start”) is not derivable from this accessibility readback. This is an acknowledged policy loss, not a parser defect.

The remaining five—LineHeight, GlyphOrientationVertical, TextDecorationThickness, RubyAlign, RubyPosition—have no current platform text property or layout/export engine. Ruby roles cross, but their layout does not. EC3 Issue #152 changes the GlyphOrientationVertical cell from `number` to `integer`; Table 377 replacement Issues #223/#226 correct applicability mappings. None of those source changes produces a missing reader behavior for this no-reflow consumer.

One policy boundary deserves precision. EC3 Table 377 explicitly permits BaselineShift on BLSEs with content and §14.8.5.4.4 allows Table 380 attributes on BLSEs for immediate child content. `viewer_core::Inline::enter` currently accumulates the sign-to-VerticalOffset choice only within inline chains and resets it at a BLSE; the existing unit test asserts a Paragraph’s own shift is Normal. A634 says reading the sign as Sup/Sub is a project mapping choice, not a source-defined meaning. For a whole Paragraph, turning its geometric baseline displacement into Sup/Sub on every text run could overstate semantic position; this viewer does not lay out or export replacement geometry where the omission can be shown to lose the block’s actual position. I therefore record a representational-policy / ADR-description boundary, not a conformance failure or test candidate. ADR 2384’s reset rationale should not be read as saying that BLSE values are outside Table 380/Table 377 applicability.

No test draft is included. The unimplemented attributes have no current consumer; their parser/producer validity alone does not create an observable display failure. A future reflow/export path must reopen their values, defaults, inheritance and Table 377 applicability. This was a bounded feature review, not full certification of Tables 379/380, BBox precedence, table geometry, or the referenced ADRs. No Cargo command or test execution was run.
