# Raster clipping and curve-flattening ADR review (updated after current-code inspection)

I checked ISO 32000-2/EC3 directly from the held primary PDF with footer locators. No tests or builds were run by me. Current code and current test bodies were re-read after discovering newer exact-meet code.

ADR0044 is well supported at normal tested scales. §10.7.2 (printed p.382, physical p.397) defines flatness as maximum distance in device pixels between the mathematical path and a straight-segment approximation, permits ignoring the document's requested flatness, and warns that visible segments make results unpredictable. `raster/tests/flatten.rs` uses closed-form cubic area and polygon area/perimeter rather than a second renderer, and checks actual raster-byte ink against an independently integrated circle area. This is meaningful evidence.

There is one mathematical residual in the absolute bound claim: `flatten_cubic` always emits at depth 16 even when the flatness predicate is still false. `cubic_tolerance` is 0.25px for large control hulls (relative term is then not active), so the claim that the cap guards only the absolute branch is not universally true at unbounded transformed magnitudes. Scene points, command transforms, and viewport coefficients are individually bounded at 1e9, but composition permits much larger finite device coordinates; a cubic on the order of 1e18 device units would still have residual curvature after 16 splits. I derived an extreme candidate but did not establish a visible-window failure: at those magnitudes most error may lie far off-screen, while the visible neighborhood around a crossing can be locally much flatter. Treat this as a testable limit qualification, not a confirmed reader-visible defect. A targeted unit regression could measure sampled curve-to-polyline distance under the maximum valid composed transform; a public-output follow-up would be needed before calling it a practical behavior failure.

For clipping, ADR0030's idempotence witness remains good: `m3::a_clip_stated_again_admits_exactly_what_it_did` uses a fractional diagonal edge and exact-compares repeated identical clips. But current behavior is richer than the older min-only ADR text. Residue meets on path geometry compute exact intersection areas from both edge sets where both shapes cut a pixel. `residue_meets_a_mark_as_a_set::a_polygon_clip_over_a_tiling_of_rectangles_meets_each_pixel_as_a_set` compares the complete output to independent f64 polygon clipping and per-pixel area, with a half-level allowance, and explicitly proves min/product would differ. Image-vs-residue tests use an independent geometric rectangle intersection. These are strong discriminating controls, not circular CPU parity.

`min` remains in clip-link composition, path-vs-rect clips, group compositing, or resource/edge-budget fallback cases where joint geometry is not retained or computed. It is a conservative upper estimate under the §10.7.4 area-floor sentence; it is not generally the exact area, nor necessarily closer than product for every fractional overlap. The 0.9/0.4 example from the earlier review is a valid counterexample to the historical interval-only “never further” argument, but current exact-meet routes address the main path/residue use case. ISO defines the geometric/pixel-set intersection and area floor; it does not specify a universal fractional antialias byte. Therefore no mandatory failing test is justified for the remaining chosen min approximation.

ADR0074's public group tests correctly cover same-edge and nested cases where min is geometrically exact, a low-opacity countercontrol where alpha is not shape, and an unknown-mask conservative fallback. For unrelated fractional group/clip boundaries, the implementation has only group alpha and clip coverage, not source edges; min is an approximation. Keep the ADR's optimization claims scoped to its proven shape/alpha cases and do not certify exact crossing geometry.

I also corrected the prior raster ADR0085 feature artifact separately: public `render-raster` does dispatch material anisotropy to path-space `kurbo::stroke`; the parent-run independent anisotropic test passed in Cpu/Gpu/Compute for straight and joined paths. The earlier scalar-only failure claim is withdrawn.
