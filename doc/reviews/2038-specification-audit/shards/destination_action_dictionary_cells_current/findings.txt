# GoToR / GoToE dictionary cells and target traversal

I selected Table 203 (remote Go-To), Table 204 (embedded Go-To), and Table 205 (embedded target path). The table headers, rows, continuations, and footers were checked directly in the held primary PDF: 203 is physical 527–528 / printed 512–513; 204 is physical 528–529 / printed 513–514; 205 is physical 529 / printed 514. Primary annotations were enumerated on those pages. #258 at physical 529 is an effective NOTE restricting name-object named destinations for this particular GoToE `/D`; it is not a requirement to reject all such values at read time. #140 on physical 526 changes Table 202 local Go-To and is context only. No other annotation changes a selected table row.

Table 203 requires S, F, and D. Its D forms are name, byte string, or array; for an explicit destination the target document's page index is an integer and zero-based. Optional SD is PDF 2.0 and should take precedence over D; NewWindow has no hard “shall” behavior for true/absent beyond its stated false same-window case and preference. The live remote tests distinguish target-page index 2 from the two-page source, verify host request purpose/name, resolve an SD ID against the remote document where its MCR is on page 2 while D selects page 0, and check a named Beside window. A scratch public candidate now also checks `/D /chapter` via target Catalog/Dests and `/D (chapter)` via target Names/Dests, with a preceding explicit-array page-index-2 control; it avoids any same-key collision and does not reopen B08. Destination view is a separate issue: B23's independent exact-xref `/XYZ` tests still fail for remote and embedded actions after Supply, observing default fit geometry; local action and target OpenAction geometry controls pass. No duplicate failure is proposed.

Table 204's F identifies a root relative to the source root; T is optional when F is present and required otherwise; D is a target-document destination. Existing viewer tests exercise the external root question/answer, child lookup, target page index, window selection, and no-file-request embedded route. Model tests verify deep N-child traversal and root resumption after a host-supplied root; URL root resolution is present because EC3 #256 makes the URI base apply across the document. `NewWindow` policy is a processor `should`, not an unconditional MUST. #258's NOTE means a Name object for named D is not a producer-supported form here; tolerant parser handling is not a defect.

Table 205 distinguishes child-by-EmbeddedFiles-name (N) from child-by-file-attachment annotation (P plus A), with both integer and string/text variants for P and A. Model unit tests `a_child_may_be_named_by_the_annotation_it_is_attached_to` only assert the resulting TargetStep data. Public viewer navigation currently exercises N, not P/A. A scratch public test uses P=0/A=1 against a FileAttachment annotation/embedded stream and checks the child target page; the sibling `embedded_go_to.rs` N-child route is the existing positive implementation control.

The other uncovered Table 205 case is parent navigation from a document that is already embedded. The clause defines each intermediate document as the current one and permits an embedded PDF to be source as well as target; `/R /P` names the current document's parent. The important scope boundary is whether the reader actually knows that parent: a PDF opened independently by the user is a root in this session and correctly has no parent context, but a child reached from an already-open PDF through an embedded-file action has a known parent whose bytes are already in the open source. That parent ascent needs no external file access, URL resolution, or new user authorization.

The implementation currently loses this known relation. `EmbeddedGoTo::target_in` accepts only `&Document`; `walk` creates a fresh `descended` stack for the current action and returns `NoParent` if its first step is `Parent`. `viewer-core::interact::jump_into` calls `Open::around(opened)` without provenance, and `viewer::outcomes` inserts that replacement under the same document ID, replacing the prior `Open`. Thus after root→child navigation the next child action cannot ascend, although it can navigate back to an ancestor only when that ancestor was entered earlier within the *same* action's `/T` path. ADR 0094 expressly makes `/R /P` from a user-opened root a refusal; that premise remains correct. Its further assertion that the sibling example is performable “only from a document that is already a child” is not wired to any persisted parent context, so it does not establish support for a child reached on a prior action. ADR 0076's refusal to write/extract attachments and ADR 1227's broker policy for a different root `/F` do not block traversal through bytes already embedded in this open document.

I drafted a two-level exact-xref regression with valid equal 16-byte IDs, exact embedded-stream length, EmbeddedFiles name-tree entry, FileSpec/AFRelationship, and page resources. It first positively opens the child from the root, then expects its parent-directed GoToE to show parent page index 1. Parent is adjusting version-dependent fixture obligations and complete-chain guards before execution. Treat this as a narrowly scoped same-root hierarchy-navigation capability gap, not yet an executed behavior finding or an unqualified ISO reader violation. Independently opened PDFs remain roots; the fixture's documented root→child route is the evidence that the parent relationship is known.

ADRs 1227 (remote broker boundary), 0076 (embedded bytes are not automatically extracted), and 1263/1264 (window preference) remain sound for their covered decisions. ADR 0094 remains sound for refusing `/R /P` from an independently opened root, but its implemented traversal model only supports a parent reached earlier in the same action path; no viewer field preserves a known parent across GoToE replacement. A user opening the original root already supplied the document bytes and thereby makes the embedded child and its actual parent available to this reader; this is not the separate-root `/F` host handoff. The source/API review therefore supports the regression as a valid missing path in the current GoToE implementation, while final product/spec duty language should stay qualified to opened-by-this-reader embedded sources. B08 remains unresolved for colliding legacy and name-tree destination keys. B24 is local FitR/FitB placement and not evidence about cross-document target view. B32 concerns page-label search. This review does not certify all destination forms, all host policies, cycle refusal, or malformed-input responses.
