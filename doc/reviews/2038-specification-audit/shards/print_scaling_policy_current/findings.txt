Audit root: `/home/cl/projects/pdf-viewer/.claude/worktrees/r2038-audit` (`pwd` and `git rev-parse --show-toplevel` both verified). Baseline inspected was the current worktree state. Read-only review; no tests were run and no tracked source, ledger, or ADR files changed.

**Result:** I found no source-backed current failure for ordinary, valid Table 147 print preference values on the supported interactive print paths. The model/query and shared `viewer_host::PrintDefaults` preserve the preferences; GTK transfers copies, duplex, no-scaling, and all valid page-range pairs into `GtkPrintSettings`; Qt transfers copies, duplex, no-scaling and every page-range pair through `QtPrintJob` into `QPrinter`/`QPageRanges`. AppDefault remains processor-defined as the table says. `/PickTrayByPDFSize` is retained in the generic plan, but deliberately not sent to GTK's source/tray field because that field chooses a named tray rather than selecting a tray by page size. The EC3 table expressly says the preference has no effect on systems without the latter ability. Qt's inspected dialog setup likewise has no matching checkbox. No target platform with the named ability was established, so this is a capability boundary rather than a demonstrated defect.

The meaningful test-quality gap is at the native settings seam. `viewer-core/tests/print_preferences.rs` verifies exact-xref parsing into `Query::Preferences` and screen-pixel independence. `viewer_host::printing` tests verify `Defaults` values and 1-based range membership. Qt's toolkit-free `Host::print_job` test uses a silent PDF and never asserts a non-default preference reaches `QtPrintJob`; the print preferences tests do not exercise `QPrinter` or `QPrintDialog`. I found no corresponding GTK test of `print_settings` or a settings object attached to `GtkPrintOperation`. The existing ADR 1180 evidence explicitly says native dialogs were compiled/reviewed but not driven. This supports a bounded missing assertion, not a behavior verdict. A focused bridge/settings assertion for `/Duplex`, `/NumCopies`, `/PrintScaling /None`, and two `/PrintPageRange` pairs would be useful; `/PickTrayByPDFSize` should be asserted only on a supported system exposing that exact checkbox.

**Source distinctions:** Table 147 (EC3 printed pp. 439–440; physical pp. 454–455) defines each of the five items as dialog state. `PrintPageRange` is an initializer and uses inclusive 1-based pairs; it is not a mandatory range restriction after the dialog. `/Duplex`, `/PickTrayByPDFSize`, `/PrintPageRange`, and `/NumCopies` all have implementation-dependent defaults. `/NumCopies` says typically one, not a mandatory one. `/PrintScaling` alone has the AppDefault fallback and explicit instruction for suppressed dialogs where parameters come from elsewhere. Table 148 only permits enforcing a valid non-AppDefault PrintScaling, which is the separately reviewed `/Enforce` boundary.

The Qt source currently narrows copy counts and page indexes to `i32`, with values outside the bridge representation becoming zero; GTK likewise only sends copies/ranges that fit its `i32` API. I do not count that as a finding: PDF number range/precision may be implementation-limited under informative Annex C, and Table 147 states no policy for nonpositive or unrepresentably large counts. Qt clamps out-of-document page ranges to the document; GTK converts ranges directly. The inspected Table 147 text does not prescribe recovery for such invalid/out-of-range input.

I did not re-audit `/Enforce`, the print-area/clip or `/PrintScaling` page-rendering interaction, toolkit behavior under an actual printer backend, or the separate no-dialog C ABI interaction between the suppressed-dialog PrintScaling sentence and a caller's explicit media/scale. ADR 1203/1204 concern print operation/placement, not the five dialog defaults; this report makes no compliance claim on that C interaction.
