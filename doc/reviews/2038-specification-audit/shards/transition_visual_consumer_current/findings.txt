# Page transition visual consumer review

## Effective source and conditional scope

The primary EC3 PDF was checked directly, including the footer numbering. §12.4.4.1's presentation permission and `/Trans` rule are on physical p.476 / printed p.461. Its Table 164 occupies physical pp.477–478 / printed pp.462–463; NOTE 2 is on physical p.478 / printed p.463. The timing example is on physical p.479 / printed p.464. The source says some interactive processors “may allow” presentation/slide-show display, so this is an optional capability at the product boundary. This viewer has taken that option: `p` starts/stops the presentation and GTK, Qt, and Quorra hosts route presentation ticks. For an enabled presentation, the `/Trans` dictionary describes the visual effect used when moving from another page to its page. Table 164 provides literal effects; omitted `/S` defaults to `R`, and `R` is a cut with no special effect. Therefore the source does not say every page must animate, and optional presentation support must not be turned into a global UI mandate.

The source overlays on physical p.478 / printed p.463 were also checked as annotations rather than inferred from extracted body text: Issue #36 has two StrikeOut/Caret replacement pairs (Caret `/Contents` values `integer` and `an integer`), and Issue #75 has two replacement pairs whose Caret `/Contents` are `uppercase`. Those corrections amend the `/Di` type and capitalization in Table 164. The implementation's acceptance of fractional angles is deliberately permissive input behavior and does not affect this sequencing review. Neither correction changes whether a supported Table 164 effect should be drawn in an active presentation. I found no other applicable §12.4.4.1 erratum in the bounded transition source review.

## What is asserted versus what reaches the window

There is genuine layered visual evidence beyond the core `Event::Transition` check. `viewer-core/tests/headless.rs::a_transition_frame_is_between_the_two_pages` opens exact-xref red/blue pages, enters presentation mode, ticks past page one’s duration, observes the incoming `/Wipe`, draws the two face rasters at 25% and 50%, and checks literal pixels on both sides of the sweep. It verifies real pixels but chooses progress directly rather than establishing that a host clock and native refresh delivered those samples. `viewer-host/src/clock.rs` separately tests elapsed-time fraction, duration expiry, and the rest/animation interval. `viewer-ui/tests/transition_frames.rs` checks static CPU/headless-device pixels against a closed-form wipe, and adds static Dissolve/Fly cases.

The integration consumer path is concrete. `NativeWindow::arm_transition` stores the incoming-page transition until that page’s `NeedsRender` request; `face_arrived` captures the outgoing and incoming pages and begins the common host `Clock`. `PresentationPump::turn_the_presentation` asks the clock for a frame and rasterizes it. GTK stores the resulting raster as a texture and refreshes; Qt stores it and sets its frame update flag; Quorra draws the transition frame through its presentation surface. This distinguishes page-transition rendering from the separate action-transition requirement in §12.6.4.15.

`tools/drive-windows.sh::transition_frames` is an end-to-end visible-sequencing assertion, not merely an event counter. It builds red, blue, and green pages with a destination `/Wipe` and `/Split`, enters presentation via `p`, takes repeated X11 window-pixel captures, and checks that it sees three settled slides, moving frames in both transitions, and no sampled color outside the pair of settled page endpoint ranges. It runs the three native hosts and both Quorra CPU/device paths. The script describes this as a manually run environment workflow rather than an ordinary test gate. ADR 0230 also reports earlier Xvfb captures, but those are historical observations, not current execution evidence.

## Disposition and residual

I found no source-backed defect in current native transition behavior and no basis to treat “may allow” as requiring all processors to expose a slideshow. Because this product does expose one, `/Trans` frames are expected in that mode; current code has a complete path and the Xvfb drive script directly checks real visible frames. The assertion concern is narrower: the normal automated test set splits the contract among event selection, clock progress, static pixel composition, and a manually invoked window-capture script. Without a current run result for the script, a passing `cargo test` suite alone does not certify that each host’s UI loop visibly sequences the frames. I did not draft another test because step 83 already provides a discriminating, source-derived end-to-end check; duplicating it as a counter or a second pixel camera would add little. Parent can decide whether the Xvfb script belongs in a repeatable CI/gate, and should report actual execution separately from code inspection.

This bounded review does not certify visual capture of all twelve styles on every toolkit, compositor scanout, every transition geometry, or sub-page-navigation behavior. The four owner-selected style quantities remain implementation choices under A72/ADR 1299.

Parent execution: explicit-X11 rerun transitions-wave72b passes all four arms (GTK, Qt, Quorra default and --cpu); three settled pictures each and nonzero moving frames in both effects. Initial inherited-display attempt was terminated after no Xvfb windows were found; it is not a PDF behavior failure. Camera endpoint pixels are captured, not independent expected page rasters. Quorra logs are overwritten between arms, so no retained hardware-adapter provenance is claimed.
