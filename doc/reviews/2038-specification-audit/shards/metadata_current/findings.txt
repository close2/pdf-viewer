This review is limited to ISO 32000-2 §14.3 and its relevant metadata decisions. It does not repeat the date parser audit. Primary evidence is the EC3 PDF at printed pp. 714–718 (physical pages = printed + 15), `doc/errata-read.md`, ledger rows 14.3.1–14.3.4, current code and test bodies. No whole-clause or whole-ADR certification is implied.

**Effective requirements and producer/reader boundary.** §14.3.1 (printed p. 714) says metadata is global information, distinguishes document and object-level metadata, prefers metadata streams in PDF 2.0, and deprecates document-information-dictionary metadata except CreationDate and ModDate. Those statements govern what a producer should write; §14.3 does not instruct a reader to reject older Info dictionaries or suppress them. The reader reaches both carriers: `pdf_model::metadata::Information::read` reads trailer `/Info`; `pdf_model::xmp::Xmp::document` reads catalog `/Metadata`; `viewer_core::Query::Properties` returns both independently. §14.1 says metadata does not affect final appearance, so the properties panel is a host/UI choice, not a page-rendering obligation.

§14.3.2 and Tables 347–348 are printed pp. 714–715. The required `/Type /Metadata`, `/Subtype /XML`, and XML/XMP content grammar are producer constraints. EC3 Issue #296 adds “All XMP metadata in PDF shall be encoded as UTF-8” (physical PDF p. 730, printed footer p. 715; transcription `doc/errata-read.md:2733`). Current writers emit UTF-8, and `pdf-transform/tests/metadata_requirements_audit.rs::emitted_metadata_streams_have_table347_names_and_utf8_packets` directly asserts both required names and valid UTF-8. `Xmp::read` deliberately reads the payload even when `/Type` or `/Subtype` is absent: those table entries bind the writer, and no reader-side rejection is stated. It works over a caller-held dictionary as well as the Catalog; `pdf-model/tests/xmp.rs::a_metadata_stream_on_a_form_xobject_reads_back` is an object-level control. Table 348 allows metadata on a component stream/dictionary; §14.6.2 allows a named metadata stream in a marked-content property list. Generic decoding is present, but no in-scope clause here requires a UI or behavioral consumer for every object-level metadata carrier. Encryption of metadata is a §7.6 / Table 21 matter, separately tested by `pdf-syntax/tests/encryption.rs::a_metadata_stream_is_in_the_clear_when_encrypt_metadata_is_false`.

Current `xmp.rs::decode` accepts UTF-8 and BOM-marked UTF-16/UTF-32. Its documentation now accurately calls the latter a deliberate permissive departure from the producer encoding requirement. This is not a reader-conformance defect: the erratum does not command readers to reject nonconforming input. Do not relabel acceptance as what PDF's encoding rule permits. Issue #398 on the §14.3.3 example (physical PDF p. 732, printed footer p. 717) corrects the example's printed BOM glyph to UTF-8 U+FEFF; the writer emits U+FEFF. It does not change a reader requirement.

§14.3.3 and Table 349 are printed pp. 715–717. Trailer `/Info` is optional. The table gives nine fields and defaults `/Trapped` to the name `/Unknown`; the two prose rules require non-date values to be text strings and require `/Trapped /True` or `/False` to be a PDF name, not a boolean. `/ModDate` is required when the Catalog has `/PieceInfo`. The primary Table 349 has six text-string fields, two date fields and the name-valued `/Trapped` field. The introductory comment in `metadata.rs` inaccurately calls the non-date counterpart set “seven text entries” (counting `/Trapped` as text); `Information::in_dictionary` correctly parses `/Trapped` as a name and strings only for the six textual fields. Treat this as documentation imprecision, not an implementation or source-rule change. The actual `metadata.rs::table_349_is_read_and_its_two_prose_rules_hold` body checks all nine fields, default/name-vs-boolean distinction, a non-string `/Title`, no `/Metadata`, and absent `/Info`; `metadata_requirements_audit.rs` checks the conditional ModDate rule. `Information::in_dictionary` also exists for the stated use with Threads. The date parse itself is outside this assignment.

§14.3.4 is printed pp. 717–718 and is specifically about creation and modification times/dates. Its four bullets impose writer duties: first-time creation date equivalence if both sources are written; preserve an existing inconsistent creation pair on modification (should); a missing counterpart may be added if equivalent; last-modification values must be equivalent if both written. For a reader that encounters inconsistent values, use is at PDF processor discretion. These sentences do not create a general mandatory precedence for all Table 349/XMP counterparts. The panel's separate rows make its chosen treatment visible without claiming a normative ranking. Existing update and merge test bodies read both emitted sources and compare corresponding values; the date consistency assertions are out of scope for retesting here.

**Consumer and assertion depth.** `viewer_core::Query::Properties` returns `Information` and `Option<Result<Xmp, XmpError>>` separately; `viewer-host::panel::property_rows` renders `/Info` entries then a separate “§14.3.2 (XMP):” group, and keeps the no-stream/refused/readable states distinct. Public core test `headless.rs::a_document_hands_over_what_it_says_about_itself` exercises a real document with both sources, checks `/Producer` against `pdf:Producer`, and checks that `dc:title` exists. It does not use conflicting values. Host panel tests presently exercise no `/Info` and Info-only rows; no test of `metadata_rows` against a packet-bearing document was found. Since displaying both is a deliberate UI choice, not a §14.3 SHALL, this is a regression-test gap rather than a standard conformance defect. `drafts/conflicting_info_and_xmp_rows.rs` exercises the public Query-to-panel path with exact xref, valid UTF-8 XMP and two different title values; it also has a catalog-no-packet control. It verifies separate labels and exact values, not a required precedence. No test was run here.

**Selected decisions.** `decisions.json` records bounded reviews of ADR 0186 (parser/dependency and limited interpretation), 1269 (archive conversion), 1473 (PDF 2.0 update/merge routing and view), 0564 (host properties panel), and 1275 (tab title). Retain these as product implementation choices while keeping scope distinct: writer obligations bind file producers; the panel choice to show both sources is not specified by §14.3; the one explicit title-bar source rule is §12.2's `/DisplayDocTitle` use of `dc:title`. For conflicting date values, §14.3.4 grants reader discretion rather than precedence. The new draft protects the current panel presentation without turning that policy into a normative requirement.
