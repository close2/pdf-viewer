Table 301 /MU–/NU overlap — interpretation question, not a confirmed defect

Table 301 printed p. 633 says any player specified in /NU is “effectively removed” from /MU, with an example that subtracts version ranges. It also says an empty array is treated as absent. Section 13.2.7.2.2(c), however, gates on whether one or both /MU arrays are non-empty and then tests whether the candidate is found in them. For an unnamed hand-off where MU=[A] and NU=[A], the source does not expressly state whether set subtraction leaves an absent effective /MU (so the hand-off is no longer constrained) or a present whitelist with no eligible player (so it remains unavailable). The logical-player algorithm may support the latter: no candidate can be “found” in the whitelisted set after exclusion. It is unsafe to infer a normative pass from the empty-set intuition alone.

The current `media::players` records whether a viable /MU entry remains but does not compute PID/version-range subtraction against /NU. Existing tests cover empty MU, NU-only, A-only and non-empty MU, but not overlap. The prior draft `drafts/first_viable_selector_handoff.rs` covers the first-viable selector and public handoff without depending on the unresolved Table 301 edge. ADR 2392's point that the hand-off identifier is unknown still explains why /NU cannot be matched against that external candidate; the Table 301 set operation is separate, but does not by itself resolve whether an emptied effective array is absent or an unsatisfiable restriction. This audit withdraws its earlier “confirmed defect” conclusion and records the question for owner/spec interpretation.

MH/BE common rules and criteria

The current Table 279 path reads `/C` criteria from MH and BE, uses MH precedence for repeated criterion keys, ignores unknown BE criteria keys and rejects unknown MH keys. Existing tests exercise those distinctions, host-language exact/primary matching, and empty/non-empty `/V`. Criteria are deliberately required regardless of whether they appear in MH or BE under §13.2.3.1. The code's no-host-facts behavior for preferences, bandwidth and monitor size/depth is aligned with the current hand-off profile.

One unresolved malformed-value question is recorded but not promoted as a confirmed defect. Table 279 declares `/L`, `/V` and `/P` arrays, while code treats a non-array as absent. Section 13.2.2 says an unrecognised value in MH makes an object non-viable, but these values are nested within Table 278's special `/C` criteria dictionary. `drafts/mh_media_criteria_value_types.rs` supplies a valid matching `/L` positive control and exact-xref malformed nested-value cases. Parent review should decide whether this nested type mismatch is governed by the MH unknown-value rule or is simply an invalid producer object with no required reader behavior. Do not count it as a conformance failure until that interpretation is settled.

Tables 293–295 assign the MH/BE option semantics and default/fallback rules for screen and floating windows. The product's hand-off does not convey these options: code uses `unhonourable` to report every MH option as unavailable and leaves BE options at best effort. Existing test `screen_parameters_must_honour_make_the_rendition_non_viable_and_best_effort_do_not` covers a single W/M BE case and a W MH case. It does not substantiate every Table 294/295 key, F nesting, conditional F requirement or fallback default. Those are assertion-coverage residuals, not established valid-input defects for this hand-off profile. Table 304 monitor choice remains in playback, which the current ratification excludes.
