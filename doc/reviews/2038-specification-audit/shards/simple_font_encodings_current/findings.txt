The high-level mapping has strong coverage for common routes: encoding tables and their disagreements are checked in `encoding.rs`; `name_keyed.rs` distinguishes a font's built-in encoding, a Differences-only overlay, explicit BaseEncoding precedence, and symbolic status for an embedded program; `truetype.rs` has direct controls for Unicode versus Mac Roman/symbol subtables, post names, and the 3,0 high-byte ranges. The real-PDF `opentype_selection_audit.rs` embeds synthetic CFF and glyf fonts in exact-xref PDFs, checks `was_recovered() == false`, and asserts nonempty selected outlines and exact GIDs. Its TrueType case swaps `/A` and `/B` with Differences and gets `[2,1]`, so it rules out a plausible direct byte/Unicode route. The ADR 2817 Type 1/OpenType CFF case likewise contrasts the wrapper and bare Type1C paths. The 4015a9ae-to-b901326c diff did not alter these mapping behaviors; it reused an error constant and exposed existing cmap fixture helpers.

I found one bounded public-test gap, not a behavior defect: no exact-xref public consumer test distinctly checks §9.6.5.4's final filling of still-undefined glyph-name table slots from StandardEncoding after applying a dictionary's Differences. Existing internal unit coverage confirms source/name-keyed behavior, but not this TrueType public route. Suggested candidate: extend `opentype_selection_audit.rs`'s checked-in synthetic glyf fixture with a Nonsymbolic TrueType case whose Encoding dictionary contains `/Differences [65 /B]` and no BaseEncoding. Assert code 65 (explicit B) and code 66 (StandardEncoding's B fill) both select GID 2, with a nonempty outline. Keep the current explicit WinAnsi `[65 /B 66 /A] -> [2,1]` test as the positive control first. A no-BaseEncoding dictionary is allowed by Table 112; the TrueType no-Differences guidance says “should,” not “shall,” so it cannot alone justify a reader refusal. This test would pin a `shall` in the algorithm without treating malformed alternatives as mandatory reader errors.

MacExpert's full 165 mapping matches a source-extraction script in the earlier `annex_d_encoding` scratch audit, but CI currently checks a small representative subset and count, not every source row. I found no reader bug and no current corpus use; this is a durable source-to-test coverage gap only. The relevant predecessor/successor decisions remain internally consistent: ADR 0286 transcribes the table; ADR 0015/0067 define the TrueType selection boundary; ADR 1942/1943 add only downstream reader-chosen paths; ADR 2520 is archive writing; ADR 2677/2683 address per-font dictionary encodings; ADR 2817 scopes Type1/CFF dispatch and leaves TrueType routing untouched.
