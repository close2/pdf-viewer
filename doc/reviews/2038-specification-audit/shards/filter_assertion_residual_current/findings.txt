This is a bounded assertion-quality review of LZW width transitions, not a certification of §7.4.4 or the full filter system. I checked the effective primary PDF pages and footer locators, the feature ledger, decoder, staged document filter path, and existing exact-output tests. EC3 has no applicable LZW amendment; #98 corrects ASCII85 and is outside this feature.

The strongest existing assertion is `crates/pdf-syntax/tests/lzw_full_table_audit.rs::full_lzw_table_clear_resets_width_and_dictionary_for_both_earlychange_values`. It states its code-index schedule from the primary thresholds, builds an input whose emitted codes stay literals until the table fills, packs using those schedules, and compares the decoder against a separately constructed expected byte sequence (`prefix + DEDE`) with no damage. This is substantially stronger than a smoke test or a round-trip. Its chosen stream goes through all widths and a table reset for explicit `EarlyChange=0` and `=1`.

One narrow gap remains: that full-width exact-output test always supplies the parameter explicitly. Table 8 defaults `EarlyChange` to 1, and `early_change()` clearly implements that default; the omitted-parameter unit test only checks a short/default example, while the stage test verifies explicit parameter propagation. I recommend adding an omitted-parameter decode of the same valid EarlyChange=1 full-table payload, asserting `prefix + DEDE` exactly and clean EOD. This verifies that the document-facing default route survives every transition, rather than merely agreeing with the explicitly configured route at a short stream. A draft addition is in `drafts/lzw_default_full_table_test.rs`.

This does not establish a production defect or require a new decoder implementation. The current function is direct and consistent with the source. The residual is test quality around a long default path, and this audit did not run Cargo. No broader conformance claim is made for LZW malformed data, predictors, stream boundaries, or other filters.
