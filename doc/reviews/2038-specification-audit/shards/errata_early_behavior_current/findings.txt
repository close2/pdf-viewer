Bounded review of five annotation-driven corrections on physical EC3 pages 1–450. Page placement is not an issue-number limit. The PDFs were inspected with annotation overlays; the printed and physical page locators below come from the actual page footers. This is not a full errata or clause certification.

Issue #10 is a reader-facing stream rule at physical p.47 / printed p.32 (§7.3.8.1, Table 5 /F): the caret inserts “shall” into the rule that embedded bytes are ignored when /F is present. `pdf-syntax/tests/spec_stream_objects_audit.rs::an_external_stream_is_refused_while_the_same_embedded_filter_decodes_without_f` is a good discriminating public assertion: identical encoded bytes decode in a no-/F control; with /F and /FFilter, the document reports external data, returns no decoded embedded bytes, and refuses nested content. The fixture uses exact classic-xref offsets. It does not load a host file, and therefore supports refusal of unsupported external data without silently misusing the embedded payload. No mismatch is established.

Issue #500 is separately marked on physical p.83 / printed p.68, Table 18 Type 1 Field 2. The red strikeout removes “Default value: 0” from the uncompressed-object byte-offset field. The matching test is `pdf-syntax/tests/cross_references.rs::a_type_1_entry_with_no_offset_field_locates_nothing`; `xref.rs::entry_location` declines a Type 1 record with no second field. Crucially, the test's /W [1 0 1] fixture is not a valid producer witness: Table 17 expressly says the second W element shall not be zero. Existing assertion checks a conservative invalid-input recovery choice (rebuild recovers the body), not a normative reader rejection/recovery obligation. No valid-input defect is identified.

Issue #146 appears on the same physical p.83 / printed p.68, but concerns Table 19 /XRefStm: a blue strikeout/caret replaces a nonsensical decoded-stream offset description with a byte offset to the cross-reference stream measured from file start. `cross_references.rs::a_hybrid_reference_file_finds_through_xrefstm_what_a_previous_section_marks_free` and `spec_objxref_audit.rs::hybrid_xref_stream_entry_precedes_an_older_free_entry` use exact file offsets and assert that the hybrid stream's entry wins over an older free entry. The fixtures use unfiltered xref streams, so the reviewed behavior is the stream-object file offset and hybrid precedence; no broader encoding claim is made. Existing assertions adequately cover this correction.

Issue #95 on physical p.89 / printed p.74 (§7.6.3.1) strikes a repeated description of AES block behavior and length rounding. The following effective paragraph independently retains the required padding formula, including a full block for an input whose size is a multiple of 16. `encryption_fixtures.rs::aes_cbc` builds that padding, and AESV2/AESV3 encrypted-document witnesses exercise decryption. The fixture helper is not an independent ciphertext oracle for every boundary size, but the erratum does not delete the operative padding requirement; no separate gap attributable to #95 was found.

Issue #87 on physical p.373 / printed p.358 (§9.10.3 Example 1) corrects the name of the Unicode scalar shown for `<3A51> <D840DC3E>` to CJK UNIFIED IDEOGRAPH-2003E. The parser's `surrogate_pairs_decode_to_one_character` unit test checks a different literal supplementary scalar, U+1F600, and thus verifies the general UTF-16BE pair mechanism but not this example through a PDF consumer. Since this is a corrected example, not a new normative mapping rule, the missing exact example fixture is a traceability opportunity, not a conformance defect.

No drafts were warranted: the directly normative paths have source-matched assertions, while the remaining differences are example/wording corrections or invalid-input recovery boundaries.
