This bounded pass covers §§14.9.2.1–.4 and 14.9.6, plus Table 354/355 fields used there. I read the EC3 primary PDF's text/layout (printed-page and physical-page locators below), current ledger rows, production paths, actual test bodies and selected ADRs. I did not recertify §14.9 generally, repeat parent-owned B01/B02 marked Alt/E escape failures, or treat producer-only array requirements as reader rejection rules.

The language hierarchy is implemented across several layers. `structure::document_language` uses the catalog default, applying EC3 #105's absent-or-invalid recovery only there. `structure::language` inherits through `/P`; `marked_ops` reads a property-list `/Lang` and falls back entry-by-entry to an MCID's structure element. `accessibility::speech` resolves nested runs by the innermost explicit tag, and `viewer-core` carries structure language to `AccessibilityNode`; `viewer-accessibility` applies it as the platform node language. This chain is exercised by the public tests for catalog+Span (Example 1), structure+inner Span (Example 2), and parent inheritance, plus unit coverage of inner-language return to outer language. The structures are not just PDFs on disk: ADRs 0134, 0214 and 0623 trace the structure node to AccessKit/AT-SPI. ADR 0063's earlier claim that there was no host consumer is stale after those successors; its remaining hierarchy rationale remains useful.

The source's Example 3 shape is distinct: a structure element's en-US content is nested inside an outer Span's es-MX. The current unit test fabricates already-resolved `Described` spans, while the public integration test has structure enclosing a nested Span (the reverse). Draft `structure_language_overrides_containing_span.rs` uses a ParentTree MCID inside the outer Span and expects es-MX / en-US / es-MX on either side, with no recovery. This is assertion coverage, not a static finding of incorrect behavior. The existing public Example 2 fixture is a minimal reader-path fixture missing required structure-element /P and /K entries, and the ancestry test leaf lacks an explicit MCR /K; those tests do not independently establish conforming structure production.

A second distinct candidate is structure-element `/Alt` and `/E`: `viewer-core::walk` decodes the phrase with `text_entry`, while its node language comes only from structure ancestry; it does not carry the phrase escape offsets to `AccessibilityNode.language`. The source allows Unicode language escapes to override prevailing Lang, and §14.9.2.1 explicitly includes element Alt/E in element-language scope. Parent-owned B01/B02 cover property-list Alt/E, not this structure consumer. Draft `structure_alt_language_escape.rs` supplies a valid `/Sect /Lang(en-US)` ancestor, an ordinary Alt inheritance sibling, and an Alt string whose UTF-16BE escape sets `es`; it checks the public Viewer AccessibilityTree and ordinary extraction independently. This remains a static candidate pending parent execution; one whole-phrase tag fits the current API, while multiple language spans may need a richer public shape.

Empty Lang is a present value meaning unknown, while an absent Lang entry is what inherits. Current code collapses both to `None`: `structure::text_entry` drops empty strings, as do the marked-content Lang readers, and `speech`/AccessibilityNode use `Option<String>` for the resolved language. The existing public test `an_empty_language_identifier_states_nothing` consequently expects an empty Span to inherit `fr`, contrary to the source distinction. Draft `empty_lang_shadows_outer.rs` asserts `None` for explicit-empty Span and structure scopes, confirms explicit `fr-FR`, and confirms outer `es-MX` resumes after the nested scopes. This is a concrete likely reader/output gap; preserve the existing public unknown representation as `None` and retain a separate override state while resolving nesting rather than inventing a sentinel language tag. #105 remains catalog-only; invalid nonempty child/property tags are not included in this finding. The RFC 5646 grammar test is broad and the public invalid-catalog test distinguishes prose from a tag. Do not infer that a writer's invalid child Lang must be rejected by a reader. `/Lang` on optional-content Language usage is explicitly outside the hierarchy; its evaluator is separately implemented in optional content.

The array feature in §14.9.2.4 is consumed for media clip alternates (`/Alt` in Tables 285/288). `media::alternate` searches exact case-insensitive, then first hyphen-delimited prefix in array order, then empty-tag default. Its unit test uses the source EXAMPLE and pins exact case, prefix direction, exact French and default; a viewer rendition test carries the selected text to handoff. Duplicate language tags, string-pair shape and an empty default are producer constraints. The reader's tolerant handling of incomplete/non-string pairs is not a standards-mandated rejection policy. The default itself is a `may` when no match, so choosing to use it is current product policy.

The pronounced-hint entries differ from mandatory hierarchy metadata. Table 355 marks PhoneticAlphabet and Phoneme as optional PDF 2.0 structure-element properties, gives the default alphabet `ipa`, makes alphabet inherit to children unless overridden, and describes Phoneme as an exact replacement. Table 354 carries optional PLS lexicon specifications. §14.9.6 then explicitly says a processor is not required to process any pronunciation hints. No parsing/consumer code exists; the test in `structure/tests.rs` confirms nearby role/Lang/Alt are returned without the Phoneme string being treated as an answer. That is a valid no-processing choice, not evidence of PLS or TTS implementation. I found no EC3 correction to these fields; EC3 namespace errata on Tables 354/355 do not amend their pronunciation meanings.

The existing test fixtures in `pdf-model/tests/accessibility.rs` use exact generated xref offsets, but its shared helper does not assert `Document::was_recovered()`. Some structure-path fixtures are intentionally minimal and omit mandatory element fields, so they are pathway checks rather than valid-producer conformance tests. The new hierarchy draft does. Pronunciation's local `Document` builder also lacks a no-recovery assertion and PDF 2.0 required trailer identity; since that case demonstrates a permission rather than a required operation, I did not request a replacement fixture as a conformance test.
