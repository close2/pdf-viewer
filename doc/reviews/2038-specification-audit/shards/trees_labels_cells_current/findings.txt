# Name/number-tree and page-label cell review (baseline b901326c)

The bounded source map is in `features.json`. I used the current ledger entries for §§7.9.6, 7.9.7 and 12.4.2, then checked the actual public consumer tests and current parent test evidence. The prior tree-shard concern about missing valid multi-level public fixtures is resolved: named destinations now traverse an exact-xref root/intermediate/leaf name tree with indirect Kids, exact Limits and byte-distinct keys, while PageLabels enumerates an exact-xref multi-level number tree and asserts literal labels. The latter deliberately is not counted as proof of generic numeric comparison because PageLabels sorts collected ranges itself.

Table 36 and Table 37 cells are mapped separately. For both, producer node-shape and key constraints do not imply a mandatory reader refusal. In particular, #307's null-key prohibition has a pair-preservation assertion for tolerance, not a required error outcome. Name-tree key identity remains byte-based after #214 removes the word “lexical”; the source's common-prefix and byte-by-byte rules remain. The current valid public destination fixture distinguishes `A` from `a` and searches both bounded branches.

Table 161's range and style mechanics have strong examples: the clause's own nine-label sequence, a prefix plus default `/St` at a range boundary, the corpus's first-page labels, and an indirect multilevel number-tree consumer. One useful assertion is still absent at the public consumer: the explicit Table 161 rule that missing `/S` means the label consists only of `/P`, including the empty result when both are absent/empty. I drafted a valid exact-xref fixture for that behavior; this is an assertion gap, not a reported implementation bug.

The alphabetic style remains a documented effective-source conflict. The accepted #432 markup changes `ZZ` to `AZ`; accepted #593 adds subsequent repeated-letter ranges (`AAA` through `ZZZ` for the next 26). The implementation returns repeated letters (`BB` at 28), supported by #593 and the base text's “next 26” count, while the current ledger/ADR records the incompatible #432 reading. I do not present that as simultaneously conforming to both amendments.

No other missing test was justified in this bounded review. It does not certify every tree consumer, all writer-generated tree forms, or every UI surface that displays page labels.
