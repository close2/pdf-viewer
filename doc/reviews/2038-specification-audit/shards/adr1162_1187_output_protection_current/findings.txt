# ADR 1162 / 1187 output-protection review

**The five-verb design is implemented, but direct transform-level proof is concentrated in redaction and linearized optimization. Archive removal is covered at the decision/output level, while the promised exact claim propagation is not directly asserted in the reviewed encrypted fixture. A public-API silent-ignore edge exists when `apply_protected` receives a Protect with an Archive plan.**

ADR 1162's `Protect` sits outside the input `Source`, `Plan`, and reader `Policy`; the implementation's separation matches those different roles. `apply_protected` passes the option to Split, Merge, Pages, Optimize, and Redact. Split/Merge/Pages/Optimize route it to `Protect::write`; Redact checks it before proceeding and uses the same writer. The CLI obtains credentials through `--encrypt-owner-fd` and `--encrypt-user-fd`, supplies `Access::ALL`, and refuses these flags on non-supported verbs. The exact ISO source cited by ADR 1162 is PDF §7.6.4; Table 22 concerns flags the output may assert, while §7.6.4.1 covers passwords. These do not prescribe this API shape.

Current test quality is mixed by path. `tests/redact.rs` builds a literal page with KEEP and SECRET, encrypts it, checks no Protect refuses, and checks Protect produces an encrypted output whose raw bytes and decrypted extracted text no longer contain SECRET while KEEP survives under the new owner password. This is a strong independent product-policy test. The test rationale should remain identified as the project's privacy policy: §12.5.6.23 asks that redaction remove all traces, but does not itself require keeping the remaining document encrypted.

`tests/linearize.rs` covers the specialized Optimize+linearize path using distinct output reader/owner passwords on a clear source, checks the empty password cannot open the output, opens with the new user password, checks pages draw identically, and inspects Annex F encryption placement. It does not cover replacing an encrypted source password or checking Table 22 flags. I found no direct Protect-supplied assertion for Split, Merge, Pages, or ordinary non-linearized Optimize. Their implementation routes to the common encrypted serializer, and corpus tests validate ordinary output rendering/structure, but they do not prove the Protect dispatch or encrypted credential/access result. This is an assertion gap, not an observed implementation failure.

ADR 1187's archive flow has a correct source-side decision boundary in code: `SourceProtection::of` is captured before rewrite, `Loss::Encryption` is authorized as an Ask, and archive output has no Encrypt entry. `archive/recovered.rs::an_encrypted_source_is_rebuilt_behind_the_encryption_loss_and_the_claim_is_the_source_s` checks the input is encrypted, authorized output conforms and is unencrypted, the report identifies `EncryptionRemoved`, and `protection` is present; with no authorization it emits no output. `SourceProtection` unit tests check the wording and which bits are listed. But the encrypted integration test does not assert the exact report fields or the output's parsed XMP history claim. The history injection and report JSON conversion are implemented; generic history tests are not a direct oracle for this encryption-specific value. A focused test with a source whose Table 22 withholds known operations should assert exact handler/revision/withheld values in the report and the same statement in the emitted XMP, plus an unencrypted-source null/no-entry control.

A policy boundary merits a decision. The CLI's `protection()` explicitly rejects `--encrypt-owner-fd`/`--encrypt-user-fd` for `Plan::Archive`. In contrast, `apply_protected` forwards `Some(Protect)` to `run_plan`, and the Archive arm calls `archive::run` without it. The API therefore silently ignores supplied protection and emits the required unencrypted archive. The PDF/A no-encryption requirement forbids encrypted output, but does not mandate what an API should do with an inapplicable request. Because `apply_protected` is documented as protection over whole files and the CLI makes the refusal explicit, either a public-API refusal or a clear documented ignore contract should be pinned. I recommend explicit refusal to avoid silent ignore; no PDF standards violation is inferred.

The ISO 19005 source documents were not found in this worktree. The archive clause statements above are attributed to repository-owned `doc/pdf-a-conversion-limits.md` and `doc/pdf-a-mitigations.md`, not presented as a fresh read of ISO's text. The cited PDF §7.6 and §12.5.6.23 source materials are within the repository's effective PDF text/ADR references; this shard did not redo crypto or encryption algorithm conformance.
