§7.9.3 says the *unencoded* bytes of a PDF stream shall satisfy text-string encoding, byte-order, and lead-byte requirements. Current callers follow that sequence: decode stream filters, then call the text-string decoder. The strong prior public witness `text_strings_spec_audit.rs::a_filtered_utf8_text_stream_uses_the_text_string_encoding_after_decoding` proves this for a variable-text field `/V`: its Flate stream decodes to UTF-8 BOM + `café`, the decoded bytes and `text_string` value are checked, the rendered result has visible ink, and it equals the equivalent text-string form rather than an empty control. Popup `/RC` has a direct stream unit test. Table 221 `/JS` also accepts a decoded text stream in `view::scripts::read_script`, and `script_unread.rs` exercises that route for stream length and chain continuation, but only with ASCII; `viewer-core/tests/open_sequence.rs` exercises the Table 32 `/JavaScript` name tree with a text-string script and no runner. Thus the main common decoder and these consumers are evidenced, but no current test composes the Table 32 name-tree handoff with filtered Unicode stream text. I drafted this narrow combination as a scratch candidate. It asserts the exact text handed to a runner and compares it with an equivalent marked UTF-8 string; it is not run.

§7.9.5 requires four numeric array coordinates giving diagonally opposite corners. `[llx lly urx ury]` is explicitly *typically*, so accepting the reverse diagonal is the source-backed interpretation; a note allows width or height zero. `annotation::rectangle`, page geometry, and structure rectangle readers normalize the two axes. Existing `annotations.rs::a_reversed_rectangle_is_normalised` checks actual placement; `page_geometry.rs::a_media_box_enclosing_no_area_is_a_rectangle_and_still_not_a_medium` keeps the type-level zero-area rectangle distinct from the MediaBox's separate medium requirement. The already-promoted `trees_rectangles_audit.rs` checks attachment-writer four-number arity, numeric values, and reversed diagonal preservation. These controls discriminate the sampled requirements; no new rectangle test is warranted. Parsing extra elements or refusing malformed short/non-finite input is permissive/error policy here, not a demonstrated defect, and I make no claim of requiring malformed-reader rejection.

Table 32's ten roots are distributed to their consuming clauses: Dests (12.3.2.4), AP (12.5.5), JavaScript (12.6.4.17), Pages/Templates (12.7.7), IDS/URLS (14.10.4, now deprecated in PDF 2.0), EmbeddedFiles (7.11.4 and associated-file consumers), AlternatePresentations/Renditions (Clause 13). Dests, attachments, named pages, and document scripts each have current public/model paths. The prior media viability shard owns the two Clause 13 roots; file-spec and encryption shards own EmbeddedFiles privacy/filename requirements. I do not recertify those owners here.

AP needs an explicit scope distinction. Table 32 identifies a name tree from names to appearance streams, but §12.5.5 says the names have no standard meaning and no PDF object may refer to an appearance stream by name. `named_appearances.rs` reads the tree generically and confirms a widget reaches its stream by object reference. That is the supported construction. It would be incorrect to infer an obligation to resolve a named AP as an annotation appearance.

Selected ADR reconsideration: ADR 0053/0054's reusable name-tree component remains supported, with ownership at each consuming clause; the generic tree test alone does not prove every key consumer. ADR 0076/0094's EmbeddedFiles/embedded-document boundary and ADR 0091's named-page boundary remain separate. ADR 0030's object-reference appearance construction agrees with §12.5.5. ADR 1950's script refusal/reporting path accepts either text-string or text-stream content, but the current public Table 32 stream encoding assertion is missing; the draft addresses it without changing policy or production code.
