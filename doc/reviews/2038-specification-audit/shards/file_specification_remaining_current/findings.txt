Bounded review: file-specification strings and embedded-file framing

Source and review boundary

I checked the effective primary text for §7.11.2.1–.2 and §7.11.4.1, Tables 44–45, rather than relying only on the ledger or old FileSpec shard. The primary footer places §7.11.2.1 at printed132 / physical147, §7.11.2.2 across printed133–134 / physical148–149, §7.11.4.1 at printed137 / physical152, Table44 at printed138 / physical153, and Table45 at printed138–139 / physical153–154. Primary annotations #155 (Table44 Subtype) narrow producer MIME syntax; #481 replaces the name-tree/EF inclusion bullets; #156 adds associated-file and RichMedia routes; #382 changes Table45 CheckSum type to byte string; and #598 adds NOTE 2 about host-supported filesystem dates. These carrier/date edits are represented in features.json; AF/MCAF semantics remain sibling scope.

§7.11.2.1 says `/` separates components, any component may be empty, literal slash inside a component is escaped by reverse-solidus syntax, and the escape is removed in processing. It explicitly says component substrings are bytes passed to the OS without interpretation or conversion. §7.11.2.2 distinguishes absolute (leading `/`) from relative, specifies replacement against the containing file's directory, gives the `..` cancellation example, and constrains URL-relative specs to RFC3986 path form.

Existing assertions

`crates/pdf-model/src/file_spec.rs::components` implements the example's `\/` escape, keeps empty components, stores bytes, and caps the vector at `MAX_COMPONENTS = 256`. Unit tests cover the source example, leading/doubled empty components, both published relative-resolution examples, an absolute control, URL-vs-path split, and the five forbidden relative-URL parts. `crates/pdf-model/tests/file_specifications_audit.rs` uses a valid exact-xref PDF, asserts no recovery, and covers simple string form and decoded byte path. These are real value assertions rather than test-presence claims.

New bounded concern: silent component merge at the limit

The source defines no component-count limit. Once `components` reaches 256 entries, a later `/` no longer matches the guarded separator arm; it falls through as an ordinary byte and is appended to the previous component. Thus a valid longer path is silently reinterpreted rather than reported as truncated/refused. The scratch draft `drafts/file_spec_component_limit.rs` uses a strict-xref minimal PDF, compares 256 components as a positive control with 257 components split independently from the literal producer string, and checks `was_recovered == false`.

This is a bounded FileSpec model and archive-report defect candidate, not a demonstrated host file-open failure. `pdf-transform/src/archive/external.rs::names` places `FileSpec::components()` and `is_absolute()` into public `ExternalData::Named`. The archive tool may ask its caller for data, but this method itself does not perform that action. ADR 1199 explicitly documents the external-data report and caller-owned fetch; ADR 1155 separately limits the host to a single permitted component. The model's cap can therefore affect the report/validation of longer names, while the host restriction still limits what can actually be opened. The new draft `drafts/archive_external_components.rs` tests the public report with a reachable Form XObject external-data `/F`, using PDF/A-4 identification, strict xref, a 256-component positive control, and a 257-component target. It asserts only the in-memory `ExternalData::Named` path/components/status; it never accesses a filesystem/network. This remains unexecuted in this shard.

Embedded-file framing and parameters

§7.11.4.1 says embedded streams are included for convenience and need not be processed directly by every PDF processor. Effective #481 makes the `/EmbeddedFiles` name tree optional unless another provision requires it; #156 adds associated-file and RichMedia routes. Table44 makes Type optional (if present, EmbeddedFile), Subtype optional except for associated files, and Params optional except for associated files. EC3 #155 narrows valid Subtype producer syntax; it does not require a reader to discard or reject an older subtype. Table45 makes Size and checksum optional, dates optional except ModDate for associated files, and checksum a 16-byte MD5 over the uncompressed bytes; #382 specifies a byte string. #598's NOTE 2 says CreationDate/ModDate are intended filesystem dates where the host supports them. These producer/host qualifications do not create general reader rejection duties.

Existing tests meaningfully cover portions of this surface: `embedded_files_spec_audit.rs` checks writer Type, subtype, exact payload length, Params Size and an independently derived MD5 of literal bytes; `attachment.rs::a_stated_checksum_is_answered_against_the_bytes` asserts matching, mismatching, absent and wrong-length checksums; `attachments_filed.rs` checks discovery, extraction payload, Size and checksum through save/reopen; `Attachment::read` retains stream metadata and carries the original stream for later decode. This shard did not certify every Table44/45 key or every carrier route.

The checksum tests over a raw stream do not establish whether the checksum is over the uncompressed bytes when the stream has a filter. I drafted `drafts/embedded_flate_checksum.rs`: a valid exact-xref EmbeddedFiles entry with `/Filter /FlateDecode`, exact encoded `/Length=27`, uncompressed `/Size=19`, and a literal zlib stream for `payload-after-flate`. The expected MD5 (`29f52318023f658f29a80b071b8c2d62`) and the different compressed-data digest are independent precomputed values. The assertion decodes through the public Document API, checks literal output, and confirms only the decoded output matches Table45. This is a coverage proposal; I did not execute it and do not claim a current failure.

ADRs and residuals

ADR 0076's list-without-eager-decode rationale remains correct under §7.11.4.1's explicit allowance that embedded data need not be processed. ADR 0145 places checksum evaluation on extraction once decoded bytes exist, which is consistent with Table45's uncompressed scope; the proposed test checks that seam. ADRs 1155/1199 keep host resolution separate and bound it; they do not erase the model's reporting contract. ADR 0223's confined attachment metadata vs extraction event separation remains unchanged.

No reader rejection duty follows from the producer rules that Type/Subtype/Params are required in some contexts, Type must have one value if present, or a checksum must match. The reader may retain and report a wrong value; the checksum is explicitly informational and not security. Conversely, a parser resource cap should not silently merge valid separator bytes when its API claims exact components; a refusal/shortfall result or a representation that retains the tail is the reviewable alternative.

Remaining scope: no host writes or fetches, no re-review of associated-file/MCAF carrier matrices, no full Table43 precedence review, and no broad certification of stream parser/filter semantics. The three drafts are source-valid candidate coverage and remain unexecuted by this auditor; parent may promote and run them.
