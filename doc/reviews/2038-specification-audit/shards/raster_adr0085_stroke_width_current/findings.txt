# Raster ADR 0085 stroke-width transform boundary — correction after caller dispatch review

I used the explicit audit checkout `/home/cl/projects/pdf-viewer/.claude/worktrees/r2038-audit` (`git rev-parse --show-toplevel` verified). This is raster ADR 0085, separate from root ADR 0085 about flattened PrintField. No Cargo command, tracked edit, or shared build was made by me.

The earlier draft conclusion that the ordinary anisotropic path uses device-space centerline expansion was incomplete: I followed `encode/stroke.rs::resolve_width` and `encode/expansion.rs::Expansion::of` without checking the public caller's dispatch. In `crates/render-raster/src/stroke.rs`, the main path computes the linear transform's anisotropy. When it exceeds `MAX_ISOTROPY_ERROR = 1.01`, the public CPU renderer calls `expanded(...)`; that function runs `kurbo::stroke` on the path-space geometry at `path_width`, then uploads/fills the outline under the transform. Its own comment cites §8.4.3.2's orientation-dependent device thickness. Scalar device-space expansion is the near-similarity route; it is not the path taken by the `diag(4,1)` candidate.

Consequently the prior source conclusion and decision are withdrawn: there is no demonstrated current runtime failure or ADR contradiction for positive-width anisotropic geometry. The public dispatch includes precisely the path-space outline route ADR 0945/todo describe. The source supports that distinction: ISO 32000-2 §8.4.3.2 (printed pp.160–161 / physical pp.175–176) defines positive-width stroke distance in user space and notes device thickness varies with orientation under anisotropic transforms; §10.7.5 treats automatic stroke adjustment separately. No directly relevant EC3 strikeout/amendment was found in the inspected pages.

The earlier draft test `drafts/anisotropic_transverse_width.rs` remains a useful independent regression: its stated diag(4,1) predictions are horizontal width 2 and vertical width 8, with the §8.4.3.2 two-device-pixel allowance and visible positive controls. Parent corrected its sample positions (horizontal x20; vertical device row60 after raster y flip), made the visibility predicate robust to transparent/white backgrounds, and ran it: 1 test PASS. Treat that PASS as positive evidence that the public anisotropic expansion branch works for this fixture, not as proof of all transforms.

I agree with the architecture boundary: resolve path width/automatic adjustment at the transform-aware caller, path-space outline when anisotropy is material, scalar device-space expansion for near-similarity transforms. Residual: one diag(4,1) horizontal/vertical fixture does not certify shear, rotated anisotropy, arbitrary paths, caps/joins/dashes, cache reuse, threshold continuity at 1.01, or all renderer/backends. No behavior defect established.
