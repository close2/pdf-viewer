# Raster ADR 0085 stroke-width transform boundary — correction after caller dispatch review

I used the explicit audit checkout `/home/cl/projects/pdf-viewer/.claude/worktrees/r2038-audit` (`git rev-parse --show-toplevel` verified). This is raster ADR 0085, separate from root ADR 0085 about flattened PrintField. No Cargo command, tracked edit, or shared build was made by me.

The earlier draft conclusion that the ordinary anisotropic path uses device-space centerline expansion was incomplete: I followed `encode/stroke.rs::resolve_width` and `encode/expansion.rs::Expansion::of` without checking the public caller's dispatch. In `crates/render-raster/src/stroke.rs`, the main path computes the linear transform's anisotropy. When it exceeds `MAX_ISOTROPY_ERROR = 1.01`, the public CPU renderer calls `expanded(...)`; that function runs `kurbo::stroke` on the path-space geometry at `path_width`, then uploads/fills the outline under the transform. Its own comment cites §8.4.3.2's orientation-dependent device thickness. Scalar device-space expansion is the near-similarity route; it is not the path taken by the `diag(4,1)` candidate.

Consequently the prior source conclusion and decision are withdrawn: there is no demonstrated current runtime failure or ADR contradiction for positive-width anisotropic geometry. The public dispatch includes precisely the path-space outline route ADR 0945/todo describe. The source supports that distinction: ISO 32000-2 §8.4.3.2 (printed pp.160–161 / physical pp.175–176) defines positive-width stroke distance in user space and notes device thickness varies with orientation under anisotropic transforms; §10.7.5 treats automatic stroke adjustment separately. No directly relevant EC3 strikeout/amendment was found in the inspected pages.

The earlier draft test `drafts/anisotropic_transverse_width.rs` remains a useful independent regression: its stated diag(4,1) predictions are horizontal width 2 and vertical width 8, with the §8.4.3.2 two-device-pixel allowance and visible positive controls. Parent corrected its sample positions (horizontal x20; vertical device row60 after raster y flip), made the visibility predicate robust to transparent/white backgrounds, and ran it: 1 test PASS. Treat that PASS as positive evidence that the public anisotropic expansion branch works for this fixture, not as proof of all transforms.

I agree with the architecture boundary: resolve path width/automatic adjustment at the transform-aware caller, path-space outline when anisotropy is material, scalar device-space expansion for near-similarity transforms. Residual: one diag(4,1) horizontal/vertical fixture does not certify shear, rotated anisotropy, arbitrary paths, caps/joins/dashes, cache reuse, threshold continuity at 1.01, or all renderer/backends.

## Newly identified near-similarity width residual

The threshold itself needs a large-width control. `crates/render-raster/src/stroke.rs::anisotropy` returns the singular-value ratio and takes the path-space outline branch only when the ratio is greater than `1.01`. At `scale(1.009, 1)`, the ratio is 1.009, so the public call remains on the scene-stroke route. The lower raster's `raster::resolve_width` is explicit: `stroke.width * t.max_stretch()`. A horizontal width-1000 band therefore becomes width 1009, despite the user-space band and its transverse device width remaining 1000. For a vertical segment, the 1009 width is correct. `/SA` is false in the proposed command (`adjust=false`), the dash array is empty, and a joined L path avoids both automatic grid fitting and the single-segment `thin_line` shortcut.

This exposes a gap in ADR 0402's comment that 1% is “under the antialiasing floor”: a percentage is not a fixed pixel bound for unbounded stroke width. The effective source §8.4.3.2 permits at most two device pixels of width deviation from grid placement. At width 1000, the scalar route predicts a 9-pixel excess. Parent integrated the independent public regression into `crates/render-raster/tests/anisotropic_stroke_width_spec_audit.rs::near_similarity_large_stroke_preserves_transverse_width_within_two_pixels` and reports a Radeon 890M Vulkan failure: identity=1000, horizontal=1008, vertical=1009. The target assertion is outside ±2; identity and vertical positive controls pass first. Parent is adding a parsed-PDF route and a CPU expected-width control. The result is confirmed for this backend/fixture, not all matrices or backends.

The earlier anisotropic test and this threshold test answer different questions: `diag(4,1)` proves the material-anisotropy route; `diag(1.009,1)` stays inside the scalar branch and makes its fixed percentage approximation visible by using a large stroke width. Exact transition behavior, alternate matrices, and the best width-sensitive dispatch criterion remain open.
