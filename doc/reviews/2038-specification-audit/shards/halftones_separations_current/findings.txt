# Halftones and separation rendering — bounded source/assertion review

At baseline `b901326c`, I reviewed §10.6.1–.4's screen applicability, the §10.6 aggregate and §10.6.5 transfer-function carrier paths, plus §10.8.1–.3 and the currently implemented separation simulation. This is not a certification of screen generation, all colour spaces, or all overprint/transparency interactions. No Cargo was run and no production, ledger, or Git files were changed.

The §10.6 `inapplicable` scope is supported by the effective source and active output routes. §10.1 applies PDF halftoning only when the raster output device supports it; §10.6.1 says a device that directly reproduces continuous-tone values need not halftone, and §10.6.2 contrasts on/off colour printers with colour displays. The application emits continuous-tone 8-bit RGB for its screen and gives RGB rasters to the print toolkit/spool; it does not directly drive a halftone-requiring printer or produce a one-bit/few-level output raster. RFC 0009 §2.4 rechecks that exact print-path question and names the route that would change the answer. Thus the status belongs to this implementation boundary, not to every physical printer. ADR 1535's row has a concrete condition and a revisit trigger. The optional choice in §10.6.5.1 concerns the screen; it does not waive §10.5's transfer function.

For §10.6.5, I used the already completed `rendering_intent_transfer_current` source and assertion review rather than repeating its details. That shard found that `/HT` TransferFunction mapping is read and applied, with useful cases for Type 1/Type 5 and `/Identity`/`/Default`, but its legacy override assertions manually apply the display-list map rather than invoking the raster consumer. It drafted exact-xref public raster controls for Type 5 and Type 6 stream overrides, distinct RGB `/TR` entries, and `/TR2` precedence. Those drafts remain the source of further verification; this shard made no duplicate test. EC3 #310 at physical 391 / printed 376 and #12 at physical 395 / printed 380 refine producer-side entries. #311 at physical 396 / printed 381 strikes the whole Type 5 contrast/fallback paragraph; current notes correctly do not use that deleted text to claim nonprimary-colourant screen behavior.

For §10.8, the source keeps three questions separate: whether separations are produced (§10.8.1 leaves that to processing software), how prepress Separation/DeviceN colours appear on other devices (§10.8.2 describes alternate spaces and possible ignored overprint), and whether the reader wants a closer separation simulation (§10.8.3 says it can be performed if that matters). ADR 1228's default-off reader preference fits that condition. It must not be conflated with Table 275's separate statement that a processor supports the simulation.

The focused test oracles I inspected are useful and mostly independent of shared implementation tables. `two_separations_multiply_in_flat_xyz` derives each neutral sRGB 0.5 tint as linear 0.214041, multiplies to 0.045814, and converts back to roughly 60/255. A zero-tint separation is checked as the identity of the white-matte multiply. `spot_planes` and `spot_press` hold process/spot plane shape, `/None`/`All`, group cases, and cyan-over-yellow press output against explicit pixels; separate controls observe ordinary alternate rendering. These support the selected simulation path but do not prove every profile, colour space, transparency combination, or backend. The GPU's refusal of separated display lists is explicitly named rather than hidden.

One source/implementation residual remains in step a). §10.8.3 says a default `DestOutputProfile` or `ColorantTable` values, if available for a subtractive device, should be consulted for process colours. `content::simulated_press` chooses a four-channel output-intent profile or an assumed press. No ICC ColorantTable/named-colour consumer appeared in the implementation search. Because the source says `should`, this is a recommendation/coverage qualification, not a confirmed mandatory SHALL defect; this audit did not construct a conforming ColorantTable-only profile.

There is a concrete ledger consistency issue: §10.8.3 is marked `implemented`, its later paragraphs say the stages are now built and the Table 275 capability is met, yet the same `note` retains the earlier “What keeps this row partial” section and says the plane model and ColorantTable remain absent. The ColorantTable observation remains a useful limited recommendation caveat, but the old `partial` explanation contradicts the current implementation and status and should be reconciled. No source errata annotations affect §10.8.1–.3; the nearby halftone annotations are #310, #12 and #311 described above.

The detailed clauses and ADR scope appear in `features.json` and `decisions.json`. No further test draft was justified for the reviewed §10.8 paths because the existing tests include numeric and consumer-level controls; the public HT override gap belongs to the prior rendering-intent/transfer shard.
