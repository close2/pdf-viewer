Table 5 stream dictionary cell audit

I read Table 5 in the effective primary EC3 PDF, at physical pp. 47–48 / printed pp. 32–33, and checked the actual annotation overlays on physical pp. 47–50. The Table 5 /F row has #10's StrikeOut/Caret; the replacement inserts “shall” into the rule that processors ignore bytes between stream/endstream when /F is present. #319 on physical p. 47 adds a NOTE that encoded data includes enveloping markers such as EOD markers; it clarifies §7.3.8.2 extent, not another row definition. #216 on physical pp. 49–50 changes §7.4.1 filter-language obligations and supports the existing Table 6 support tests. #246 on physical p. 81 widens directness only for cross-reference streams. No other Table 5 cell correction was found in the inspected effective annotations.

Cell mapping:

- `/Length` is required and counts bytes in the stream data, which are encoded bytes where a filter applies. The optional EOL before endstream is excluded. Direct/indirect equivalence applies to ordinary streams under §7.3.10; the xref-stream directness rule is a local exception. Parser behavior and length/resource tests are owned by the earlier stream-extent shards (`stream_length_bound.rs`, `spec_stream_extent_delimiter.rs`). I read the assertion bodies rather than inferring from references; they distinguish stated direct/indirect extent and the endstream boundary. Invalid or inconsistent lengths have explicit recovery behavior, not an automatic mandatory rejection claim.
- `/Filter` is optional, as a single name or an array of zero or more names. The array's order is application order. The table's “not recommended” note against repeating one filter is advisory, not a valid-reader rejection requirement. `Document::filter_chain` resolves direct/indirect ordinary values and preserves the order; an empty chain leaves stored bytes as the decoded bytes. `filters.rs::a_filter_array_is_a_pipeline_decoded_in_the_order_written` uses a noncommuting ASCII85/Flate chain and literal output; `every_filter_table_6_names_is_supported_under_both_of_its_spellings` covers the Table 6 names/abbreviations. Inline image extent is separately checked by `inline_filter_chain_spec_audit.rs`; I did not duplicate it.
- `/DecodeParms` is optional and may be a dictionary or array. Table 5's conditions describe valid producer representation: a nondefault parameter for a single filter needs its dictionary; for multiple filters with any nondefault parameters, use one aligned slot per filter, with null for a filter with no nondefault parameters. When none are needed or all are defaults, it may be omitted. Existing direct tests assert per-stage null/dictionary association and literal predictor bytes. The promoted outer-indirect tests cover Filter/DecodeParms containers and array members. Inner numeric references remain a confirmed behavior failure B54: indirect Predictor 15 is treated as the default and indirect Columns 3 refuses, while each literal direct control passes. That defect is separately recorded and is not duplicated here. Malformed parameter shapes are not turned into rejection criteria.
- `/F` is optional from PDF 1.2. When present, its external file is the data source and processors shall ignore embedded bytes. Length should still state the embedded bytes' extent, commonly zero. `FFilter` and `FDecodeParms` describe the external data, not the ignored embedded sequence. Public `spec_stream_objects_audit::an_external_stream_is_refused_while_the_same_embedded_filter_decodes_without_f` compares identical encoded embedded bytes with and without F: the no-F case returns literal page content; the F+FFilter case reports `External`, yields no decoded bytes, and the nested-content route also refuses. It uses exact xrefs and no host-file access. The implementation deliberately does not fetch external files. Since there is no file provider in this reader route, not executing FFilter/FDecodeParms is not a missing codec claim.
- `/DL` is an optional non-negative decoded-byte count, explicitly “only a hint.” The decoder ignores it. `filters.rs::dl_is_a_decoded_length_hint_and_does_not_replace_encoded_length` now checks a valid Flate stream with literal decoded bytes, a correct DL, and an encoded Length of a different size, alongside the no-DL case. The fixture includes a PDF binary comment and page Resources, exact xref, and no cut-chain guards. Parent reports all 14 filters tests PASS in decoded-length-wave103.log. This closes the sampled assertion gap; decoder ignoring DL was not a behavior failure.

The current implementation path is `Document::decoded_stream_data_reported` → `chain_with_parms` → `filter_chain` / `decode_parms` → `chain_over`, with external-source refusal in `Document::decoded_chain` before a filter chain executes. Inner indirect numeric DecodeParms references remain a distinct confirmed B54 failure: the direct controls pass but `indirect_predictor_number_keeps_the_same_decoded_samples` and `indirect_columns_number_keeps_the_same_decoded_samples` fail on ordinary streams. Outer indirect Filter/DecodeParms structures are separately covered by passing tests/T74; I do not recertify B54 here. The public stream-source and nested-content paths use the same refusal. The exact Table5 statements are also cited in the current ledger's §7.3.8, §7.3.8.1, §7.3.8.2 and §7.4.1 rows; the aggregate entry specifically records DL as unused because it is only a hint.

ADR review: ADR 0102's filter pipeline and per-stage parameter allocation are exercised by the direct filter tests; ADR 0587's route-specific damaged-prefix semantics remain distinct from valid Table 5 shapes. ADRs 0365/0427 distinguish windowed versus whole-stream consumers without changing the Table 5 fields. ADR 0014's sandbox boundary and ADR 1199's caller-owned external-data reporting explain why no filesystem fetch is expected here. ADR 0266's empty-stream behavior and ADR 0343's reported damaged prefix are prior stream-specific decisions, not reopened. No current decision premise was found obsolete by this bounded review.

Residuals: I did not run Cargo. Parent reports the integrated DL assertion passes in decoded-length-wave103.log. This audit does not certify every codec's DecodeParms semantics, every malformed dictionary recovery, image/XRef special streams, encryption, or all producer versions. No claim is made that optional producer fields must be rejected when malformed, and no host file/network operations were made.
