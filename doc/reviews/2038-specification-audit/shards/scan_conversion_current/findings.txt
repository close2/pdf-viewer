# Scan conversion details audit

The source locators and feature map are in `features.json`. This is a bounded source/assertion review at `b901326c`, not a full backend certification. I did not run Cargo or modify production files. I did not draft a new test: the identified concerns are about policy scope and ledger descriptions, while current positive fixtures already exercise the reader-to-raster path; a new fixture would not settle those questions without a source-defined oracle.

The source has five distinct subclauses: §10.7.1 General; §10.7.2 Flatness tolerance; §10.7.3 Smoothness tolerance; §10.7.4 Scan conversion rules; and §10.7.5 Automatic stroke adjustment. EC3 #371 changes §10.7.2's flatness range to 0 through 100 inclusive, in output-device pixels, with 0 selecting the device default. Since the clause separately lets a processor ignore file-specified flatness, this edit creates no duty to use `/FL` or `i`; the current tests correctly defend the permission and non-leakage into other graphics-state parameters.

§10.7.1 requires scan conversion, and its NOTE says algorithm details are not defined and device techniques differ. It is not an express override of the result requirements that §10.7.4 states with `shall`. The parent family ledger note calls §10.7.1 what “licenses the departures”, while the §10.7.4 ledger note and ADR 1560 say the NOTE licenses none of the explicit departures. Reconcile the contradictory wording. The specific departures—area coverage/antialiasing, reduced-image area averaging, and selected retraced subpaths—remain accurately marked `departed` in the clause row. This review does not reopen their policy or measurements.

Flatness is intentionally ignored and tested against valid curve fixtures via both operator and ExtGState paths. The flatness range erratum affects producer validity, not a reader that elects to ignore the parameter. Smoothness `/SM` is carried into shading ramps and mesh refinement. Tests use a nonlinear `t^80` ramp with an absent-`/SM` control and analytic component values, and mesh tests report when a discontinuity defeats the attainable tolerance. The device's 1/256 default and 4096 cap are implementation choices within the source's internal-tolerance latitude. The code's `1/t` sample-count language should remain a heuristic, not a general proof of the §10.7.3 error bound for every nonlinear function; Note 1 explicitly describes cases where sampled conversions can defeat the requested accuracy.

For §10.7.5, `pdf_render::grid_fit` is turned on by default under `/SA true` after A714/ADR 2553. The checked-in tests have literal CPU-raster results for a thin axis-aligned rule at eight placements, and compare all three raster lanes on rules and rectangle outlines. They also exercise sub-half-pixel promotion. The implementation fits only thin axis-aligned strokes under near-uniform transforms; curves, diagonals, general anisotropic transforms and other widths retain their original path/coverage. That is the precise owner-selected construction, not a textual limitation in §10.7.5. The test suite supports the selected case, but does not establish full general-family conformance. Reconsider whether the row's unqualified `implemented` label and family prose state that residual clearly.

There is a separate stale parent ledger description: §10.7's family note still says the first §10.7.5 requirement “is decided against in ADR 0028” and only the sub-half-pixel requirement is implemented. That predates A714/ADR 2553, which turns the fit on across the CPU and three raster lanes and updates the §10.7.5 subclause row. The family note also says nothing is `partial`, then describes §10.7.5 as only its grid-fit status without restating the newer implementation. Update/reconcile the family summary before promoting its claim.

The B20 degenerate pattern BBox, B19 page-boundary cases, sample-image point mapping, and all detailed scan-conversion departure proofs remain outside this shard as directed. No behavioral defect was demonstrated in the sampled current tests; the concrete findings are source-scope/policy framing and stale ledger prose.
