# Collection sort, colors, and split cells

I read the preceding collection/date/sort/UI findings in `scratchpad/r2038/spec-audit/collections` and the current ledger/ADRs before selecting these cells. The primary captions and footers are directly verified: Table 156 is physical p.467 / printed p.452; Table 157 starts there and continues on physical p.468 / printed p.453; Table 158 is on p.468 / p.453. The type comparison prose and lexical NOTE 3 are on physical p.466 / printed p.451. The related Table 153 `/Split` default-orientation row is physical p.464 / printed p.449. EC3 pages 467–468 have no StrikeOut/Caret/Text errata annotations; the two markup objects are Table-reference links. The effective #477 navigator renumbering was already handled in the earlier collection shard and does not change these rows.

Table 156 requires the reader's sort key names (`/S`) and ordering; an array uses successive named fields to break ties. `/A` can be one Boolean or a Boolean array by key; default is true, short arrays supply true for missing entries, and extras are ignored. Source compares numbers numerically, dates by time order, and text lexically (with NOTE 3 explicitly identifying lexical choice as an implementation dependency). Implementation follows these rules in `Collection::sort`, `Sort::ascending`, `sorted_keys`, and `sortable/compare`. The named field values are consumed at the model seam because collection item `/CI` values and FileSpec values must be combined before host rows can be ordered; `viewer_core::Query::Collection` carries the order and `viewer_host::panel::collection_rows` applies it to the actual row list shared with hosts.

The existing assertions are meaningful but do not cover every Table 156 branch: model tests assert numeric ascending/descending, a two-field mixed direction tie, default ascending, and no-sort behavior; host rows assert visible lexical order; the email example parses a date schema and direction but never sorts date values. I did not find a date comparator assertion or a short `/A` array where a later `/S` field uses the assumed-true default. The scratch exact-xref PDF 1.7 test uses two runs with identical data and independent direction inputs. First, `/A [false true]` is the positive control for a rank tie between UTC instants 23:00Z and 23:30Z (the raw date strings sort the other way); expected public order `a.txt, b.txt, c.txt` independently proves numeric descending followed by chronological ascending. Second, `/A [false]` over the same two `/S` fields must produce the same order, isolating Table 156’s omitted-entry default from the date comparator. The shorter array is producer-valid: Table 156 sets no equal-length constraint and expressly says missing entries are assumed true (physical p.467 / printed p.452). The PDF has explicit page Resources, embedded-file streams and indirect CollectionItem dictionaries, exact xref offsets, strict no-recovery and complete-chain checks. This is a proposed assertion-quality improvement, not a known current failure; it has not been executed.

Table 157's five color entries are optional DeviceRGB triples with components in [0,1]. Table 153 calls `/Colors` a suggested set, and its NOTE recommends use by a layout. The model reads known values; host code does not apply them to native widgets and reports the choice to use platform styling. Existing model assertion reads Background [1,1,1]; the host assertion tests only that the request is disclosed, not the actual RGB rendering. Treat this as a declined recommendation with an owner rationale, not a mandatory SHALL defect and not as rendered color support. Producer range/shape rules do not imply that a reader must reject malformed arrays.

Table 158's presentation context says the available area may be divided between collection navigation and a preview of the initial/current selected embedded document. H/V and Position describe that optional arrangement; Position is 0–100 and ignored when Direction=N. Direction N is different: it says no split and that the whole window region shall be dedicated to file navigation. `panel::whole_window` implements that choice, with hidden View H handled as a conflict. `viewer-host/tests/host_mappings.rs::table_158s_n_gives_the_whole_window_to_the_file_navigation_view` tests N, absent Split, and hidden View; a companion test verifies H/V and color requests are named. GTK removes the page child, Qt hides the secondary splitter widget, and viewer-ui gives the sidebar the logical window width when `whole_window` is true. I found no native pixel assertion specific to this path in the bounded test search. This is a residual test-depth limitation, not a demonstrated UI failure.

When Table 153 `/Split` is absent, it says the preferred orientation follows `/View`: D or no value indicates horizontal, T vertical, and H/C have no splitter. Table 158 provides no explicit default for a Direction omitted from a present `/Split`. Since the current product does not implement the collection's navigation-plus-embedded-preview pane, lack of H/V/Position behavior is a capability decision; do not infer that an optional producer entry alone mandates building that UI. Likewise, Table 153's default preferred orientation should not be conflated with an ISO command to create the optional second pane.

The current collection ledger claim is aggregate `implemented`; its note says colors and split direction/position are unused “as a choice the clause leaves open.” That is accurate for the optional preview split and the color SHALL status, but it should preserve that color use is recommended and that `/Direction N` is independently implemented and mandatory when stated. ADR 1168 correctly places sorting at the model seam; ADR 1252 supports /N and the product split/color choices; ADR 1622 explains why a declined recommendation is not recorded as a departed SHALL. I make no whole-clause or whole-ADR certification. No tests were run in this shard.
