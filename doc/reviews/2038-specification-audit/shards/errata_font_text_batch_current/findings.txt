# EC3 source-led font/text errata batch

Baseline reviewed: `b901326c`. Primary source is `doc/ISO_32000-2_sponsored_EC3.pdf`. I read the annotated pages directly with pikepdf and checked the defining paragraphs and ISO footers using page-specific `pdftotext`; `uncited_issue_candidates.json` was used only to locate annotation object IDs. Its page numbers match the pikepdf physical page number; they were not incremented. Replies/status and IRT links were inspected. The effective-source classification below does not rely on annotation absence of State/IRT to reject an edit.

The strongest runtime assertion gap in this batch is EC3 #550. On physical p.325 / printed p.310, three strikes and a caret replace the old inline syntax discussion with the direction that literal-string rules apply before a text-showing operand is interpreted as one- or multiple-byte character codes. The surrounding paragraph is §9.4.3, immediately before the §9.4.4 heading. This is a consumer ordering requirement: literal syntax yields string bytes, then the selected font's encoding/CMap groups those bytes into codes. The implementation has that order: `pdf-syntax`'s literal-string lexer resolves escapes before `pdf-model` text interpretation calls `LoadedFont::decode`. The inspected test coverage establishes literal escapes with simple-font codes (`text_state_units_audit.rs`) and composite-font source-code/ToUnicode behavior with hexadecimal operands (`tounicode_keeps_source_code_length_spec_audit.rs`), but no found public assertion joins a literal escape that contributes a byte to a multi-byte CMap code. `drafts/literal_escape_before_composite_code.rs` proposes one exact-xref public test: octal `\000` plus ordinary `A` must produce the same independently mapped `A` as `<0041>`, with no recovery and an embedded matching Liberation Sans program. This is a coverage proposal; the implementation was not observed failing, and the draft was not compiled or run.

EC3 #165 is on the same physical page and changes the string-writing sentence: a writer using parenthesized literal strings must escape CARRIAGE RETURN (0Dh), and a cross-reference points to §7.3.4.2. This is a producer obligation. `pdf-syntax`'s ordinary serializer writes strings as hexadecimal; the viewer's constructed field-appearance path does write literal Tj operands, and `variable_text::push_code` escapes every non-printable byte in three-digit octal. It therefore escapes CR. The direct test helper can decode those escapes, but the inspected assertion set does not isolate CR. I did not draft a second test because this is already a straightforward branch consequence of the existing all-nonprintable writer and there is no demonstrated output defect; an unescaped CR in an input string is not a reader-conformance finding.

EC3 #384 is the substantive current-source citation correction. Physical p.330 / printed p.315 has the corrected standard-14 name list, with `Courier-BoldOblique` as the fourteenth name. The list's bulleted/alphabetical presentation is editorial, but the corrected hyphenated token is operative because §9.6.2.2 defines the names. `pdf-font::standard::STANDARD_NAMES` accepts both the corrected spelling and `CourierBoldOblique`; that permissive alias need not be removed. However, comments in `standard.rs` and `substitute.rs` still quote the old spelling as the standard's own spelling and use that premise to explain the alias. Accepted ADR 0396 likewise quotes the old list in its source argument; ADR 1916 repeats the same spelling while describing published AFM selection. The contour-direction and AFM choices remain independent of the spelling, but their *current explanatory citation* should be corrected while historical ADR text remains a record of its earlier premise. Existing tests already cover both spellings; no new runtime test is warranted.

The other annotations do not establish new reader obligations:

- #44, physical pp.335–336 / printed pp.320–321, corrects/captions the worked Type 3 example. The executable reader rule remains the normative encoding-to-glyph-name-to-CharProcs steps; the Type 3 integration fixture already distinguishes the two glyph descriptions.
- #161, physical p.132 / printed p.117, repairs informative NOTE 4's character-name list from `dieresis` to `idieresis`. The UTF-8 marker decoder follows the normative marker bytes and does not consume the NOTE.
- #178, physical p.359 / printed p.344, adds an explanatory FontWeight NOTE. Table 120 contains the operative optional-field type/value restrictions and expressly says specific interpretation varies by font; the note does not require CSS matching.
- #337, physical p.360 / printed p.345, adds a contextual FontDescriptor NOTE about embedded versus referenced fonts. The individual table entries and font program clauses supply producer requirements; this note does not require a reader to validate descriptor data against program tables.
- #372, physical p.320 / printed p.305, clarifies a NOTE example as a “zero-length line” and corrects a typeset Tm symbol. Neither edit changes the text-rendering-mode rule or matrix update.
- #553, physical p.21 / printed p.6 (reference insertion) and physical p.332 / printed p.317 (name-guidance note), adds Adobe Technical Note #5902 to clause 2 and points writers of variable-font instances to name-generation guidance. The §9.6.3 naming language is guidance on the font writer's BaseFont name. The inserted note/reference does not require a PDF reader to instantiate variable fonts or generate a PostScript name.

Selected decision reviews are in `decisions.json`. No behavior claim is inferred from citation presence alone. I did not run Cargo or modify tracked source/test/ledger files. Parent test execution was not attempted or reported from this shard.
