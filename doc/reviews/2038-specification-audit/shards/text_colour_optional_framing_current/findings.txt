Colour-space framing

§8.6.4/.4.1 and §8.6.5–.6.2 route source colors to the detailed device, CIE/ICC, special-space and pattern clauses. Existing owners use independent expected anchors and controls: asymmetric CalRGB primaries/gamma, CalGray luminance, Lab anchors, DeviceN/Indexed examples, pattern-cell colors, image conversion and ICC profile inputs. Those leaf results do not make the aggregate rows blanket proof. The colour-space shard retains an ICC unsupported-profile `/Range` fallback candidate and the already-passing public DeviceRGB reset assertion T27; this framing pass neither reproduces nor closes them.

§8.6.4.1's closing warning concerns a writer choosing device color operators within a CIE-based transparency group; where device mappings are not remapped, results are described as implementation-dependent/unpredictable. This is not a reader rejection rule. The default-space and group-space work is separately owned. The #19 amendment that makes DeviceGray/RGB/CMYK/Pattern names identify their color spaces directly or via Default entries is in later Table 74, not this general clause; EC3 #551 alters the later color-operator resource-shape row (the source/ledger correction is handled in `font_colour_aggregate_current`). Do not misattribute those table edits to §8.6.4.1.

§8.6.6.6 is a worked example, not a separate required color algorithm. The actual source includes two duotone examples, explanatory notes for the gold alternate, and a quadtone image/stream lookup table. `multitone_examples.rs` compares literal sample colors against direct-color squares for Example 1, Examples 3–4, and Example 5; Example 2 gives the possible function approach as prose rather than a complete runnable function. These controls are useful evidence for selected composition routes but do not predict a physical press's spot inks.

Optional content

The source text and tests split §8.11 into group/membership evaluation, where content becomes optional, default configuration, UI presentation, and purpose/usage adjustment. EC3 #225's nonempty RBGroups inner-array rule constrains producer input; #686/#707 correct examples; #567 says the Usage Language entry changes no content language. None by itself mandates parser rejection or a language change. Existing public assertions in `optional_content.rs` exercise base state, ON/OFF overrides, OCMD policies, visibility expressions, hidden graphics-state effects, marked content and View/Print/Export overlays. Parent reported the new `optional_content_nested_spec_audit` cases passed: an ON form is still suppressed inside hidden outer BDC and appears in the corresponding outside control; a null reference makes the membership policy neutral relative to a real OFF group. This supersedes stale “unrun” text in the earlier optional-content scratch finding. It does not certify every layer-panel ordering/RBGroups/Locked behavior or every Language match branch. Optional alternate configurations and labels do not force an alternate-configuration UI.

Text/font framing and current residuals

§9.3's sentence that text state values can be set outside text objects and persist across objects is implemented by state living in the graphics state. Current tests assert selected horizontal and vertical axes, Tc/Tw/TJ/Tz/rise, q/Q text-matrix save/restore, clipping at ET, and knockout behavior. The ledger's §9.3.2 note omits the vertical Tc result already checked by `text_state_residual_audit.rs::vertical_spacing_rise_and_horizontal_scale_keep_distinct_axes`; this is a test-evidence-note correction rather than a runtime bug. Parent T22 already passes the embedded-font vertical numeric TJ control. §9.4 aggregates BT/ET and positioning/showing rules; malformed nesting/operator placement constraints do not automatically require reader rejection.

For §9.6.5, `simple_font_encodings_current` has synthetic embedded-font public controls for base encoding/Differences and symbolic status. One meaningful missing public assertion remains: StandardEncoding's fill of still-undefined glyph-name slots after Differences in a TrueType font. The same shard notes full MacExpert assignments are source-extracted but CI checks representative rows/count only. Neither is a found mis-mapping. EC3 #47/#48 retire the former Standard 14 metrics compatibility MUST; do not retain it as an active reader requirement.

§9.7.5–.6's current pending public candidates are accurately separated in `text_extraction_cmaps_current`: length-sensitive source codes, multiscalar sequential bfrange, and stream-valued UseCMap. Parent outcomes supersede the initial reviewer status: B27/B28 FAIL with passing controls; T30 stream UseCMap PASS. Their fixture must include a valid embedded Type2 font when a custom Encoding CMap is used; the source validity correction is already noted in that shard. EC3 #324 corrects Table 119's ToUnicode cross-reference; Table 125a is the appended erratum page at physical 1022, not the original clause introduction page. No inference about rendered glyph correctness follows from extraction-only results.

§9.8 is a source-to-ledger qualification issue: EC3 #453 changes Table 120's `/MissingWidth` text so the predictable effect depends on all uncovered codes actually having that advance; otherwise behavior is implementation-dependent. The current deterministic zero/default policy is allowed, and existing tests assert explicit width and zero default. The ledger note omits the #453 condition. This is existing D10, not a new behavior failure. §9.9 and Table 124 have independent format-specific loaders. The current exact-xref Type1+CFF OpenType test with conflicting cmap and bare Type1C control supports that named-glyph route, but the full key/subtype/table-format cross-product was not certified.
