# Unknown annotation pointer-state review (baseline b901326c)

The public pointer path is reachable. `viewer-core/src/viewer/pointer.rs::Viewer::pointer` transforms the pointer to page user space, calls `pdf_model::view::annotation_at`, then changes the view state to `Pointer::Over` or `Pointer::Down` only when `interact::has_appearance` says the picture can differ. `annotation_at` accepts a common `/Rect`; `annotation::interacts` does not reject an unknown subtype with `/F 4` (Print only). The `R` and `D` entries make the pointer transition eligible. This is an actual `Command::Pointer` route, not a manually assigned `ViewState`.

The mismatch is localized in `pdf-model/src/annotation.rs`: `decide` consults `STANDARD_SUBTYPES` for the Invisible flag, while `stored_appearance` unconditionally maps `Appearance::Normal`, `Rollover`, and `Down` to `/N`, `/R`, and `/D`. Thus the existing unknown-subtype test only proves fallback rendering when `/N` is the sole state; it does not test the explicit §12.5.5 normal-appearance rule against generic pointer-state selection.

The normative source places two general rules next to each other. Table 170 and the preceding prose describe N/R/D for annotations generally. The following §12.5.5 sentence says that a processor without native support for a particular annotation type shall render its normal (N) appearance. EC3 #1 redirects the expected behavior for unrecognized types from §12.5.2 to §12.5.5 and Table 167 bits 1–2. A direct reading favors N for the unsupported type. The potentially competing reading is that generic AP interaction is native support for the rendering mechanism even when type-specific behavior is unsupported; because the clause does not define “native support” here, parent review should settle whether the specific fallback overrides the generic rollover/down mechanics.

The existing fixture is weak for this question: `annotations.rs::an_unknown_subtype_still_draws_its_normal_appearance` includes only `/AP /N`, so both interpretations produce red. The scratch regression adds red N, green R and blue D. It first checks a known Square through the real Viewer API as a positive control (`red -> green -> blue`), then expects an unsupported second-class extension type to remain at N. The proposed type is `/GLGR_R2PointerProbe`, identified by a direct catalog `/Extensions` entry using the GLGR prefix/BaseVersion/ExtensionLevel form shown by Annex E; all common annotation fields and valid Form AP streams are present. This improves the source premise over an unregistered arbitrary name, although it does not assert that the real-world GLGR extension defines this synthetic subtype.
