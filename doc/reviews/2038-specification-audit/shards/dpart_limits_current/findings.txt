# DPart depth and count limits — bounded source and consumer review

## Result

The comments in `document_part.rs` overstate what the standard says: a DPart chain deeper than 64 is not necessarily a cycle. §14.12.2 says a child cannot be referenced by more than one parent and Note 2 says a DPart can have any number of children; the reviewed clause and tables specify no depth ceiling. The existing `seen: BTreeSet<ObjectId>` is intended to stop repeated references, but does not catch children in EC3 #612’s effective flat shape: `collect` resolves each outer `/DParts` element before matching on `Object::Reference`, so a direct flat child has already become a dictionary when the guard runs. The nested-array compatibility path still exposes references to the guard. `MAX_DEPTH` is therefore also the current recursion bound for malformed flat cycles; that does not make a valid acyclic chain beyond 64 a cycle. Table 409 requires child references to be indirect, so a valid finite unary chain can follow a single-parent path well beyond 64 without repeating an object.

The guard does have a user-visible consequence. `collect` silently stops when `level > 64` or `out.len() >= 65_536`, and the resulting `Hierarchy` has no `complete` or truncation field. The adjacent code comments also mischaracterize both guards: Table 409 requires child DPart references to be indirect, so “inline” depth is not the valid-tree case, and “handful levels” is not a standard limit. Although leaves cannot outnumber pages, a branching tree can have many internal nodes; 65,536 total nodes is a code-selected budget, not a bound derived from page count. The PDF model then uses that list to enumerate §14.13.8 DPart `/AF` files. `Query::Attachments` exposes the resulting list; no corresponding partial-result note was found in `notes::about`. Separately, `first_page_at` stops at the same depth and `DocumentPartJump::page_in` maps that to no navigation target. The audit found only shallow tests for each public behavior.

This is a resource-limit transparency/policy concern, not a confirmed standards violation. The source defines a DPart tree and page-order relationship but does not say a processor must support arbitrary resource consumption. A finite `MAX_DEPTH` can be a deliberate safety policy. The current API, however, cannot distinguish a complete answer from a silently truncated one. Parent should decide whether the cap remains, whether it is raised, or whether truncation becomes observable. No unbounded-support requirement is inferred here.

## Primary source and effective EC3

- §14.12.2, “DPart tree structure,” physical p.850 / printed p.835: the catalog references a DPartRoot dictionary; DPart leaves may define page ranges; ranges do not overlap; every page belongs to exactly one range; immediate descendants and parents are explicit. The child rule is “A child DPart dictionary shall not be referenced by more than one parent DPart dictionary.” Note 2 says a DPart has “any number of children.” Neither supplies a numeric maximum depth.
- EC3 Issue #609 is annotated on physical p.850: it replaces the original single-hop “DPartRootNode dictionary” wording with a reference to the DPartRoot dictionary and Table 408. Table 408 then supplies `/DPartRootNode` as the indirect reference to the tree root, at physical p.851 / printed p.836. The actual PDF annotation is needed because extracted base text retains the struck wording.
- Table 409, physical p.851 / printed p.836: `/Parent` is an indirect reference to the immediate ancestor; `/DParts` and `/Start` are exclusive; `/Start` is an indirect page ref; a leaf may carry `/AF`. EC3 #612’s annotation on physical p.851 replaces the original DParts cell with a flat array of indirect references to immediate descendants and says the array shall not be empty. The base PDF text extraction still shows the struck “array of arrays” cell; the annotation is effective text.
- §14.12.3, physical pp.850–851 / printed pp.835–836: pages in a range point back to that leaf, each page belongs to only one DPart range, and page-tree order equals depth-first leaf traversal. This constrains a valid boundary fixture; it adds no depth maximum.
- §14.13.8, physical p.855 / printed p.840: any DPart may have an `/AF` array. This is the consumer whose content disappears when its DPart falls beyond the hierarchy limit.
- Table 29 `/DPartRoot` indirect-reference change is EC3 #614 on physical p.117. The proposed fixture uses an indirect root dictionary.

## Code, consumers, and assertions

`document_part::hierarchy` starts at the catalog’s `/DPartRoot`, resolves its `/DPartRootNode`, and recursively walks children. `collect` stores each visited indirect object in `seen`; it also returns without status at `MAX_DEPTH` or `MAX_PARTS`. The depth limit is checked before pushing the node, so levels 0 through 64 are retained, while level 65 and its descendants disappear. The part-count cap similarly returns a prefix. `first_page_at` has an independent depth check and no cycle set; a requested GoToDp target whose first leaf lies beyond the cap returns `None`.

`attachment::attachments` maps the hierarchy to its returned `parts`, then enumerates each part’s associated files. `viewer_core::Query::Attachments` uses this list for the attachments panel. The list itself carries no indication that traversal was partial. `notes::about` contains general document notes but no DPart truncation disclosure. Thus the open question is not only internal hierarchy completeness: a deep leaf attachment can vanish from an otherwise valid panel answer.

Existing useful controls include `dpart_af_current_shape_spec_audit.rs`, which uses current flat `/DParts [6 0 R 7 0 R]`, reciprocal page `/DPart` pointers, matching leaf `/Start`s, and a distinct catalog attachment; and `goto_dp_node_spec_audit.rs`, which covers a shallow leaf target and an interior DPart target. These assert actual output, but neither reaches a depth boundary. The older nested-array fixtures predate EC3 #612 and are not evidence for current grammar.

## ADR review

ADR 1040 correctly records the missing DPart AF consumer and the two-hop catalog/root shape after #609. Its assertion that the no-multiple-parent rule itself bounds traversal and makes a cycle finite is too broad as a depth-limit rationale: it does not set a numeric depth. Also, the implementation `seen` check applies to refs in the nested-array compatibility path, but effective flat #612 child refs are resolved before that check. The depth cap currently bounds recursion through that flat shape, including malformed cycles, but this does not justify calling a valid acyclic chain beyond 64 a cycle.

ADR 1461’s writer-side evidence for §14.12.2/.3 (dropping or retaining DPart references during page edits) is separate and remains supported by this review. The read-side behavior is reached through GoToDp and DPart AF; aggregate ledger status does not itself prove deep-tree completeness.

EC3 #612 supersedes the array-of-arrays cell. The current shape test uses the corrected flat array, but stale source comments and old unit fixtures still describe nested arrays. This is a documentation/fixture provenance issue adjacent to, but separate from, depth truncation.

## Limits and disposition

The test draft in `draft-tests/dpart_depth_public_spec_audit.rs` builds exact offsets and a one-page unary chain with depth-64 and depth-65 variants. It uses indirect `/DParts` children in the EC3 flat shape, immediate `/Parent` references, the root dictionary two-hop structure, leaf `/Start`, page `/DPart` back-pointer, and one leaf `/AF` attachment. It asks the public viewer’s `Query::Attachments` for the payload. The depth-64 fixture is a positive control; depth 65 is expected to expose the current silent drop if the test is executed.

This draft is deliberately not labeled a normative fail. It gives the parent a reproducible observation for deciding whether to report a partial list, adjust limits, or leave an explicit resource policy. MAX_PARTS=65,536 was inspected but not crossed with a large fixture. A shallow tree with many internal nodes can exceed the cap even if its number of leaves/pages is lower than the node count; the review does not infer a required node population from typical documents or corpus absence. The draft is unexecuted; no Cargo commands were run.
