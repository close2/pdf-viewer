## Coverage and current conclusions

`features.json` records the required/optional/default/range cells individually. The key assertion families are `crates/pdf-colour/tests/functions_spec_audit.rs`, `sampled_functions_spec_audit.rs`, and the focused unit tests in `crates/pdf-colour/src/function.rs`. The latter’s exact width test checks all eight Table39 values; the public 12-bit test checks high-order-first continuous packing. Type0 tests have independent literal expected values for default/explicit Encode, input clipping before Encode, sample-table clipping, Decode default and post-Decode Range clipping, two output components, first-input-fastest storage, Size=1, and 2D bilinear interpolation. The prior function audit also traced stream extent.

Type2 has separate checks for nonlinear N=2, componentwise Range clipping, absent Range preserving unbounded output, C0 and C1 independent defaults, and valid fractional/negative exponents. Type3 covers one-child/empty Bounds, ordinary right-hand bound selection, per-interval nonidentity/reversed Encode, Domain endpoints, nested functions and signed-zero cases. The signed-zero endpoint issue is already documented in `functions_current`; it is not recertified here. Type4 common dictionary and fault/report paths belong to `functions_current` and the calculator shards; Table42’s explicit operator list is not independently re-proven by this table inventory.

I found no additional distinct valid-input combination defect in the requested table cells. Required-entry/type/dimensionality clauses chiefly constrain producers; absent required keys, inconsistent child dimensions, non-integer counts and Type2-invalid domains are not promoted here as mandatory reader-rejection requirements. The parser’s tolerance/fallbacks for some such malformed dictionaries are a recovery boundary, not proof of conformance. Source does not provide a universal malformed-input rejection algorithm. Resource bounds (`MAX_VALUES`, `MAX_SAMPLES`, `MAX_FUNCTIONS`, nesting depth) are code policy, not standard-defined numeric ceilings.

## Decisions and limits

The current Order3 code and tests are consistent with the adopted choice in ADR 1636, which implements ADR 1623’s correction to ADR 0098: not-a-knot tensor-product cubic interpolation, with the source’s ignore rule when any dimension is under four. This is a deliberate choice because Table39 specifies “cubic spline” without its endpoint condition; it is not an ISO-mandated not-a-knot algorithm. The prior narrative in ADR 0098 should not be carried forward as today’s unresolved Order3 status.

ADR 0261’s Type3 function-tree resource bound remains a project policy: Table41 specifies no maximum k. Type4 operator semantics are delegated to PLRM3; prior calculator-oracle review appropriately distinguishes this delegation, literal expectations, production, and GPU tests. This review does not certify every operator or every consumer. The only prior distinct numerical gaps relevant here are the Type0 sub-EPSILON span and Type3 signed-zero endpoint, already recorded in `functions_current`; no duplicate draft was created.
