# Font overview, graphical effects, and text extraction introduction

This is a bounded review at baseline `b901326c`. I read the effective PDF text and the primary PDF annotations that intersect the sampled scope. Physical and printed page locators in `features.json` were checked against footer pages.

The overview text has no independent font algorithm hidden behind its general labels: §9.2.1 distinguishes character information, glyph shape, the PDF font dictionary, and font program; the test/code evidence is owned by loading, decoding, rendering, and extraction rows. §9.2.2's minimal Tf/Td/Tj sequence is supported by text-state and show-font tests. The remaining text matrix recomputation edit I saw is EC3 #376 at §9.4.4 physical p. 326, outside this bounded clause list; I record it as a dependency only and make no claim that this shard reviewed it.

§9.2.3 describes the actual graphical effect of glyph outlines used as paths and clipping later paint. Current text-rendering-mode tests are strong about paint command type/order, clipping path shape, ET application timing, Q lifetime, empty-outline behavior, and Type 3 exceptions. The selected mode-7 test does not independently assert the CPU raster result. The exact-xref draft `drafts/text_clip_affects_later_paint.rs` samples an interior and exterior pixel after glyph clipping and compares the exterior with the same page without Tr 7. It uses Standard 14 Helvetica in a PDF 1.7 fixture. The draft is unexecuted.

The CID overview rows are materially supported by variable-length code fixtures, a Type 0/descendant path, vertical metrics, and a code-to-program witness whose width is independently measured from the font program. No unbounded CID requirement is inferred: Annex C allows implementation limits. Detailed collection compatibility and individual CMap/CID mechanics remain the specialized owners' work.

§9.10's introduction draws an important line between glyph appearance and character information for search/index/export. The implementation's public text readback has independent Poppler/PDFBox comparisons and tests showing that no glyph paint (Tr 3) can still yield extracted text, while unmapped codes and ActualText take distinct routes. The source permits choosing a character value when mapping fails, so the current non-error fallback is not a reader defect by itself. EC3 #324 changes Table 119's ToUnicode cross-reference to §9.10; it corrects the citation and does not alter extraction behavior.

The current ledger rows are all marked implemented, and the selected assertions support those sampled claims. No behavior defect was identified in this scope. The pixel clipping draft is a consumer-coverage proposal, not a claim that the current rasterizer fails. No Cargo command was run.
