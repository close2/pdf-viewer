Bounded source-to-assertion review of ISO 32000-2 Annex Q Q.1–Q.5 at baseline b901326c. Scope is page-wide detection, traversal population, method optionality, and current archive consumers; compositing math was not re-audited. Physical/printed locators below refer to the sponsored EC3 primary PDF, whose printed page numbering is physical minus 15.

Annex Q is captioned normative, and Q.1 says a processor “shall use” its method, but the NOTE in the same Q.1 explicitly says the method “is not required by this document” and lists subset standards that choose to mandate it. This resolves the apparent strength conflict: a PDF 2.0 reader/rendering product need not expose or call a page-wide detector solely because Annex Q exists; a processor validating a profile that adopts the method must implement its stated method. ADR 1461 and the ledger’s Q rows make that distinction, and the current `Survey::page_is_transparent` consumers found are archive graphics checks for ISO 19005-2 §6.2.10 and ISO 19005-4 §6.2.9. The rendering interpreter follows transparency per painted object and does not call this page-level API. ADR 0981 separately records why ISO 19005-2 cites its own Annex A method rather than a non-existent Annex Q in its PDF 1.7 base standard.

The direct primary Q.2 rule has four tests on the state of each graphical element to be rendered: an SMask key with dictionary value, ca<1, CA<1, or BM other than Normal. The current operator walk updates state on `gs`, preserves it through relevant content, restores it with Q, and marks the page at Show, Invoke, Shade, Paint, and InlineImage. Current assertion bodies include explicit alpha at/under one boundaries, Normal/Compatible/Multiply and BM-array behavior, state restored before an element, and path termination without paint. Q.2’s type-1 pattern clause enters the tiling pattern as a form. The audit does not certify every malformed operator/resource case.

Q.3 requires a transparency Group form to mark the page and directs its content to be processed under Q.2. `survey/xobjects.rs::form` does this and processes form content with the form’s resource dictionary or, where absent in legacy form files, the effective page dictionary. EC3 §7.8.3 physical 127 / printed 112 expressly says all resources of forms/fonts that omitted Resources in earlier PDF versions are inherited from the page on which used. `Page.resources` includes inherited page-tree Resources; nested forms lacking Resources return to that page dictionary. Existing `resource_fallbacks.rs` tests nested form name lookup but not its Annex Q result; `drafts/inherited_nested_form_resources.rs` adds inherited page ExtGState (ca .5 vs 1) through an outer form with its own XObject table and an inner no-Resources form. This is an assertion addition, not a found implementation error.

Q.2’s annotation sentence requires appearance streams for every annotation to be processed as forms. Current `pages.rs::annotations` iterates AP dictionary entries and, for state dictionaries, each contained stream. Existing tests assert transparency inside a normal AP, opaque CA-in-AP ExtGState control, and transparency in an alternate AP state. Direct EC3 Issue #51 annotation object 16428 is on physical 997 / printed 982; its `/Contents` inserts “Any annotation that has a BM key (PDF 2.0) in the Annotation dictionary with a value other than Normal shall be considered to contain transparency” with a Table 166 cross-reference. Its reply object 16430 is `/State (Completed)` and the issue object’s `/M` is 2022-06-15. This is a substantive effective correction; current `annotation_is_transparent` correctly checks annotation BM, and the audit tests BM Multiply plus absent/Normal controls. Direct Q.5 annotation Issue #295 object 8772 on physical 998 / printed 983 inserts “if it was”; its CreationDate is 2024-04-29 and modified date is 2026-04-16. It is editorial, not a Type 3 method change.

There is one concrete over-detection in the annotation path. Table 166 /CA and /ca rows on physical 484–485 / printed 469–470 describe opacity for regenerating an annotation appearance and expressly state that the specified value “shall not be used” when the annotation has an appearance stream; that stream must specify transparency. Yet `pages.rs::annotation_is_transparent` returns true for any annotation `/CA < 1` without checking for AP. It therefore reports transparency for an explicit opaque AP with `/CA 0.5`, contrary to the source’s rendering rule. Issue #51 adds `/BM` to Q; it does not add annotation `/CA`, and this CA value is producer-side regeneration data once AP exists. Draft `annotation_ca_and_state_scope.rs::annotation_ca_does_not_override_an_explicit_opaque_appearance` uses a PDF 2.0 pushbutton Widget (a non-markup annotation for which Table 166 permits /CA), a valid normal AP, blank opaque page content, and an independent annotation-BM positive control. It remains uncompiled/unexecuted.

Q.4’s image-XObject test is exact: an SMask value that resolves to a stream, or SMaskInData integer >0. Current implementation tests resolved stream type and integer boundary. Tests distinguish stream vs dictionary/null and 1 vs 0 vs absent. This does not conflate an image’s SMask subsidiary image stream with the graphics-state SMask dictionary used in Q.2.

Q.5 directs each Type 3 CharProc to Q.3 after text is drawn using a Type 3 font. Existing assertions include an unshown CharProc with a non-Normal blend plus a Normal control, verifying that the method’s population is every CharProc once Type 3 text is rendered, not only the glyph selected. The current traversal joins group/content paths; no full Type 3 validity claim is made.

One possible Q.2 scope issue remains provisional. `graphics_state.rs::soft_mask` follows a dictionary SMask’s G as a form immediately when `gs` sets it. `xobjects.rs::form` marks a page transparent as soon as that G is a Transparency group. That is earlier than `operators.rs`’s rendered-element test. A valid soft-mask dictionary set by `gs` but never followed by a painting/show/Do operator may therefore mark a blank page transparent; Q.2 defines its population as elements “to be rendered.” `drafts/annotation_ca_and_state_scope.rs::a_soft_mask_group_only_counts_when_an_element_is_painted_under_its_state` contrasts a state-only page with a painted mask-state positive control and opaque control. There is a possible counterreading that the referenced group itself is already “otherwise involved in a transparency operation”; the audit leaves this as a source interpretation candidate for parent review, not a settled defect.

Selected decisions: ADR 1461’s scope and ledger classification are reaffirmed; ADR 0981’s ISO 19005-2 separate-method explanation is relevant and consistent; ADR 1059’s fallback-to-page-resource choice is source-supported by EC3 §7.8.3; ADR 0933’s soft-mask image boundary concerns colour validation, not the Annex Q detector and was not treated as a transparency exclusion. ADR 2080 is only the code module split. No new issue or broad Annex Q certification is claimed.

Remaining work: parent review of annotation /CA and unpainted soft-mask scope drafts; optional execution of the two new tests; no Cargo test was run in this shard. Survey traversal bounds (token, form depth, stream count) and malformed PDF recovery behavior are not adjudicated here. The detector exposes `stopped_short()` separately, while page_is_transparent returns a bool; archive consumers’ handling of an incomplete walk was not reviewed to a final verdict.
