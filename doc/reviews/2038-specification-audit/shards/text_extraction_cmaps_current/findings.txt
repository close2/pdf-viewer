Bounded scope: ISO §9.10.1–§9.10.3 ToUnicode extraction paths, with §9.7.6.2 consulted for encoded source-code identity. This is not a certification of all CMap syntax or the full Unicode mapping algorithm. Excluded by assignment: AGL multi-scalar/unknown-component B15/B16 and ActualText B12.

Effective-source check: §9.10.3 is printed pp. 357–359 (physical pp. 372–374) in the combined ISO+EC3 PDF. On physical p.372 / printed p.357, the old first bullet is struck and has an EC3 annotation marker. The actual replacement Table 125a is on the separate EC3 Issue #462 page, physical p.1022 (no ISO printed page): it adds optional stream-dictionary fields Type, CMapName, CIDSystemInfo, WMode, and UseCMap; UseCMap accepts a predefined name or stream. The table says the referencing map states only differences from its base. The table does not make the other optional metadata fields part of text extraction's mapping result. The sequential `bfrange` destination-string form appears on physical p.374 / printed p.359 and explicitly increments the destination's last byte for every source code, with a bound preventing overflow. Its array form maps each source code to a full destination string. §9.7.6.2 on physical p.357 / printed p.342 says code-space matching and mapping lookup are both length-specific. No directly relevant source change to source-code length or bfrange semantics was found.

The visible, public text path is concrete: `LoadedFont::text(Code, out)` in `crates/pdf-font/src/loading/codes.rs` receives a decoded `Code`, tries its ToUnicode map first, then the collection and later fallback methods; `crates/pdf-model` accumulates the result in `Interpretation::text`, which feeds page text/readback consumers. The first priority and common ToUnicode forms have real tests, but two precise key/representation details are not exercised by inspected assertions.

1. Candidate behavior defect — ToUnicode loses source-code byte length. `Code` still distinguishes encoded length during CMap decoding, but `LoadedFont::text` passes only `code.value()` to `ToUnicode::append`. The ToUnicode parser likewise reduces each source hex string to a `u32` key (`code_of`), and `singles` and base/range lookup are keyed on that integer. Thus `<01>` and `<0001>` both become key 1 even though one is a one-byte character code and the other a distinct two-byte character code. §9.7.6.2's same-length codespace comparison and length-specific mapping lookup make the distinction explicit. The draft first asserts isolated one-byte→A and two-byte→Ω public readback controls, then the mixed-width case. It embeds `data/standard-fonts/LiberationSans-Regular.ttf` (SHA-256 `f8ace1f892b2bd9dc1792ba7f097fa7588f84fed48321480e04de5390828221f`); the program's postscript name is LiberationSans. The fixture uses `/CIDToGIDMap /Identity`, maps every probe code to CID/GID 36, and gives the independently measured `/hmtx` advance 1366/2048×1000 = 666.9921875. Descriptor FontBBox is the embedded TrueType `head` bbox scaled to 1000 units; ascent, descent, and cap height use the embedded OS/2 typographic metrics. Matching Type/CMapName/CIDSystemInfo stream metadata is supplied, and the custom encoding CMap is paired with an embedded Type 2 program. All xref offsets are exact and `was_recovered() == false` is asserted. Public expected text is `AΩβ` from literal ToUnicode values. The assertion concerns extraction only, not rendered glyph output. Draft is not run here; if it fails, trace the mixed code through encoding decode to confirm the issue is ToUnicode lookup rather than segmentation.

2. Candidate behavior defect — multi-scalar sequential bfrange destinations are not continued. `take_ranges` stores a sequential range as `Span` only when `scalar_of(target)` returns one Unicode scalar. For a valid destination string containing multiple scalars, `text_of` succeeds but the code inserts it only at `low`, with the comment that it cannot be incremented. §9.10.3 specifies the different result: increment the final destination byte for each consecutive source code, provided it stays within the bound. For `<00660061>` and three source codes the results are `fa`, `fb`, and `fc`. The draft first executes standalone bfchar `fa` and explicit-array `fa`/`fb` positive controls before the target sequential bfrange assertion. It embeds the same SHA-256-pinned Liberation Sans program; every source code maps to CID/GID 36, with its measured width 666.9921875 and exact program-derived descriptor metrics. The PDF has required Type 2 font/CMap dictionary entries and matching CMap metadata. Exact xref and no-recovery are asserted; expected text is `fafbfc`. This is an extraction assertion, not a glyph-rendering assertion. Draft unrun.

3. Coverage gap, not a known defect — public valid stream-valued UseCMap. The implementation resolves `/UseCMap` dictionary names and stream references recursively and local mappings are consulted before the base. Unit assertions exercise inheritance/override; a corpus test `a_to_unicode_cmap_built_on_a_published_one_reads_back_through_it` exercises `issue5010.pdf`, whose in-stream `usecmap` lacks the dictionary `/UseCMap` that §9.7.5.4(a) requires it to match. ADR 0298 correctly treats that as malformed producer input tolerated by the reader. EC3 Table 125a now makes a stream reference explicit. `drafts/tounicode_usecmap_stream_inheritance.rs` constructs the valid dictionary-ref case with base `A/B`, child `Ω` override, exact xref and no-recovery; public expected text is `AΩ`. This is a focused coverage opportunity, not evidence of behavior failure, and remains unrun.

Current tests at `crates/pdf-font/src/tounicode.rs` assert single mappings, consecutive scalar ranges, explicit destination arrays, UTF-16BE surrogate-pair decoding, multi-character bfchar output, range bounds, and base precedence. The corpus comparison assertions provide a useful independent baseline but do not isolate the two forms above. Assertions that a ToUnicode stream shall be well formed, use matching codespaces, or match its `usecmap` operator to the dictionary entry constrain producer conformance; they do not automatically require a reader to reject a malformed file. Here the candidate gaps concern valid small inputs and do not depend on malformed-input recovery policy.

ADR review: ADR 0298's valid dictionary-base route and malformed issue5010 tolerance distinction remain sound; the valid stream-valued public case is not shown in inspected focused tests. ADR 0971's finite limits and carried-file census are orthogonal; these two losses happen in tiny maps, so no unbounded processing conclusion is implied. ADR 0426 correctly applies Issue #462's revised table and does not imply new mapping behavior. ADR 0252's effective-source fidelity is upheld: the two candidate semantics are present in the combined ISO+EC3 primary text, not only in stale Markdown.
