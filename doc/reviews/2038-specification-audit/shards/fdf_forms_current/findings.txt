# FDF file structure, imported annotations, and non-interactive forms

Bounded source/assertion review of §§12.7.8.2, 12.7.8.2.2–.2.4, 12.7.8.3.4, and 12.7.9, with the §14.8.5.6 dependency named by §12.7.9. No tests were run and no new fixture was drafted.

## Source and errata

Effective EC3 source: §12.7.8.2.1 General is printed p.557 / physical PDF p.572; the FDF header and body, §§12.7.8.2.2–.2.3, are printed p.558 / physical p.573; the FDF trailer §12.7.8.2.4 continues printed pp.558–559 / physical pp.573–574. §12.7.8.3.4 FDF annotation dictionaries begins printed p.566 / physical p.581; Table 254’s /Page requirement is on printed p.567 / physical p.582. §12.7.9 Non-interactive forms begins on printed p.567 / physical p.582. These physical locators use the primary PDF footer, not the outline index.

§12.7.8.1 states the FDF differences from ordinary PDF syntax: the cross-reference table is optional; FDF files are not updated; objects have generation 0 and distinct object numbers; the body has one required object; and stream lengths are direct. §12.7.8.2.1 makes the xref and trailer optional. §12.7.8.2.2 requires %FDF-1.2 as the first-line header, with a later conformance version available via the catalog. §12.7.8.2.3 defines a sequence of indirect objects for the catalog and referenced objects. §12.7.8.2.4 gives the trailer's required /Root when a trailer is present. These shall restrictions characterize conforming FDF producers; the clauses do not separately prescribe that a reader reject an FDF with updates, nonzero generations, repeated object numbers, or indirect stream lengths. Do not convert malformed-producer cases into mandatory reader-refusal tests without another reader requirement.

§12.7.8.3.4 and Table 254 require /Page on each FDF annotation and define it as the zero-based page ordinal in the source document. Table 246's list of allowed FDF annotation subtypes is also a format constraint; that it excludes several subtypes does not by itself prescribe the error recovery a reader must use on an FDF containing one. EC3 #685 repeats the annotation /Page qualifier (for annotations in FDF files) in a later table; it does not change Table 254's requirement. Table 254 itself is physical p.582 / printed p.567 (the §12.7.8.3.4 lead-in begins on physical p.581 / printed p.566). No directly applicable erratum changes the scoped structure clauses. EC3 #176 changes the MIME-type text in §12.7.8.1, outside this structure review. EC3 #54 strikes the numeral 0 in §12.7.9's typo attrib0ute; it leaves the PrintField reference intact. Primary layout is scratchpad/r2038/spec-audit/ec3-parent-layout.txt around lines 33633–33695, 34209–34215.

## FDF structure and assertions

The parser route is pdf-syntax::Document::open (header/xref/trailer/object resolution), then pdf-model::FormsData::read (requires an FDF dictionary under the catalog). forms_data.rs unit helper writes %FDF-1.2, indirect object(s), trailer with /Root, and EOF without an xref table; an_fdf_file_is_read_by_the_pdf_reader demonstrates reading fields from this permitted minimal form. the_version_an_fdf_conforms_to_the_later_of_its_header_and_its_entry tests later, earlier, and absent catalog /Version cases. a_file_with_no_fdf_dictionary_is_not_forms_data controls the FDF-vs-PDF catalog distinction. The public viewer-core/tests/fdf_pages_import_audit.rs separately constructs an exact-xref %FDF-1.3 file, asserts no recovery on source and FDF, supplies it through the public import action, and observes page count/navigation/rendering. However, §12.7.8.2.2 literally requires the %FDF-1.2 first-line header; its catalog /Version rule allows a later conformance version, but does not itself establish that %FDF-1.3 is a conforming header. Do not call this fixture a valid producer control until the header is corrected. Parent is correcting it to %FDF-1.2 with a later catalog /Version and rerunning. The unit helper’s %FDF-1.2 fixture remains the direct header control.

The writer side in pdf-model::submission::fdf emits a %FDF-1.2 header, one catalog object, generation-zero object ids, a cross-reference table, /Root trailer, startxref, and %%EOF; direct stream lengths are used by its object writer. Its table is permitted though optional, and useful when its body includes the full PDF as an embedded stream. The scoped clauses are well represented as parser/writer behavior. Tests do not claim or need a refusal for the producer-only restrictions above. Existing code comments and tests describe the optional xref accurately. The current ledger rows §12.7.8.2 and .2.1–.2.4 are implemented; the evidence is proportionate to the narrow behavior stated, though the generic FDF unit fixture does not itself assert was_recovered()==false (the exact-xref public import test does).

## FDF annotation placement

FormsData::read_annotations retains /Page as an optional parsed value; missing /Page is named in FormsData::owed. ViewState::import places valid annotations on the named target page; invalid page ordinals and unsupported/out-of-format types are reported/refused by this implementation. forms_data.rs::an_fdf_annotation_is_placed_on_the_page_its_ordinal_names is an exact usable drawing fixture for Page 0 and checks the imported FreeText appears in rendered text. Separate controls check excluded Widget subtype and out-of-range page. This directly tests the clause's one annotation-specific field and its consumer. It establishes this product behavior; the subtype-refusal branch is a chosen handling of an invalid FDF, not a separate mandatory-reader rule inferred from the producer constraint. Ledger §12.7.8.3.4 is implemented; ADR 1224 treats the dictionary as an annotation, carries its object relationships within the target file, and applies the Page ordinal.

## Non-interactive forms and PrintField consumer gap

§12.7.9 says a non-interactive form has page content rather than widget annotations and is defined by the PrintField attribute for repurposing and accessibility purposes. Its referenced mechanism is §14.8.5.6 / Table 383 (printed p.791 / physical p.806), which describes a flattened field's role, checked state/default, alternate description, and—in the text-value role—the Form element's content. This is not an obligation to recreate an interactive widget or to make the printed marks editable.

At this baseline, pdf-model::structure::Tree::print_field parses the Table 383 values and model tests assert these values. However, a repository search for print_field( finds only the method and its model unit tests; viewer-accessibility does not consume it, and viewer-core::AccessibilityNode has no PrintField role/state/alternate-name slots. The public consumer test viewer-core/tests/print_field_consumer_spec_audit.rs was run at checkpoint 26: title variation passed, while the role (cb/rb), checked state (off/on), and description variation each failed because the public AccessibilityNode vectors were identical. This is concrete evidence of information loss, not merely a static call-graph concern. The assertions discriminate the relevant fields but do not yet prescribe exact platform role/name/state representation. The executed result is recorded in scratchpad/r2038/spec-audit/print-field-wave26.log and doc/reviews/2038-specification-audit/shards/structure_attributes_remaining_current/parent-review.json. In source and production call graph, the ledger's 12.7.9 implemented conclusion currently rests on parser coverage rather than an accessibility consumer. ADR 0085 similarly says that reading the model accessor makes a flattened form accessible, but a parsed field that never reaches the accessibility tree is not yet a consumer.

This is a source-backed consumer gap candidate in the stated accessibility purpose. The existing candidate public test should assert the exact answer for checkbox/radio/text roles, checked state/default, alternate name, and Form text value, with identical page marks and non-PrintField controls; avoid requiring widget behavior. Because the consumer regression was already run at checkpoint 26 and independently recorded in the parent review, I did not create a duplicate. The three information-loss failures are confirmed at that checkpoint; no rerun was performed during this shard. Ledger 12.7.9 needs reconsideration.

## Decisions reviewed and limits

- ADR 1066's FDF header/root/xref choices fit the source: the header belongs to the FDF file even when its body contains an embedded PDF, /Root names the FDF catalog, and an optional xref table is still useful.
- ADR 1224's Page-ordinal annotation placement is supported by a public render assertion. Refusal of out-of-format types is implementation policy; the source constraint alone should not be described as a mandatory reader refusal rule.
- ADR 0085's Tree::print_field parsing is source-aligned, but reading the attribute in a model accessor is not accessibility delivery. Current public accessibility consumer has no call to Tree::print_field; ledger 12.7.9 should not claim complete reader accessibility from parser-only tests.

This is not a whole §12.7.8 or §12.7.9 certification. It does not re-audit field import/rename, page persistence, attachments, XFA, interactive widget behavior, or all accessibility semantics.
