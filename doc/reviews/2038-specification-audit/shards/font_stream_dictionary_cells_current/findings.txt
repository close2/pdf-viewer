# Embedded font stream dictionary cells

Baseline b901326c. This review is limited to effective §9.9.1 Table 125 and its nearby Type 1 completion / CFF length text, plus the §14.3.2 note about metadata on embedded font streams.

I rendered and inspected the primary page images. Table 125's caption and Length1, Length2, Length3 cells occupy physical page 368 (printed 353); the Subtype row continues on physical page 369 (printed 354). The NOTE 2 Type 1 fixed-content description and following CFF paragraph are on physical 369. EC3 page annotations on 368–369 do not alter these cells. The separate Table 125a on appended physical 1022 concerns ToUnicode CMaps only. Physical 730 / printed 715 contains §14.3.2 Table 348 and NOTE 1, which says metadata about embedded font files belongs on their program streams, not their font dictionaries.

Table 125 distinguishes writer constraints from the one direct processor command. Producers must state Length1 for Type 1/TrueType, and Length2/Length3 for Type 1, in decoded-byte units. A stated Type 1 Length3 of zero is different: the processor shall add 512 ASCII zeros and `cleartomark`. CFF programs do not need and shall not carry the three section lengths. These producer requirements do not themselves prescribe a reader refusal for missing/wrong entries.

The Length3=0 path is implemented at `pdf-font/src/program.rs::with_fixed_content`, called by `embedded_program` for Type 1 programs. The direct test `a_stated_length3_of_zero_restores_the_512_zeros_and_cleartomark` checks the original payload remains intact, the exact count of added zeros, and the required operator. It passes in `broad116.log`. The fixture is intentionally only a small parser-helper setup, not a complete conforming Type 1 font, so I treat it as a byte-transform assertion rather than end-to-end producer evidence.

There is also an actual valid Type 1 consumer. `pdf-model::font_paint_type_audit::embedded_painttype_2_is_ignored_for_type1_type1c_and_cidfonttype0c` creates a Type 1 program with proper Length1 and Length2 and `/Length3 0`, imports it in a PDF, calls public `LoadedFont::load`, and asserts a nonempty outline and the program's literal half-em advance before checking PDF fill/stroke controls. It passed in `broad116.log`. The test's main purpose is PaintType, so it is call-path evidence for the reconstruction but not an independent before/after-tail comparison. Combined with the direct literal bytes assertion, this is adequate coverage of the specified processor behavior; I found no distinct behavior gap to draft another test for.

One assertion should be read narrowly: `any_other_length3_leaves_the_program_alone` includes a `Length3 533` case, but its payload is the no-trailer `type_1_without_its_trailer()` bytes. The stated positive length and actual bytes do not match, so that is malformed producer input and not a conforming positive-Length3 control. Its missing-Length3 variants are similarly invalid Type 1 stream dictionaries because Table 125 requires that key. The test documents recovery behavior only; it must not be cited as valid positive-length producer coverage. The direct zero test and public zero test remain sound for their claims.

`Length1`, `Length2`, and `Length3` are also consumed by `stated_extent`: `/FontFile2` uses Length1 and `/FontFile` uses the Type 1 sum when judging a truncated filter; the stated extent is supplemental reporting on check-value damage. This is separate from ordinary Type 1 parsing, which finds its encrypted section from the program bytes. The direct damage tests assert exact stated extents, and §7.4 filter coverage is maintained in its own shard.

`Subtype` is required for a producer's FontFile3 entry and lists Type1C, CIDFontType0C or OpenType. The current parser chooses bare CFF or sfnt from the program signature and tolerates contradictory subtype metadata. A valid program has matching fields; the specification does not state that readers must reject a mismatch. Table 124's valid pairings are already reviewed in `embedded_font_format_cells_current` and are not recertified here.

Table 125 has no Metadata cell. The independent Table 348 NOTE 1 is a placement rule for optional generic object-level metadata, not a font-program parsing rule. `pdf-model::xmp::Xmp::read` accepts an arbitrary component dictionary, and `xmp::a_metadata_stream_on_a_form_xobject_reads_back` covers that generic route. No font loader consumes XMP and no current UI promises per-font metadata. I found no font-specific reader failure.

ADR 0459 is the current basis for extent use. ADR 0040's statement that the lengths were read by nobody predates that work and is stale historically. ADR 0475 correctly records current length use but its “still not executed” line about Length3=0 is superseded by `with_fixed_content`, the passing byte test and the current implemented §9.9.1 ledger row. This is a correction to old ADR prose, not a current conformance finding.

No Cargo command was run and no test was drafted: the explicit processor requirement has both a literal output assertion and a public consumer path. This is a partial Table 125 review, not certification of every font program or malformed stream condition.
