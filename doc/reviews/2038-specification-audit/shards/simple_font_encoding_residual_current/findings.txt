# Simple-font encoding residual: TrueType StandardEncoding fill

This shard is a focused source-to-public-API check, not certification of §§9.6.5.1/.4. I read the effective ISO 32000-2:2020(E) PDF and checked the printed footer on each source page: Table 112 is physical p. 338 / printed p. 323; the §9.6.5.4 mapping algorithm is physical pp. 341–342 / printed pp. 326–327; Table D.2 is physical pp. 871–873 / printed pp. 856–858; and Table D.4 is physical pp. 884–887 / printed pp. 869–872. Table D.2 row `currency` gives StandardEncoding octal 250 (= decimal 168). Table D.4 does not assign decimal 168 in MacExpertEncoding. I did not find a relevant EC3 correction changing these entries or the fill sequence.

The narrow sequential requirement is explicit in §9.6.5.4: for an Encoding dictionary the table is initialized from BaseEncoding, any Differences entries update it, and finally any undefined entries are filled using StandardEncoding. This applies when Differences is absent as well as when it is present; “any entries” is conditional. The main fixture therefore uses an explicit `/BaseEncoding /MacExpertEncoding` with no Differences. It avoids Table 112's embedded default-base interpretation and the recommendation against Differences on TrueType. A second, supplementary test uses a distinct Difference at code 40 only to check that overlay route; Table 112 says that form should not be used with TrueType, so it is not the premise for the clean fill finding.

The current code path raises a concrete concern. `truetype_code_table` calls `encoding_names` with Standard fallback enabled for nonsymbolic fonts. `encoding_names` first chooses a present BaseEncoding, copies its 256 names, applies Differences, and does not subsequently fill remaining empty slots. Thus the Standard fallback only becomes the *base* when BaseEncoding resolution returns none; it is not a post-Differences fill. For the proposed MacExpert case, a still-empty code 168 can reach the later reader-chosen direct-cmap fallback. This can return a glyph, but the source clause has already specified its mapping. A `reader_chosen` mark would not make that alternative compliant for this covered mapping.

The public exact-xref draft `drafts/truetype_standard_fill_dictionary.rs` embeds the checked-in Liberation Sans TTF and uses the exported `pdf_font::LoadedFont` API. Independent fontTools/sfnt values for the checked-in file (SHA256 `f8ace1f892b2bd9dc1792ba7f097fa7588f84fed48321480e04de5390828221f`, UPM 2048) are: `currency` GID 101 / hmtx 1139; `dieresis` GID 105 / hmtx 682; and `parenright` GID 12 / hmtx 682. It declares matching PDF widths 556 and 333. The WinAnsi code-168 control expects `dieresis`/105, advance 0.333; the clean MacExpert code-168 target expects Standard-filled `currency`/101, advance 0.556. A second, optional MacExpert + Difference code-40 control expects `/parenright`/12; this only tests overlay separately and is not required for the clean target. The tests assert nonempty outlines, the stated `/Widths`-driven advance and independent program `hmtx` advance, plus exact xref/no recovery. These controls distinguish Standard fill from both WinAnsi and direct code-to-Unicode cmap mapping.

The draft is not run. It is a candidate source-derived regression, not evidence of a current failing test run. Parent should validate all producer premises and execute it before recording a durable defect. Its main case uses the clean Encoding-dictionary/MacExpert-base form with no Differences; the supplemental Difference case alone carries the Table 112 SHOULD qualification. It asserts glyph selection and font advances through the public font API, not final page pixels or extracted text. It intentionally covers one code and one TrueType font only.

The prior shard's `standard_encoding_fill_liberation.rs` should not be promoted as proof of the absent-BaseEncoding case without resolving a source interaction. Table 112 says an embedded program supplies the default base when BaseEncoding is absent; Liberation's cmap maps codepoint 39 to `quotesingle`. §9.6.5.4 separately describes a StandardEncoding final fill as part of the nonsymbolic/dictionary glyph-name-table algorithm. The precise integration of that default base with the dictionary algorithm needs a bounded source reading, so I do not assert either interpretation here. The new explicit MacExpert-base fixture avoids the absent-BaseEncoding question.

I did check the controlling branch of §9.6.5.4: it applies when the font has a named MacRoman/WinAnsi Encoding **or** the descriptor's Nonsymbolic flag is set; the draft uses Flags 32 and an Encoding dictionary, so the latter condition selects the table-building algorithm. The next paragraph explicitly distinguishes a font with no Encoding entry or a Symbolic flag. Because the fixture states an Encoding dictionary, states Nonsymbolic, and supplies a BaseEncoding, neither the missing-BaseEncoding default nor the no-Encoding direct-cmap branch controls the target.

MacExpert table data was not re-transcribed. Existing `encoding.rs` tests cover representative values, sparse code behavior and 165 assignments. The Annex D scratch comparison `scratchpad/r2038/spec-audit/annex_d_encoding/drafts/compare_local_annex_d.py` reports source/implementation 165/165 with zero MacExpert mismatches; this is useful repeatable scratch evidence, not an in-CI assertion. No full MacExpert assignment defect or user-visible MacExpert corpus issue was found here.

## Decision review

ADR 0286's choice to implement Annex D.4 MacExpert instead of rejecting it remains justified: Table 112 permits the base and the independent table comparison found no assignment mismatch. ADRs 0015 and 0067 remain consistent with the ordered TrueType route and distinguish normative routes from the processor-choice permission. ADRs 2677/2683 correctly keep code tables per font dictionary. None supports skipping a defined §9.6.5.4 fill step. The source/test gap is more specific than a general “StandardEncoding default” claim and should be tracked against the sequential algorithm above.
