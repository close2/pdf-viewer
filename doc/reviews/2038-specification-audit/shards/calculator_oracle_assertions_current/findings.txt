# Calculator supplemental-oracle review

I verified the worktree root as `/home/cl/projects/pdf-viewer/.claude/worktrees/r2038-audit`. This is a bounded review of the supplemental evaluator and its named corpus/device tests for §§7.10.1, 7.10.5.2 and 7.10.5.3; no Cargo commands or tests were run.

The independent expectations are useful: each corpus case stores explicit numbers or an explicit error/refusal plus a source citation. The gate `every_expectation_agrees_with_the_reference_evaluator` checks the separately written evaluator against those constants. The device sibling compares the GPU against the evaluator, documents the precision bound as a WGSL test instrument rather than ISO precision, and counts skipped/refused/compared cases so an empty run is not silently green. The two tests answer different questions and should not be described as a single production-vs-standard oracle.

For §7.10.1, `corpus/clipping.rs` contains controls and discriminators: the clause's upper-domain example (6 clipped to 1, result 3), the lower endpoint, an input already within Domain, a second-input-only clamp, the clause's lower-Range example, upper-Range clamp, and distinct output-component bounds. The expectations are literal, not obtained by calling the reference. The GPU harness explicitly skips four out-of-Domain cases because its Type 1 shading consumer discards those points before invoking the function; this correctly narrows the device assertion while retaining the reference-only check. `reference.rs` hardcodes a four-number Domain and refuses more than two inputs because this harness specializes to the two-input Type 1 shading. The PDF model evaluator accepts a variable-length Domain up to its own configured limit. I treat the supplemental harness as bounded rather than generic m-input proof; this is not by itself a production failure.

For §7.10.5.2, the current ledger names targeted operator tests for stack effects, tie rounding, exact equality, integer division/remainder, atan quadrants, boolean/bitwise distinction, overloaded `not`, integer-preserving arithmetic and bitshift. The source's semantics delegation to PLRM is normative; the corresponding operator cases are not derivations from Table 42 alone. ADR 0369 records earlier round/equality fixes and the choices/limitations made where the available source does not decide. ADR 0412 changes the former boolean-as-number behavior for provable boolean inputs to `ge`/`gt`/`lt`/`le`; the current ledger and code must be read after that successor rather than quoting ADR 0371 historically. EC3 #269 and #669 correct Table 42's `If` spelling and RIGHT CURLY BRACE hex respectively; these are editorial corrections, recorded in `doc/errata-read.md` under the next heading due annotation placement. They do not change operator semantics.

For §7.10.5.3, the reference uses an operand stack capacity of exactly 100. That is a lawful implementation choice: the source requires room for at least 100, does not require more, and makes overflow an error. Its 101-push refusal is not a reader obligation. The output-count and non-number cases are directly tied to the clause and have literal outcomes. Empty-stack-pop returning integer zero is a different question: while §7.10.5.3 itself does not spell out underflow, §7.10.5.2 normatively delegates operator semantics to PLRM3, and the existing 1983-specification audit records the PLRM3 stack-operator entries as specifying `stackunderflow`. ADR 0339's zero fallback is retained only as a qualified recovery policy; the 1983 audit disposition calls it a semantic gap for malformed programs, not a standards-derived choice. Current `Function::eval` remains infallible for underflow and `EvaluationFault` has no underflow member, although later watch/report machinery exists for other Type 4 runtime errors. The older ADR 0339 per-pixel/report-cost rationale should be reconsidered against this changed baseline; I did not remeasure underflow population or reporting cost, and this bounded oracle review proposes no API change. The sibling `functions_current` review records a separate production 100-entry positive-capacity test and separate runtime-error-report caveats.

No new test draft is warranted from these inspected supplemental files. Remaining limits: this does not certify all Type 4 operators or PLRM3 details, all generic m/n inputs, all function consumers, production evaluator internals, or host-visible reporting of future device-side faults. Current ledger excerpts are at `doc/conformance/ledger.toml` around lines 995, 1043 and 1051; effective primary source excerpts are in `scratchpad/r2038/spec-audit/ec3-parent-layout.txt` around 7974, 8454 and 8495, with corrected source locators physical138/printed123 (§7.10.1), physical146/printed131 (§7.10.5.2), and physical147/printed132 (stack/input/output rules of §7.10.5.3).
