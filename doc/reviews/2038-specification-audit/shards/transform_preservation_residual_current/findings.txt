This shard audits one narrow cross-layer boundary: a real §7.5.6 incremental save of an already signed file and the signature evidence visible afterward. The effective primary is ISO 32000-2:2020 PDF with EC3 checked; no EC3 correction changes this boundary. §7.5.6 printed pp.60–61 / physical pp.75–76 requires appending changes while leaving original contents intact. §12.8.1 NOTE 1, printed p.568 / physical p.583, says a valid signature's covered data is preserved by an incremental update so the document state at signing can be recreated. ADR 1003's reading of the signing-time revision remains sound.

Implementation is aligned in the inspected code. `pdf-syntax::write::incremental_update_extending` copies original file bytes as the prefix, serializes replacements in an appended section, and links a new cross-reference section to the previous one. On encrypted files, it sends replacement objects through `Document::encrypt_for_update`; the signature `/Contents` exception is shared with read-side decryption, while xref-stream and `/ID` cleartext cases are constructed outside the encryptor. `pdf_signature::Signature` separately reports digest integrity, key authenticity, and range coverage. The viewer's notes path reports an appended tail as bytes not covered by a signature.

The existing assertions are good but disjoint: `signature.rs::a_signed_document_says_whether_its_signed_bytes_moved` checks a signed fixture, a changed byte within the signed range, and an arbitrary raw comment appended after it; `pdf-syntax/tests/incremental_update.rs` writes a real update, reopens it, checks exact-prefix preservation, and has an encrypted update round trip that ensures plaintext does not leak. The checked-in `pdf-signature/tests/fixtures/docmdp_dts/base-signed.pdf` is already a real signed input; the DocMDP DTS tests independently exercise its integrity/authenticity. I found no existing test that composes this signed input with `incremental_update` and then rechecks signature integrity, authenticity, and an unsigned tail.

`drafts/signed_incremental_save_boundary.rs` supplies that integration candidate: open the signed fixture with exact xref/no recovery, verify the original signature, write a standard catalog `/Lang` value via the public incremental writer, check the original bytes remain a prefix, reopen, and assert the signature is still cryptographically unchanged while its current-file coverage reports a positive unsigned tail. This is only evidence that the old signed revision remains verifiable. It does not assert external trust, revocation, or that the new catalog edit is permitted by the fixture's certification transform; that separate question belongs to DocMDP's revision comparison. The draft is uncompiled and unexecuted.

No production issue established. ADR 1043's prefix/revision comparison and ADR 0129's encryption mirror/exemptions were inspected only at their interfaces. Existing tests already cover encrypted update behavior and clear signature contents, so this shard does not create a duplicate crypto case or infer a combined encrypted-signature requirement. Parent should promote/run the standalone draft if the composition check is useful. No Cargo, Git, production, or ledger changes.
