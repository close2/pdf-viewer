# External stream parameter cells and resolver boundary

This review covers Table 5 `/F`, `/FFilter`, and `/FDecodeParms`, plus the matching §7.4.1 references. The actual Table 5 caption and rows are on physical page 47 (printed 32) for F and FFilter, and page 48 (printed 33) for FDecodeParms. Section 7.4.1 is on physical pages 49–50 (printed 34–35). The primary PDF confirms that `/F` is optional from PDF 1.2; when present, its external file is the source and embedded stream bytes **shall be ignored**. `/FFilter` and `/FDecodeParms` describe filtering of that external data. Section 7.4.1 says the PDF reader shall apply corresponding filters; it names FFilter/FDecodeParms for an external stream. It does not say that processors must access arbitrary files or URLs.

The direct reader path is deliberate. `Document::is_external` tests whether `/F` is present, and decoded stream, image stream, and source/pump APIs refuse external bytes before ordinary filter execution. The public syntax test `spec_stream_objects_audit::an_external_stream_is_refused_while_the_same_embedded_filter_decodes_without_f` has an exact-xref control pair over identical embedded ASCIIHex bytes: without `/F`, the decoded page-content bytes are literal and can be pumped; with `/F` and `/FFilter`, both `stream_source` and `decoded_stream_data` refuse, as does nested content. This provides direct evidence for the effective #10 correction. The viewer and sandbox do not have filesystem/network access, so the refusal preserves the Table 5 distinction instead of mislabeling ignored embedded bytes as the external source.

The external keys do have a separate, explicit consumer path in archive conversion. ADR 1199 supplies caller-resolved data through `ArchivePlan::external_data`; the converter's opt-in local resolver reads only a plain name beside the input, refuses URLs and paths escaping that directory, and passes data into a pure conversion plan. `external::embedded_stream` transfers FFilter/FDecodeParms to ordinary Filter/DecodeParms, replaces data and recalculates Length. The current archive test `the_external_filter_becomes_the_streams_filter` supplies Flate data, but its Predictor 1 parameter is a default and it checks key spellings rather than decoded samples. Thus it does not prove a nondefault FDecodeParms value survives the whole transform.

I drafted `drafts/external_filter_decodeparms_archive.rs` for that narrow gap. It uses a one-row Flate-encoded PNG Up payload. With Predictor 12, Colors 1, BPC 8, Columns 4, decompression first produces `[2, 'q', LF, 'Q', LF]`; the first Up row subtracts zero prior-row bytes, so the independent expected decoded Form stream is exactly `q\nQ\n`. It supplies those bytes directly to the existing archive plan helper, then opens the rewritten document and checks the public stream decoder returns the literal bytes with no damage. This is a test of the converter's caller-supplied-data route; it does not add file/network access to viewing. The draft is unrun and parent-owned.

ADR review is recorded in decisions.json. ADR 0014's confined decoder boundary and ADR 0104's read-versus-follow distinction remain sound for the viewer. ADR 1199 is a distinct built converter path; it supports the proposed in-memory assertion but does not turn the viewer into a resolver. ADR 1176's orphan FFilter/FDecodeParms interpretation is retained; `a_filter_key_with_no_file_is_removed_and_nothing_else_changes` already checks the archive transformation. No mandatory behavior is inferred for malformed external-key combinations, and no arbitrary file or network access is proposed.

No Cargo command, Git operation, tracked edit, production edit, or subagent was used. Only the scratch artifacts and unrun test addition were written. No whole-clause certification is claimed.
