Scope: effective ISO 32000-2:2020 §§12.9–12.10 (EC3), current ledger, current tests and public consumers. The EC3 extraction is in `scratchpad/r2038/spec-audit/ec3-parent-layout.txt`; defining locators are printed 597–600 for measurement tables/algorithm, 602–605 for geospatial tables, and physical pages are the printed page plus 15. I checked the defining text and footer rather than assigning a page from a section heading. EC3 annotations for #533/#534/#284/#358 are on physical 618 (printed 603); #321 is physical 619 (printed 604), as recorded in `doc/errata-read.md`.

§12.9 is materially implemented. The model's first-point viewport and per-axis conversion test uses distinct viewport dictionaries, different conversions and literal output (18.36 u vs 5 pl). The public viewer test proves the selected viewport name changes when reversing a path across the inset boundary, but both dictionaries reference the same `/Measure`, so it cannot detect choosing the wrong viewport for the numeric scale. The end-to-end public formatting test calls `Query::Measure` but only asserts that the output begins with `0 mi`, contains ` ft ` and ends with ` in`; it would pass many incorrect distances. The standard's own exact formatted example is independently checked in the lower-level model test. Draft `drafts/public_measure_numeric_selection.rs` adds a standalone public-query fixture with exact xref entries and separate 0.01/0.02 scale controls, asserting literal `1 u` / `2 u` results for opposite path directions. This addresses assertion depth, not an observed implementation defect.

§12.10 also has substantial implementation and evidence, within explicit limits. Public Query tests locate a geographic viewport's center to independently stated coordinates and convert a geographic point into a projected `/DCS` with stated easting/northing tolerances. Projection methods are a selected finite set tested against the cited IOGP Guidance Note 7-2 examples; WKT/ISO 19162 parsing and EPSG behavior are likewise bounded, with code-only EPSG declined. These do not certify all EPSG, ISO 19162, datum operation, grid, epoch, projection method, or coordinate-system behavior. §12.10.2's projected eastings/northings requirement has a ratified departure in ADR 1918/A271 for degree-shaped registrations; do not mistake this for implementation of the unmodified source rule.

EC3 issue #534 is effective evidence for `/PCSM`: it defines an affine 4×4 matrix in row order acting on `[x y z 1]` and limits application to projected GCS. Existing tests distinguish order and translation with asymmetric values. Issue #533 changes `/LPTS` from Optional to Required; standard-valid fixtures should include it. Issue #321 corrects the internally contradictory prose from “either or both” to “any”; the mutually exclusive Table 270 entries already drove the parser, so no behavior change is due. #284 extends triples into RichMedia annotation scope; that separate annotation pathway is not covered by the page viewport code and is outside this audit's supported scope.

Table 269's PDU is explicitly “Preferred Display Units” (linear, area, angular), while the DCS row says the processor controls formatting of displayed position values. The host currently reports positions as decimal degrees and displays supported projected DCS values in the projected system. Model parsing exposes PDU, but I found no public consumer applying the linear/area preferences in the position-only query. ADR 1593 chooses decimal degrees and states that the angular PDU is for angles, not positions. I did not find a strict source rule mandating how this UI should apply PDU, so this is not a confirmed conformance failure; qualify any ADR/ledger wording that presents the local interpretation as a mandatory source rule. Point-data values are parsed/preserved as PDF objects and dimensions are tested, but no viewer consumer was found. Table 272 describes custom point-data columns without a display workflow, so current user-facing omission is not established as a defect. The ledger's `implemented` claim should describe read/preservation narrowly.

Selected ADR review is in `decisions.json`. Key residuals are accurate finite geospatial support, the explicit projected-degree departure, incomplete public numeric assertion for §12.9, and no identified consumer for PDU/point-data in the current UI. I found no other source-backed defect within this bounded shard.
