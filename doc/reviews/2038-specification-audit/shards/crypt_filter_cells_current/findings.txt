This is a narrow cell-and-assertion review, not certification of §7.6 or the encryption subsystem. The primary EC3 Table 20 and Tables 25–27 were checked in the source PDF/layout, and annotations on the relevant physical pages were read directly. Table 21 EncryptMetadata is physical p.94 / printed p.79 (Table 21 begins on physical p.93 / printed p.78). The effective corrections matter: #74 permits crypt filters at V=5; #184 distinguishes Length units for public-key and Standard handlers; #16 changes Table 27 CMS recipients to byte strings; #25 limits the public-key 0xFF sentinel to the StmF/default-key metadata-plaintext condition. None changes Table 20's defaults or EFF rule.

The main default routes are represented by public consumers. The clause-derived R4 fixture `an_identity_stream_filter_leaves_streams_and_decrypts_strings` checks both a literal page stream and Info Title with `/StmF /Identity` and `/StrF /StdCF`; the corpus test independently checks an actual Identity stream's bytes. The EFF test uses a real corpus PDF, removes the embedded stream's own Crypt selector so EFF is observable, then removes EFF as a control and checks exact stream bytes fall back to StmF. The paired AuthEvent tests make opening and attachment refusal distinct. Static traversal agrees: `document/encryption.rs::stream_filter` gives an explicit Crypt filter precedence, then uses EFF for embedded-file streams and StmF otherwise; `crypt_filters` stores absent EFF as StmF.

One small assertion gap remains: the source-specific absent defaults are not isolated from one another in the sampled tests. The insertion draft in `drafts/absent_stmf_strf_identity.rs` uses the existing exact-xref R4 fixture builder and literal stream/Title values. Along with both-absent and explicit-Identity controls, it omits StmF while setting StrF to AESV2, then omits StrF while setting StmF to AESV2. Thus an implementation that incorrectly copies the other default instead of selecting Identity fails at an observable plaintext consumer. The draft also asserts no recovery. This is a test-coverage candidate only; the code branch itself is explicit and no defect is alleged. It does not overlap the known public-key B57 defect for two *different named* default filters.

EncryptMetadata is split by handler and must not be merged into one rule. Standard-handler Table 21 (physical p.94 / printed p.79) defaults true for V=4/5; false affects legacy R4 key derivation and exempts the document-level Metadata stream. Tests check an R4 false-key control, corpus plaintext XML when false, and writer output with false. R6 writer bytes including the Perms metadata byte are independently pinned. Public-key Table 27 instead places EncryptMetadata on a crypt filter and says it is used only when referenced from StmF; EC3 #25 narrows the key-derivation sentinel accordingly, covered by the public-key corpus witness audit. A missing-key R4 Metadata-stream positive is not in the sampled assertion set; this is a residual, not a proven failure.

The Table 25/27 cells have source-matched controls: CFM supported/unsupported behavior, AES method and key-size pairing, DocOpen default, EFOpen deferral, StmF/StrF AuthEvent coercion, Identity pass-through, Table 27 stream-local single CMS value and default-filter recipient arrays, and Length unit interpretation. B57 is specifically the existing failure for distinct public-key StmF/StrF recipient arrays; the shared-filter control passes. It is not repeated here. The R6 mismatch/tamper behavior is malformed or nonconforming-input policy and remains separate from valid-entry coverage.

No new production issue is asserted. Tests were inspected but not executed in this shard; the proposed omitted-default test remains an unrun scratch draft. No claim is made about every cryptographic algorithm, every recipient/profile combination, or all invalid encryption dictionaries.
