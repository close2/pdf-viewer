# Image filters remaining: selected source/assertion review

This bounded pass covers selected behavior in effective ISO 32000-2:2020 EC3 §§7.4.8–7.4.10. The defining locations are DCTDecode physical PDF pp.63–64 (printed pp.48–49), JPXDecode physical pp.65–67 (printed pp.50–52), and Crypt filter physical p.67 (printed p.52). Parent layout mapping is `scratchpad/r2038/spec-audit/ec3-parent-layout.txt`; physical primary PDF annotation #29 is preserved at `errata-29-primary-page.png`.

For DCTDecode, Table 13 is on physical p.64 / printed p.49. Current `dct.rs::adobe_transform` reads the JPEG marker stream through the frame header and first scan; `colour_transform` selects the marker value, filter DecodeParms value, or Table 13 default by frame component count. `colour_transform.rs` gives direct pixels for the decisive precedence pairs and arithmetic controls. Separate tests cover one/two component ignore and the three/four-component behavior. The foreign APP14 identifier control distinguishes the Adobe marker identifier from an arbitrary APP14. This substantially exercises Table 13, but does not certify all Adobe TN #5116 marker semantics or every progressive JPEG process; progressive support is explicitly SHALL in §7.4.8 and remains an unenumerated residual here. ADR 1183's old no-marker RGB-name departure was superseded by ADR 2468; the current default is supported by direct arithmetic and identity controls. ADR 0203/0266 retain their bounded component-count decisions.

For JPXDecode, the annotation on physical p.65 changes “except for” to “excluding” in the PDF-data producer restriction. T.801 M.9.2.4 includes enumerated color space 19 (CIEJab) in the JPX baseline, but the corrected effective PDF 2.0 producer statement excludes enum19 from data used in PDF image XObjects. On physical p.67 / printed p.52, a distinct processor sentence says PDF processors shall support the JPX baseline set of enumerated color spaces, which still includes enum19. This adjacency leaves a bounded scope question: the producer restriction means this shard cannot construct a conforming PDF witness for the separate reader-support sentence, and it does not infer that the processor obligation disappears. Current fallback for enum19 is not promoted to a behavior defect from these facts alone. Existing enum19 cases remain malformed-input recovery or stated-ColorSpace override controls. No conclusion about legacy PDF versions is made.

`jpx_colour_choice` implements dictionary ColorSpace override, ranks candidate data color spaces by descending precedence, better approximation, then file order, and uses channel-count Device fallback when none is usable. Existing tests include full JP2 packages and direct pixel controls for supported choices, override, and fallback. The valid package controls avoid mistaking bare codestream tolerance for proof of the “full JPX file structure” expectation. The explicit unsupported-ICC lower-choice SHALL is not independently proven: current tests exercise unsupported enumerated choices, but this review did not validate a profile that is conforming input and unsupported by this implementation, then pair it with a lower supported space. Do not use the current synthetic/unsupported enumerated fixtures as a substitute for that profile. Prior B14 premultiplied-opacity behavior is excluded.

For Crypt, §7.4.10 states the Crypt-first filter ordering and says DecodeParms Name names the crypt filter. The actual data decryption route is in `document/encryption.rs::stream_filter` and `crypt.rs::decrypt_stream`; `filter.rs::decode_reported` treats the Crypt decode stage as pass-through because decryption occurs at the stream/object boundary. `public_key_witnesses.rs::a_stream_s_own_crypt_filter_decrypts_under_its_own_recipients_key` uses a non-Identity stream-specific filter with a source-documented CMS/key fixture and asserts the decrypted text for both the document key and the filter's own recipient list. Its companion unauthorized-recipient test checks refusal of that stream while the document remains open under EFOpen. This is actual reader integration, unlike a helper-only mapping check. A Crypt entry in a non-first location would violate the producer requirement, but no required reader rejection response is inferred. Prior CFIdentity B07 coverage is not relied upon here.

No test draft was added: the selected Table 13 behavior already has discriminating assertions; a new JPX unsupported-ICC fallback test needs an independently validated profile that is valid for the applicable JPX method and genuinely unsupported by the current profile reader; and the named Crypt route already has an end-to-end, independently generated CMS fixture. The shard remains partial and makes no whole-filter or cryptographic certification claim.
