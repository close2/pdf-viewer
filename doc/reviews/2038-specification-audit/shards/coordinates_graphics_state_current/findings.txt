# Coordinate systems and selected graphics-state defaults

## Source boundaries

Primary source is the EC3 layout at `scratchpad/r2038/spec-audit/ec3-parent-layout.txt`, grounded at its defining headings and page footers. Figure 9 is §8.2 printed p.148. It draws a hard object-context boundary: path construction starts a path object and remains there through W/W* until path painting; only path-construction and clipping operators are permitted in that interval, not q/Q/cm. The example explicitly contrasts path construction with general graphics-state operators. The NOTE says a reader *can* process sequences violating those graphics-object rules, but behavior may be unpredictable; that is permission to be robust, not a valid producer-conformance witness.

Coordinate source: §8.3.2.3 printed p.150 says default user space has x right/y up, CropBox defines the visible region, Rotate alters axes, and UserUnit changes unit size with default 1/72 inch. §8.3.4 printed pp.155-156 defines matrices and says new transformations concatenate before the current transform; multiplication is noncommutative. Table 31 printed p.121 identifies Rotate/UserUnit and inheritance. §7.7.3.4 controls nearest-ancestor inheritance. Table 51 spans printed pp.157-158, and Table 52 starts at p.159; §8.4.2 stack rules print p.160; Table 56 operators print pp.164-165. No in-scope erratum to these passages was identified in `doc/errata-read.md`.

## Validity check for the path/CTM concern

The possible “cm or q/Q mid-path” concern is not a valid-input defect. `graphics_stack_paths_audit.rs::q_and_q_operators_leave_the_current_path_outside_the_stack` builds `10 10 m q 20 20 l Q 30 30 l S`: q and Q occur while Figure 9 says a path object is open. The test helper asserts exact xref and complete interpretation, but syntax/xref validity does not make its graphics-object sequence conforming. It remains useful as a robustness/recovery-policy witness, as the parent requested. Proposed correction to its test comment is in `decisions.json`; do not delete the test or cite it as §8.4.2 conformance proof.

There is valid evidence for q/Q: `line_parameters.rs::the_stack_saves_and_restores_them` places q/Q at content-stream level and checks restored line cap, join and miter; `graphics_stack_paths_audit.rs::nested_restores_pop_the_most_recent_graphics_state_first` and `clipping_is_deferred_until_paint_then_restore_returns_the_prior_clip` use q/Q around completed path objects and assert nested/restored clips. The `a_pending_clip...` test likewise restores after painting. These tests assert specific state facets, not every graphics-state property.

## CTM and page-coordinate evidence

`content/run/graphics.rs::run_graphics_state_op` composes each `cm` as `matrix.then(state.transform)`, which agrees with §8.3.4's new-before-existing rule under `Transform::then`'s documented application-order semantics. `page::build_page`, `content::displayed_size` and `base_transform` read CropBox/display area, Rotate and leaf UserUnit; the base map translates the selected page-box origin, rotates clockwise into the positive quadrant, then scales by UserUnit. `image_coordinates_audit.rs` is a valid exact-xref raster test of a single scale, reflection and skew; `page_geometry.rs` tests UserUnit dimensions and mark placement, inches, inheritance, offset CropBox and leaf override; `content.rs` maps all four rotation corners at 0/90/180/270. These are good component checks.

A focused gap remains for the composition path: I found no independent assertion that sends *two noncommuting cm operators* through the PDF parser/interpreter together with a non-origin CropBox, page Rotate and UserUnit, then observes both the final geometry and Q restoring the initial CTM. `Transform::then` has a unit order test, but it does not test PDF `cm` dispatch or page-base composition. `drafts/coordinate_graphics_state.rs` proposes an exact classic-xref fixture with a valid Figure-9 operator sequence, `Document::was_recovered() == false`, direct expected matrices and raster-point controls for the combined path and post-Q path. It has not been compiled or executed.

## Initial state and defaults

`GraphicsState::initial` supplies Table 51/52 values through `Stroke::default`, `Intent::Relative`, black/Gray color, Normal blend, no soft mask, alpha 1, default black-point compensation, false overprint/AIS, zero OPM and device-dependent values left as implementation defaults. `Stroke::default` supplies width 1, butt cap, miter join, miter 10, solid dash, stroke adjustment false. Existing assertions in `extgstate_missing_line_keys_audit.rs::the_initial_line_parameters_match_table_51` and `line_parameters.rs::the_initial_values_are_table_51s` substantiate selected line parameters, while the content/display tests exercise clip and color outcomes. This audit did not check every field in either initial table. Table 52 expressly leaves several initial values suitable/device-dependent; renderer-selected values there are not fixed ISO values.

## Limits

No nonconforming producer data is turned into a mandatory rejection rule. In particular, `/UserUnit` range is implementation-dependent; current upper bound 1000 is the program's supported range. A non-multiple or negative `/Rotate`, invalid CropBox and missing required MediaBox recovery are not normative duties unless another clause states one. The default initial clip is enforced at the target/page boundary rather than stored in `GraphicsState.clip`; current raster evidence confirms the visible effect, but internal consumers outside this path were not audited. This pass does not certify all coordinate spaces, every parameter in Tables 51-52, or every backend's inverse-transform behavior.
