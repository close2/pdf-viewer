# Compatibility operators and extension declarations

This bounded source and assertion pass covers §7.8.2, §7.12.1–.6, Annex E.1–.2, and only the Annex I compatibility handoff that §7.12/Annex E invoke. Defining source pages are §7.8.2 physical PDF p.126 / printed p.111 and Table 33 physical p.127 / printed p.112; §7.12 physical pp.156–158 / printed pp.141–143; Annex E physical pp.892–893 / printed pp.877–878. Primary rendered pages are kept in this directory. The errata images show #732 on physical p.157, #399/#239 on p.158, and #229/#340 on p.893.

`content_streams.rs` directly checks unknown operators outside BX/EX are reported; balanced unknown operators inside are silent; an unknown operator after the matched EX is reported again; and a nested inner EX leaves the outer section active. `run_from` clears ignored operands and uses the depth in `Machine.compatibility`, matching Table 33's “along with their operands” and “may be nested.” The tests inspect reports, but the test named “drawing around it still happens” does not assert pixels. `drafts/compatibility_operator_pixels.rs` is a public-render draft comparing a valid balanced unknown-operator section against an independently stated ordinary fill control, with exact xref and a visible center-pixel assertion.

Unmatched BX and stray EX are separate malformed-input boundaries. Table 33 says BX/EX shall occur in pairs, but ISO gives no recovery semantics for an unpaired operator. Current code increments BX nesting, saturating-decrements EX at zero, and `report_leftover` discards the leftover compatibility depth. Thus stray EX is treated as a no-op and unmatched BX can suppress unknown-operator reports through stream end without a specific diagnostic. This is a product-policy residual only; the source's writer-side pairing rule does not justify a reader defect claim. The existing “silence stops at matching EX” case is paired and then tests an outside unknown, not a stray EX.

§7.12 states catalog `/Extensions` and required nested direct objects. Table 48 supports one developer extension dictionary or, in PDF 2.0, an array; Table 49 names BaseVersion and ExtensionLevel as required, URL is required by EC3 #732, and ExtensionRevision is optional. The effective source differs from base `doc/md` on URL, and the primary annotation on physical p.157 confirms the change. The public model parser reads the prefix map and PDF 2.0 arrays. Its unit test checks two prefixes, two ISO extensions in one array, URL on one item, and retention of a second item missing the now-required URL. That is an intentional reader tolerance, not producer conformance. A separate assertion checks missing ExtensionLevel; no focused assertion covers missing BaseVersion. The code does not compare BaseVersion with the PDF version and does not enforce registered prefix names or direct-reference rules. Those are producer constraints; no required reader rejection was found.

EC3 #399 changes text in §7.12.4's BaseVersion comparison; #239 changes the monotonic ExtensionLevel-over-time wording to a recommendation. Neither changes the selected parser route: it preserves version names and integer levels rather than validating producer chronology or document-version eligibility. Annex E #229 refines a second-class-name exception and #340 expressly prohibits registering private `XX` names. Both remain name-generation rules. No current production writer was found that emits a developer extension, so the producer requirements have no current output witness.

Annex E.1 sends processors that do not support developer-specific features to Annex I; it does not demand rejection of an unfamiliar prefix. Existing `objects_not_understood.rs` asserts that an unknown dictionary entry is passed over while an unsupported object is named and supported content still draws. This is selected evidence for the Annex I per-feature distinction, not a full Annex I audit. `Extensions::read` is public but has no searched production caller or user-facing UI path; no statement is made that the viewer informs users about every declared extension. §7.7.4 is the Name dictionary/name trees, not the extension dictionary; that section is out of this shard.

The durable feature ledger already contains parent-reviewed Annex E and §7.8.2 rows. The clause inventory marks §§7.12 and 7.12.1–.6 implemented, but no dedicated §7.12.1–.6 feature rows were found in `doc/reviews/1983-specification-audit/features.json`. This is a traceability gap in the feature mapping, not evidence that implementation behavior is absent. ADR 0041 remains sound for the selected compatibility-depth behavior; no dedicated Annex E ADR was found.

No tests were executed. The compatibility pixel draft is the only new test proposal; unknown operator behavior is the only actual consumer path where current tests would benefit from a rendered control. No producer test is warranted while current writers emit no extension declarations, and no normative tests are proposed for unmatched BX/EX recovery.
