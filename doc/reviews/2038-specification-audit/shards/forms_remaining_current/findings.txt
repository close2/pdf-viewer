The assigned effective clauses are §12.7.5.5 “Signature fields,” §12.7.6.1 “General,” §12.7.6.2 “Submit-form action,” §12.7.6.4 “Import-data action,” and the signature-specific boundary of §12.7.4.3 “Variable text.” In EC3, §12.7.5.5 is printed pp.543–545 (physical PDF pp.558–560); Table 235 begins on printed p.544, and Table 236 / the signing condition sit across printed pp.544–545. Locators name the primary PDF's printed footer rather than guessing from physical page number.

EC3 annotations found at the boundary are #131, which adds the DSS/DTS-only exception to Table 236 `/P`; #680, which leaves Table 237 `/Ver` untouched; and #158/#159, which rewrite the `/DigestMethod` guidance. `doc/errata-read.md` records #131 at line 237, #680 at line 117, #158 at line 236, and #159 at line 1786. Those seed-value edits do not create an open-time validation requirement. The current signature field source calls `/SV` constraints for when a signature is applied; §12.8.3.4 also says seed values are not validation constraints.

The signature field's primary rules are distinct from its signature cryptography: FT is Sig; present V is a signature dictionary; the annotation rectangle supplies the location and an invisible signature field uses a zero-area rectangle; Hidden and NoView make it invisible; a field never refers to more than one annotation. For a visible field, AP *should* be created at signature time. AP exists for human rendering and shall not be used by verification; a processor shall not incorporate validity status into AP. The general variable-text machinery is not a signature-field value renderer: signature V is a signature dictionary rather than variable text.

The submit action's central obligation is an actual transmission of names and values to the specified URL. Table 239 selects fields and describes the URL/charset; Table 240 selects format, method and optional extras. Table 243 names the required ImportData file specification. “Any other data format” in §12.7.6.4 is conditional on what the processor supports; the current FDF and XFDF readers meet the formats this implementation claims to support. The clauses do not specify the host's filesystem/network consent policy.

## Concrete test-fixture defect: existing `/Lock` “signed” witness omits required `/Contents`

`crates/pdf-model/tests/forms_data.rs::form_locking` (line 653) manufactures `/V 9 0 R` with object 9 `<< /Type /Sig /ByteRange [0 100 200 300] >>`, with no `/Contents`. Table 255 in §12.8.1 says `/Contents` is required; §12.7.5.5 itself cross-references Table 255 when it defines a signature-field V. The neighboring test `a_signed_signature_field_locks_the_fields_its_lock_names` (line 698) then claims this object has been signed and uses it as the positive condition for All/Include/Exclude; `a_signed_locks_permission_entry_states_what_may_still_be_changed` (line 781) reuses it for `/P`. The test helper's comment says this is “the smallest one `signature::read` accepts” and “signs nothing,” which is direct evidence that it is only a partial parser fixture, not a signed signature value. This is a witness-quality gap, not proof that `field_locks` or `/P` production behavior is wrong.

I sent this issue to the parent before drafting. The scratch fix is a real independent witness: `drafts/generate_signed_lock_fixture.py` emits an exact-xref signature field with indirect Table 235 `/Lock`, a real `/Type /Sig`, `/Filter /Adobe.PPKLite`, `/SubFilter /ETSI.CAdES.detached`, a full `/ByteRange`, and a CMS `/Contents` signed over that range with OpenSSL `cms -cades` (including signingCertificateV2). ## Explicit residuals and implementation limits

The `/Lock`/`/P` positive evidence gap should be addressed with the CAdES fixture before anyone says the existing placeholder test proves a signed field. Parent should independently verify no recovery and run the Rust draft; neither this shard nor the fixture's external commands establish execution of the new Rust assertions. The fixture covers field-scoped `/Lock`, not `/P`; the latter existing tests share the old incomplete `/V` witness and still need a conforming signed control.

Table 240 bit 11, `ExclNonUserAnnots`, remains explicitly owed in `submission.rs`: selection is limited to markup annotations whose `/T` matches the current user *as determined by the remote server*. This viewer has no server-derived user identity channel, and the implementation reports the limitation and withholds this subset. Do not label this path fully conforming for contexts where the remote server identifies a current user. Likewise, do not interpret producer-side combinations marked “shall be used only when” as a mandatory malformed-input rejection rule for a reader.

`/SV` and its changed DigestMethod cells are not processed because there is no PDF signing operation here. The current source's use of seed values is at signing time, so this is a consumer/scope boundary rather than an open-time validation defect. The reviewed scope files and the owner's A800 answer do not establish a permanent ratified exclusion of PDF signing; revisit when there is a signing consumer. No exact-xref valid signed `/P` regression was drafted separately, and no all-host import dialog / submission policy test was repeated here.
