Soft-mask group `/CS` conditional: a narrow follow-up

The earlier `soft_mask_cells_current` matrix covered the Table 142 fields and public assertions, but its Alpha mask fixtures all supplied `/CS` on the mask group. I followed the conditional from Table 142 into Table 145 rather than treating that fixture convention as a requirement.

The primary EC3 text makes `/CS` conditional. Table 142 (physical p. 434, printed p. 419) requires the soft-mask group attributes to contain `/CS` when `/S /Luminosity`. Table 145's `/CS` row (physical p. 437, printed p. 422) says it is otherwise optional, defaults to the parent group or page's color space, and becomes required when an XObject group has no parent from which to inherit, specifically naming a Luminosity soft-mask group. The Alpha prose computes group alpha and says color compositing may be omitted. Therefore a valid Alpha mask group can omit its own `/CS` when the page group supplies one; an isolated Alpha mask group without any inheritable parent is not the right fixture for that case.

The table-cell review also checked the relevant primary annotations. Issue #134's Caret on Table 145 inserts “of the transparency group XObject” into the resource-dictionary sentence for default-space remapping. That affects which resource dictionary controls a declared device space; it does not change the `/CS` inheritance condition. The fixture uses explicit `/DeviceRGB` on the page group and leaves the child mask group `/CS` absent, so it does not rely on a device default or test #134's remapping branch. No Table 142 annotation changes were found in the prior directly checked pages.

The ledger's 11.6.5.1 row is implemented and cites Table 142 behavior. `soft_mask::read` gets the group `/CS` but resolves it only in the Luminosity branch; Alpha derives from group alpha. The group interpreter receives the page/resource context. Source and code therefore agree on the conditional; no runtime defect is indicated. The missing direct assertion is narrow: current Alpha test fixtures consistently put `/CS` on the mask group, and the existing “no resources” case concerns inherited resources rather than inherited group color space.

I drafted `drafts/alpha_mask_inherited_group_space.rs` for parent integration into `crates/pdf-model/tests/soft_masks.rs`. It renders an explicit-child-`/CS` control first and then the valid inherited-space case. Both assert literal blue pixels inside the mask group's BBox and white outside; the second group omits `/CS`, is an Alpha mask, and inherits from a page group that explicitly names DeviceRGB. Both fixtures use exact xrefs; the draft guards against recovery and a cut xref chain, while the existing `render` helper requires complete interpretation. This draft has not been run and establishes a coverage candidate only.

This remains a bounded cross-reference check between Table 142 and Table 145, not a review of every Table 145 field, group inheritance behavior, or the wider 11.6.6 implementation. No malformed-input rejection requirement is inferred.
