# EC3 errata dispositions, batch 6

This review covers only #632, #656, #680, #691, and #731. I inspected their primary annotation objects, marked locations, caret contents, and corresponding effective text in `doc/ISO_32000-2_sponsored_EC3.pdf`. The page locations below are physical PDF page / printed footer.

**#632 — Table 383 `lb` label.** On physical p.806 / printed p.791, StrikeOut 7745 is paired with Caret 7746, whose actual Contents is “List box.” It replaces the displayed gloss “Listbox” after code `lb`; it does not change the code or role meaning. `FieldRole::read` already maps `lb` to `FieldRole::ListBox`. The parser test `a_flattened_form_field_says_what_it_was` does not test `lb`. Separately, `structure_attributes_remaining_current` identifies a larger reader-facing gap: §14.8.5.6 calls PrintField the accessibility mechanism for flattened noninteractive forms, but the parsed role/state/description is not carried through the public accessibility node. The tracked public viewer-core test lacks an lb fixture; parent reports its cb/rb role, checked-state, and description assertions failed while the title control passed at checkpoint26. That broader gap is not caused by the spelling edit. No new test was drafted here because it would duplicate the already identified consumer issue without settling its API representation.

**#656 — Geospatial/requirement table headings.** Text object 6096 at physical p.616 / printed p.601 says Tables 269–274 and 276 have an inconsistent third-column title and directs “Value” instead of “Description.” Paired marks show selected visible edits at Table 269 (p.617 / printed p.602), Table 273 (p.621 / printed p.606), and Table 274 (p.622 / printed p.607). The Text annotation itself applies the editorial correction to every named table, even where the underlying printed table still shows the old word; this is not an unimplemented runtime change. The key/value semantics are unchanged, and no behavior finding or test follows from the heading.

**#680 — Signature seed-value `/V`.** On physical p.561 / printed p.546, StrikeOut 5793 and Caret 5794 alter Table 237's `/V` definition. The caret inserts the PDF 1.7-and-earlier boundary and repeats the version-3 capability statement; read with the marked text, `/V 2` covers seed-value entries through PDF 1.7 and `/V 3` covers entries through PDF 2.0. This is the minimum capability of a seed-value-dictionary parser for the signing operation. §12.7.5.5 says those entries constrain signature application. The current viewer verifies signatures but does not apply signatures, so no such reader path is owed by this correction. Do not confuse Table 237 `/V` with the separate catalog `/Requirements` `/V` covered in the document-requirement shard; its tests are not evidence for seed-value parsing.

**#691 — Identifier uniqueness example.** StrikeOut 6784 on physical p.734 / printed p.719, using two QuadPoint bands to span a wrapped line, deletes “such as MD5 (described in Internet RFC 1321)” from the §14.4 `should` recommendation. It is separate from #328's two strikes narrowing the identifier descriptions to file contents. Writers still should attempt uniqueness, but the standard no longer names MD5 as its example or prescribes a digest. `write.rs::identify` and `serialize.rs::identify` use MD5 as a local choice and their comments recognize #691. `identifiers_procsets_current`'s classic and stream writer controls inspected both ID values and passed; incremental-update tests check preservation/change. These assertions do not establish MD5 conformance or collision resistance.

**#731 — Hexadecimal-string comments.** Text annotation 1497 on physical p.42 / printed p.27, §7.3.4.3, says whitespace is permitted within a hexadecimal string but comments are prohibited. The lexer ignores whitespace, tolerates other nonhex bytes while recording them in `HexadecimalStrings::strayed`, and the archive validator consumes that count. Thus a percent/comment sequence inside angle brackets is not interpreted as a PDF comment; it is malformed in-token data that the reader can recover from and diagnose. The source correction states a producer syntax constraint, not mandatory rejection. Existing lexer assertions cover all six whitespace bytes and record arbitrary stray bytes; a comment-specific fixture could be redundant with that category assertion, so no test draft was warranted.

No new confirmed valid-input behavior defect emerged. No test was run, and no Cargo, Git, production, or ledger mutation was performed in this shard.

Parent correction: the lexer test named ignore_junk has no junk case; the separate records_how_written test actually asserts the stray byte. Corrected Table269 annotation object IDs to6105/6106;5793/5794 belong to #680.
