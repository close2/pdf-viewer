## #200 — a conflicting Scope cell in the implicit header search

EC3 #200 applies within §14.8.4.8.3 on physical p.783 / printed p.768. Immediately before its new clarification, the current text says that if `/Headers` is unspecified, a cell “may” use the implicit search. The search conditions include a data cell found after a header and a header cell whose `/Headers` is set; the next sentence filters collected headers by Scope. The inserted prose says that a cell with Scope conflicting with the direction of the search “should not terminate” the search and, regardless of that cell's `/Headers`, “should not be added” to the list. Its example makes the column-search case explicit. Thus #200 constrains the implementation that uses this optional search; it does not make the algorithm mandatory for every reader.

The current reader has adopted the algorithm and returns its result through the public `Query::AccessibilityTree` answer. In `crates/pdf-model/src/structure.rs:1618-1631`, every encountered TH sets `after_a_header`; then `/Headers` resolution may append targets and return. Scope is checked only for appending the found TH at lines 1625-1627. A mismatched TH that carries `/Headers` therefore triggers an immediate return, contrary to #200's direct instruction that the conflicting cell should not terminate the search. It also resolves that cell's separately named IDs; the overlay clearly says the conflicting TH itself is not added but is less explicit about whether its named IDs contribute as the search continues. The test does not assert that disputed point. The separate question of whether a mismatched TH with no `/Headers` sets the state that lets a later TD terminate is also unresolved; no downstream-TD conclusion is made here.

The current ledger row `doc/conformance/ledger.toml:5940-5945` marks §14.8.4.8.3 implemented and claims that the data-after-header, header-with-Headers termination, and Scope filtering conditions are all implemented. It does not qualify that claim with the conflicting-Scope exception or cite #200. Existing `crates/viewer-core/tests/headless.rs:5393-5444::a_cell_is_given_the_header_cells_that_describe_it` is a real public-consumer test: it checks a row-scope cell being stepped over during a column search and ordinary header stopping. It does not test the case where that conflicting cell itself appears in the search, nor the case where that cell has `/Headers`. The existing array route and this implicit-search route should remain separate: this draft varies the discovered cell's Scope/Headers and reads the returned indexed nodes' literal names; it does not alter `/Headers` on the target cell.

The scratch draft `drafts/table_header_conflicting_scope.rs` supplies three public integration assertions from one fixture builder. It includes consecutive exact objects 1–20, an explicit structure IDTree with sorted `(conflict)`, `(far)`, `(middle)`, `(named)` IDs, a page ParentTree mapping MCIDs 0–6, valid Table/TR/TH/TD hierarchy, and correct stream length. Each case checks `Document::was_recovered() == false` before opening through the viewer. The grid has no intervening data cell on the column path: Target encounters conflicting `/Row` Conflict, then eligible `/Column` Middle and Far. Without `/Headers`, the expected names are Middle and Far; with `/Headers [(named)]`, the test requires continuation to Middle and Far and absence of Conflict, but leaves Named's contribution unasserted. A matching `/Column` control expects Conflict and Named and terminates. The test renders and queries actual public accessibility nodes and resolves header indexes back to names. I did not run Cargo; the parent ran an adapted promoted derivative (table-scope-wave55c): the no-Headers Row case and two matching-Scope controls passed; the Row-with-Headers case failed with `[Named]`, lacking Middle/Far continuation. Earlier fixture layout guards failed because extracted names included whitespace; parent corrected layout/label checks. Those are parent-reported results, not execution of this scratch draft.

ADR 0312 adopted this search, but it is narrowly incomplete on this edge: it quotes the search/filter language, explains why a data cell before any header does not terminate, and records the prior Scope filtering test. Its accepted date (2026-08-13) is after the #200 annotation modification date (2026-05-22), yet neither the ADR nor the ledger addresses the inserted exception. The action recommended here is to amend that algorithm discussion/test evidence for the conflicting-Scope case; the overall accessibility design and the optional-algorithm choice do not need to be reopened.

One preceding review sentence should also be corrected during artifact reconciliation: `doc/reviews/2038-specification-audit/shards/structure_types/features.json` says the relevant ledger note “discloses that limitation.” The current ledger note does not; it claims all four conditions are implemented. The limitation was this shard's discovery and should not be attributed to that prior ledger text.
