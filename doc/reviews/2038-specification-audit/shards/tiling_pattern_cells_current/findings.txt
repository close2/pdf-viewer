# Tiling-pattern dictionary cell review

I checked the effective primary PDF and Table 74 directly. The table header and its first rows are physical p.236 / printed p.221; the YStep, Resources and Matrix continuation is physical p.237 / printed p.222. Table 74 on p.236 includes EC3 #294’s caption edit adding “stream”; it clarifies the stream-dictionary form and does not change a field rule. Physical p.235 / printed p.220 carries EC3 #428 (“implementation dependent”) on the area-filling order, not a Table 74 row. No exact paint order is claimed. The current ledger marks §§8.7.3 and .1–.3 implemented, but this review maps only Table 74 cells and directly related prose, not the whole family.

The core dictionary cells have meaningful consumer evidence. The paint-type tests distinguish the stencil color from fill-time color, including a Separation red tint against the one-component DeviceGray-white fallback; Type 1/2/3 lattice tests compare actual positions/pixel periods and measure the Table 74 distortion bound; BBox tests include the ordinary clipping consumer. The known degenerate-BBox failure is B20 and is explicitly not duplicated here. Matrix phase, parent-stream initial colors, saved state, and cells-read-once assertions have named witnesses. EC3 #294 is editorial/object-form clarification; #428 qualifies the order of tiling and is honored by making no sequence claim.

The clearest narrow gap is valid negative nonzero step rendering. Table 74 explicitly permits negative XStep and YStep. In an infinite lattice, changing either sign maps integer site index i to -i, so the same cell origins are present and the key cell at the origin remains fixed. The current implementation normalizes step signs to magnitude, and the site-coverage helper also orders bounds for either sign. That is a valid geometric realization, with no failure seen in the source trace. However, I found no named public pixel test for a negative step. `drafts/tiling_signed_steps.rs` proposes one exact-xref/no-recovery TilingType 2 fixture for positive steps and three sign variants. Literal red-cell and transparent-gap controls run before full-raster equality checks. The draft is not run, and no implementation defect is claimed.

`/Resources` is required on producer inputs. Missing-resource handling is already owned by the pattern resource-repair work and ADRs 1059/2820; it is not turned here into a reader failure. Similarly, required PatternType/PaintType/TilingType fields and nonzero-step constraints describe valid writer output; this matrix does not demand mandatory rejection or invent a recovery rule for malformed entries. The code’s absolute-value step normalization is appropriate to the infinite-lattice equivalence, and Type 2 avoids introducing optional device-grid snapping into this comparison.

Residual scope: this is a bounded cell mapping, not a whole-clause certification. The negative-step draft remains unexecuted. B20 is the known Table 74 BBox failure. No other new behavior defect emerged from this review. Coloured/uncoloured content semantics, transparency groups, archive repair, nested Type 1-in-Type 1 paint, and all raster backends are not recertified here.
