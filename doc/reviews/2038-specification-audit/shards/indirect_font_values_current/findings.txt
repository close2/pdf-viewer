I read §7.3.10 at printed page 34 / physical page 49. Its closing rule is broad: “Except where documented to the contrary, any object value may be a direct or an indirect reference; the semantics are equivalent.” The same clause explicitly describes references as array elements or dictionary-entry values. This is the controlling rule for the font metrics below; no contrary rule was found in the applicable metric passages.

For simple fonts, Table 109 (printed pp.313–314 / physical pp.328–329) calls `/Widths` an array and says an indirect reference is preferred. Its entries are the glyph widths indexed from `/FirstChar`. I directly inspected EC3's #106 StrikeOut on physical p.329 / printed p.314; it removes the Table 109 `/FontDescriptor` row's “shall be an indirect reference” phrase. The separate standard-14 all-or-none paragraph is struck by #47/#48 on the same page. After #106 a direct descriptor is permitted; §9.6.3 says a TrueType font dictionary uses the same Table 109 entries with its listed differences, so the draft's direct-descriptor variant is within the effective rules. §9.8.1 Table 120 (printed p.344 / physical p.359) defines `/MissingWidth` in the descriptor. The current `stated_widths` implementation in `crates/pdf-font/src/metrics.rs` obtains `/Widths` through `Document::get_key` and resolves each array item with `Document::resolve`; `missing_width` reads the descriptor entry through `get_key`. Existing `simple_font_widths_audit.rs::embedded_truetype_widths_are_indexed_from_firstchar_and_place_each_glyph` checks actual glyph origins against literal widths but uses inline `/Widths` values. The draft instead uses public `LoadedFont::metrics_only` with a valid nonembedded TrueType font, so asserted advances come from PDF dictionaries rather than an embedded or substituted program. A/B use exact hmtx widths 1366/2048 em; C/D are outside `/FirstChar`–`/LastChar` and use descriptor `/MissingWidth` 1479/2048 em, matching their source glyph advances. Direct and indirect controls pin those literal values, including a direct descriptor and indirect MissingWidth value.

For CID fonts, §9.7.4.3 (printed pp.332–334 / physical pp.347–349) defines `/W` as outer groups containing either a nested array of per-CID widths or a range and one width; `/W2` uses the analogous forms with three values per CID. `/DW2` is a two-number array. The same section explicitly requires `/W` and `/DW` widths to be consistent with the CIDFont program. I read Liberation Sans hmtx directly: GID/CID 5 (`quotedbl`) is 727/2048 em = 354.98046875 units; GID/CID 6 (`numbersign`) is 1139/2048 em = 556.15234375 units. The draft uses those exact values for `/W` and `/DW`, avoiding a producer-mismatched metric fixture. It uses explicit vertical metrics in `/W2` and `/DW2`, where W2 CID 5's horizontal position component is exactly half its stated width. The corresponding code in `metrics.rs` resolves the outer array through `get_key`, each outer element, every nested array element, and each `/DW2` item. `composite_font_fixtures.rs` checks the literal ISO examples and `composite_fonts.rs` checks vertical placement, but those fixture assertions use direct values throughout. The draft's exact-xref direct control and indirect counterpart assert the independent hmtx-derived advances and literal W2/DW2 vectors.

`glyph_names.rs::apply_differences` resolves each `/Differences` array item, including names, so the examined path is consistent with §7.3.10. Its current visible assertions largely use inline Differences arrays. I did not draft a third test: a glyph-remapping control needs a carefully chosen embedded font name and a literal consumer consequence, while two metric tests directly cover the highest-risk nested arrays and numeric consumers. Differences remains an explicit assertion-coverage residual rather than an asserted defect.

The ledger rows are implemented: §7.3.10, §9.6.2.1, §9.6.5.2, and §9.7.4.3. Their current cited direct-value tests do not establish equivalence by themselves. The code inspection is positive evidence that the implementation currently resolves references at each level; the finding is limited to missing regression assertions, not an observed failure. §7.3.10 is broad, but this shard does not certify every object consumer.

ADR 2722 addresses direct font dictionaries encountered by archive conversion and quotes §7.3.10; ADR 2162 also covers materializing an inline font dictionary for transformation. Neither discusses nested numeric references in Widths/W/W2 or current display-time metric loading, so neither is evidence for the tested feature. No source basis exists to treat a font with otherwise conforming metrics as invalid solely because it uses an equivalent indirect spelling. The test controls preserve the same stated metric values and valid metric grouping; they vary only direct versus indirect representation. The drafts assert literal font advances/positions, not agreement with another renderer.
