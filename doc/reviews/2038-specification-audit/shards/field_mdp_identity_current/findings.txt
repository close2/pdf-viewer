FieldMDP name identity across a signed/current comparison

Source checked: ISO 32000-2 primary physical pp. 587 / printed 572 (Table 256 /Data), 588 / printed 573 (§12.8.2.2.2 signed/current comparison), pp. 591–592 / printed 576–577 (§12.8.2.4 and Table 259), plus §12.7.4.2 (physical p.547 / printed p.532) for full field-name construction. I corrected the §12.7.4.2 locator by searching the held primary PDF; physical p.124 is unrelated string syntax. Table 259's /Fields row on p.592 has two actual caret annotations recorded by `doc/errata-read.md` Issue #33; they insert “fully qualified” and the §12.7.4.2 cross-reference. I read those carets rather than relying on the generated errata heading owner.

The signed transform's selection is fixed text in the signed signature dictionary. Issue #33 makes those strings fully qualified field names. §12.8.2.2.2 places the analysis after digest validation and compares the signed revision to current. The strongest reading is to resolve `/Fields` against the signed field tree and follow the selected field object(s) into the current revision. This allows a protected field’s later `/T` rename to remain the same selected object during the comparison. This is an inference: no sentence prescribes the cross-revision name/object mapping algorithm directly.

At `crates/pdf-signature/src/revision.rs`, `Comparison::of` reconstructs the signed prefix and compares object identities. It builds the field-subject map by walking current fields first and signed fields second; each walk inserts with `entry(id.number).or_insert_with(...)`. Consequently, an indirect field dictionary at object 6 named `Name` in the signed state and `Other` in current remains named `Other` in the map. `against_field_mdp` applies the signed transform’s `FieldSelection` to that one stored name. With `/Action /Include /Fields [(Name)]`, object 6’s `/T` and `/V` update is reported `Other Outside`, and the summary can say no covered field changed. Under `/Exclude /Fields [(Name)]`, the same rename may reverse the result to covered. The expected `Name Covered` for a same-object rename is therefore the key candidate.

The existing `a_field_mdp_transform_selects_by_the_fields_table_259_names` has useful stable-name controls: changed `Name` under Include(Name) is covered, the same field under Include(Other) is outside, and Exclude selection is checked in both directions. It does not change `/T` after signing. There is no rename regression in `revision.rs`. ADR 1096 §3 only resolves `/Data` as a required analysis-scope object; it does not set the FieldMDP name snapshot rule. ADR 1096 §5 says no host currently calls the comparison. Search likewise finds `against_field_mdp` only in `pdf-signature` tests and `signature_algorithm_census`; this is not a demonstrated user-facing viewer error today. `pdf-model::restriction::asserted` checks current field names for a prospective FillInForm warning and is a separate code path from comparing a signed revision.

A narrowly scoped test draft is in `drafts/field_mdp_signed_name.rs`. It uses a real incremental revision/xref and a signed-prefix ByteRange, includes an actual FieldMDP reference with Table 256 Data naming the catalog, requires `was_recovered == false` and an intact xref chain, and compares three controlled cases: stable Name/value change (covered), a distinct Other/value change (outside), and same object renamed Name→Other while changing V (should remain covered if signed identity is the intended rule). The fixture is deliberately described as a comparison-seam test and makes no cryptographic-integrity claim; `Comparison::of` explicitly leaves digest verification to its caller.

Verdict: likely bug in the public comparison's chosen subject name, with an inference-qualified source rationale. Keep the “likely” qualifier and note the lack of production callers. Parent should run/review the draft and decide whether to reverse the walk precedence or preserve both signed and current subjects explicitly. No Cargo or test command was run in this shard.
