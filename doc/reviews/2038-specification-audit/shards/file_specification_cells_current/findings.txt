Bounded review: FileSpec and embedded-file parameter table cells

I checked the exact Table 43, Table 44, and Table 45 rows in the EC3-integrated primary text and inspected the relevant primary-PDF annotations directly with pikepdf. Table 43 begins at physical 149 / printed 134 and runs to physical 152 / printed 137; Table 44 is physical 153 / printed 138; Table 45 occupies physical 153–154 / printed 138–139.

The key reader rule here is not a writer-only check: Table 43 says that when UF is present a PDF reader shall use UF instead of F. The EF dictionary carries embedded streams corresponding to its F and UF entries. A reader that presents UF but extracts the EF/F stream when those streams differ would join a preferred filename to the other file's bytes. The current `attachment::read` selects EF keys UF-first, so inspection suggests correct behavior; the direct/indirect T88 test has only one EF key and does not independently prove this case. I added `drafts/uf_embedded_stream_selection.rs`, a small exact-xref, no-recovery public `attachment::attachments` test with distinct F and UF embedded payloads plus an F-only fallback control. It asserts the chosen displayed file name and literal decoded bytes. The FileSpecs include Type, Desc, and EF; each stream has Type, valid #155-compatible Subtype, exact Length, and Params Size/ModDate. This is a coverage proposal only; it is not executed here and does not claim an implementation failure.

The remaining reviewed entries are well bounded by existing consumers or by their source status:

* `/Desc` is producer-required for file specifications in the EmbeddedFiles name tree; existing attachment tests assert the description reaches the listing model. This does not establish every UI presentation path.
* `/V true` means applications shall not cache an external file copy. This viewer does not fetch external targets, so there is no active cache consumer to test and no basis for alleging the requirement is violated.
* `/RF` must use keys represented in EF and its values are related-file arrays. `attachment::related` and its pairing test cover the reader representation; ADR 0145 records that the current product has no related-file extraction action. I do not turn that product boundary into a reader failure.
* AFRelationship has default Unspecified and enumerated semantic meanings, but Table 43 NOTE 3 says it gives no processing instructions. Current parser/tests retain the relationship. Producer-side requirements about which relationship is correct do not establish a reader rejection duty.
* Table 44's Type/Subtype/Params conditions and Table 45's associated-file ModDate condition constrain producers. #155's MIME subtype restriction is specifically a producer syntax constraint. #598's new filesystem date note is conditional on host filesystem support. These are not grounds for demanding that readers reject files or invent missing dates.
* Table 45 Size states uncompressed byte count. CheckSum is a 16-byte MD5 over uncompressed embedded bytes; #382 changes its representation to byte string. The already passing T62 test uses a distinct compressed stream and decoded payload with independent digest controls, so no duplicate draft is added. The note expressly disclaims security use.

No broader ADR conclusion is made.
