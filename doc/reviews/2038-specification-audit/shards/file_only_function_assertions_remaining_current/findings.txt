Function-family file-only pointer assertion map

This map follows the 19 `(clause, reference path)` pairs under §§7.10, 7.10.1–.5, .5.2 and .5.3 in `file_only_reference_assertions_current/inventory.json`. It reads pointers as leads, not automatic proof that a file tests every requirement of its owner.

`crates/pdf-model/tests/shadings.rs` contains substantial public-consumer evidence: Type 2 ramps produce literal endpoint/midpoint pixels; Type 1 Type 4 functions paint the transformed domain and a discontinuity at selected device-pixel centers; a Type 4 mesh passes an interpolated parameter to a nonlinear Type 2 function (65 vs 129 distinguishes ordering); comments do not change Type 4 output; and the owner's BBP witness produces its stated digits and 3.141. This gives broad cross-pipeline evidence for function-bearing shadings. It does not test every function family. In particular `ShadingType 3` is radial, not `FunctionType 3`, and the mesh's `/Function` is Type 2, not sampled Type 0.

The two sampled-function pointer files have different claims. `shadings.rs::a_mesh_with_a_function_interpolates_the_parameter` is a nonlinear order-of-operations test for a Type 4 mesh with Type 2 Function. `sampled_function_extent.rs` is the Type 0 stream-length pair: four literal samples at four encoded positions, then a three-byte short stream that must refuse instead of synthesizing a fourth sample, plus a public page incomplete-state check. It writes xrefs/lengths explicitly, though neither this helper nor the shadings helper calls `was_recovered()` as an explicit guard. The valid narrow-domain B10 defect is already in global findings; it is not discovered by these file pointers.

`hostile_functions.rs` is the substantive Type 3 function evidence despite the `shadings.rs` inventory pointer. It tests self/mutual cycles terminate, a nested chain inside the bound still evaluates, a 255-subfunction function with reverse Encode evaluates the literal endpoint correctly, and a 5000-subfunction input refuses with the actual count. The latter is the reader's resource policy, not an ISO maximum for k. The separate nested-function unit test checks outer-domain breakpoint mapping. The signed-zero degenerate-endpoint B09 failure is already recorded globally; no new Type 3 claim is created here.

For aggregate/reference owners, `case.rs` defines typed source-cited cases and expectation categories but is not itself an assertion. Its actual consumer `raster-function-conformance/tests/corpus.rs` checks literal expected values/errors against a separate evaluator, operator/refusal/rule coverage, unique case names and source citations. `corpus/clipping.rs` stores literal Domain and Range cases, including each input and output component, and output-count failures. `reference.rs` is that evaluator. Prior `calculator_oracle_assertions_current` reviewed its independence, PLRM provenance, exact two-input specialization, and limitations; it did not certify all m-input behavior.

`reference/stack.rs` and `corpus/refusal.rs` include a reference stack of exactly 100 and a 101-push refusal. Since ISO requires room for at least 100 and does not require more, 101 refusal is valid implementation-profile behavior, not a mandated rejection. `function_faults.rs` assertions and public routes were already examined in `functions_current`; representative dynamic Type 4 errors are reported to interpretations and post-draw Type 1 grids, with the recorded GPU and low-bit palette caveats. Those are not duplicated here.

The directly relevant source/errata decisions remain bounded: the supplemental oracle review read §7.10.1 clipping, §7.10.2 interpolation, §7.10.5.2's normative PLRM3 deferral, and §7.10.5.3's output/overflow errors. It reviewed EC3 #30, #269, #446 and #669 as not changing those selected behaviors. EC3 corrections and successor ADRs must be read from current artifacts: in particular ADR 0412 supersedes prior boolean coercion for ordering operators; ADR 2811's right-shift behavior is a locally sized 32-bit policy supported by PLRM, not a universal Annex C width; empty-pop zero is a recovery decision and the delegated PLRM source does define stackunderflow. These qualifications are already preserved in prior oracle/function shards.

No new draft is warranted by the remaining file-only pointers. Existing targeted assertions are meaningful, and the two current specific failures B09 and B10 already have source-derived tests and global entries. This map does not certify complete function conformance or assert that the 19 pointer pairs exhaust the clauses.
