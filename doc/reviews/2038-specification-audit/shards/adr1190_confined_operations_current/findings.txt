ADR 1190's operation-level rule survives; its factual inventory does not. ADR 1592 adds confined text entry and Ctrl+S save, and ADR 1987 makes checkbox field fill reachable by pointer. The current host still sends no `Command::Restrict`, so core's `RestrictionPolicy::default()` governs: Off for all listed operations except OverridePreference Warn. The argument parser rejects document-restriction settings by name. This is consistent with the project-owned Off default, but leaves no confined-host route to the other three levels. No later accepted ADR I reviewed reconciles this after those operations were added. Record as stale premise/policy question, not a confirmed PDF requirement violation.

The form commit drive in `tools/drive-windows.sh` is meaningful end-to-end evidence: in all four windows it edits and commits fields, presses Ctrl+S, parses the resulting `.edited.pdf`, and checks literal values/appearances. The confined-worker integration test separately checks Save returns bytes with the original prefix. The drive removes any preexisting output first, and neither it nor the confined unit tests check that the source file stays unchanged or that an existing destination is handled as intended. `write_saved` writes `self.path.with_extension("edited.pdf")` with `std::fs::write`; for a normal `document.pdf`, that writes `document.edited.pdf`, replaces an existing file at that path, and prints a note if writing fails. I initially hypothesized that an input already named `document.edited.pdf` aliases the target; a standalone Rust check disproved that: `Path::with_extension("edited.pdf")` produces `document.edited.edited.pdf`. The path check is preserved in `path_check.rs` with its standalone output. A host unit test with `Host::event(Event::Saved { ... })` can verify literal output and source preservation for both ordinary and already-edited names. A deterministic failed-write case can use a directory at the destination; it checks no source corruption, though not the stderr message itself. Capturing/reporting the error would need a subprocess or more observable API. Do not assert an overwrite policy for an existing regular target absent an owner contract.

The future “anything that writes a file brings the save question” sentence in ADR 1190 does not alone require a confirmation here. Ctrl+S is the reader's direct save action, and ADR 1592 names it as such. The operation-level settings in ADRs 2040/2076/2171 govern host choices to open or transmit things, not document permission bits; their ask-card tests/drive evidence are separate from this no-Restrict policy.

Scope limits: this is an ADR/current-policy and assertion review, not a standard-clause audit. I did not execute the non-gating UI drive or Cargo tests. The worker's no-filesystem boundary is preserved: it returns Event::Saved bytes and the host performs the disk write. I found no host unit test exercising unexpected Event::Asking, but the branch reports it as unanswerable and answers `proceed: false`; no event is expected under the current Off default.
