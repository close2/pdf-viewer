# Default colour spaces, implicit conversion, BPC, and opaque overprint

This is a bounded source-to-consumer audit at baseline `b901326c`, not a certification of the whole clauses. Primary source locators in `features.json` were checked against PDF footer pages. The effective text was checked against EC3 and the source annotations.

Default-space behavior has good distinct-value consumer evidence across page/form resource scope, DeviceCMYK initial components, array and named routes, Indexed bases, uncoloured Pattern bases, selected DeviceN alternates, images, inline images, and shading. The tests compare against no-default or named-resource controls. The code resolves defaults in the shared colour parser and image/shading routes pass the resource scope in force. I found no new default-space failure. Invalid default types and component-count mismatch remain producer validity constraints; this audit does not infer mandatory reader rejection.

The implicit-conversion row's policy is not a general reader MUST. Source says a processor *should* avoid conversion when the CIE source accurately represents the output device, then explicitly says PDF cannot specify those calibration conditions. The implementation preserves colours when a page group establishes the target press profile and carries the corresponding device semantics; the public press-profile and overprint tests distinguish this route from a converted foreign profile. No conformance failure follows from declining a universal same-profile shortcut on an ordinary RGB display.

BPC is implemented at the paint conversion boundary. Existing tests exercise synthetic ICC conversion carriers, ON/OFF/Default choice, absolute intent, intent ordering and alternate intent routes, including images/shadings. EC3 #360 deletes the Table 57 stated default but leaves §8.6.5.9's absent/Default behavior to the processor; choosing compensation is therefore still an implementation policy. EC3 #63's Table 69 standard name is `AbsoluteColorimetric`; the clause's prose says `AbsColorimetric`. I found no effective erratum establishing that the shorter spelling is a PDF name alias, and the tests correctly use the standard Table 69 spelling. This remains a terminology/citation ambiguity, not a defect claim.

The narrow remaining test gap is an independently observable public case for §8.6.7's explicit OPM exclusion for sampled images. Existing tests pin direct DeviceCMYK OPM behavior, non-CMYK-device behavior, and spot-image overprint, but do not compare a sampled DeviceCMYK image's zero K value with an equivalent direct current-colour OPM1 operation. `drafts/cmyk_sampled_image_ignores_opm.rs` supplies that exact-xref, no-recovery and complete-interpretation comparison, with the ordinary sampled-image behavior as a positive control. It is a test proposal only; it has not been run and establishes no current behavior result.

For §8.6.7, OPM's zero-retention rule applies only to current-colour DeviceCMYK operations and does not apply to images or shadings; transparent compatible overprint belongs to §11.7.4 and is not reopened here. Parent separately confirmed the prior transparent-stroke regression against its control and is reviewing the existing selected overprint suite.

No Cargo command was run by this shard.
