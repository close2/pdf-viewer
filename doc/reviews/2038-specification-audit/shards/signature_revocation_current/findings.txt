# Signature revocation and PAdES dictionary audit

## Main finding: signature timestamp consumer uses a known-revoked TSA time as historical proof

EC3 §12.8.3.4.8 (printed pp.583–584; physical pp.598–599) is more specific than “a trusted timestamp path exists.” It requires checking the timestamping-unit path's revocation status at current UTC. If any authority-path certificate is revoked for `keyCompromise`, `cACompromise`, or has no reason, the timestamp instant cannot be used; for another reason the instant is usable only when revocation occurred after that instant. This distinction governs whether the signature's own signer path can be checked at an earlier time.

The strongest issue is at the consumer, not the structured timestamp result. `signature_timestamp_established` in `crates/pdf-signature/src/timestamp.rs` returns `Time::Established { at, revocation, .. }` for an anchored authority path and preserves its revocation answer. `viewer_core::notes::signature_timestamps_instant` in `crates/viewer-core/src/notes.rs` extracts `at` from every such result without inspecting `revocation`; the signer loop then uses it as `BestSignatureTime`, allowing it to govern the signer path and verdict. The structured `Time` answer may properly report an anchored token alongside its revocation status; the assigned clause issue is using the genTime as reliable historical proof despite a known-disqualifying status. `established_over` has a similar omission for document timestamp links, but that path is adjacent scope and is not needed to establish this signature-timestamp finding.

This is not the prior initial-Open timing finding or the DTS-only DocMDP classification finding. Nor is it a demand that “valid” be shown in a UI. It is specifically the use of a known-revoked TSA certificate path as the source of a historical verification instant. `Acceptance::UnknownRevocationAccepted` addresses missing/undetermined evidence; it should not erase a known `Revocation::Revoked` condition.

A genuine offline regression fixture and copy-ready consumer test draft are now under `drafts/tsa_revocation_fixture/` and `drafts/timestamp_revocation_notes_test.rs`. It includes a valid OpenSSL-signed detached CMS value, a genuine RFC 3161 token whose imprint binds the actual `SignerInfo.signature`, a TSA chain reaching the supplied root, a clean current CRL positive control, and a root-signed CRL listing the TSA serial as `keyCompromise`; a tampered-CRL Unknown control is also in the test draft. The consumer assertion targets `signature_timestamps_instant` and checks whether `BestSignatureTime` remains at the injected current instant. The exact test fixture exercises the keyCompromise rule with the revocation entry at genTime; that reason disqualifies time use regardless of its position. The broader matrix still includes no-reason and non-compromise-before/after cases, which remain follow-up fixtures. OpenSSL independently verified the CMS signature, RFC 3161 token, certificate paths, CRL signatures, and revoked serial/reason. Cargo was not run and the Rust test has not yet been promoted/executed.

## Additional gaps in .4.7 and .4.8 revocation timing

The direct §12.8.3.4.7 rule for a CRL checked at current UTC is that now lies in the interval bounded by `thisUpdate` and `nextUpdate`. `revocation::from_list` enforces only `at <= nextUpdate`; it does not check `at >= thisUpdate`. The existing `a_list_issued_after_the_instant_asked_about_is_evidence_about_it` test therefore cannot establish current-time .4.7 conformance. It is relevant as a historical-time control, where later-collected evidence may still answer a past instant subject to .4.8's independent conditions. The evaluator receives an instant and issuance constraints, but no explicit current-vs-past mode. This is a source-to-code gap; however, the implementation comment cites ETSI EN 319 102-1's one-ended freshness construction. A final decision should record that interpretive disagreement rather than silently classify the CRL check as globally wrong. Any correction must preserve the historical case.

Section .4.7 also requires an OCSP response used for current verification to have been captured before the signer's certificate expires. The revocation evaluator receives no signer `notAfter`, and no inspected wrapper enforces this cutoff. Section .4.8 repeats the capture-before-expiry condition for historical checks. The parsed response exposes `producedAt`, but the source says “captured”; do not treat these as interchangeable without an explicit source basis. A useful end-to-end test needs fixed signer validity and response timestamps bracketing expiry, with otherwise identical authorized, correctly signed responses.

For §12.8.3.4.8, source again requires CRL/OCSP evidence captured before signer-certificate expiry. The trust walk knows the target certificate's validity, but `revocation::Subject` has no `notAfter`, and `from_list` / `from_response` do not compare material collection time with signer expiry. Thus the PAdES revocation code does not appear to enforce this cutoff. For CRLs, `thisUpdate` is the available issuance time; for OCSP, the response exposes `producedAt`, but equating it with capture time needs source confirmation. A test should use otherwise-valid, issuer-authorized material on both sides of signer expiry and keep `nextUpdate` (or `producedAt`) after the historic validation instant.

The reason-specific TSA rule above is another independent historical-time condition. The `.md` file lists follow-on reason and expiry cases; the keyCompromise case now has genuine signed offline evidence, while no-reason and non-compromise before/after cases remain ungenerated.

## Other assigned areas

§12.8.3.2 is printed p.578 (physical p.593). It calls PKCS #1 signatures deprecated in PDF 2.0, says the only SubFilter that should be used is `adbe.x509.rsa_sha1`, and requires signer chain in `/Cert`. Existing `signature.rs` tests prove direct public-key verification, wrong-key failure, absent-cert answer; trust/verdict tests separately prove anchor-dependent trust. These distinctions are sound. The producer “should” is not a reader rejection instruction.

§12.8.3.3.2 is printed p.580 (physical p.595). Its scope is producer-side “SubFilter other than ETSI.CAdES.detached”, and it gives the `adbe-revocationInfoArchival` OID plus exact `RevocationInfoArchival` grammar (optional `[0]` CRLs, `[1]` OCSP, `[2]` custom OCTET STRING values). `revocation::archived` reads the signed attribute's CRL/OCSP sequences and `Signature::trust` merges that material with the DSS. Unsupported `otherRevInfo` is not interpreted because the type's format is explicitly unspecified. The CRL/OCSP validators have meaningful cryptographic positive/negative controls. I found no test directly calling `archived()` or demonstrating that a signed CMS archive attribute is routed into revocation status. `drafts/revocation_archival_attribute.rs` contains a focused module-test proposal; it makes only the attribute-extraction-and-status claim, not a claim that the containing CMS signature is valid.

§12.8.3.4.2 is printed p.581–582 (physical pp.596–597). `pades_departures` asserts DER SignedData, whole-file ByteRange excluding Contents, forbidden `/Cert`, and mutually exclusive `/M` versus signing-time. Its tests include departing and conforming controls. BER outside RFC 5652's signed-attribute DER-only region can be reported yet read; don't turn every producer departure into cryptographic failure.

§12.8.3.4.6 is printed p.582 (physical p.597). The path-level loop checks each certificate and can consume CRL/OCSP material without network access. §12.8.3.4.7 is printed pp.582–583 (physical pp.597–598). Existing fixed-time vectors assert CRL `thisUpdate`/`nextUpdate`, revoked/clean serials, stale/invalid issuer/signature, and OCSP issuer/delegate authorization. These are strong algorithm-level controls, but no assertion tests either the current-time CRL lower bound or the PAdES-specific OCSP capture-before-expiry condition.

No relevant errata annotation was found on the six assigned source locators. External RFC/ETSI behavior is considered only where this repository holds and uses it; no network or live revocation fetch was used.
