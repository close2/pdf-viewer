# Structured-reference security errata batch

This batch reviewed issue annotations #16, #24, #25, #81, #114, #135, #219, #325, and #424 in the primary EC3 PDF. It did not certify surrounding clauses. Annotation subtypes, rectangles, contents, and reply links were read directly with pikepdf. The cited physical pages and printed footers are recorded in `features.json`.

The clearest behavior links are #16, #24, and #25. #16's three StrikeOut/Caret pairs on physical page 107 replace Table 27's “string” with “byte string.” This applies to crypt-filter recipients, not Table 23's recipient list shape. The s5 path in `public_key.rs` reads those values as raw byte strings; the checked-in s5 and stream-own-recipient fixtures contain real CMS envelopes and assert decrypted page content. That provides a meaningful byte-consuming control, although it does not cover every CMS encoding. #24 removes the mistaken IV wording from three ECB descriptions. `perms_block`/`perms_entry` use ECB and the named `a_perms_block_yields_the_permissions_algorithm_10_stored` unit test inspects the result, while `wrap_key` remains AES-CBC with the zero IV. The issue is not a global removal of IVs. #25 inserts the conditional metadata notes on physical page 105. The public-key file-key path tests the default stream crypt filter and `EncryptMetadata` condition; two independently produced ExposedMeta PDFs assert plaintext and exercise the false-metadata path. This is useful branch evidence rather than a complete SubFilter/filter cross-product.

#81 is an effective note added to Table 31 on physical page 120: a page with no `/Contents` still needs `/Resources`, either locally or inherited. Its wording constrains a conforming page producer; it does not direct readers to reject a file that violates it. Page resource inheritance is implemented, but I did not find a sampled assertion that isolates this exact absent-Contents case, so I record a case-specific coverage limit, not a reader defect.

#114 is an effective producer constraint inserted before Note 3 on physical page 77: an ObjStm dictionary value must be direct or an indirect uncompressed object. Existing object-stream header/order tests do not exercise that precise value form. The earlier valid-input draft has since been integrated as `crates/pdf-syntax/tests/cross_references.rs::object_stream_dictionary_values_may_reference_uncompressed_objects`; parent reports it and the direct-value control PASS. The test uses indirect uncompressed `/N`, `/First`, and `/Length`, exact xref offsets, and a compressed Info member whose title contains a literal `endstream` sequence. It should remain a valid-input consumer test and not become a malformed-input rejection assertion. This covers those three values only.

#135 adds a Table 29 `/Lang` note on physical page 116 clarifying that “text” includes PDF text strings and textual content. `viewer-core/tests/lang_hex_consumer_spec_audit.rs::hexadecimal_lang_strings_reach_accessibility_with_catalog_and_structure_precedence` supplies a public consumer assertion: UTF-16BE hex Catalog Lang falls back to an accessibility node when structure Lang is absent, while a hex child Lang overrides a literal ancestor. This supports the specific catalog-string/accessibility consumer path, not every language precedence route.

#219's Carets on physical page 102 annotate the §7.6.5.2 prose list of public-key SubFilter names with PDF 1.3/1.4/1.5 labels; they do not annotate Table 20 rows (Table 20 is referenced in the surrounding prose). On physical page 584, Carets label three Table 255 signature SubFilters and a StrikeOut removes a blanket PDF 1.6 label. These are version/producer metadata. The reader code has branches for legacy signature forms, and Table 255's reader backward-compatibility direction remains distinct from the writer's corrected version labels. `signatures_current` explicitly limits its certification of the SubFilter matrix; I did not find a version-pairing integration matrix in this review. That absence is not a rejection defect: no sampled path gates the legacy values solely on the declared PDF version.

#325's StrikeOut/Caret pair on physical page 97 rewrites Algorithm 2.B step (a) as a two-case `K0`: the owner case includes the 48-byte `/U`, while the user case does not. `hash_2b` implements that distinction via `extra`; `authenticate_aes256` supplies `/U` for owner hashing and empty bytes for user hashing. `encryption_fixtures.rs::a_revision_6_document_opens_on_either_password_and_decrypts` exercises both branches, but the fixture generator reimplements the algorithm, so it is not an independent known-answer oracle for the owner extra. `standard_security_algorithms_current` also records external R6 corpus coverage. No full Algorithm 2.B matrix is certified.

#424's Caret on physical page 109 corrects `/V2` in the final §7.6.6 example by adding the missing SOLIDUS. It changes an example token, not the wrapper or crypt-filter algorithm. The wrapper shard correctly keeps it outside its §7.6.7 behavior claims.

No new test draft was justified in this batch: the only concrete assertion gaps are either producer constraints (#81) or already have an unexecuted valid-input draft (#114). Parent owns execution and promotion. No Cargo commands were run.
