# Font and colour aggregate framing (bounded)

I checked the effective PDF 2.0 text and relevant primary-PDF amendments for aggregate clauses that can otherwise hide cross-cutting requirements behind broad ledger claims. This is not a second pass over each font/colour leaf. Primary footer locators used here: §8.6.1–.3 printed177–179/physical192–194; §8.6.8 printed216–219/physical231–234; §9.1 printed293/physical308; §9.2 printed293 onward; §9.7 printed327 onward; §9.10 printed355/physical370. EC3 #551 is relevant to §8.6.8/Table73's CS row: the old producer statement that the resource entry shall be an array is removed. `colour::parse_at` already accepts the name form, so no reader defect follows. EC3 #324 only corrects Table119's ToUnicode cross-reference to §9.10.

For §8.6.1, the normative reader-facing frame is colour reproduction by a rendering processor; colour specification is in Clause8, device-dependent rendering facilities are in Clause10. The same paragraph says a reader may support separation simulation optionally. I found no separate requirement to emulate one particular output device or to implement separation simulation on every display. This is consistent with the colour-space, rendering-intent, transfer, overprint, and image shards owning their detailed obligations. Their existence does not mean the aggregate row alone proves the full chain.

§8.6.2 makes the graphics-state colour space determine the meaning/range of colour components, while image samples are sourced independently of the current graphics-state colour but must enter the same later colour-processing stages as SC/sc values. The implementation has distinct sample/Decode and operator input paths that converge on colour conversion. Existing image and colour-space shards audit those routes separately. The colour-space shard already recorded a narrowed ICC `/Range` fallback concern and a missing public DeviceRGB reset assertion; this aggregate pass neither repeats nor closes them. It did not test every codec/family pair for operator/image equivalence.

The most behavior-dense aggregate clause is §8.6.8. Table73 defines the colour-space/value operators and the following text limits which colour/graphics-state instructions take effect in d1 glyph descriptions and uncoloured tiling patterns. The rule extends through content streams invoked from those contexts, ignores the listed `/ExtGState` entries, and suppresses image painting except an image mask. It separately requires space-family-specific initial current colours. Existing tests have meaningful, asymmetric consumer assertions for d0/d1 colour inheritance, an uncoloured-cell colour operator, transfer-function state, and family initial values; `colour::parse_at` also consumes the #551-corrected name resource form. The pattern shard expressly left the complete operator/image table unrecertified, so I retain that as a coverage boundary. The current evidence does not establish a new runtime bug or justify requiring malformed producer input to be rejected.

§9.1 is a roadmap distinguishing text state/operators, font data structures and glyph painting. §§9.2, 9.7, and 9.10 summarize semantics whose operative algorithms reside in their detailed clauses. The code architecture mirrors this split between `pdf-model` interpretation, `pdf-font` code/font processing and `pdf-render` paint. Existing aggregate tests show some connections, including multi-byte selection and extraction independent of paint; specialized shards own exact encodings, metrics, CMaps, replacement text and reader order. Annex C expressly permits implementation limits on CID ranges; §9.10 permits a processor-selected fallback when all mapping methods fail. Neither condition alone is an implementation failure.

No missing overview-only font algorithm or new aggregate colour defect was established. The concrete limitation is evidence scope: the ledger's aggregate rows name a small set of representative tests, and those cannot be read as proof of every child feature. Leaf residuals remain open. I drafted no tests because the useful candidate assertions either duplicate leaf owners or would require a complete operator/image census rather than a narrow independent regression.
