# Annotation and page additional-action event cells

This bounded review covers Tables 197 and 198 in ISO 32000-2:2020 EC3. Captions and footers were checked in the primary PDF: Table 197 is physical p.523 / printed p.508; Table 198 is physical p.524 / printed p.509. The preceding §12.6.3 explanation is physical p.522 / printed p.507 and explains that `/PV` and `/PI` distinguish pages that are open from pages that are visible. Mouse constraints continue on physical p.525 / printed p.510. I inspected the actual pikepdf annotation arrays on physical pp.522–524: objects 13509–13519, 13520–13523, and 13524–13527 are `/Link` annotations, with no Caret/StrikeOut/Text issue annotation editing Tables 197 or 198. EC3 #618 changes a separate Table 226 `/AA` cross-reference on physical p.546, not these event definitions.

For pointer/focus events, `script_triggers.rs::a_widgets_pointer_and_focus_events_reach_the_runner_in_their_order` checks an enabled recording runner receives E, D, Fo, U, X and Bl in order; the distinct URI action test in `headless.rs::a_press_may_not_enter_and_a_release_needs_its_own_press` checks the source constraints on E/X/U. The separate `/A` over `/AA /U` precedence is tested in `pdf-model/tests/actions.rs::an_annotations_own_action_takes_precedence_over_its_mouse_up_trigger`. This pass did not find a distinct uncovered pointer/focus trigger assertion.

Page actions have solid non-script timing coverage. `headless.rs::a_page_turn_raises_the_events_the_clause_orders` asserts initial page O then annotation PO/PV and a page-turn sequence PC, PI, C, O, PO, PV using distinct URI payloads. `script_triggers.rs::a_page_turn_hands_the_runner_the_close_and_then_the_open` separately verifies page C then O reach a supplied runner. The multi-page visibility tests assert a neighbor's URI PV is delivered when it becomes visible before it is current, and that a page that remains in a two-page spread does not get PI merely because another page becomes current. B22's catalog OpenAction cross-order remains a separate established issue; B62 concerns field-AA inheritance and is unrelated.

There is a distinct enabled-script timing gap. Table 197 `/PV` says the action is performed when its page becomes visible; `/PI` says when it is no longer visible in the interactive UI. The source's preceding paragraph expressly distinguishes visible from open pages. Current `navigation::visibility_of` computes the shown arrangement and raises `Trigger::PageVisible`/`PageInvisible` at that transition, so non-script actions (such as the tested URI action) are timely. But `pointer::raise` treats these trigger variants as already scripted when a runner is enabled without invoking `run_annotation_scripts`. Instead, `ViewState::run_page_scripts` only runs them in `script_sites.rs::annotation_triggers`, paired with PageOpen's PO/PV and PageClose's PC/PI. In a two-page layout this makes a visible-neighbor PV script wait until that page becomes current; when it becomes current, PV is then run alongside PO even though the page did not just become visible. The ledger's exact overclaim is `doc/conformance/ledger.toml:3952`, which says PV/PI coincide with PO/PC because "this layout has one page" despite current TwoPageLeft support and tests.

ADR 2814 §3 explicitly accepts this script delay. The primary row does not state a JavaScript exception, and accepted A286/A193 scope includes document/viewer script effects when enabled (while `Off` remains the default). This appears to be a mismatch requiring a scoped ADR correction or implementation change, not an engine-disabled policy question. The supplied PDF 1.7 exact-xref fixture uses a fake `ScriptRunner` and does not execute ECMAScript. Parent ran the initial test in `page-visible-wave128.log`: page-zero's open/visible control passed, then page 1's expected `Annotation(PageVisible)` callback was absent when it became visible beside current page 0. Two new, unexecuted fragments now independently assert (1) no premature page-zero PI or duplicate page-one PV when page zero remains visible as page one becomes current, and (2) page-one PI delivery when changing back to a single-page arrangement actually removes page one from view. No Cargo was run by this reviewer.

Limits: this is not a complete audit of every §12.6.3 event/action type, every layout or native pointer host, nor all scripting/worker behavior. No Cargo or test execution was performed in this shard.
