# §12.11 document requirements — bounded source, policy, and consumer review

## Main findings

The requirements reader handles the common dictionary shape and exposes the stated type/version/penalty. The clearest gap is that a present `/V` is parsed into `Requirement.version` but never affects the capability verdict, penalty total, restriction, or user report. Table 273 describes `/V` as the minimum version support needed to satisfy a requirement; §12.11.4 says a present PDF version may identify the minimum required for successful interpretation, while an absent `/V` expressly removes version from the decision. For example, the code treats `/S /Navigation /V /2.1` as met because `Kind::unmet` treats all Navigation as met, although this processor's supported PDF version is 2.0. An exact-xref public test draft covers a supported-version control, absent-version control, and forward-version requirement. The future-version witness uses a dotted PDF version permitted by §12.11.4; parent review confirmed it discriminates the current supported maximum.

The `/RH` alternate-handler path is substantially evidenced. `disabled_handlers` handles `/RH` as one dictionary or an array, disables JS handlers under recognized Table 275 types whether met or not, leaves a vendor/unknown requirement type's handler active, and ignores NoOp or unknown handler types. A model test checks the returned script names, and a script-engine test observes the known handler skipped while ordinary and vendor handlers execute. `opening.rs` evaluates the Process restriction before `process`; the script-site path computes disabled handlers before iterating the document JavaScript name tree. The engine test is not a full public Viewer integration, so I do not certify every host/runner configuration.

The model penalty calculator sums only requirements `Kind::unmet` marks unmet and applies Table 273's default 100. The source's strict threshold is `exceeds 100`, and the exact 100 versus 115 boundary is asserted. The public restriction levels are separately tested: On refuses; Ask holds; Warn proceeds with a warning; Off proceeds and is the default. These choices do not indicate that a parser or evaluator is missing. They do mean ADR 1167's statement that the normative “shall not continue” is implemented at every reader level is overbroad: the source does not state a reader override. Treat Off/Warn/Ask-then-proceed as an explicit product policy departure unless the project has a source-backed interpretation authorizing it. The relationship between §12.11.6's “cannot be met” and §12.11.3's >100 threshold is the point that needs careful framing; do not flatten them into a general requirement that any unmet entry blocks processing.

The code computes Process before the document's further processing and before ECMAScripts. `notes::about` and the public `Command::Report` are separate: the hosts ask for the report after a frame has been presented. §12.11 requires evaluation before ECMAScripts, not that the warning appear before first-page display, so report timing is not a §12.11 defect. ADR 0207's “before a page is drawn” and the requirement module's “before they trust what they are looking at” are not literal descriptions of host chronology. Also, because notes only format the type and penalty, `/V` cannot currently be explained to the user.

## Source and errata

- §12.11.1/Table 273 is physical pp.621–622 / printed pp.606–607. Table 273 says `/S` is required; `/Penalty` defaults to 100 with 0..100 inclusive; `/V` is the minimum version level of support needed to satisfy the requirement; if `/V` is absent, version is disregarded; `/RH` is one dictionary or an array (default empty), and a checkable `/S` disables its alternate handler whether or not the processor can satisfy it.
- §12.11.2/Table 275 is physical pp.622–625 / printed pp.607–610. It lists 25 requirement types, with additions possible through Annex E. Note 1 of §12.11.2 distinguishes capability requirements for interactive processors from viewing; the general requirement feature is a statement of expected functionality, not an instruction to run a matching feature automatically.
- §12.11.3 and §12.11.4 are physical p.626 / printed p.611. §12.11.3's final paragraph is conditional on evaluating the base PDF and no other alternates; it says a total strictly greater than 100 should not be displayed/processed. §12.11.4 says a present `/V` can name PDF, XFA, U3D/PRC, or a vendor extension level; a PDF version can be a minimum version for success. Its extension dictionary must have exactly one registered-prefix key. These semantics are not met by merely retaining a string.
- §12.11.5/Table 276 is physical p.627 / printed p.612. It defines JS and NoOp handlers, requires a checkable parent requirement to disable its identified JS script, and says unknown handler types are ignored.
- §12.11.6 is physical pp.627–628 / printed pp.612–613. Requirements are evaluated before document ECMAScripts. When requirements cannot be met according to the §12.11.3 computation, processing shall not continue. For an acceptable document, subsequent processing proceeds without regard to the computation outcome; NOTE 1 says there is no formal connection from type to operation, and unsupported uses still take normal fallback actions. No exact report/display timing is specified here.
- EC3 #187 has effective annotations on physical pp.621, 622 and 625: the /S reference changes from Table 276 to Table 275; Table 274's heading and introductory wording are corrected. This supports `Kind::read` matching Table 275.
- EC3 #195 has effective StrikeOut/Caret pairs on physical pp.623–624 changing the U3D and PRC cell text from “shall apply” to “applies”. It does not create a new command to process 3D data.
- EC3 #656 changes the third-column heading on Table 273/274 from “Description” to “Value” on physical pp.621–622; this is editorial for the parser. No annotations are present on physical pp.626–628 for §§12.11.3–.6.

## Implementation, ledger, and test quality

`requirements::read` reads the catalog array, ignores malformed entries or dictionaries without required `/S`, keeps unknown names, reads `/V`, and defaults/clamps `/Penalty`. `Kind::unmet` contains a static project capability mapping for all 25 names. `unmet` filters that mapping, and `penalty_total` sums the penalties of unmet types. However, `Requirement.version` is only read in the parsing test; a search finds no consumer outside assignment/test. `Kind::unmet` receives no version argument. Thus a present minimum version is not factored into either unmet status or policy total.

`notes::about` names each unmet type and its penalty, gives the general Annex I warning, then reports a total only when it exceeds 100. It omits version. This is produced on `Command::Report`, which `viewer-host::report::Due` and the UI request after a first frame; no §12.11 source sentence demands earlier visibility. In contrast, `viewer-core::opening::open` computes `restriction::asserted(Operation::Process)` before calling `process`, so the evaluation occurs before the later `Presented` script sequence.

The focused model tests assert default, type, raw version retention, unknown type, total sum, and handler mapping. The requirement parser test helper builds calculated xref offsets. `viewer-core/tests/restriction_levels.rs` and the headless threshold-report test build short no-xref PDFs and do not assert non-recovery; those tests prove the chosen policy behavior but are weaker conforming-input evidence. The open-order test currently covers catalog/page/annotation triggers, not a requirement-specific prohibition of ECMAScript. The separate PDF-script engine test does cover handler suppression during document-level script execution.

`MAX_REQUIREMENTS=256` silently bounds the number of requirement dictionaries read and each handler array considered; no number appears in Tables 273–276. This appears to be a chosen resource budget. I did not build a large test or infer a required unbounded array size. It remains an incomplete-result disclosure question.

## ADR reconsideration

- **ADR 1923:** The handler decision remains supported by current Table 273/276 text and both model/engine assertions. Keep the distinction between being able to check a requirement type and being able to satisfy it. Scope is the current host/runner path, not a claim that all ECMAScript execution is enabled.
- **ADR 1220:** The no-modal-verb conclusion for intermediate weighting remains correct. It does not justify ignoring a present `/V`; version semantics explicitly participate in whether a requirement is satisfied.
- **ADR 0460:** The sum and strict >100 threshold are source-grounded and tested. Keep the “base PDF/no alternatives” condition visible. The process calculator and user policy are separate concerns.
- **ADR 1167:** The `Process` operation is a real product setting and each level has distinct behavior. The ledger statement that the `shall not continue` is obeyed “at whichever” reader level is not true as literal behavior: Off/Warn/Ask-then-proceed continue. Reader override is a project policy choice, not authorization located in §12.11. The stop/threshold relation remains a qualified interpretation issue.
- **ADR 0207/2815:** Requirements are evaluated before ECMAScripts, while the user report is requested after a frame. §12.11 supplies no pre-display reporting timing. Avoid converting the report's later timing into a conformance failure; also avoid describing it literally as an early warning.

## Residual scope

This review does not independently validate all 25 Table 275 feature mappings, the `/Encrypt` and `/DigSig` type-specific Table 274 entries, all future extension-level comparisons, alternate-document selection, oversized requirement arrays, or every embedded script host. The exact-xref version test in `drafts/requirements_version_public_spec_audit.rs` is a parent-run draft; it has not been executed in this audit.
