# Indirect values in annotation and action consumers

I checked §7.3.10's full operative rule directly in the held primary extraction: on printed p. 34 it states “Except where documented to the contrary, any object value may be a direct or an indirect reference; the semantics are equivalent.” Its preceding note permits chains of references. Thus entry tables and clauses provide the exceptions; it is not valid to infer that an object must be direct just because the table names its resolved type.

For common annotations, Table 166 printed pp. 467–468 specifies `/Rect` (rectangle), `/F` (integer), `/AP` (appearance dictionary), and `/AS` (name), with no direct-only rule. The same table explicitly requires `/P` to be an indirect reference to the page when present. Current annotation consumer paths resolve the general fields with `Document::get_key`; `rectangle` and `numbers` also resolve each member of the array. `stored_appearance` resolves `/AP`, appearance mode, and the selected state stream while preserving the referenced stream's identity. `annotation::opacity` resolves indirect `/CA` and `/ca` numbers for regenerated appearances; Table 166 says those opacities are not used when a stored appearance exists, which is distinct from `/BM` and keeps the prior stored-appearance opacity departure in its actual scope. Stored `/BM` also uses the resolver, and parent already owns that pixel audit. The appearance-state bytes are looked up by exact name bytes, consistent with ADR 0439. The recent Table 166 EC3 blend/opacity edits (#23/#34 as tracked in the annotation artifacts) concern compositing semantics; they do not add a directness constraint. Current pixel tests exercise stored `/BM` and state selection, though most use inline values for the surrounding annotation fields.

For links and actions, Table 176 printed p. 483 permits a link `/A` action dictionary and `/Dest` target; Table 196 printed p. 506 defines `/S` and `/Next`; Table 202 printed p. 511 defines GoTo `/D`. The public paths handle both forms: `link::links` passes raw `/A` to `action::read`, which resolves a direct action dictionary or a reference; `link::destination` passes raw `/Dest` to `Destination::read`, which resolves; destination view parsing resolves every array operand. `action::Walk` resolves `/Next` whether it is a single action or an array, and `/S` is read with `get_key`.

Raw references are deliberate for schema exceptions and identity: Table 166 `/P`, Table 213 movie `/Annotation`, rendition annotation targets, and GoToDp `/Dp` must remain actual indirect references. Thread action `/D` and `/B` intentionally distinguish references from direct integer indices; the source permits both. I did not mechanically replace those raw reads with `get_key`. ADR 0338's “An object reference has two answers” distinguishes an object's value from the identity that names it; ADR 2814 treats reference-reachable click behavior as part of the viewer consumer. Both remain compatible with the current code. ADR 0439's byte-preserving appearance-state lookup is likewise still necessary.

No behavior defect was confirmed. I drafted two exact-xref public-consumer tests to give the indirect-value routes an explicit positive assertion: one renders a visible annotation whose `/Rect` array and all four numbers, `/F`, `/AP`, `/AS`, and appearance-state dictionary are indirect, then checks a NoView variation against a green-page control; the other resolves a link through an indirect GoTo action, `/S`, `/D` array and `/Fit` operand and compares it with a direct GoTo control. The pixel expectations are literal opaque red/green samples; the action oracle is target page index 1. Both assert complete interpretation or the public target and `!Document::was_recovered()`.

The drafts have not been run. They are additive regression proposals, not evidence of a failure. This shard did not inspect every action subtype or claim full §12.6 conformance; GoToDp and other specific action semantics remain in their own shards.
