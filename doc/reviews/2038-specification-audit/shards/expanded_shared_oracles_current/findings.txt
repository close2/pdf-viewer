Three selected tests use shared numeric helpers, but they do not all leave the consumer unanchored.

`the_three_routes_to_a_press_all_composite_in_it` renders three source routes into an ICCBased CMYK page group (primary §11.7.2, physical 440 / printed 425) and compares pixels with `Profile::to_rgb` on the same generated profile. It is a useful routing and assumed-press-discrimination test, but the expected value shares ICC parsing/BPC/sRGB conversion with rendering. The sibling press-grid test also calls `Profile::to_rgb`; the lower-level XYZ-LUT test has a literal midpoint but does not anchor this custom CMYK fixture. The synthetic profile is generated locally and this review does not certify all ICC profile validity requirements. I drafted an optional literal replacement, [169,149,147], for the test's half-registration sample. The scratch script derives it from the 16 quantized CLUT corners at the midpoint, the fixture's all-ink black point, and the selected sRGB output map without calling Profile::parse/to_rgb. It is a fixture-specific renderer oracle, not a PDF-required exact device pixel. `drafts/press_routes_literal_oracle.rs` plus `drafts/derive_press_pixel.py` are unexecuted.

`an_images_rgb_samples_use_the_black_generation_pair_at_its_do` has correct source arithmetic: bytes 0x33/0x66/0x99 mean DeviceRGB (0.2,0.4,0.6); k=.4; BG(k)=.6 and UCR(k)=.2 yield CMYK (.6,.4,.2,.6). This is the specific §11.7.5.3 painting-time rule (physical 450 / printed 435); §10.4.2.4 is physical 377 / printed 362. Its expected final pixel calls `device_cmyk_blending_space().convert`, shared with the compositor. However `black_generation_paint::solid_selection_order_matches_image_and_clause_arithmetic` exercises the same inline image and explicit pair and compares to literal `[52,62,79,255]`, with solid/stencil controls. Thus the exact visible route has an independent numeric assertion. EC3 #640 on p.377 changes the gray spelling in §§10.4.2.2/.3 and retains the one-minus-gray term; it does not modify this .4 formula. ADR 1207 is appropriately scoped to the explicit pair; ADR 2549's profile-default decision is not at issue here.

`a_spot_colourants_curve_is_its_separations_flat_xyz` checks `SpotColourants::readable`'s 256-entry curve length and white-matte first sample. Its final expected calls the same `ColourSpace::flat_ratio` helper used to generate each curve entry; the fixed full-tint CMYK vector [0.84,0,0.44,0.21] is an independent Example 2 tint-transform oracle, but its flat-XYZ numeric conversion is shared. The actual public consumer is exercised separately by `spot_press.rs`: literal expected pixels cover LogoGreen at tint .5 [134,198,183], full-tint yellow/spot [69,139,0], and black/spot [2,13,11], with additional group-space samples. Those tests are independently derived from the tint transform and named process-device assumptions and provide meaningful end-to-end controls for selected interior and endpoint tints, not every curve slot. ADRs 1229/1317 remain supported for these sampled behaviors; no new duplicate test is warranted.

The source locations and bounded dispositions are in `features.json`; selected ADR reviews are in `decisions.json`. No behavior defect was identified. No Cargo or tests were run in this shard.
