The image dictionary's final `/Measure` and `/PtData` entries are meaningful to the existing measurement feature, but they support different conclusions.

The source chain for image measurement is direct. Table 87 (physical 276 / printed 261) says a present image `/Measure` specifies the scale and units “which shall apply to the image.” §12.10.2 Table 269 (physical 617–618 / printed 602–603) defines the GEO coordinate mapping on the object: `/Bounds` is relative to the image XObject's unit-square bounds, and `/LPTS` maps that square to the rectangular bounds of the image. Effective EC3 #533, visibly annotated on physical 618, makes `/LPTS` required. §12.10.5 then permits `/PtData` on a 2D image/form/viewport carrying a GEO measure.

The implemented public measuring feature is narrower than that source coverage. `Query::Measure` accepts a user-traced page path. `viewer-core/src/viewer/geometry.rs::measured` converts those device points back to page default user space, reads `Viewports` from the page dictionary, and formats/locates against the chosen `/VP`. The rendered image route has the image's CTM while constructing `pdf_render::Command::Image`, but its source image dictionary is not retained in the measurement query. `pdf_model::measurement::Viewports::read` reads only a page `/VP`; the only public host path is the same page-oriented gesture in `viewer-host/src/measuring.rs` and `native_window.rs`.

Current tests verify the page-viewport behavior, not image-attached measures. `viewer-core/tests/measuring.rs` exercises the ordinary page path and viewport's selected scale; `measurement_numeric_spec_audit.rs` adds distinct numeric viewport controls (T52). `pdf-model/src/measurement.rs` tests GEO registration from a viewport. Image tests exercise decoded pixels and painting, without `Query::Measure`. The focused scratch draft `drafts/image_xobject_measurement.rs` uses a valid PDF 2.0 image-only GEO registration, an exact xref/no-recovery check, a page-viewport positive control with the identical rectangle and registration, and a literal second-point location of 11° N, 21.5° E. It is a query-semantics test, not a pixel assertion. It has not been run.

The current clause inventory marks §8.9.5.1 `implemented` while its Table 87 review is explicitly partial; §12.9.1 is `implemented`; §12.10.2 is `departed` for bounded geospatial scope. Those aggregate statuses do not separately demonstrate the Table 87 image-measure route. ADR 0417 directly says image `/Measure` and `/PtData` remain rows “to owe,” and ADR 1191 establishes the page-path query without resolving the image object route. ADR 2170 is a later adopted source-reading decision but does not discuss §12.9/§12.10 or close this gap; it should not be treated as a superseding measurement scope decision.

This is a supported-feature coverage gap with an actionable source-derived regression candidate, not a rendering defect. The query is explicitly an interactive measurement tool, so an image's declared mapping should be available when the path is over that image. The source defines the expected object-space mapping; the draft does not require an extra UI, new command, or parser rejection. It does not settle precedence for an overlapping page viewport and image, nested transformed forms, or every image placement; its focused image-only case avoids the overlap question. Reconsider ADR 0417's accepted statement that image `/Measure` is a row “to owe”: it correctly identifies a boundary but does not add an image consumer. ADR 0082 and ADR 1191 document the built page-viewport path and do not resolve image dictionaries; their historical boundary is not evidence the image semantics are inapplicable.

For `/PtData`, source describes an optional extended-data table whose `Names` label tuple columns and whose rows have no guaranteed order or relation. It does not specify a drawing, display action, or user workflow. The model helper parses point data when handed a viewport dictionary, but image painting has no structured PtData consumer and the public measurement answer exposes coordinates/measurements rather than arbitrary columns. I found no basis in the cited clauses or ratified product contract to demand a PtData panel or to call its lack a reader failure. Keep that as a narrow model/interchange coverage residual; do not manufacture a second test for display.

Limits: source and consumers were inspected for this feature boundary only. The draft's WKT/GEO path is one supported geographic case; it does not certify all coordinate systems, every LPTS interpolation arrangement, image transforms, the wider `/PtData` parser, or every part of §§12.9–12.10. Table 87's optional producer entry is not a rejection condition when absent.
