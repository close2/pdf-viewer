# Deprecated web and prepress feature review

Scope is effective EC3 §14.10 (all children), §14.11.4, §14.11.6.1, §14.11.6.3, and §14.11.7. Source page numbers below are the PDF's physical pages and printed footer pages, checked against the held primary PDF; this was a source/code/assertion review only. I did not run tests or edit implementation.

§3.15 (physical 23, printed 8) defines a deprecated feature as one that “should not be written into a PDF 2.0 document” and “should be ignored by a PDF processor.” The modal force is SHOULD. §14.10.1 (physical 817, printed 802) marks the family deprecated with PDF 2.0. It describes web capture's save/retrieve/update/find operations and requires a web-capture information dictionary and content database. The children cover `/SpiderInfo` and its version/command references; URL and MD5 lookup trees `/URLS` and `/IDS`; content-set records; source/command metadata; and object `/ID` and `/PZ` attributes. EC3 #672 marks `/SpiderInfo`, `/IDS` and `/URLS` deprecated in their tables, corroborating these entries. #619 marks page and XObject `/ID` deprecated as well; `/ID` is contextual because it is not a target here beyond web-capture provenance.

The prepress clauses separately state their own deprecation. §14.11.4 “Separation dictionaries” (physical 834, printed 819) concerns preseparated pages represented by separate page objects, grouped through `SeparationInfo`; Table 400 names the DeviceColorant and permits ColorSpace information for an interactive preview. §14.11.6.1 “General” (physical 840, printed 825) describes traps created by a PDF-generating application, intermediate application, or RIP for press misregistration. §14.11.6.3 “Trap network appearances” (physical 842, printed 827) adds Table 404 process/trap metadata. §14.11.7 “Open prepress interface (OPI)” (physical 843, printed 828) describes replacing a low-resolution proxy with external high-resolution data before printing; #619 also marks XObject `/OPI` deprecated. None of these clauses requires this screen viewer to perform prepress generation or external OPI substitution. I found no reader SHALL in scoped text that requires interpreting these optional prepress metadata structures. The ordinary page/image content is rendered; annotation appearances remain governed by §12.5.5 and §14.11.6.2, outside this shard.

Ledger statuses match the source condition: all §14.10 rows are `inapplicable`; §14.11.4, .6.1, and .6.3 are `inapplicable`; aggregate .6 is `implemented` because .6.2 TrapNet annotation appearances are handled. ADR 1535's rule—quote the source condition for inapplicable rows—fits these explicit deprecation statements. ADR 1461 requires checking writer, print, and archive paths before leaving a row inapplicable; ADR 1172 classifies `/SeparationInfo` under the deprecated reader-side condition. The section 14.10 feature condition is not “this structure never occurs”: corpora and fixtures can contain it, and §7.7.2/#672 confirms entries exist.

There is a concrete qualification to the existing writer rationale. `support::web_capture()` builds a syntactically exact-xref **PDF 1.7** fixture with a catalog `/SpiderInfo`, `/IDS` and `/URLS` trees, page `/ID`, and a page-set dictionary. `a_piece_carries_no_web_capture_database` and `a_merge_carries_no_web_capture_database` assert that split/merge omit the trees and issue warnings. Split retains the source version; merge writes the maximum source version. Thus the current tests establish the deliberate omission/reporting behavior, but the accompanying comment that cites “deprecated with PDF 2.0” cannot be the reason for dropping metadata from this PDF 1.7 test output. The implementation is a transform data-retention policy, not a reader refusal, and no source rule found in this shard mandates preserving web-capture bookkeeping through merge/split. I therefore record the mismatch as a rationale/policy qualification, not a confirmed normative defect.

The same version boundary matters for the general producer SHOULD. Merge/split use generic object copying for page and XObject structures, and I found no blanket `SeparationInfo`/`OPI` removal in those writers. If a source PDF 2.0 carries such data and a transform emits a PDF 2.0 output retaining it, that appears contrary to §3.15's SHOULD-not-write recommendation. Since the source uses SHOULD rather than SHALL, I am not promoting this as a mandatory conformance failure. This was static path inspection only; no PDF 2.0 transform output was constructed and asserted. The archive path removes OPI from image and form XObjects, but those tests cite ISO 19005 requirements and do not demonstrate general PDF reader behavior.

The current comments also accurately explain why the records do not change displayed page content: SeparationInfo concerns a distinct preseparated workflow; OPI describes replacement of a proxy with an external original, and this viewer has no external OPI server. The optional interactive separation preview is not a reader SHALL. §10.8's computed separation simulation begins from composite page content and is distinct from these page-level `/SeparationInfo` dictionaries.

No new test draft is proposed: the remaining finding concerns the strength and scope of an explicit SHOULD and a writer-retention choice, not an unambiguous missing SHALL behavior. A future policy decision can add a PDF 2.0 merge/split fixture that states OPI/SeparationInfo and asserts either documented preservation or removal plus a report; it should not be presented as an ISO-mandated failure oracle. No tests were run for this shard.
