Bounded review: DPart hierarchy/metadata, annotation AF and associated-file examples

This pass sampled the consolidated ISO 32000-2 primary PDF (including its EC3 annotations), the current conformance ledger, implementation call paths and assertion bodies for §14.12.1–.4.2 and §14.13.9–.10. It builds on but does not repeat the prior GoToDp action review. It does not certify the full DPart writer family, every associated-file site, the MCAF reader, or UI beyond the annotation activation route.

The most concrete source discrepancy is EC3 Issue #612. On primary physical p.851, it replaces Table 409's `/DParts` array-of-arrays with a flat array of indirect references to immediate child DPart dictionaries and prohibits empty arrays. `doc/errata-read.md` currently records only the empty-array change. `document_part.rs` accepts the correct direct refs and the obsolete nested form, but its comments still label the nested form normative; the main hierarchy and DPart-AF unit fixtures also use the retired nested form. The earlier scratch GoToDp-node draft used it too and should be corrected before execution; parent already flagged that fix. This inherited permissive support should not be described as a conformance gap. This evidence points to stale source rationale and invalid positive-fixture premises, not a reader behavior failure: direct child references are already traversed. The §14.13.8 DPart AF draft uses current direct references, correct Parent links, each leaf's Start and the page's back-pointer, and keeps depth-first leaf order aligned with the ordinary page tree. Its separate catalog AF object controls the generic attachment read, while the DPart-only file and literal decoded bytes establish the DPart-root route.

§14.12.3 imposes a coherent hierarchy/page mapping on conforming PDF data: each page in a leaf range carries that leaf's `/DPart`, ranges are ordered in page-tree order, and depth-first leaf order agrees with that tree. The reader stores and walks the hierarchy but is not a full consistency validator. The subclause's producer requirements do not create a requirement to reject or diagnose a malformed mapping, so the draft is a valid positive fixture rather than a malformed-input test.

The Table 408 path reflects #609/#614's corrected two-hop structure: Catalog `/DPartRoot` to DPartRoot dictionary to its required `/DPartRootNode`. It carries `/RecordLevel` and `/NodeNameList`, and Part exposes the source dictionary. DPM remains opaque: its stated audience is a downstream production receiver, and the current reader has no JDF or print-purposing consumer. The allowed DPM key/value types and XML-name rules constrain files/producers; EC3 #86 adds PDF names to allowed DPM values and requires PDF-name keys after # expansion to be valid UTF-8. EC3 #290 withdraws Table 409's `/Metadata` stream entry and says XMP metadata streams shall not be used in DPart dictionaries. This is also a file constraint; it does not imply that a reader must reject a DPart containing that entry. The primary physical page 852 includes the correction, and physical 852–853 / printed 837–838 contain §14.12.4.2.

For §14.13.9, the effective source says an annotation dictionary may carry an `/AF` array of file specifications and that `/AFRelationship` describes the file's relation to that annotation. The current public viewer test clicks a generic Square annotation, verifies literal extracted bytes, and clicks elsewhere as a negative control; it does not demand a FileAttachment subtype. Its fixture generator computes xref offsets, but the test does not explicitly reject recovery, and the EmbeddedFile has no Params dictionary; §14.13.2 says Params SHOULD be present and, if present, SHALL include /ModDate; absence alone is not a mandatory producer defect. The draft supplies Params with ModDate and Size as a stronger valid-input fixture. The draft preserves the demonstrated interaction while adding a PDF 2.0 ID, Params with ModDate/Size, explicit no-recovery check and a neighboring annotation without `/AF`. EC3 #568 makes `/AFRelationship` required, and the existing fixture already supplies it. This is a fixture-quality improvement; the viewer route already exists.

§14.13.10's three model-level fixtures assert distinct file-site facts: catalog `/AF`, a marked-content range carrying a file, and a Form XObject `/AF`. They assert literal filenames, relationships, MIME values, and `Hello` text range for EXAMPLE 2. EC3 #637 corrects EXAMPLE 3's MathML subtype, and the current fixture uses the corrected type. EC3 #374 separately changes §14.13.5's property-list route to `/MCAF`; the printed Example 2 still names `/AF` and directly maps the named resource to a file-spec array. The example test is evidence for the example as printed, not for the amended MCAF property-list form. Table 409a is present in the held primary PDF at appended physical p.1015. It defines optional PDF 2.0 `/MCAF` as one or more file specifications with required `/AFRelationship`, and note 4 requires a named property resource because content streams cannot contain indirect references. EXAMPLE 2’s direct-array `/AF` remains a distinct legacy/example form; no reader rejection rule is inferred. Existing tests are model-level and do not prove panel UI behavior for all three examples.

Selected ADRs 1461 and 1040 remain sound on writer applicability and root-based enumeration for DPart AF. ADR 0295's caller audit is reflected in the annotation route, with current fixture validation caveats. ADR 1065 supports interpreting activation through the annotation handler boundary without importing clause 13 multimedia playback. No conclusion here relies on ADR 1184, which is about JPX baseline rules and contains no Issue #29 claim.

The two drafts are proposals only and were not run. No malformed-input rejection duty or broad DPart/associated-file certification is claimed.
