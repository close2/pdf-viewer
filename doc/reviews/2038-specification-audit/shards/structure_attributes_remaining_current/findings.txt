Scope and source check
======================

I checked the effective EC3 PDF itself. Page locators below are physical page / printed footer. Table 382 is physical 805 / printed 790 (its lead-in is physical 804 / printed 789); Table 383 is physical 806 / printed 791; Table 384 is physical 807–808 / printed 792–793; Table 385 is physical 808–809 / printed 793–794. These are the table pages, not just the section starts.

The EC3 PDF identifies its Table 382 and Table 383 definitions directly. Issue #346 adds “not inheritable” to ContinuedList and ContinuedFrom and to the Table 385 artifact entries. It does not add that property to ListNumbering or change Table 383. The table footers and actual cells were checked in the PDF extraction, not inferred from ledger locators.

§14.8.5.6 has the clearest source-to-consumer discrepancy. Physical 805's lead-in says the next table “define[s] the accessibility mechanism for non-interactive PDF forms”; it explains the field identity and value are on Form elements because interactive elements no longer determine them. Physical 806 / printed 791 Table 383 states five field roles, requires the tv field's textual value to be the Form element content, describes Checked/checked and its Off default, and supplies an alternate field name analogous to interactive /TU.

At b901326c, `pdf-model::Tree::print_field` parses these values and `pdf-model/src/structure/tests.rs::a_flattened_form_field_says_what_it_was` asserts role/state/description/default behavior. A repository-wide call search finds no production caller; the only other match is this test. `viewer_core::AccessibilityNode` has no PrintField role/state/alternate-name field, and `viewer-accessibility::tree` builds Form nodes from standard role, name/text, and widget state, not from PrintField. Thus the existing test proves parsing, not the source-described accessibility mechanism reaching a user. The current ledger row and ADR 0085 call the clause implemented on the basis of that parser. This is a concrete integration gap, not a claim that it renders incorrectly or that a noninteractive Form must become interactive. A follow-on public-tree test should show a flattened check-box with its declared name and state; controls should include an otherwise identical Form without PrintField and a textual-value Form whose content, rather than an attribute string, is exposed.

Table 382 needs a narrower reconsideration than the current rationale provides. Physical 805 / printed 790 states that ListNumbering values “shall be applied as described here,” defaults to None, and identifies the ordered values; the following sentence classifies all other lists as unordered. The NOTE says this attribute allows a content-extraction tool to autonumber, while warning that Lbl may already contain explicit results. The current code consumes neither the classification nor the scheme, and all standard List nodes cross as one generic List role. The NOTE is a good reason not to synthesize duplicate printed labels; it does not on its face cancel the ordered/unordered classification earlier in the table. ADR 0743/0748 correctly separate the continuation pair from the numbering scheme, but the rationale that treats the remaining entry solely as a renumbering request leaves this list-kind signal unaddressed. Whether the current public accessibility API has a place to express it needs owner decision; this shard does not label generic-list role as a proven source violation. ContinuedList/ContinuedFrom source, implementation, and consumer paths were not re-audited because those were covered by the preceding navigation shard and ADR 0748.

Table 384 and Table 385 were checked at the table cells and mapped against their ledger/test entries only to prevent scope drift. Table 384’s spans, header recursion/order/scope, Summary and Short are already represented by the cited model/headless/accessibility tests and earlier table shard reviews; I found no new defect here. Table 385's Type/BBox/Subtype and its “should appear only” wording are in the existing artifact shard; I found no new defect and do not certify its full assertion quality again. No role/namespace issue arose that required reopening §14.8.6.

No test draft is included. The PrintField issue is a missing consumer path, so copying the current parser test would only duplicate an assertion that already passes and could not prove delivery. A public-tree test requires an API representation decision first. For ListNumbering, an assertion likewise depends on deciding how the generic platform list role should carry orderedness. Both test shapes are specified above so a follow-up can build them against settled public behavior.
