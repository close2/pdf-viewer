It has the inverse: identical displayed names Twin, distinct exports x/y. Its V is nevertheless correctly the displayed name (the second item of each Opt pair), and its two-element array names two selected options. I [0,1] matches those same two options; the V-vs-I disagreement clause does not discard the matching I. The special mandatory use case does not constrain this test because /I is otherwise optional.

The source states that V is an array of strings when multiple options are selected; each string represents a selected Opt item, and no uniqueness constraint on displayed names is stated. In a valid file with two distinct options both named Twin, `[(Twin) (Twin)]` is the two selected names, and sorted indices [0,1] confirm the same pair. Current `form::selected` maps both strings to index 0 and then removes duplicate indices. The tracked public `Query::Fields` test fails [0] versus [0,1], while the distinct-label and single-index controls pass. This supports retaining B26, but qualify the rationale as the general array/multiset selection rule, not as an extension of #468's mandatory condition. The source does not spell out duplicate string multiplicity expressly; if the owner rejects the natural one-entry-per-selected-item reading, B26 becomes an interpretation gap.
