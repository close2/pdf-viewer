# Live scripted `charLimit` versus value truncation

This bounded review found an untested interaction between the accepted mutable `charLimit` property and the limit used for later text writes. Table 232 says `/MaxLen` is the maximum length of a text field's text (printed 541 / physical 556). Effective EC3 erratum #191 annotates the Table 232 row and adds that `/MaxLen` is an integer greater than or equal to zero. That correction constrains producer-valid values; the review does not infer reader rejection of a negative one. A834 item 1 explicitly includes script writes in the model-level cut. ADR 1617 maps `charLimit` to Table 232 `/MaxLen` and writes the property on save; ADR 2840 says script values are cut on entry to the edit log.

The model keeps two views of the limit. `FieldState::apply(Property::CharLimit(n))` changes the live state and `ViewState::script_properties` returns that override. On save, `scripted_entries` writes the override as `/MaxLen`. But `held_to_max_len` resolves `/MaxLen` from the original `Document`. `scripts::write_text` calls that helper for ScriptEdit value writes, and `set_field` also calls it after an open-action property has already been applied. Consequently, for a stored limit of 5 followed by ordered edits `CharLimit(3)`, then `Value("abcdef")`, the path appears to retain five characters while saving `/MaxLen 3`. In the reverse direction, stored 3 then `CharLimit(5)` and a six-character value appears to retain only three.

`max_len_live_property_spec_audit.rs` contains an exact-xref PDF 1.7 fixture with an AcroForm `/DA`, `/DR`, and `/NeedAppearances true`, a Helvetica resource, a one-page widget and an OpenAction. Its `ScriptRunner` supplies edits, so it tests model behavior and does not claim to execute JavaScript. Stored-limit controls cover both truncation and a value within the limit. Changed-limit cases cover a property edit followed by a script value edit and a property-only OpenAction followed by public `set_field`, in both the increase and decrease directions. Each computes one observation and compares the full live `charLimit`, live value, saved `/V` and saved `/MaxLen` tuple. The draft is not run.

This is a bounded consistency concern, not a claim that the PDF standard defines statement ordering inside ECMAScript. The source/owner record does say scripts may change `charLimit`, says those values are model-cut, and identifies `/MaxLen` as the field's text maximum. Parent review should decide whether that is sufficient to promote the proposed expectation or should remain an implementation policy question. No production or ledger changes were made and no Cargo command was run.
