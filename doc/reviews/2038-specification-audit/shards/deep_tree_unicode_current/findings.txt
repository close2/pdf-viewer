The current public destination tree test reaches an indirect root→intermediate→leaf hierarchy with exact Limits and separates ASCII A/a/b/z, including absent B. The multibyte composed/decomposed and prefix test is in `pdf-syntax/tests/trees_rectangles_audit.rs`, but uses a flat in-memory helper root. It cannot show that the public named-destination path preserves those keys end to end.

I drafted `drafts/deep_name_tree_unicode_destination.rs` as a valid PDF 1.7 destination fixture. It retains the existing ASCII lookups and adds `a\0`, UTF-8 decomposed `e + U+0301`, and UTF-8 composed `é`. The exact stored byte order is A, a, a-NUL, b, e+acute, z, composed-é; the non-ASCII order is deliberate because the composed key begins with C3 and therefore follows ASCII z (7A). Each key has a distinct literal page target by class, and exact child/leaf Limits cover the corresponding ranges. A zero-recovery check, indirect Kids, indirect destination arrays, page Resources make the fixture premise explicit. It also preserves the existing absent-B negative control and guards both recovery and xref-chain cutting. Absent `aa`, `e`, and `É` are negative controls. A small independent byte-vector ordering check verified the key order; no Cargo command was run.

The date path has no similarly plausible uncovered point in this bounded pass: §7.9.4 defaults and zone precision have direct parser tests; instant ordering is tested with an independently visible string-vs-instant reversal and an absent-zone equivalence; and T01 adds independent writer classification. Month-specific calendar validation beyond printed day range 01–31 remains the prior interpretation question and is not extended here.

The draft is only an assertion-quality improvement proposal. It is uncompiled/unrun and does not establish a production defect. Remaining scope is other name-tree consumers and key encodings, all malformed producer/recovery shapes, and all date-property readers/writers.
