Bounded Type 3 review: §§9.6.2.3, 9.6.4 fields relevant to Encoding, widths, FontMatrix and glyph bounds, and §9.6.5.3. I checked the primary text and EC3 transcription, current ledger entries, implementation paths, public assertion bodies and selected ADR rationale. This is not whole-clause certification.

The strongest direct assertion is the ordinary Type 3 fixture in `crates/pdf-model/tests/type3.rs`: the page has an exact xref, a real Encoding dictionary with Differences, matching CharProcs, explicit FirstChar/LastChar/Widths and two visibly different glyph descriptions. The public width test observes the second glyph's position under two FontMatrix scales, and the internal model test checks zero width outside the declared range. The residual audit test gives an omitted code tempting `/.notdef` and other CharProcs but expects no fallback, which aligns with §9.6.4 steps a-b and §9.6.5.3's no-default note.

One ledger claim needs narrower wording: the three tests named `a_named_encoding_maps_codes_to_glyph_names_out_of_annex_d`, `a_named_encodings_names_that_char_procs_has_no_key_for_paint_nothing`, and `an_encoding_name_that_is_not_a_predefined_encoding_is_no_encoding` use direct-name `/Encoding`. Although the generic §9.6.5.1 discussion covers named encodings, Type 3 Table 110 specifically requires the Encoding entry to be a dictionary. These tests therefore pin reader tolerance/refusal policy for malformed producer input; they are not valid-input conformance evidence. The scratch patch labels them accordingly without demanding rejection.

The same test file has two bounds fixtures that were internally inconsistent with the stated operators. A 72-unit stroke around a 750-unit rectangle reaches -36 and 786 in each axis, including square-rectangle miter corners. The scratch glyph explicitly sets width, cap, join, dash and miter limit (`72 w`, `0 J`, `0 j`, `[] 0 d`, `10 M`) rather than relying on incoming graphics state. Both the d1 glyph box and FontBBox are enlarged to `[-36 -36 786 786]`; the 1000-unit d1 advance is unchanged. A d0 inline image transformed by `[750 0 200 375 0 0]` reaches x=950, while the other glyph reaches y=750, so the font box becomes `[0 0 950 750]`. The patch parameterizes FontBBox in the test helper and adds an explicit no-recovery guard. No test or finding asserts clipping: ISO says marks outside nonzero bounds make behavior implementation-dependent.

The model reads widths from FirstChar and applies FontMatrix.a, so a rotated matrix leaves the horizontal advance horizontal. Tests cover two scale factors, outside-range zero behavior and a rotated case. The reader's no-inverse FontMatrix refusal is separately tested; this shard did not broaden that claim to all malformed matrix recovery.

For §9.6.2.3, `a_simple_fonts_subtype_selects_nothing` compares dispatch on intentionally invalid font-program bytes, so it proves the simple-font subtype does not get a separate MMType1 parsing path, not successful parsing of a real MMType1 instance. The clause says such an instance's embedded program is an ordinary Type 1 program and explicitly says the BaseFont naming convention is not prescribed. I found no reason to demand a reader parse instance coordinates from the name; the absence of a successful real-instance fixture remains an evidence limitation, not a demonstrated defect.

Cache behavior is not an ISO obligation. Type 3 glyph streams flow through the document stream cache; ADRs 0018/0427 describe implementation/performance choices. The generic cache tests do not certify a Type 3-specific raster cache, and no such certification is needed here.

EC3 #144 changes the example LastChar to 98 (the fixture already uses 98); #111/#128 are contextual but do not alter these claims.
