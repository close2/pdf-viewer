Second review of B19, B20, B25, B33 and B35 finds no premise correction that withdraws the executed failures. The five tests have different scopes; each finding should retain its own source condition and limits.

**B19 is valid-input behavior.** The primary text at physical 831 / printed 816 says page boxes should not ordinarily extend beyond MediaBox, then directly says a processor shall treat an extending box as its intersection with MediaBox. The first sentence is not an input-invalidity rule. The test uses ordered, nondegenerate boxes, exact xrefs, no recovery and complete interpretation. It first proves partial-overlap clipping, then uses boxes wholly outside the page to distinguish an empty intersection from the current larger-box fallback. `ViewArea=MediaBox` keeps the raster target nonempty while `ViewClip` selects each boundary. ADR 0414's absent/default-box rationale does not answer behavior for a present disjoint box. No fixture edit is needed.

**B20 cleanly isolates the defined degenerate-BBox case.** Table 74 at physical 236 / printed 221 requires `/BBox` clipping and says a zero-width or zero-height box still paints one pixel. §7.9.5 at physical 134 / printed 119 permits zero-size rectangles; §10.7.4 at physical 399 / printed 384 explains that their boundary is scan converted. The test changes only the vertical extent of a valid colored tiling pattern BBox from ordinary to zero, retains positive cell steps and a valid nondegenerate cell painting operation, and checks both a boundary band and a distant cell pixel. The executed red distant pixel contradicts clipping; no boundary-row ownership assumption is involved. ADR 0056's interpretation of the one-pixel note as grounds to drop clipping remains unsupported. Zero-width is a residual rather than an executed second case.

**B25 uses a conforming later-version profile that this parser cannot process.** Table 65 at physical 206 / printed 191 allows later ICC versions and requires the alternate when the processor cannot process that profile. Its fallback rule clips to ICCBased `/Range` before applying Alternate's range. Tables 67–68 at physical 207–208 / printed 192–193 support the Lab profile's data space and range. ICC's independent iccDEV validation returned OK for the generated ICC.2:2023 v5 Lab profile; the PDF stream's `/Range` matches Lab limits, and the alternate Lab range is wider so clipping at 127 is observable. The exact-xref PDF 2.0 fixture supplies IDs and correctly framed streams. The direct-Lab control is a strong relational oracle for the range-order defect and proves [50,127,0] differs from [50,150,0]. Its limitation is that both direct and fallback pixels pass through the same Lab-to-RGB renderer; the two-level output delta is executed evidence, not an independent analytic color-conversion oracle. Keep the claim specific to the unsupported-profile fallback branch.

**B33 is conditional on the product choosing to honor output intents.** Table 401 at physical 836 / printed 821 permits a missing `DestOutputProfile` when `OutputConditionIdentifier` names a standard production condition. The page uses the standard CGATS TR 001 condition and registry named in Example 1; the catalog's distinct custom intent has both required `Info` and an embedded GRACoL profile. The page-level `OutputIntents` entry is PDF 2.0. At physical 839 / printed 824, the source expressly permits processors to disregard output intents, but requires a page-associated intent if they do respect them. Exact-xref page-only/catalog-only/both controls are sound. The public `in_force_on_pages` result is an independent literal assertion; the raster values only show that this implementation's selected routes differ. Do not turn the observed RGB into a universal colorimetric requirement or claim all readers must honor output intent data.

**B35 is limited to the archive transparency survey.** Table 166 at physical 485 / printed 470 says annotation `/CA` shall not be used when an appearance stream exists; the appearance then specifies transparency. Issue #51 at physical 997 / printed 982 adds `/BM` handling to Annex Q, not a change to `/CA`. The PDF 2.0 pushbutton widget has valid field/annotation keys, an explicit non-regenerated opaque Form appearance, exact xrefs, and no recovery. `/CA` is permitted for this non-markup annotation, so `.5` is a valid, discriminating input; no `/CA` and `/CA 1` are opaque controls, while `/BM /Multiply` is the positive transparency control. Existing in-module coverage separately shows that CA inside an appearance's ExtGState is detected; this regression specifically catches misuse of the annotation-dictionary CA. Annex Q.1 says PDF 2.0 does not generally require every processor to run its detection method, so this is a defect in the implemented public `Survey` policy and downstream survey consumers, not a general rendering/conformance assertion. The survey test checks `stopped_short == false`; it does not establish full PDF/A conformance.

No new draft was warranted. Fixture correction, if any, is editorial qualification rather than an input repair: describe B19 boxes as unusual (not invalid), describe B33 as conditional on the selected intent-aware path, and keep B35 scoped to Survey. The current executed regressions are all present in this worktree's `doc/reviews/2038-specification-audit/findings.json` and corresponding wave logs.
