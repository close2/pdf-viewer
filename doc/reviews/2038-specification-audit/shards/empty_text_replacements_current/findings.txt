Empty text replacements audit (baseline b901326c)

Scope: EC3 §14.9.3, §14.9.4, §14.9.5 and the Table 355 rows for `/Alt`, `/E`, `/ActualText`; distinction between an absent dictionary key and an explicit zero-length PDF text string. Source locators are physical/printed: §14.9.3 physical 815 / printed 800; §14.9.4 physical 815–816 / printed 800–801; §14.9.5 physical 816 / printed 801; Table 355 entries physical 740–741 / printed 725–726; general text string §7.9.2.2 physical 131–132 / printed 116–117.

The strongest source-derived gap is `/ActualText`. §14.9.4 says its value “shall be used as a replacement, not a description” and is “a character substitution” for enclosed content. It specifies the structure-element route and the marked-content property-list route. A PDF literal string `()` is an explicitly present text string with zero decoded characters, while the absence of `/ActualText` states no replacement. The source supplies no empty-string exception. Accordingly, applying a present empty replacement should cut the enclosed text and add zero characters. Current code conflates it with absence: `structure::text_entry` returns `None` for an empty decoded string, `MarkedContent::accessibility` filters empty ActualText in the property-list closure, and `end_marked_content` only cuts content when the resulting `Option` is `Some`. For a line-end hyphen, this retains the hyphen and inferred line break, rather than removing the replacement span and joining the word. The same helper drops empty structure-element `/ActualText` before it reaches the marked-content fallback.

Existing assertions demonstrate ordinary nonempty behavior but not this empty case: `accessibility.rs::a_replacement_keeps_the_break_before_it`, `::consecutive_replacement_texts_are_not_separated`, and `::an_artifacts_replacement_text_replaces_what_it_encloses`; `tagged_pdf_fixtures.rs::a_soft_hyphen_reads_back_through_either_route_the_clause_names`; `text_render_modes.rs::actual_text_replaces_what_a_sequence_reads_back`. The artifact test is an important positive control for EC3 #483 but its replacement is `(7)`, not empty. The new draft models the clause's hyphenation example with a discretionary `co-` / `operate` line break: absence and `(-)` retain `co-\noperate`; explicit `()` should produce `cooperate`. It uses independent tests for the Span property-list, Artifact property-list, and structure-element routes. The property-list fixtures have no structure tree or MCID; the structure fixture has one MCID, avoiding B12's structure-scope defect. Each test uses exact xref/no-recovery checks and unchanged positive glyph counts to show replacement changes extraction rather than removing marks. The draft remains uncompiled/unexecuted.

`/Alt` and `/E` share the low-level empty filtering but not `/ActualText`'s normative rule. §14.9.3 makes Alt a complete/whole word or phrase substitution for the current element and directs property-list Alt use for marked content; it does not say that empty Alt suppresses underlying speech or that a reader shall treat it as absent. §14.9.5 defines E as a word or phrase substitution and mandates a word break before/after; an empty string is not a word or phrase, but the reviewed text provides no reader rejection or fallback rule. Therefore the code's empty-to-None behavior for Alt/E is not asserted as a bug, and no test is drafted by analogy. Current positive tests cover nonempty Alt and E in their speech consumers.
