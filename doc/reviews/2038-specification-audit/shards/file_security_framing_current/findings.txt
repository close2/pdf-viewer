## Main candidate: valid page-tree shape beyond the local traversal bound

On physical 117 / printed 102, §7.7.3.1 says the tree defines document page ordering and compliant processors “shall be prepared to handle any form of tree structure built of such nodes.” Table 30 starts physical 118 / printed 103 and defines the page-tree node’s `/Kids` and `/Count` constraints. The source does not state a numeric depth ceiling. The earlier `page_resources_current` shard confirms representative unbalanced/branching orders and selected malformed trees, but specifically left graph/bound behavior for later review.

`crates/pdf-model/src/page.rs` uses `MAX_TREE_DEPTH = 64`. A valid deeper tree may make `reaches_a_page` report false; `Pages::new` then scans objects for pages. The scan sets `found_by_scanning`, and `crates/viewer-core/src/notes.rs::about` makes that recovery visible to a host. Its literal note says the tree “leads to no page”; that description is false for a valid tree whose page is simply below the implementation bound, although it does disclose the scan and the resulting object-number order. The scan orders by object number, though, while §7.7.3.1 assigns order to `/Kids`. A valid tree whose leaf object numbers oppose its `/Kids` order can therefore have its order changed at the depth limit. This is a concrete boundary candidate, not yet a confirmed conformance defect: the user-facing notice may qualify the product’s resource-limit behavior, and the source does not provide a specific resource ceiling. Parent should decide whether truthful scan reporting is sufficient or whether the page-tree order must be preserved.

`drafts/deep_page_tree_order.rs` creates a shallow control and a depth-boundary unary tree with valid reciprocal `Parent`, `Kids`, and `Count`, page `MediaBox` and empty `Resources`, plus exact classic-xref offsets. Terminal `/Kids` is `[4 0 R 3 0 R]` while scan order is object 3 then 4. It checks public `Pages::get` page identity/order, per-page content bytes (blue then red), and includes `found_by_scanning` in the deep assertion diagnostic; the depth-64 control also asserts no scan. It is uncompiled and unrun. This is source-based expected ordering, not an assertion that a producer-malformed cycle must be rejected.

ADR 0782 correctly addresses an inconsistent `/Count` claim and does not justify altering a valid deep tree’s Kids order. ADR 1533 makes scan recovery explicit when a tree yields no page; it merits a scope question because a valid shape crossing the implementation bound is a different condition. No other page-graph policy is newly claimed here.
