Bounded audit: ISO 32000-2 §§7.9.6 and 7.9.7 tree traversal at the shared implementation boundary, with current public lookup/enumeration consumers. Source locators: name trees printed pp.119–121 / physical pp.134–136; number trees printed pp.122–123 / physical pp.137–138. EC3 #214/#307 affect key wording/producer constraints, not traversal depth. Annex C.1/C.2/Table C.1 printed p.850 / physical p.865 says every processor has practical limits and exceeding an internal limit causes an error; Annex C.3 printed p.851 / physical p.866 recommends balanced trees for portability. It sets no numeric name/number-tree depth limit.

The source defines tree shape (one root, indirect Kids, intermediate/leaf Limits, Names/Nums leaves and ordered nonoverlapping key ranges) but not a balanced-tree requirement or maximum depth. §7.9.6 explicitly says the structure can represent an arbitrarily large collection and enable efficient lookup without reading the whole tree. This does not require unbounded reader work: Annex C allows an implementation limit. It does mean a depth-65 unary chain is not intrinsically a cycle or invalid solely because it is deep. The `tree.rs` comment that a tree claiming greater depth “has a cycle or is trying to make the reader walk forever” overstates what the source establishes; cycle detection is already separate from the resource bound.

Current implementation sets `MAX_DEPTH` to 64. At depth 65 `lookup` returns `None`, indistinguishable from a missing key. The enumeration helper returns `()` from the cutoff and leaves the ordinary accumulated `Vec` intact, indistinguishable from a complete shorter tree. This helper feeds named destinations, page labels, embedded-file attachments, collection key listings, named pages, and the JavaScript library. For example, `PageLabels::read` builds ranges from `number_pairs` and `label` returns `None` where no range was collected; `attachment::attachments` returns a normal `Vec<Attachment>`; neither carries a limit/truncation diagnostic. I found no consumer layer that recovers this lost distinction. A limit/error is allowed in principle, but the current ordinary absence/partial-success answer does not communicate that the implementation limit was reached.

This is a bounded resource-limit/API observability concern, not a blanket conformance defect. Annex C does not define how a library must surface the error, and this audit does not invent a viewer UI requirement or require arbitrary-depth traversal. A useful regression needs an agreed result contract first: a valid exact-xref depth-64 tree as the complete positive control, plus a valid beyond-limit tree whose public result says “incomplete/unsupported” (or otherwise reports the resource error), instead of silently representing entries as absent. I did not draft a test that would either bless silent loss or assert an unratified reporting API.

The prior `trees_strings_current` drafts exercise valid indirect Kids and correct Limits at modest depth, including named destination lookup and page-label enumeration; they do not test boundary exhaustion. Separate `deep_page_tree_order_spec_audit.rs` is the page-tree issue B48 and is explicitly out of this shard. Structure, DPart, and parent-tree limits B03/B04/B36 are likewise not recertified here. NumberTree extension in ADR 2671/2672 has a writer-specific refusal result for unreadable extension inputs; that does not give generic read-only `number_pairs` the same diagnostic behavior.

No runtime test drafted; no Cargo/Git/production changes. Remaining question for the owner is which public model/host contract should report tree enumeration exhaustion. Once settled, add a boundary fixture at the generic helper's exact limit and route it through at least one key-lookup and one whole-tree consumer without duplicating unrelated tree-family audits.
