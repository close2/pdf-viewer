I verified the Type 3 source in the primary EC3 PDF and its physical/printed footer labels: Table 110 starts on physical page 332 (printed 317) and continues on physical 333 (printed 318); the mandatory glyph-invocation steps are on physical 334 (printed 319); Table 111 is physical 335 (printed 320). Table 110 requires the Type/ Subtype, FontBBox, FontMatrix, CharProcs, Encoding dictionary, FirstChar, LastChar and Widths entries. FontDescriptor is required only in Tagged PDF; EC3 #106 removes the table’s “shall be an indirect reference” restriction for that descriptor. Resources and ToUnicode are optional; Widths should be indirect. FontBBox is a glyph-space extent and does not require ordinary renderer clipping. The standard explicitly makes out-of-box behavior implementation-dependent.

Table 111 says d0/d1 wx must agree with Widths and wy must be zero. This is a source-side consistency condition. The PDF/A archive validator has a dedicated consistency check for rendered Type 3 glyphs, while the general model advances from the font Widths array. I did not find a PDF 2.0 rule requiring general readers to reject a producer that violates the duplicated-width condition, so no malformed-width rejection test is proposed. Similarly, Table 110's required entries do not on their own establish a reader refusal obligation when a malformed dictionary omits one.

The current primary corrections #111 and #128 are relevant. #111 replaces the glyph-description reference wording, adds an operator-category note subject to this clause's restrictions, and says recursion behavior is implementation-dependent; it does not erase d1 or image restrictions and the sampled operator tests do not cover every category. #43 corrects Table 111 operand labels, #44 amends the example Encoding, and #128 amends resource lookup and the current stream/font/page collision tests exercise the effective lookup. The bounds policy here follows the primary's express implementation-dependent language; ADR 0216 concerns font-metric selection line boxes and is not a Type 3 FontBBox decision.
