# Structure content-item dictionary cells: bounded audit

The source was read in `doc/ISO_32000-2_sponsored_EC3.pdf` by the actual table caption and page footer, not by nearby clause references: Table 357 is physical 746 / printed 731; its form-content context and multiple-`Do` rule continue on physical 747 / printed 732; Table 358 and its two notes are physical 749 / printed 734. Effective headings reflect EC3 #452 renumbering. The selected rows are implemented in the ledger, but this is not a whole-clause certification.

Table 357's five cells map as follows: required `/Type /MCR`; optional indirect `/Pg` (precedence and required-if-no-element-`Pg`, amended by #431); conditional non-page indirect `/Stm` and the absent-entry page-stream rule; optional indirect `/StmOwn`; and required integer `/MCID`. `Tree::child` carries these references and `content::named_sequences` matches MCID with stream identity. Existing tests use literal page/form MCID collisions and an appearance stream plus `/StmOwn`, so they distinguish the core stream and owner identities. One weakness in the older ledger note is that the named mixed-child test gives the MCR and element the same `/Pg`; it does not prove that MCR `/Pg` overrides a conflicting element page. `drafts/mcr_page_override.rs` now supplies that conflict plus an inherited-page control and a no-parent-element-Pg positive case; it uses a real page-stream MCID, the correct ParentTree array and exact xref/trailer ID. It is unexecuted. No reader rejection of missing producer-required values is inferred here.

Table 358's three cells are required `/Type /OBJR`, optional indirect `/Pg`, and required indirect `/Obj`. Table 358 says `/Pg` overrides the containing structure element and is required when that element lacks `/Pg`. The current parser implements this (`dict.get("Pg").or(page)`), and `Tree::logical_order` filters by the resolved page, but the relevant existing assertions do not exercise conflict precedence: the mixed-child fixture omits the OBJR `/Pg` and therefore tests inheritance; the ParentTree fixture's explicit OBJR `/Pg 3` matches its containing element `/Pg 3`. `a_pages_annotations_state_where_they_are` checks annotation_rectangles only and has no StructTreeRoot/OBJR. That leaves a narrow, source-backed assertion gap. `drafts/objr_page_override.rs` builds a two-page PDF with exact xref offsets and an annotation on page 2 while its containing element says page 1; it asserts the item appears in page 2's logical order, with an inherited-page control and a no-parent-page/explicit-child-page control. It is scratch-only and unexecuted.

The object identity and actual annotation consumer are otherwise strongly exercised: model tests check OBJR, ParentTree routes and page annotation association; the Viewer headless test checks literal annotation bounds and widget control; tagged-copy tests check structure-order placement and that an annotation named twice contributes once. ADR 0338's distinction between an annotation rectangle and invocation-specific XObject placement is consistent with the source; its placement discussion is deliberately limited. Table 358 NOTE 2 says one OBJR suffices for multiple same-page renditions. Where a producer needs to distinguish individual XObject `Do` occurrences it must associate particular invocations using MCRs, so this audit does not assert per-`Do` geometry through OBJR.

EC3 annotation handling checked against the actual target: #431 revises the `/Pg` wording for both MCR/OBJR; #339 separately changes Table 358's *used* to *required*, overlapping #431 but agreeing in meaning. The table row is on physical 749, despite the errata index filing the correction by a later heading. The Table 357 `/StmOwn` note and examples were checked on physical 746–748. ADR 1970's once-only object text rule is consistent with Table 358 NOTE 2 and NOTE 1's separation of partial object-stream text into MCR. No other uncovered requirement is promoted from this bounded pass.
