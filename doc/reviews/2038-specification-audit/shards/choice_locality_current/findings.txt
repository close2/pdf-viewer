Choice-field /TI and /I locality audit

Source. §12.7.4.1 (physical pp.545–546 / printed pp.530–531) expressly says inheritable field attributes are designated in Tables 226 and 227. Table 226 (physical pp.545–546 / printed pp.530–531) marks /FT, /Ff, /V and /DV inheritable. Table 234 places /Opt and /TI on physical p.557 / printed p.542, and /I on physical p.558 / printed p.543. Its /Opt, /TI and /I are not marked inheritable (unlike Table 230 button-field /Opt). The absent-/Opt note says no choices SHOULD be presented, a recommendation. Its /TI row sets the default at 0. EC3 #468 applies to the /I row on physical p.558 / printed p.543; its actual StrikeOut/Caret correction removes the retired MultiSelect/value-array limitations. This review keeps that correction in force.

The model needs to look through a separate widget annotation to its associated terminal field: a widget dictionary can carry /Parent to that field. That structural hop does not by itself make every Table 234 entry inheritable above the terminal. `inheritance.rs:42` `READ_UP_THE_CHAIN` currently includes /Opt, /TI and /I in the same aggregate as table-designated inheritable entries; `Inherited::of` merges those from all ancestors. `form.rs:670–719::options` also takes /Opt from the full chain; `form.rs:653–661` obtains ChoiceControl.top via `inherited_number(TI)`, and `form.rs:722–785::selected` finds the first /I array in `field.chain()`. Both permit a nonterminal ancestor's Table 234 entries to influence a terminal choice field. `appearance.rs:4050–4070::list_box_options` independently obtains /TI through the same lookup for rendered list content.

Existing assertions test local/merged choice fields: `the_top_index_says_which_option_the_list_starts_at` covers default, explicit, and out-of-range TI; `choice_value_wins_when_the_stated_index_disagrees` covers V-over-I; `duplicate_choice_labels_spec_audit` covers #468. None distinguishes widget-to-terminal access from terminal-to-nonterminal leakage. The analogous `field_aa_noninheritance_spec_audit` and `rich_text_default_style_noninheritance_spec_audit` establish a fixture pattern for noninheritable entries, not evidence for TI/I.

ADR 2448's rationale that a separate widget does not hold TI/I supports reading the terminal field through the widget's Parent. It does not authorize inheriting those values through a further nonterminal ancestor. The 13-key aggregate currently erases this boundary. The /TI default behavior is the strongest requirement-level concern. The /Opt presentation difference is covered only as the table's SHOULD recommendation; /I is a locality/assertion question because required-I inputs must state I on the terminal field. No malformed-PDF rejection claim is made.

Draft `drafts/choice_locality_spec_audit.rs` uses a one-page PDF 1.7 with exact xref, AcroForm `/NeedAppearances true`, `/DA` and `/DR` font resource, page/widget `/P`, reciprocal `/Parent` and `/Kids`, and coherent option/value pairs. It asserts: terminal `/TI 1` wins and is read through its separate widget; absent terminal `/TI` yields the specified default 0 despite an in-range ancestor `/TI 1`, matching the same terminal under a parent with no TI. For `/I`, the parent owns its own Opt/V/I consistently; the terminal owns a different coherent Opt/V. The terminal-local I control demonstrates widget-to-terminal access; the missing-local-I comparison uses same terminal data under ancestors with and without I and asserts only equality, not a chosen fallback index. The draft is not run. Its /Opt control tests the table’s recommended absence behavior and is not a mandatory conformance finding. It asserts public `pdf_model::form::fields` ChoiceControl values consumed by viewer-core/UI; it does not assert exact pixels or AP regeneration. The /I same-input comparison has no fixed fallback-index assertion; the terminal-local positive control is separate.
