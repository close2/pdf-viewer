Public-key encryption current audit — b901326c

Source and scope

I reviewed the supplied primary ISO PDF at physical pages 101–103 (printed pages 86–88), with the repository's text extraction at `doc/md/ISO_32000-2_sponsored_EC3.md:2847–2945` used for searchable wording. The PDF page text confirms §7.6.5.1, Table 23, Table 24, and the printed §7.6.5.3 algorithm text. EC3 #196 inserts an effective §7.6.5.3 Public-key security permissions heading while saying current text and Table 24 remain unchanged (`doc/errata-read.md:464`); therefore the printed algorithm .3 becomes effective .4. This audit preserves original published numbering and calls out the changed effective numbering.

The reader's direct requirement in .1 is recipient-list scan and certificate match, followed by private-key decryption. Current `public_key.rs::scan` walks lists in order, uses pdf-pki CMS recipient matching, and returns no-match separately from a matched but non-opening key. The PDFBox witness tests have independent expected page strings and actual certificates/keys; no-key, wrong-key, and EC-key positive/negative controls supplement them. `viewer-core/tests/recipient_key.rs` verifies public consumer handoff, including a document-open event when no key is held. These support representative reader paths without certifying all CMS or certificate cases.

In .2, the inspected code separates s3/s4's Table 23 recipient array from s5's crypt-filter lists and rejects the named cross-pairing of SubFilter/V versions. The Table 24 adapter treats the permission field as big-endian four-byte data and then maps the resulting word. Existing s3/s4 assertions set bits 3 and 5 and check print/copy positive plus modify/annotate/owner negative; this does not directly prove the full Table 24 permission mapping the ledger claims. `drafts/table24_permissions_unit.rs` supplies a focused source-derived helper test for each documented flag, ignored bit 10, unrelated bits, and s3/s4/s5 revision values. This helper-level draft does not prove the four-byte byte order or full CMS/PDF adapter. Its second test snippet separately asserts that `pdf-model::restriction::withheld` honors the consumer-facing `owner` grant for all seven restriction operations even when each individual permission boolean is false. Both are drafts and were not run.

Table 24 position 2 is not merely another grant boolean: its text says it "permits change of encryption and enables all other permissions." The code represents it as `Permissions::owner`, and `withheld` returns no restriction for owner access. The generic checked-in downstream test currently proves the owner exception for form filling and annotation; the draft expands it to all represented operations. Position 10 requires careful distinction: processors ignore it, but PDF writers shall always set it to 1 for compatibility with older readers. Table 24's assistive-technology carveout is attached to bit 5 and says a reader shall behave as if bit 5 were set for that limited purpose; it is not conditional on bit 10. No accessibility consumer claim is established by this permission-map test. A bit-10-zero input is therefore a processor robustness comparison, not a proposed conforming writer fixture.

The key derivation and CMS opening have useful independent controls: the two `ExposedMeta` PDFBox witnesses distinguish the four-0xFF metadata input; s3/s4 files have actual OpenSSL CMS envelopes and expected page text; the KARI document has expected plaintext and an RSA nonrecipient control. The PDFBox samples independently cover AES-128 and AES-256. Primitive vector and external-envelope coverage is recorded in pdf-pki ADRs, but this shard did not rerun or verify the whole algorithm matrix. EC3 #16 affects Table 27's raw byte-string representation; code retains raw bytes for hashing.

The stream-own-recipient test path belongs partly to Table 27 / §7.6.6: real generated CMS fixtures assert successful content, wrong-recipient stream refusal at EFOpen, and failure at DocOpen. ADR 2810 itself says the V5 stream-local variant is reasoned, not witnessed; retain this caveat. ADR/test descriptions cite generator scripts retained with their implementation rounds, but those scripts are absent from this checkout. The checked-in artifacts' expected plaintext/control assertions are reviewable, but this audit cannot reproduce the generation from the current tree.

Unsupported crypto and obligations

The primary PDF lists all seven envelope ciphers, including four marked deprecated; deprecation alone is not a reader refusal requirement. ADR 2809 says these are read-only and supported against standards vectors and OpenSSL envelopes. RSAES-PKCS1-v1_5 and OAEP are implemented; EC key agreement covers supported curve paths. The optional one-pass ECMQV and unavailable brainpoolP512 support gaps are explicitly identified by ADRs 2821/2827 and are not silently represented as complete cryptographic coverage. User credential handling in ADR 2822 is a product input/policy path, not an extra PDF-reader requirement.

Change and validation

Read-only comparison of 4015a9ae..b901326c shows `public_key.rs` added and `public_key_witnesses.rs` changed (+430/−19). The new assertions expand from the earlier refusal state to PDFBox s5, real s3/s4, stream-own recipients, and EC KARI. No Cargo command was run; parent owns current-baseline execution. Additional residuals are recorded in `features.json` and `decisions.json`; this shard does not certify all of §7.6.5, all CMS/X.509 cases, or all algorithm combinations.
