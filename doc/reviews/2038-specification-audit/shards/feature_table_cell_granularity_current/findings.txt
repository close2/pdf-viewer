This inventory selects two broad implemented form-dictionary rows rather than treating their ledger status as evidence that each entry is equally covered. I read the Table 224 and Table 226 pages in the effective EC3 PDF (physical pages 544–547; printed pages 529–532), then compared each cell with the current feature records, code consumers, tests, and the targeted ADR sections. The detailed cell map is in features.json.

Table 224 has a distinct reader or writer path for every key. `/Fields` starts field-tree and signature discovery; `/NeedAppearances` is a writer-side residual condition; `/SigFlags` contains a positive signature declaration and a discretionary append-only warning; `/CO` is a conditional recalculation sequence; `/DR`, `/DA`, and `/Q` feed variable-text appearance construction; `/XFA` carries a deprecated optional static/dynamic form resource. Coverage is uneven: CO order and quadding have direct behavioral assertions, XFA stream/array parsing and archive preservation have separate evidence, and DR/DA are observed on appearance paths. The bounded NeedAppearances residual is the table-wide “all visible widget annotations” writer condition versus save code that marks changed widgets owed and does not census untouched widgets. Existing tests establish changed-widget residue and successful appearance construction. Because an untouched visible widget without AP may be a nonconforming producer input, this is an unresolved writer-boundary question rather than a confirmed defect.

ADR 0181 originally inferred absent/clear bit 1 meant no signature fields; ADR 2814 section 6 corrects that reading. Current tests assert public candidate discovery for set, absent, and zero flags, and the unit test `pdf-signature/src/signature.rs::tests::a_form_declaring_no_signature_fields_is_walked_all_the_same` independently exercises absent flags. They establish discovery, not cryptographic validity. Bit 2 remains a may about warning before full save, not a mandatory dialog.

Table 226 is also a collection of different contracts: FT is terminal type with inheritance; Parent/Kids encode immediate tree edges and a merged-widget exception; T is optional after EC3 #28, while TU is UI/accessibility naming and TM is export naming; Ff/V/DV are inheritable and flow into controls, edits, reset, and save; AA connects field-level events to widget triggers. Prior tests substantively cover inheritance depth, reset behavior, T absent-versus-empty, TU shown-versus-identity, common flags, and several widgets/merged fields. They do not prove every multi-key combination. In particular, the common inherited-V/shared-parent persistence candidate is separate from the runtime read path: parent reported its runtime control passed and its save/reopen assertion failed.

Table 226 says `/TM` is the mapping name to use when exporting interactive form field data and does not mark it inheritable. The existing coordinate test is `crates/pdf-model/tests/form_actions_spec_audit.rs::submit_coordinates_suppresses_name_for_space_tm`; it covers suppression for a one-space mapping and the no-mapping fallback. Parent reports a public HTML-only export test where `/T person`, `/TM exportkey`, `/V Ada` still emits `person=Ada`, while a no-`/TM` control emits the same expected `person=Ada`; that is a confirmed HTML export gap. No conclusion is made for FDF/XFDF. The implementation also walks ancestors for coordinate `/TM`; its terminal-vs-ancestor test draft remains unrun, and Table 240 needs to be reconciled before classifying it.

I also found code for Table 226 `/AA` trigger resolution but no cell-isolated assertion in the reviewed feature record. Action and trigger shards test their own routes; they cannot automatically certify that a field-level additional action inherits and dispatches with widget proximity. This remains a bounded assertion gap, not a claim that every scripting effect is missing.
