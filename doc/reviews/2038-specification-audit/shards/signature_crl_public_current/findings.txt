# Current-time CRL interval through public signature reporting

**The public path has an unambiguous host-current context.** ISO 32000-2:2020 + EC3 §12.8.3.4.7 (physical p. 598 / printed p. 583) says a CRL is appropriate for a current-time check only when current UTC is in the interval delimited by `thisUpdate` and `nextUpdate`. Section 12.8.3.4.8 (physical p. 599 / printed p. 584) separately covers historical signer-path validation and allows later-collected evidence when its historical conditions hold. EC3 does not change these two conditions. The test draft does not ask a generic revocation API to infer which mode the caller intended.

`viewer-core::notes::signatures` begins with `BestSignatureTime::now(trust.anchors.at())`. This fixture has no signature timestamp or document timestamp, so nothing establishes a past instant. The command's host-supplied `TrustPolicy.anchors.at()` therefore is the fixed current instant. `about_one` passes that instant through `Signature::trust`; `trust::Search::walk` calls `revocation::status_within` for the signer certificate. The fixture's host instant is deliberately generated after its certificate `notBefore`, and OpenSSL independently verifies that certificate path at that exact instant.

**The public Report route appears to accept a CRL that is not yet current.** `revocation::from_list` validates issuer/key usage and verifies the signed CRL, then preserves a listed `Revoked` answer before freshness logic. For an unlisted certificate it calls `Issuance::admits(thisUpdate)`, whose default imposes no lower bound, requires `nextUpdate`, and then returns `Good` whenever the requested instant is no later than `nextUpdate`. The implementation's comment explicitly treats a CRL issued after the queried instant as fresh evidence. That can serve a historical best-signature-time question, but the public route also uses it when the question is current host UTC. The ledger marks both §12.8.3.4.7 and .8 `implemented`; its .7 note specifically claims the full interval.

The proposed `current_crl_public_report.rs` addresses the gap with one public trigger and a paired positive control. Both PDFs are exact-xref, unrecovered, PDF 2.0, detached CAdES signatures with a real `SigningCertificateV2`; each CMS signature covers the whole document except its Contents value. The same PDF structure carries an empty, issuer-signed CRL in Catalog `/DSS /CRLs`. Both files use the same logical PDF ID, leaf certificate, root anchor, fixed host time, signature shape, and `nextUpdate`; only the CRL `thisUpdate` differs relative to the validation time. The current CRL is one minute before host time and must permit the `Good` positive control. The future CRL is one minute after host time and must leave status undetermined; with host `RevocationMustBeGood`, `Report` must withhold “signature is locally valid.” Both test branches require the successful RSA signature and signer-certificate binding sentences, so an unrelated signature failure cannot satisfy the negative assertion.

The reproducible generator and public artifacts are in `generate.sh`, `make_pades.py`, and `generated/`. I ran the generator successfully after adding explicit `openssl cms -verify ... -attime HOST_EPOCH` and `openssl verify -attime HOST_EPOCH` checks. Both CRL signatures verify with the root; each PDF passes `qpdf --check`. These checks do not prove all PDF producer-conformance claims, but the generated xref is exact, the PDF parser recovery guard is part of the draft, and the CMS check verifies the actual signed ByteRange. The generator removes its ephemeral CA/signer private keys and CSRs; no private material is retained.

**Decision boundary.** ADR 1112 remains right that a later-issued list may answer a proven historical time; its shared one-ended behavior cannot also be the .7 current-UTC rule. An explicit caller mode, or an equivalent explicit current-time applicability argument, is needed while preserving the historical path. ADR 1067's asymmetry is untouched: an explicit revocation entry remains a revocation statement even if its list is stale; this issue asks only whether “not listed” establishes Good. ADR 2775's policy-specific issuance bound is not exercised by the draft and should remain distinct from the PAdES current-time interval.

I did not run Cargo or claim the draft test has passed. Parent should promote and execute it. If the expected future-CRL assertion fails, that is direct public evidence of the current-time applicability defect; if it passes, inspect the public note and actual material/result path before retaining the finding. The previously considered duplicate-call low-level test was rejected because identical mode-less inputs cannot coherently be required to yield two answers. This fixture avoids that problem by making the call context unambiguous through the real `viewer-core` host-clock path.
