# EC3 errata dispositions, batch 4

This review covers only issues #310, #311, #328, #330, #365, #366, #367, #379, #398, and #403. I read the actual annotation objects, rectangles, replies/replacements, and the effective primary text in `doc/ISO_32000-2_sponsored_EC3.pdf`. Physical page locations below are verified against the printed footer; an issue ID mention elsewhere is not treated as coverage.

The clearest source-boundary point is #311. On physical p.396 / printed p.381, StrikeOut 4489 has no replacement and spans the entire Type 5 paragraph: the one-halftone-per-component sentence, the contrast with a graphics-state halftone applying to all components, and the gray-screen/transfer-function fallback for nonprimary colourants. The transfer shard correctly limits its positive claims to DeviceRGB primary components. ADR 0505's surviving Table 52 and Type 5 introduction may support that selected path, but the deleted paragraph cannot be cited as a current requirement. #310 is a distinct producer clarification: its Caret reply to StrikeOut 4443 on physical p.391 / printed p.376 says when a Type 5 component's `TransferFunction` entry is required; the related Text note is at physical p.395 / printed p.380. Neither issue creates a general reader rejection duty, and the four executed RGB-primary raster controls do not certify nonprimary or nonstandard components.

The other replacements are bounded clarifications, not reader failures. #328 removes only the contents-based narrowing from both file-identifier sentences (§14.4, physical p.734 / printed p.719); it leaves the optional uniqueness computation as a `should`. The existing ID audit reads both strike rectangles and ran public writer controls for incremental updates and new files. #330 adds a Text note at physical p.812 / printed p.797 clarifying that `/Lang` values are text strings with literal or hexadecimal syntax. The existing language consumer path uses generic PDF text-string decoding; a direct hex-form `/Lang` integration control could make that path more explicit, but absence of this extra assertion does not establish a defect.

#365's two Carets point Table 2's brace rows to footnote (a); the actual scope text is in separate Text annotation 1452. Braces are regular outside a Type 4 calculator program and delimiters in that program's tokenizer. The lexer, name writer, and Type 4 path have separate existing assertions. #367's StrikeOut/Carets at physical p.728 / printed p.713 change the ProcSet sentence's history to distinguish “considered unnecessary” from “deprecated in PDF 2.0”; the PostScript-compatible output condition remains. The current raster-output route keeps §14.2 conditionally inapplicable; no ProcSet consumer or output route is claimed.

#366 illustrates why paired marks matter. The physical p.55 / printed p.40 Text note says the Predictor DecodeParms `/BitsPerComponent` is unrelated to the similarly named image-dictionary entry. On physical p.274 / printed p.259, StrikeOut 3632 with Caret 3633 inserts “the”; StrikeOut 3634 removes “if a predictor function is used” from Table 87's statement that LZW/Flate deliver samples of the specified size. Thus image sample-size consistency is not limited to predictor use, while the predictor decoder parameter remains a separate field. These are conforming-producer consistency requirements. A malformed mismatch test would not prove an obligation to reject; current direct filter/image tests assert each interpretation separately. This is at most an optional paired-field consumer control.

#379 is a producer-syntax correction, not a rejection command. The two StrikeOut/Caret pairs at physical p.48 / printed p.33 replace the object and generation number text: object numbers are positive digit strings without `+` or leading zeroes; generation numbers have the same syntax except that `0` is allowed. §7.3.10 continues on physical p.49 / printed p.34. Existing parser tolerance for other spellings must be described as permissive recovery rather than as source-approved syntax.

#398 corrects the BOM glyph in the §14.3.3 example. The primary PDF's StrikeOut object 6734 and Caret 6736 are on physical p.732 / printed p.717. `metadata_current/findings.txt` retained physical747/printed732; its parent-review and decisions already used732/717 correctly. Parent reconciles the stale findings prose in this checkpoint. The writer's UTF-8 U+FEFF behavior is already directly asserted; this issue does not expand reader acceptance requirements.

#403's five notes are local consequences of direct-object rules, not a blanket rule against metadata or Associated Files: physical p.81 / printed p.66 (xref stream dictionary); p.157 / p.142 (extensions dictionary); p.583 / p.568 (signature dictionary when a byte-range digest is present); p.899 / p.884 (linearization parameter dictionary); and p.902 / p.887 (hint-stream dictionaries). The applicable restrictions are contextual producer constraints. Their notes do not require general reader rejection. In particular, xref-stream directness is a bootstrap exception and must not be generalized to ordinary streams.

**No confirmed new behavior defect emerged.** The reviewed implementation paths either have relevant assertion evidence or bind producer choices, optional output routes, and reader-discretion areas. Hexadecimal `/Lang` and paired image/filter BitsPerComponent consumer assertions could improve coverage, but no failure draft is warranted from these corrections alone.
