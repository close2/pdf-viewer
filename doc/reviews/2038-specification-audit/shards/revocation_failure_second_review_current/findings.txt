B41 — retain; the private seam is valid for the narrow time-selection claim

EC3 §12.8.3.4.8 (physical 599 / printed 584) requires current-time checking of every certificate on the timestamp-unit path. It says that where any certificate was revoked for `keyCompromise`, `cACompromise`, or no reason, token UTC cannot be treated as reliable and cannot be used; other reasons are usable only if the revocation occurred after token time. This is a specific PAdES rule, not a statement that every revoked token or every unknown revocation answer has the same effect.

The current test `crates/viewer-core/src/notes/timestamp_revocation_spec_audit.rs` calls the exact `signature_timestamps_instant` helper that is the consumer of `Time::Established`. That helper currently selects `at` for every `Time::Established { at, .. }`, ignoring its `revocation` field. The fixture is a real CAdES CMS carrier, its signature-time-stamp attribute has an imprint over the actual CMS `SignerInfo.signature`, and the generator README records independent OpenSSL verification of outer CMS, token, chains, CRLs and the revoked serial/reason. Both TSA and document certificates remain valid through 2036. The positive CRL is Good; the negative current CRL is root-signed and lists the TSA certificate as KeyCompromise effective at genTime; both CRL windows include `genTime` and verification now (16:12:23Z and 17:12:23Z respectively). The test checks the positive selector result, confirms the exact Revoked(KeyCompromise) result, checks a corrupted-CRL Unknown control, then expects the consumer to return None. The prior recorded run has one failing selector assertion.

Retain this as a direct consumer-level defect: the function that supplies the later signer check with a best-signature time is using a time the source says cannot be used. Qualify the evidence: the Rust test invokes a private helper, not `Command::Report` or the full signer-verdict fallback. It does test the actual production selection consumer, not just a parser or timestamp API. The outer CMS's signature verification is in the committed fixture's independent verification record, not an assertion inside this Rust test. Do not claim a complete public verdict finding or any required user-visible note wording.

B44 — retain as a current-time PAdES case; do not globalize the rule

EC3 §12.8.3.4.7 (physical 598 / printed 583) states that a CRL for current-time validation is appropriate only when current UTC lies in the interval delimited by `thisUpdate` and `nextUpdate`. The current source code's `revocation::from_list` checks the issuer, CRL signing permission, signature and listed serial; for an unlisted certificate, the no-policy branch rejects only when the requested instant is later than `nextUpdate`. It does not reject a current-time query earlier than `thisUpdate`. `notes::signatures` starts from the host-supplied clock and passes it to `Signature::trust`; the test has no trusted timestamp that could choose a historical time.

The promoted `crates/viewer-core/tests/current_crl_report_spec_audit.rs` is a strong public-path test. Both PDFs are exact-xref, guarded against recovery, and the shared helper requires the PDF ByteRange digest, RSA CMS verification, signer-certificate binding and reported host time. Their fixture README gives host time 2026-11-16 17:09:46Z, leaf validity starting 16:39:46Z, a same-root/same-leaf signature pair, and an identical nextUpdate at 2027-01-15 17:09:46Z. The positive CRL's thisUpdate is one minute before the host instant; the negative CRL's is one minute after. Both CRLs are signed by the issuer. The positive Report says locally valid under `RevocationMustBeGood`; the parent-run record says the future-thisUpdate case also says locally valid, contrary to the current-time interval. Parent independently verified both actual ByteRanges, CMS signatures, signer path at host time, CRL signatures and qpdf syntax.

Retain the finding for the public PAdES/current-time context. ADR 1112 deliberately moved generic freshness to a one-ended test based on ETSI EN 319 102-1; ADR 1067 keeps known Revoked answers distinct from Good; ADR 2775 supplies policy-specific issuance bounds. The implementation comment and historical test explain why a CRL issued after a *historical* signature time can answer that past query. That rationale cannot be applied to current .4.7 without contradicting its explicit two-ended interval. Thus the actionable boundary is current versus historical mode at this PAdES consumer, not “all future thisUpdate is always stale.” The generic evaluator's one-ended behavior may remain appropriate for historical validation and policy profiles.

B47 — retain the producedAt failure, explicitly separate capture provenance

EC3 §12.8.3.4.8 (physical 599 / printed 584) says historical OCSP material is appropriate only if it was captured before expiry of the signer's certificate and its response-level `producedAt` is after the trusted past UTC instant. Those are two separate conditions. `revocation::from_response` preserves `BasicResponse.produced_at` but the Good-response branch uses authorization, `SingleResponse.thisUpdate`, `nextUpdate`, and status without comparing `producedAt` with the asked time. The public Report path supplies the trusted signature-timestamp time to the signer-path check.

`crates/viewer-core/tests/historical_ocsp_report_spec_audit.rs` shares one signed PDF revision, CAdES signer, RFC 3161 token, signer/TSA anchors, host time and TSA CRL across its two inputs; the appended DSS OCSP payload is the varying evidence. A helper used in both branches asserts PDF ByteRange digest, CMS signature, SigningCertificateV2 binding, token imprint and exact historical time before asserting local validity. At trusted T=2026-11-16 17:09:09Z, early response producedAt is 17:09:06Z and late is 17:09:11Z. Both say Good, and both thisUpdate/nextUpdate windows bracket T: early 16:59:06–18:09:06Z, late 16:59:11–18:09:11Z. The five-second difference in windows is recorded rather than misdescribed as identical; both pass the independently checked window condition. The fixture's signer cert is valid from 17:09:06Z in 2026 through 2036. Its OCSP responses and DSS were generated before expiry as part of the fixed fixture construction, but the PDF does not cryptographically timestamp the appended DSS revision. Parent's recorded public run says the late positive control passes and the early producedAt response also yields local validity; independent OpenSSL checks cover ByteRanges, CMS, token/imprint, OCSP signatures/CertID/status, certificate paths and CRL; qpdf checks syntax.

Retain B47 for the separately explicit producedAt rule. Qualify the capture-before-expiry predicate as unproven for arbitrary input: this test's fixture is created before signer expiry, but `producedAt` is not proof of capture time and the appended DSS update lacks a trusted timestamp. The negative assertion is not a proof that all PAdES historical semantics are wrong. ADR 1112's freshness rule does not address response-level producedAt; ADR 2775 explicitly distinguishes OCSP SingleResponse `thisUpdate` from `producedAt`, which is useful to the distinction; ADRs 1067 and 1071 preserve separate revocation evidence and trusted timestamp semantics.

No clause-wide certification, live OCSP/CRL retrieval, external trust-list conclusion, or new test run is claimed.
