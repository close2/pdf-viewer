# Rendering intent, transfer functions, and selected halftone transfers

This is a focused source/assertion review at baseline `b901326c`. It is not a clause-wide certification. Effective source titles and locators are in `features.json`; printed and physical PDF page numbers are distinguished there.

For §8.6.5.8, EC3 #63 strikes the Table 69 note phrase that excused support for all PDF rendering intents. The remaining text still requires recognition of the four standard names, while extra device-specific intents may be supported. The implementation and public CPU raster tests distinguish Absolute, Relative, Saturation, and Perceptual, as well as `ri`, ExtGState `/RI`, image `/Intent`, current-state default and unknown-name fallback. Profile fixtures use distinct transform outputs, so the tests are not merely asserting shared-table interpretation. No sampled valid-input defect found. ICC conformance and complete black-point/output-intent behavior are outside this review.

For §10.5, source specifies a single transfer function or four-entry array; RGB uses the first three entries. It describes transfer after color-space conversion and before any halftoning, componentwise, with subtractive inputs converted to additive form. The existing transfer unit test maps all four slots with the same function, so it cannot detect selecting the gray slot for RGB. Existing `/TR` consumer tests use CpuRasterizer, but the Type 1 and Type 5 `/HT` override assertions apply the display-list map directly in a helper rather than testing the public raster consumer. `/TR2` precedence over `/TR` in Table 57 also lacks a distinct-value assertion in the inspected tests. The draft has exact-xref raster cases for distinct four-slot functions and `/TR2` precedence with a `/TR` control.

For the selected §10.6.5 TransferFunction entries, current code routes Type 1/Type 5 overrides into the transfer map. Do not conflate the continuous-tone permission to ignore the halftone screen (§10.6.5.1) with the independent transfer mapping defined in §10.5. Table 129 provides a Type 6 stream-dictionary TransferFunction and is not covered by the inspected tests. `drafts/halftone_transfer_public.rs` adds public CPU-raster assertions for Type 5 `/Red` plus `/Default`, Type 6 stream override, the four-entry RGB map distinction, and `/TR2` precedence. Each override has a valid same-route control without the override. Expected constant outputs are independently given by the function C0/C1 constants. The fixture writes exact xref offsets, asserts non-recovery and complete interpretation, then rasterizes through `CpuRasterizer`.

EC3 #310 is a Type 5 producer clarification for nonprimary/nonstandard-primary components; it does not by itself require malformed-reader rejection. EC3 #311 strikes the paragraph about nonprimary-colourant fallback. This audit's positive claims are limited to DeviceRGB primary components. The draft is unexecuted; no Cargo was run by this shard. Parent execution is needed before treating the proposed assertions as verified. No screen algorithm, screen name dispatch, spot functions, nonprimary component behavior, or CMYK-native output device behavior was certified.
