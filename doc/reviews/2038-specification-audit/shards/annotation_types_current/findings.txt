Scope is limited to the four changed/assigned rows: §12.5.6.7 Line annotations, §12.5.6.10 Text markup annotations, §12.5.6.19 Widget annotations, and §12.5.6.23 Redaction annotations. Their ledger titles/statuses are as recorded in `doc/conformance/ledger.toml` at rows beginning around 3772, 3796, 3868 and 3900. **Line annotations.** Effective Table 178 is printed pp. 486–488 and Table 179 pp. 488–489 in the EC3 PDF (physical pages are printed page + 15). `/L` is required. When `/LL` is present, its endpoints are the `/L` endpoints; `/LL` supplies signed leader length, `/LLE` extension, and `/LLO` offset. `/LE` styles the two `/L` endpoints; `/IC` fills the applicable closed shapes; caption entries apply under their stated `/Cap` condition. The current implementation and tests use this geometry. `line_ending_endpoint_spec_audit.rs` checks exact xref/no recovery and includes first/second endpoint and positive/negative leader controls; `annotations.rs` adds leader, caption and ending coverage. That audit test's introductory comment still states an obsolete ADR 0192 displacement interpretation even though its body and assertions test the current Table 178 reading; correct that comment if the test is promoted. EC3 Issue #515 (physical p. 504, printed p. 489; `/State /Review` then `/Completed`) supplies the filled `RClosedArrow` text obscured by Table 179 layout. This resolution must be read with the table; Issue #513 is only an editor note about the clipped OpenArrow row height, not an erratum changing semantics (`doc/errata-read.md`, entries around lines 1089–1117). Public viewer test `viewer-core/tests/line_annotation_popup_spec_audit.rs` opens a valid associated Popup with `/Open false`, activates the Line, and checks the popup object, parent, contents and title. That is observable evidence for the clause's opened-note behavior.

**Text markup.** §12.5.6.10 and Table 182 are printed pp. 492–493. The four mark types are distinct. QuadPoints are 8 coordinates per quadrilateral in default user space; the producer's quad shall encompass one word or contiguous words. Vertex order is counterclockwise, with x1y1→x2y2 defining the text edge. The rendering implementation uses all four corners and the text edge. `text_markup_orientation_audit.rs` has exact-xref/no-recovery geometry controls for horizontal, rotated and trapezoid cases; `annotations.rs` asserts the four subtype marks. The word-enclosure sentence constrains valid producer geometry; I found no separate reader duty to repair/validate a malformed quad. Table 182 also requires that opening each of these four annotations display its associated popup. The model's popup data and activation machinery exist, but I did not find a public viewer test exercising that requirement for all four subtypes. `drafts/text_markup_popup_spec_audit.rs` supplies one: it varies all four subtype names over the same valid, text-covering quad; uses an explicit Popup with `/Open false` as the initial-state control; opens via public `Command::Activate`; checks the popup parent, note and author; and checks exact xref without recovery. The draft is intentionally scoped to observable popup behavior, not popup window placement or host font choice.

**Widget annotations.** Tables 191–192 are printed pp. 498–500. Table 191's `/H` default is `I`; its highlight modes are `N`, `I`, `O`, `P`, and `T`, and the table explicitly says any mode other than `P` overrides a down appearance. Current changed behavior follows that: widget pixel test `a_widgets_highlighting_mode_overrides_its_down_appearance` tests `N`, `O`, `P`, plus omitted `/H` with a down stream and the default-I effect; `widget_annotation_spec_audit.rs` directly covers that omission. The legacy appearance-selection test now states `/H /P` when testing N/R/D appearance selection, avoiding conflation with Table 191. Table 192's `/MK` characteristics are implemented in `appearance.rs` and covered by widget MK/icon/caption tests. ADR 2813's bounded Table 191 decision is supported by direct appearance assertions; its printed-output policy is separate from screen highlight behavior. This sample does not independently certify every widget field route.

**Redaction annotations.** Table 195 is printed pp. 504–505. It distinguishes identifying content from applying a removal. An interactive processor that supports redaction must provide a removal mechanism; masking/clipping is insufficient, and actual image data must be destroyed. `/QuadPoints` may identify regions, otherwise `/Rect` applies. `/RO`, where present, is drawn after removal and has precedence over `/IC`, `/OverlayText`, `/DA`, and `/Q`; the latter overlay entries are ignored when `/RO` is present. Current transform deletes/redacts source content before placing `/RO`, validates the referenced form and rejects artwork that reaches the original page/redaction content. `redaction_is_removal.rs` checks extraction and retained output, text/path/image removal, redaction annotation removal, no prior revision, overlay order, geometry and unsafe form references. `redaction_projection_spec_audit.rs` verifies `/RO` output after removal. The current ledger `departed` status remains bounded to owner-ratified lack of `/OverlayText` and `/IC` composition (A834/A842; ADR 2869), not `/RO`; ADR 2868 restores valid `/RO` as drawn-after-removal behavior. This is an implementation scope choice and does not turn the standard's conditional redaction requirement into an optional one. Do not use superseded ADR 2841 to classify `/RO` as presently withdrawn.
