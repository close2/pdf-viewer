# Independent signature-time / CRL-window cross-check

Scope is limited to the two candidate semantics in the parent assignment. This is an independent source/caller review, not a new fixture or a cryptographic certification.

## Source

Effective ISO 32000-2:2020 + EC3, §12.8.3.4.7, physical p. 598 / printed p. 583: for current-UTC revocation checking, a CRL is appropriate only when current UTC falls within the interval delimited by `thisUpdate` and `nextUpdate`. §12.8.3.4.8, physical p. 599 / printed p. 584: for historical signer-path checking, the CRL conditions are capture before signer-certificate expiry and `nextUpdate` later than the historical UTC time; it does not require `thisUpdate` at or before that historical time. The same §12.8.3.4.8 then requires the timestamp-unit path to be checked at current UTC and gives the reason-dependent rules: the path must be checked at current UTC; keyCompromise, cACompromise, or missing reason makes token time unusable; other reasons permit it only if revocation occurred after token `genTime`. Otherwise validation falls back to current time. Primary extraction is `scratchpad/r2038/spec-audit/ec3-parent-layout.txt` around source-layout lines 35218–35264. Primary PDF annotation inspection found no material erratum on physical pp. 598–599; this is not an inference from the errata index alone.

## Candidate 1: timestamp reliability is lost at the consumer

`pdf-signature::timestamp::{established, signature_timestamp_established}` return `Time::Established` for any `Trust::Anchored`, carrying its `revocation` field but not applying §12.8.3.4.8's reason-dependent reliability test. That enum is a path result, not an assertion that the revocation field is Good: `Trust::Anchored` deliberately carries `Revocation::Revoked`, `Unknown`, `NotChecked`, or `Good` separately (`crates/pdf-signature/src/trust.rs`, `Trust` definition). Therefore the low-level timestamp API's name can reasonably mean that an authority anchored a token's asserted `genTime`; alone, its result is not sufficient to claim a normative defect.

The consequential consumer is clearer. `viewer-core::notes::signature_timestamps_instant` takes every `Time::Established { at, .. }` and supplies `at` as `BestSignatureTime`; `established_over` does likewise for a document-timestamp chain. Those times are then used for signer verification. In the signature-attribute path, the timestamp authority's own path is checked at `now`, as §12.8.3.4.8 requires, but no code inspects the returned revocation reason before using `genTime`. This can apply the historical signer-check time in cases the clause says must fall back to current validation: revoked TSA-chain member for keyCompromise/cACompromise/missing reason, or a non-compromise revocation whose revocation time is not after `genTime`. The check must account for revocation on every certificate in the timestamp-unit path, not just its end-entity certificate. The clause first requires checking that path at current UTC; `NotChecked` or indeterminate status does not establish the “no certificate has been revoked” branch. This is a strong consumer-level gap candidate, conditional on a reliable current-time status and represented reason; avoid reporting it as “all revoked TSA certificates invalidate timestamps.”

`established_over` concerns document timestamps and §12.8.5 chain rules, not the signature-attribute paragraph verbatim. It should not be grouped into the confirmed scope without separately resolving the applicable §12.8.5.3 rules for an outer timestamp's own path. Existing ADR 1071 discusses timestamp path establishment and next-token time, but I did not find an explicit treatment of §12.8.3.4.8's reason-dependent reliability selector. ADR 2720 establishes purpose-specific TSA path/revocation checks; it does not appear to supersede that selector. ADR 1067 intentionally preserves a revoked statement through stale-list handling, which makes passing the reason through to the timestamp-time decision important.

Existing timestamp tests establish an anchored token/time with no revocation material and verify valid CMS/imprint behavior; I found no reason-specific TSA revocation regression. That is an assertion gap, not independent proof of a runtime failure.

## Candidate 2: `thisUpdate` is intentionally context-sensitive

`revocation::from_list` checks issuer/usage/signature and entries, applies issuance policy, then only rejects `at > nextUpdate`; for a Good response it does not reject `at < thisUpdate` (`crates/pdf-signature/src/revocation.rs`, `from_list`). Trust path construction sends one `at` into the shared revocation API, with no current-vs-historical mode. `viewer-core::notes` supplies the host clock for ordinary current checks and a proven signature timestamp for historical checks. I found no caller-side lower-bound filter.

This is not a global CRL defect: rejecting a CRL merely because `thisUpdate` follows a historical signer time would contradict §12.8.3.4.8's expressly one-sided historical test (`nextUpdate > historical time`) when the CRL was captured before signer certificate expiry. Existing `revocation::tests::a_list_issued_after_the_instant_asked_about_is_evidence_about_it` asserts precisely that historical-style behavior; it is a valid counterexample to changing `from_list` globally.

For current-UTC uses governed by §12.8.3.4.7, however, `at < thisUpdate` currently appears to produce `Good` if the other checks pass. The shared call chain has no mode bit or wrapper to apply the current-time interval while retaining the historical rule. This supports a context-dependent API/consumer gap: distinguish current from historical evaluation at the call site or in the API, and preserve the future-issued-CRL historical behavior. It does not establish that every caller of `status` must enforce the lower bound, since other policies may intentionally define issuance separately. Adjacent source condition: §12.8.3.4.7 also says a current-time OCSP response is appropriate only if captured before the signer certificate expires. The viewer reviewer found no apparent wrapper for that cutoff either; this is not part of the CRL lower-bound conclusion and needs its own bounded review.

The test suite includes the historical future-issued control and a CRL timestamp assertion, but I found no paired current-time test where `thisUpdate > now` and `nextUpdate > now`. No fixture is drafted pending parent coordination on the intended mode seam.

## Conclusion

Candidate 1 is strongest as a missing gate before a signature timestamp's `genTime` is promoted to the signer's `BestSignatureTime`; do not redefine generic `Time::Established` without considering its API meaning and other consumers. Candidate 2 is a likely current-time PAdES gap but explicitly not a blanket `from_list` bug. Both need a targeted regression with valid, signed revocation evidence and an independent expected result before promotion.
