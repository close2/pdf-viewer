# PDF/A: every problem the converter knows, and every remedy for it

Status: **standing** — the owner's "big table with all possible problems, and possible remedies (and
which remedy fits best for which profile(s))" (2026-10-27). The design it feeds is
[`doc/rfc/0014`](rfc/0014-a-profile-answers-each-site-in-order-and-states-what-it-could-not-keep.md);
the reading behind its shape is ADR 2514; the owner's word it waits on is `doc/questions/Q706`.

**What this is beside the other three PDF/A documents.** [`pdf-a-mitigations.md`](pdf-a-mitigations.md)
argues each requirement's remedies at length; [`pdfa-blocking-issues.md`](pdfa-blocking-issues.md)
says which of them real documents are blocked on and in what order to build them;
`quorra-transform archive --remedy-sites --to <target>` says what this version carries out. This
file is their join, one row per problem, so that an operator writing a profile and a round
choosing a build read the same list. Where a cell here and the listing disagree, **the listing is
right**, because it is generated from the table the converter decides from; a row here that has
fallen behind is corrected by a small edit.

ISO 19005 is cited by part and section and never quoted (`doc/third-party-data.md`); a `§` is a
clause of ISO 32000-2. ISO 19005-3 is not held (`doc/questions/A60`), so no row says what part 3
admits.

## 0. How to read a row

- **site** — the requirement's identifier without its family (the family is the heading), and in
  brackets the remedy family of `doc/pdfa-blocking-issues.md` that real documents meet it under
  (R01–R18).
- **the problem** — what the requirement asks, in `pdf_archive`'s own words (its `asks`), the ISO
  32000-2 clauses the catalogue entry names, and in square brackets the ISO 19005 section each part
  states it in and which parts it binds (`2` is 2b, 2u and 2a; `4` is 4, 4f and 4e, where the
  requirement does not itself name a level).
- **remedies** — numbered. The first is what the converter does on its own today: a lossless
  rewrite (*built*), a removal behind a named loss (*built*, which a profile authorises), or a
  refusal and its kind. The rest are `doc/pdf-a-mitigations.md`'s remedies for the entry, each
  with its kind (RFC 0007 section 2's words: `discard`, `preserve-append`, `preserve-attach`,
  `derive`, `supply`, and `mechanical` or `stated` for a lossless rewrite), its status — **built**,
  **buildable** (the remedy is argued and no code carries it out), **external tool** (a program
  the operator declares, RFC 0007 section 4) or **rejected** — and the loss it names. Every remedy
  but a departure satisfies the row's own requirement; a departure (RFC 0007 section 4.7) goes
  against it by name and is counted, not listed, because its classes are argued per entry there.
  "Target the flavour that admits it" changes the target rather than the file.
- **profiles today · proposed** — what each shipped profile answers at the site, read from
  `doc/profiles/` (a site a profile does not name is `stop`), in its letters below; then the two
  profiles RFC 0014 section 7 proposes, as the ordered `try` list each would state. Those two lists
  are section 7's rule applied to the row's remedies and the loss index's classes; they are a
  proposal, as the profiles are, and the owner's answer to `doc/questions/Q706` settles them.

| letter | profile | its sentence |
|---|---|---|
| R | `refuse-any-loss` | every site stops |
| M | `only-metadata-loss` | metadata may be discarded, nothing else |
| P | `as-if-printed` | discard what a print-and-scan would not carry (A694) |
| S | `as-shown` | keep what the window showed |
| K | `keep-everything` | keep, else keep elsewhere, else derive, else stop |
| D, F | `derive-attachments`, `factur-x` | single-purpose |
| **N** | `no-data-loss` (proposed) | no information is lost; a presentation loss is discarded and stated |
| **E** | `state-every-loss` (proposed) | convert what the window shows; every loss is stated on an appended page |

**No loss is definite.** Where no rewrite of this tree reaches a problem, an external program the
operator declares is a remedy row like any other (the owner, 2026-10-27: "definite losses was a
bad description from me, as external tools can remedy these as well"); section 3 below lists the
problems that only such a program reaches, and section 4 the two the owner named first.

## 1. What the join found

The brief's hypothesis was that the remedy sites, the losses and the blocking reasons are three
views of one set. **It held for two of the three and not for the third.** Every configurable site
is a requirement row (none is outside `pdf_archive`'s tables), and every loss word is taken at a
site or by a profile-level key; but the blocking reasons include problems that are no
requirement's — a document declined as a source (R01), a header no version names (R06a), a filter
no reader decodes (R07), an unreadable or pageless document (section 7 of the blocking list) — and
a requirement may refuse without being a site an operator can answer. So the table has three
parts: the requirement rows (section 2), the losses (section 5), and the problems no requirement
states (section 3). Of the requirement rows, those that are a processor's obligation, unchecked or
outside validation never refuse a file and are listed in one line per family; those every profile
answers without loss are listed in another; the rest are rows.

## 4. The two problems the owner named first

The owner's stance of 2026-10-27 names two refusals "we definitely can not remedy without losing
information": embedded files this tree does not understand, and multimedia. Both have remedies
once an external program is a remedy, and both differ by target.

**4.1 An attachment no reader of this tree draws** (an office file, an archive, an unknown type),
`embedded-files/embedded-file-is-itself-pdfa` and its part 4 twin. ISO 19005-2 section 6.8 admits
an attachment that conforms to part 1 or part 2; ISO 19005-4 section 6.9 one that conforms to part
1, 2 or 4; Annexes A.2 and B.4 admit an attachment of any type at 4f and 4e.

| step | 2b, 2u, 2a | 4 | 4f, 4e | status | loss |
|---|---|---|---|---|---|
| keep it unchanged | — | — | ✓ | built | none |
| a declared program makes a PDF; this converter makes that PDF/A; attached | ✓ (as part 2) | ✓ (as part 4) | ✓ | program built, the second conversion buildable (RFC 0014 section 5) | none; "derived, not original" |
| the same PDF's pages appended | ✓ | ✓ | ✓ | buildable | none; derived |
| an image, a text file or a PDF this reader draws, appended as pages | ✓ | ✓ | ✓ | built (R15, ADRs 2490, 2536) | `attachment-as-pages` |
| a PDF attachment converted by this converter and attached | ✓ | ✓ | ✓ | buildable | none |
| removed, and a page appended stating what it was | ✓ | ✓ | — | buildable (RFC 0014 section 4) | `embedded-file`, stated |
| removed | ✓ | ✓ | — | built | `embedded-file` |

**4.2 Multimedia** — a Screen, Movie or Sound annotation, a RichMedia annotation, and the
Rendition, Movie and Sound actions. ISO 19005-2 section 6.3.1 admits none of the three annotation
types (nor RichMedia, which ISO 32000-1 does not define); ISO 19005-4 section 6.3.1 admits none of
the three and RichMedia only at 4e (Annex B). Playing media is `CLAUDE.md`'s clause 13 exclusion;
keeping the media is not.

A reading this table leaves open: Annex B admits a RichMedia annotation at 4e and its section B.2.2
restricts only a 3D stream's format, so whether a RichMedia annotation carrying video is admitted
at 4e is for the round that builds the row to read in Annex B and in §13.7 — not decided here.

## 6. Re-counting this table

The cells are a join of four instruments, each of which re-counts its own part:

```sh
cargo run -q -p pdf-transform --bin quorra-transform -- archive --remedy-sites --to <target> [--config doc/profiles/<p>.toml]
python3 -I -B doc/pdfa-blocking-issues/rank.py census.log --repository . --render <quorra-transform>
grep -n 'check: Check::' crates/pdf-archive/src/table/*.rs
grep -n '=> "' crates/pdf-transform/src/archive/decision.rs   # the loss words
```

The first is the authority for whether a site's remedy is carried out; `doc/pdfa-blocking-issues.md`
section 1 is the census whose rank says which row to build next.
